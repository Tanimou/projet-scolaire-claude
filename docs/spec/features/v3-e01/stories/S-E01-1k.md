## 1. The problem, in one paragraph

`APP_ROLE_REQUIRED_PRIVILEGES` (`apps/api/src/shared/prisma/tenant-scope.ts:156`) is a hand-written literal list of
`{ table, privilege, why }`. **Measured this run: 37 entries.** `appRoleVerdict` (same file, `:536`) walks it **at
boot**: any declared pair the probe does not report as held returns `enforcing: false`, and
`transactionRunnerOrNull()` then 503s **the whole application's second connection** — not the offending module's.
Because the list is written separately from the code it describes, the two drift, and the drift is invisible: a
missing pair is **neither a compile error nor a test failure**, it is a `42501` at request time on exactly the
deployments where the tenant scope actually works. It has already drifted twice, measured: `S-E01-1i` sized
student-portal at 3 grants when the truth was **5** (`assessment`, `term` — relation targets a nested `select`
traverses); `S-E01-1j` added seven more relation-deep entries, 30 → 37.

The routine's own rule applies verbatim: **two hand-maintained lists = silent drift; fix by DERIVING, never by
adding one more literal.**

### 3b. The relation walk (AC-3) — feasible, and it finds a **real missing grant**

A crude walker (BFS over `schema.prisma` relation fields whose name appears in the call's argument object) returns
**15 relation-derived `SELECT` pairs**, **0 unparseable argument objects** on the 70 scoped sites, and:

- it **covers all three** of 3a's false-dead entries — `assessment.SELECT` via `Grade.assessment`

  derived set covers **37 / 37** declared pairs and the `dead-entry` list is **empty**;
- it finds **one pair the hand list does not have**: **`guardian.SELECT`**.

```
apps/api/src/modules/lessons/lessons.controller.ts:366   (inside this.scope.run(tenantId, async (tx) => …))
  const gship = await tx.guardianship.findFirst({
    where: { tenantId, studentId, status: 'active', guardian: { userProfileId: me.id } },

```

`guardian: { userProfileId: … }` is a **relation filter**, and under RLS a relation filter is a **READ of
`guardian`** exactly like an `include`. The declared list has `guardianship.SELECT` and **not** `guardian.SELECT`.
This is `PF-246`'s failure mode, live, on the **parent** ABAC branch of `/lessons/list`. Recorded as **`PF-249`**
and closed by this slice.

Measured on the running stack (`docker exec pilotage_postgres psql -U pilotage -d pilotage`):

```
assessment       | DELETE|INSERT|SELECT|UPDATE
guardian         | DELETE|INSERT|SELECT|UPDATE     <- SELECT is HELD; declaring it is safe
guardianship     | DELETE|INSERT|SELECT|UPDATE
teacher_profile  | DELETE|INSERT|SELECT|UPDATE
term             | DELETE|INSERT|SELECT|UPDATE
guardian: relrowsecurity = t, 1 policy
```

**So `guardian.SELECT` must be ADDED, not the three entries deleted.** That is the AC-5 reconciliation, decided by
measurement and not by tuning the derivation.

### 3c. The trap, confirmed (AC-2)

Deriving from **all** call sites instead of `scoped` ones adds ~150 pairs, including the three the brief predicted:

## 4. Functional requirements

**FR-1 — `derivePrivilegeClosure()`, a pure exported function in `scripts/tenant-adversarial-check.js`.** It walks
the same corpus with the same matcher and the same `covers()` attribution, keeps only sites attributed **exactly**
`scoped`, and returns a Map keyed `` table\0PRIVILEGE `` carrying `{ table, privilege, origin: 'root' | 'relation',
example: 'file:line', via?: 'Model.field' }`. It must **not** re-attribute anything: reuse the existing predicates.

**FR-2 — a relation resolver read from `apps/api/prisma/schema.prisma`.** Measured: **54 models, 54 `@@map`
directives** — every model carries one, so `model → table` is total and needs no fallback guess (but keep one that
**fails closed and names the model** if a future model drops its `@@map`). Build `model → { relationField →
targetModel }` by recognising a field whose type is a declared model name. `modelToTable` alone does **not** carry
relations; do not try to make it.

**FR-3 — the relation walk.** For each `scoped` call site, extract the call's argument object by **balanced-paren
matching, starting at the opening parenthesis that follows `.<verb>`**, then collect relation field names appearing under `where`
(including `some` / `every` / `none` / `is` / `isNot`), `select` and `include`, descending into nested objects and
resolving each field against the model reached so far. Each resolved target contributes `(table, 'SELECT')` with
`origin: 'relation'`.

**FR-4 — `readDeclaredPrivileges(sourcePath)`, the SINGLE source.** The declared side is read **from
`tenant-scope.ts`**. It is never re-typed into the script — a third hand-written list *is the disease*. Because the
script is `.js` and the list is `.ts`, the reader parses the source region between
`export const APP_ROLE_REQUIRED_PRIVILEGES` and the array's closing bracket. **Do not read `dist/`**: agents never build, and
`scripts/tenant-scope-check.js` already demonstrates the stale-`dist` hazard.

**FR-5 — `privilegeClosureDrift(declared, derived)`, pure, exported, returning a LIST of named findings.** Kinds, in
the image of `enumerationDrift`:

| kind | fires when |
|---|---|
| `undeclared-pair` | a derived pair is absent from `APP_ROLE_REQUIRED_PRIVILEGES` |
| `dead-entry` | a declared pair no derivation supports, and no exception covers |
| `entry-without-reason` | `why` is missing, blank, or **vacuous** (see FR-7) |
| `unparseable-argument` | a `scoped` call site whose argument object did not brace-match — **named, never skipped** (DNC-08) |
| `unmapped-relation-target` | a relation field resolves to a model with no table — fail-closed |
| `exception-without-reason` | an FR-7 exception whose reason does not say **why the derivation cannot see it** |
| `dead-exception` | an FR-7 exception the derivation now covers on its own |

**FR-6 — set equality in BOTH directions**, over `(table, privilege)` as a **set** (not a multiset: unlike
`enumerationDrift`, a second call site needing the same privilege is not a second obligation).

**FR-7 — exceptions carry a reason about VISIBILITY, not about the table.** Any pair the derivation provably cannot
see gets an explicit entry whose reason says **why the derivation cannot see it** — never a blanket allowance, never
a bare literal. **On today's corpus the expected number of exceptions is ZERO** (§3b: the walk covers 37/37).
Shipping an exception you did not need is how the mechanism starts rotting on day one.

**FR-8 — no bypass (DNC-10).** No env var, no CLI flag, no `SKIP=`, no "warn-only" mode. The existing gate spec
already asserts this repository-wide (`tenant-adversarial-gate.spec.ts:322`, *« AUCUN drapeau, AUCUNE variable ne
peut changer un verdict »*) and it will read the new code.

**FR-9 — add `guardian.SELECT`** to `APP_ROLE_REQUIRED_PRIVILEGES` with a non-vacuous `why` naming the parent ABAC
branch and the relation filter, e.g. *« filtre de relation `guardian: { userProfileId }` de la branche parent de
`/lessons/list` — sous RLS un filtre de relation est une LECTURE de `guardian`, pas seulement de `guardianship` »*.

**FR-10 — the count assertion moves with the list.** `apps/api/src/modules/remediation/remediation-scope-ownership.spec.ts:670`
holds `expect(APP_ROLE_REQUIRED_PRIVILEGES).toHaveLength(37)`. Adding `guardian.SELECT` makes it **38**; update it,
and **do not delete it** (it is a ratchet, merely a misplaced one — recorded as `PF-250`).

## 5. Acceptance criteria

- **AC-1 — derived from `scoped` sites only.** The observed set comes from call sites attributed exactly `scoped`;
  **not** from all call sites. Prove it by asserting the three §3c pairs (`booking.INSERT`, `booking.UPDATE`,
  `audit_log.INSERT`) are **absent** from the derived set.
- **AC-2 — the `tx` ambiguity is resolved positionally.** A unit fixture containing both
  `this.scope.run(id, async (tx) => …)` and `this.prisma.$transaction(async (tx) => …)`, each with one
  `tx.<model>.<verb>`, yields **one** derived pair and not two.
- **AC-3 — relation depth walked, verified on the two known instances.** `/student/grades` descends
  `grade → assessment → term`; the `S-E01-1j` remediation entries resolve (`Grade.assessment`,
  `TutorAvailability.tutor`, `Tutor.availabilities`, `Enrollment.academicYear`). An **unparseable** construct is
  reported as `unparseable-argument` and **fails the check** — never silently skipped (DNC-08). Assert
  `unparseable === 0` on today's corpus so the branch is proven *reachable and currently empty*, not merely absent.
- **AC-4 — equality in both directions**, against the list **imported/read from `tenant-scope.ts`**, with a
  **non-vacuous-corpus floor**: if `readDeclaredPrivileges` returns fewer than, say, 30 pairs, or the derivation
  returns 0 scoped sites, the check **fails closed** (a parser that silently returns `[]` is a green light that
  proves nothing).
- **AC-5 — reader fidelity is TESTED, not hoped for.** In `apps/api/src/shared/quality/tenant-adversarial-gate.spec.ts`
  — which already `require()`s the checker's pure exports (`:181`) and imports from `../prisma/` (`:4`) — assert that
  `readDeclaredPrivileges()` returns **exactly** the set built from the genuinely imported
  `APP_ROLE_REQUIRED_PRIVILEGES`. This is what stops the regex reader from becoming the third hand-written list.
- **AC-6 — the disagreement is reconciled by MEASUREMENT.** On today's corpus the check must end with
  `undeclared-pair: 0` and `dead-entry: 0` **after** adding `guardian.SELECT` — and the `guardian.SELECT` decision
  must be justified by the stack measurement of AC-8, not by the derivation agreeing with itself.
- **AC-7 — `privilegeClosureDrift` is driven to RED on purpose**, in the gate spec, for **every** kind in FR-5's
  table, with no repository scan and no database (the pure-function pattern the file already uses for
  `enumerationDrift` at `:1380`).
- **AC-8 — executed evidence on the runtime target, positive control first.** Measure via
  `docker exec pilotage_postgres psql -U pilotage -d pilotage …`. **`localhost:5432` on the host is a DECOY
  (`TOOL-38`)** — `pilotage_postgres` publishes no host port; the host's 5432 is the native Windows
  `postgresql-x64-15` service (55 tables, 2 migrations, no RLS, 0 rows), and measuring there reads exactly like
  "unverifiable". Show, in order: (1) the probe **can see a privilege that is held** (positive control), then
  (2) `guardian` holds `SELECT` for `app_user`, (3) `guardian` has `relrowsecurity = t` with a policy, (4) the full
  **38/38** closure is held. **Named limit to carry, not hide:** `guardian` holds **2487 rows, all in
  `voltaire-demo`; `demo` has zero** (measured), so a foreign-GUC probe returning 0 on `guardian` is ambiguous — the
  discriminating controls available here are *own tenant returns 2487* and *unset GUC returns 0*. Say that; do not
  claim the strong `S-E01-1j` control shape for this table.
- **AC-9 — non-regression, numbers before and after.** `scoped + enumerated === total` and the triple
  **70 scoped / 120 enumerated / 818 corpus** must be **byte-identical** before and after. This slice adds a
  comparison; it re-attributes nothing. Report both readings.
- **AC-10 — the derivation is wired into the check's verdict**, not printed as a note. A drift finding makes
  `tenant-adversarial-check.js` exit non-zero. Adding a `[LIMIT]` line that nobody fails on would reproduce `PF-02`
  inside the mechanism built to close it.
