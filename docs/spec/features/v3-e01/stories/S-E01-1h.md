# S-E01-1h — The tenant scope stops being a property of the SOURCE TREE and becomes a property of the RUNNING STACK

- **Epic:** `V3-E01` — Tenant isolation and identity resolution
- **Layer:** L0 · Trust and production foundation
- **Closes:** `PF-242`
- **Advances:** `PF-02` (half (a) — the **deployment** half; the source-side counter does not move)
- **Records:** `PF-243` (P2), `PF-244` (P3)
- **Falsifies:** one hypothesis of this story's own drafting — see §2
- **ADR:** [`ADR-056`](../../../../adr/ADR-056-tenant-scope-deployment-declaration.md)
- **Gates:** G-TENANT, G-MIGRATION, G-DNC

## 1. The measurement that produced this story

Selection began where `NEXT.md` pointed — a fourth module conversion, continuing `S-E01-1e/1f/1g`.
Step 2 asks whether the finding still reproduces before any code is written. Checking the grant
closure the fourth module would need meant reading the grants `app_user` actually holds, and that read
returned nothing:

```
select count(*) from information_schema.role_table_grants where grantee='app_user';   →  0
```

Not on a scratch database — on the database the local Docker stack runs on. Following it upward:

| measured on the stack, 2026-08-22 | value |
|---|---|
| migrations applied vs shipped | **2 / 7** |
| tables with RLS enabled | **0** |
| policies | **0** |
| `app_user` table privileges | **0** |
| `DATABASE_URL_APP` in the api container | **empty** |
| occurrences of `DATABASE_URL_APP` in `infra/docker-compose.yml` | **0** |

`AppRolePrismaService` opens its second, RLS-bearing connection **only when `DATABASE_URL_APP` is
declared**. It was declared in `.env.example` and in no compose service. So the api ran in
`degraded_no_app_url` and **all 36 converted call sites executed on the owner connection** —
`pilotage`, measured `rolbypassrls = true`.

**Three runs of conversion work had never once been exercised on the runtime target.** The
scratch-database proofs (`scripts/tenant-scope-check.js`) were true and remain true; they prove the
*mechanism*. Nothing proved the *deployment*, and the deployment was the half `PF-02`'s closure
condition is actually about (`ADR-032` §D5–§D8).

The failure is silent by construction, and that is the part that needed a gate rather than a fix.
`AppRolePrismaService` degrades instead of crashing — correctly, since a deployment that cannot open
the second connection must still serve. The cost is that four different mistakes produce one
observable: a healthy stack with `pilotage_tenant_scope_enforced` at 0. Nothing goes red.

## 2. A hypothesis this story raised and then FALSIFIED

The api printed *"Preflight migrations OK — 2 appliquée(s)"* while the repository shipped seven. The
obvious reading is a preflight that checks *applied-and-clean* instead of *applied-vs-shipped*, and a
finding was drafted saying so.

It is wrong. `apps/api/src/shared/migrations/migration-state.ts:120` computes
`pending = shipped.filter((m) => !applied.includes(m))`, has a dedicated `pending` status, and reads
`prisma/migrations` from disk. **The preflight was right.** The *image* shipped two migrations,
because it was built before the other five existed. No finding is spent on the preflight, and the
draft is recorded here rather than deleted, because the next reader will have the same idea.

What is true is one layer up, and is `PF-243`: nothing on this stack can detect that its image
predates the repository. `GET /version` answers in its own words —
`buildSha: "unknown"`, `verdict: "unverified"`, *"EXPECTED_GIT_SHA non déclaré : la version qui
tourne n'est comparée à rien (R-05)"*. The machinery exists; it is not armed.

## 3. What this slice changes

### 3.1 The declaration (`infra/docker-compose.yml`)

`DATABASE_URL_APP: postgresql://app_user:app_user@postgres:5432/pilotage?schema=public`, on the **api
service only** — not on the `x-app-env` anchor. `ADR-056` §D1 carries the reasoning; in short,
`migrator` must keep the owner (a role cannot grant itself privileges) and `worker` has no request
tenant (its 99 call sites are enumerated *outside* any scope).

### 3.2 The ratchet (`scripts/tenant-scope-deployment-check.js` + its gate spec)

**Tier 1**, source-only, no Docker — deliberately, and this placement is the decision. Its neighbour
`compose-invocation-check.js` sits in `--full` because it shells out to `docker compose config`. The
diff that reintroduces *this* regression is a compose edit, and a compose edit does not schedule a
`--full` run, so a `--full`-only gate would never have seen it.

It refuses **four** shapes, not one:

| # | shape | why it is not merely wrong |
|---|---|---|
| 1 | absent / empty | what shipped — gauge 0, nothing red |
| 2 | `localhost` / `127.0.0.1` | does not resolve in the network; degrades identically. `.env.example` ships exactly this literal |
| 3 | database or host ≠ `DATABASE_URL` | two addresses for one database is how `PF-86` happened |
| 4 | **the owner role** | the only shape that reads as **enforced** while isolating nothing |

Shape 4 is the reason the checker does more than test for presence: the owner carries `BYPASSRLS`, so
pointing the "app" connection at it makes the probe pass and the gauge read **1** over zero isolation.
A gate asserting only "declared" would be green on the one configuration worse than the bug.

## 5. AC-7 — the denial, on the stack's own database

The positive control comes first on purpose. `app_user` held **zero** privileges before this slice, so
a proof showing only *absence* of rows would have been green for the wrong reason — it would have been
measuring a missing `GRANT`, not a working policy.

| connection | `app.current_tenant_id` | `count(*) from calendar_event` |
|---|---|---|
| owner `pilotage` | tenant **B** (foreign) | **17** ← the hole, and what the api used to be |
| `app_user` | tenant **A** (own) | **17** ← rows APPEAR |
| `app_user` | tenant **B** (foreign) | **0** ← DENIED |
| `app_user` | none | **0** |

The first row is the finding restated as a number: before this slice the api was that connection, and
a foreign tenant returned seventeen rows.

## 6. What this does NOT claim

- **`PF-02` does not close.** The counter is unchanged at `36 / 816`; 660 call sites would still
  return zero rows after a `DATABASE_URL` cutover, and the application is still not ready to cut over.
  What changed is that the 36 already-converted sites now actually run under RLS on the target.
- **Nothing is claimed about `pilotage.srv861861.hstgr.cloud`.** Per Step −1 it is an audit fixture,
  was not contacted, and its realm and database are untouched.
- **The gate does not inspect a running container**, by choice. Enforcement is a property of a
  process; a checker that answered from whatever happens to be running locally is precisely the defect
  `TOOL-36` names. The running-stack claim above is evidence, produced by execution, not a checker.

## 7. Rollback

Remove the `DATABASE_URL_APP` line from the api service and recreate: the api returns to
`degraded_no_app_url` and every converted site runs on the owner again. No schema change is undone —
the five migrations are additive policy/grant work and were already in the ledger; they simply had
never reached this database. The gate would then go red, which is the intended behaviour and the
reason it exists.
