## 1. The slice in five sentences

`calendar_event` carries four **mono-column** foreign keys to tenant-owned rows (`academicYearId`, `cycleId`,
`gradeLevelId`, `classSectionId`), and the two write handlers check that the *right kind* of id was supplied for the
declared scope while never checking that the id **belongs to the caller's tenant**. RLS cannot close this, and the
reason is structural rather than a policy gap: PostgreSQL evaluates referential-integrity checks **outside** row
security, so `tenant_isolation`'s `WITH CHECK` only ever sees `calendar_event.tenant_id` — a foreign `cycleId` inserts
cleanly under a perfectly correct policy. The consequence is a **cross-tenant read on the parent portal**, live on
every deployment today. This slice adds an **ownership assertion per supplied scope id, issued on the scope's own
transaction client, before the write**, enforces **mutual exclusivity** of the three scope ids (which also closes a
real coherence hole the inference path opened), and **amends `ADR-048 §D3`'s measured transaction budget honestly**
rather than pretending the check is free.

## 3. The design tension, resolved out loud

`ADR-048 §D3` records a **measured** bound — *"AC-8 bounds it at ≤ 2 statements inside the scope"* — with a
per-handler table (`list` 1–2 · `update` 2 · `remove` 2 · `create` 1) and the rule *"late scope, early close; all
validation is pure and happens outside"*.

**Ownership validation is not pure.** It needs the database, and it **must** run inside the scope: running it outside,
on the owner connection, validates against a connection that can see every tenant — which is precisely the bug. So
this slice necessarily adds statements inside the interactive transaction. You may not pretend otherwise, and you may
not quietly move the number.

**The resolution is (a) + (c), and both halves are required.**

**(a) Mutual exclusivity of the three scope ids.** At most one of `cycleId`, `gradeLevelId`, `classSectionId` may
carry a truthy value; two or more is a `400`. This is a genuine hardening on its own — it closes `§2.3`'s inference
hole, where an unvalidated `cycleId` rides into the row behind a `class_section_scope` — **and** it bounds the work:
the ownership plan can never exceed **one scope id + `academicYearId` = 2 statements**.

**(b) is not available, and here is why rather than "we chose not to".** Batching the checks into one statement would
require a single query across four different tables. Prisma cannot express that without raw SQL, and adding a raw-SQL
site to reduce a statement count would trade a bounded, visible cost for the exact class of site `PF-197` is open
about. `$transaction([...])` is unavailable inside an interactive transaction. So (b) is refused **by measurement**,
not by preference, and that sentence belongs in `ADR-049`.

**(c) The bound is amended HONESTLY to ≤ 3, with a republished per-handler table.** `§D3`'s "≤ 2" was a *measurement
of what those four handlers happened to need* — it was never an architectural invariant, and `ADR-048` says so in the
same breath ("the measurement, not an assumption"). The new table, which you must verify by reading your own diff:

| Handler | Statements inside the scope, after this slice | Composition |
|---|---|---|
| `list` (`:229`) | **1**, or **2** on the parent branch | unchanged |
| `create` (`:461`) | **1** to **3** | 0–2 ownership checks, then the `create` |
| `update` (`:273`) | **2** to **3** | guard `findUnique`, 0–1 ownership check, then the `update` |
| `remove` (`:318`) | **2** | unchanged |

New maximum **3** (`set_config` still not counted). The worst case is reached only when a caller supplies a scope id
*and* an academic year — the admin UI's normal create. Three statements inside a transaction whose `timeout` is 5 s,
on the lowest-traffic converted module, is the price of not shipping a live P1 cross-tenant read; state it that way in
the ADR, with the number, and do not round it.

### 3.1 One more design decision, and it is measurable

Put the ownership statements **inside the `run(...)` callback body**, not in a private method that receives `tx`.

`PF-200` (open, P1) records that the coverage attribution is **lexical**: a call site is attributed *covered* when its
**text** sits inside a brace-matched scope callback. `resolveParentClassSectionIds` is the live proof — it takes `tx`
as a parameter, is perfectly safe, and is nevertheless counted **uncovered**. A private `assertScopeIdsOwned(tx, …)`
would add up to four more uncovered-but-safe sites and push the published ratio in the wrong direction inside a
diff whose whole subject is tenancy. Knowingly re-creating `PF-200`'s shape in new code is not acceptable here.

**Therefore:** the *impure* part (the `findFirst` calls and the `switch` that picks the delegate) is written **inline
inside each callback**; the *pure* parts (mutual exclusivity, the ownership plan, the refusal factory) are
module-level exported functions that touch no Prisma at all and are unit-tested directly. That split is what makes
the duplication small (≈ 8 lines per handler) and the logic testable without a database.

### 4.1 `apps/api/src/modules/calendar/calendar.controller.ts` — the pure half

Add three **exported**, Prisma-free functions near `calendarVisibilityWhere` (same register: French docblocks,
explaining *why*, not *what*).

**`SCOPE_ID_FIELDS`** — the closed set, as a `const` tuple:
`['academicYearId', 'cycleId', 'gradeLevelId', 'classSectionId'] as const`. A closed set, never a dynamic key walk
over the body — the body is attacker-controlled.

**`assertSingleScopeId(body)`** — refuses when **two or more** of `cycleId` / `gradeLevelId` / `classSectionId` carry
a **truthy** value (`§2.5` point 1 — `null` is not "supplied"). One `BadRequestException`, naming the fields that
collided. Its docblock must state the hole it closes (`§2.3`), because that is not obvious from the code.

**`scopeOwnershipPlan(body)`** — returns `Array<{ field: ScopeIdField; id: string }>` for every scope id carrying a
truthy string, in a **stable order** (`academicYearId` first, then whichever scope id is present). Pure, total,
allocation-only. `update` calls it on a body from which `academicYearId` has been dropped (`§2.4`).

**`unknownScopeRef(field)`** — returns **one** `BadRequestException` whose message is **identical** for "does not
exist" and "belongs to another tenant". Suggested French, keep the register: `` `${field} ne référence aucun élément
accessible.` `` The message may name the **field**. It must never name the tenant, the owner, the id's existence, or
anything derived from the row that was not found.

### 4.2 `calendar.controller.ts` — the impure half, inline in both callbacks

In `createEvent`, **outside** the scope (it is pure): call `assertSingleScopeId(body)` **before** the coherence checks
at `:438`, and build `const plan = scopeOwnershipPlan(body)`.

Then, inside `this.scope.run(me.tenantId, async (tx) => { … })` — note this converts the current expression-bodied
callback at `:461` into a block body — issue, **before** the `create`:

```ts
for (const { field, id } of plan) {
  // Contrôle de PROPRIÉTÉ, et il DOIT être ici : dehors, il s'exécuterait sur la
  // connexion du PROPRIÉTAIRE, qui voit tous les tenants — c'est-à-dire qu'il
  // validerait exactement le défaut qu'il est censé refuser.
  const owned =
    field === 'academicYearId'
      ? await tx.academicYear.findFirst({ where: { id, tenantId: me.tenantId }, select: { id: true } })
      : field === 'cycleId'
        ? await tx.cycle.findFirst({ where: { id, tenantId: me.tenantId }, select: { id: true } })
        : field === 'gradeLevelId'
          ? await tx.gradeLevel.findFirst({ where: { id, tenantId: me.tenantId }, select: { id: true } })
          : await tx.classSection.findFirst({ where: { id, tenantId: me.tenantId }, select: { id: true } });
  if (owned === null) throw unknownScopeRef(field);
}
```

Requirements on that block, each of which a reviewer will check:

- **`findFirst`, not `findUnique`.** `findUnique` cannot take a non-unique `tenantId` in its `where`, so the
  composite predicate would have to be applied *after* the read — i.e. the row would be fetched across the tenant
  boundary and then discarded, which is a different program with the same output shape.
- **`select: { id: true }`** — never fetch a foreign row's columns; `PF-204`'s payload is a **name**.
- **an explicit closed `switch`/ternary chain over the four fields** — never `(tx as any)[modelName]`. A dynamic
  delegate lookup keyed on request data is a new dynamic-dispatch surface and would be an ADR-level change.
- **`throw` inside the callback.** The interactive transaction rolls back; nothing is written. That is the point of
  doing it here rather than after.
- **no `process.env`, no flag, no option bag, no `catch` that downgrades** (`DNC-10`, `DNC-08`). The controller
  contains **zero** `process.env` occurrences today — measured — and must still contain zero after your diff.

In `update`, inside the **existing** `this.scope.run(...)` at `:273` — **the same scope that already holds the guard
read**, never a second one and never outside — place the identical loop **after** the `!event || event.tenantId !==
tenantId` guard and **before** the `try { … tx.calendarEvent.update }`. Build its plan from a body with
`academicYearId` excluded (`§2.4`). `assertSingleScopeId(body)` runs at the top of `update`, before `run` opens.

**Ordering inside `update` is load-bearing**: the event-existence guard first, the ownership checks second. Reversed,
a caller could probe scope ids against an event id they do not own.

### 4.3 The status code, decided — 400, and the justification for `ADR-049`

**`400 Bad Request`, with one message shared by both failure modes.**

The deciding question is whether the response distinguishes *"exists but belongs to another tenant"* from *"does not
exist"* — it must not, because that difference is itself a cross-tenant existence oracle (the general rule
`ADR-048 §D9` states: *when a database refusal replaces an application refusal, the two must be indistinguishable
from outside*). The single predicate `findFirst({ where: { id, tenantId } })` returns `null` for both cases, so the
two are indistinguishable **by construction**, not by careful message-writing — and that is what makes 400 safe here
rather than merely conventional.

Given that either code leaks nothing, 400 is chosen because the offending value arrived **in the request body** and
the surrounding refusals in the same function are already `BadRequestException` (`:439`, `:442`, `:445`); a 404 on
`POST /calendar/events` would additionally have to be distinguished from "the endpoint does not exist". The `404` used
by `update`/`remove` for the **event id** is untouched and is a different resource. One sentence of this goes in
`ADR-049`; it is `AC-3`'s deliverable.

### 5.2 The cases (all of them are required)

**Negative, one per scope id — these are `AC-4`.**

| # | Handler | Foreign id supplied | Must assert |
|---|---|---|---|
| N1 | `create` | tenant B's `academicYearId` | rejects `BadRequestException` **and** `calendarEvent.create` was **never called** |

"`create` was never called" is the load-bearing half. A test that only asserts the throw would still pass if the

**Positive controls — mandatory.** P1–P4: the same four requests with **tenant A's own** ids succeed and reach
`calendarEvent.create` / `.update`. Without these, a fix that refuses everything is green, and the negative tests
prove nothing.

**No-oracle.** X1: `create` with a **randomly generated, nonexistent** `cycleId` and `create` with **tenant B's real**
`cycleId` produce responses whose status **and message string** are **strictly equal**. Assert the equality of the two
captured errors, not two separate `toThrow` matchers — the point is indistinguishability, so compare them to each
other.

**Mutual exclusivity (`§3` (a)).** M1: `create` with both a truthy `classSectionId` and a truthy `cycleId` is refused
before any scope opens (`insideScope` never became true). M2: the admin UI's real payload shape — one truthy id and
the other **explicitly `null`** — is **accepted** (`§2.5`; this is the regression test that keeps the admin calendar
working, and it must exist).

**Inside-the-scope, per handler.** S1/S2: for `create` and `update`, every recorded `findFirst` carries
`where.tenantId === A` and was issued while `insideScope` was true.

**Budget (`§3` (c)).** B1: count the statements the fake `tx` recorded per handler and assert **≤ 3** for `create`
and for `update`, and that `remove` is still **2**. This pins the amended `ADR-048 §D3` number in executable form, so

**`AC-9` premise pin (`§2.4`).** G1: read `calendar.controller.ts`'s own source and assert that `update`'s `data`
object does **not** contain `academicYearId`. When a future author adds it, this test goes red and the omission

**`DNC-10`.** D1: the controller source contains **no** `process.env`, no `SKIP_`, no `ALLOW_` (measured zero today),
and there is no code path in which a supplied scope id reaches the `create`/`update` `data` without having been
