## 4. PART 1 — the conversion

### 4.1 The pattern, and the two rules that are not style

Copy the shape of `calendar.controller.ts` (`:340`, `:397`, `:485`, `:644`) and read
`tenant-scope.service.ts`'s docblock before editing.

* **LEXICAL, never behind `this.<method>()`.** The attribution counter brace-matches the callback range and does not
  traverse `this` (`PF-200`). A helper that *takes `tx` as a parameter* is correct and safe but its text sits outside
  the range and will count UNCOVERED — `calendar.controller.ts:582`'s `tx.enrollment.findMany` inside
  `resolveParentClassSectionIds` is exactly that case, measured today as the single uncovered site in the converted
  module. **Write the probe loops inline in each callback.**
* **Inside the callback use `tx`, never `this.prisma`.** A `this.prisma` call inside a scope runs on the OWNER
  connection and nothing catches it.

### 4.2 Identity resolution stays OUTSIDE — and that now means TWO resolvers, not one

Before any `this.scope.run(` in this file:

```
const me = await this.users.ensureUser(jwt);          // PF-199 — produces the tenantId
const tenantId = me.tenantId;                          // ONE expression, reused by filter AND scope
const roles = jwt.realm_access?.roles ?? [];
```

`ensureUser` reads `user_profile` — one of the 44 policied tables — from the Keycloak `sub`, with **no tenant known**.
Inside a scope on `app_user` it returns zero rows and every authenticated request of every portal answers **403
`ACCOUNT_NOT_PROVISIONED`**. It produces the key; it cannot consume it.

**`ensureForUser` must be hoisted the same way.** Required refactor of `assertOwnership`:

* `assertOwnership(teacherProfileId, me, jwt)` currently *calls* `ensureForUser` internally. Change it to a **pure**
  decision that takes the already-resolved profile id: e.g. resolve `const myTeacherProfileId = isPrivileged ? null :
  (await this.teachers.ensureForUser(me)).id;` **outside** the scope, then a pure
  `assertOwnership(rowTeacherProfileId, myTeacherProfileId, roles)` that throws `ForbiddenException` with the
  **unchanged message** `'Vous ne pouvez modifier que vos propres entrées.'`.
* **G-AUTHZ: refusal semantics must not change.** `super_admin` / `school_admin` still skip the check; every other
  role still compares to its own profile; the `@RequiresPermission` decorators on all five handlers are untouched.
  For `update` and `remove` the ownership check reads a `teacherProfileId` that is only known **after** the row is
  read inside the scope — so the *comparison* moves inside the callback while the *resolution* stays outside. That
  ordering is the whole point and AC-2 asserts it.
* `list`'s `mine=true` branch already resolves `ensureForUser` before any query (`:175`) — keep it there, outside.

## 5. PART 2 — settling `PF-199`: the allow-list becomes TWO LAYERS

### 5.1 What exists today, measured

`ENUMERATED_OUTSIDE_SCOPE` (`scripts/tenant-adversarial-check.js:2172`) is **already** a named constant where every
entry carries its own reason, and `cutoverVerdict` already enforces `scoped + enumerated === total` plus an
`unreasoned` branch that refuses the verdict when an entry loses its reason. **That wall exists. Do not build a
second one.**

**The gap is granularity: every entry is a FILE GLOB.** One reason excuses *every* Prisma statement in the file,
forever, including statements written tomorrow. For a bootstrap file that is sound — "this file runs before any
request exists" is true of every statement in it by construction. For an **identity-resolution** file it is not:
"this file resolves the tenant" is true of `ensureUser`'s reads and false of an unrelated `notification.create`
someone adds to `user-sync.service.ts` next month. **The `PF-199` files are precisely where a new statement can hide
behind someone else's reason**, and the brief's requirement — *"one named entry per statement, each with a specific
reason"* — is the correct remedy for exactly those files.

### 5.2 The ruling: a STRUCTURAL layer (glob) and an IDENTITY layer (statement)

**Do not convert all ~111 enumerated sites to statement entries.** Hand-authoring 111 literals is the repeat defect
this repo has already recorded (*"two hand-maintained lists drifting apart"*) reproduced inside the fix. Instead:

**Layer A — STRUCTURAL, stays glob-level.** `main.ts`, `config-preflight.ts`, `shared/migrations/**`,
`shared/release/**`, `modules/health/**`, `apps/worker/src/**`, `calendar-seed.service.ts`. Each reason is a property
of the *file or process phase*, true of every statement in it. Unchanged, except: each entry gains an explicit
`layer: 'structural'` and a one-line note stating **why file granularity is sound here** (that note is itself the
reason-per-entry discipline applied to the choice of granularity).

**Layer B — IDENTITY, becomes statement-level.** The `PF-199` seams:

| File | Sites | Status |
|---|---|---|
| `shared/auth/user-sync.service.ts` | 5 | already enumerated (glob) |
| `modules/school-structure/school-context.service.ts` | 4 | already enumerated (glob) |
| `modules/students/student-access.service.ts` | 2 | already enumerated (glob) |
| **`modules/teaching/teacher-profile.service.ts`** | **6** | **MISSING — added by this slice (§1.3)** |

Each entry becomes `{ layer: 'identity', file, model, verb, reason }` — **one entry per `<receiver>.<model>.<verb>(`
statement**, each reason naming *what that specific statement resolves* (e.g. "`user_profile.findUnique` maps the
Keycloak `sub` to the profile that CARRIES the tenantId — it is the statement that produces the scope's key";
"`teacher_profile.upsert` provisions the teacher identity on first sight, before any teacher-scoped row exists to
which a tenant scope could apply"). **No shared boilerplate string.** Two entries with byte-identical reasons is
itself a smell the ratchet should surface.

**⚠️ Sizing note the dev may overturn.** Adding `teacher-profile.service.ts` moves **6 sites** from UNCOVERED to
enumerated. That is an increase in the enumerated term, and an increase in `enumerated` is *arithmetically
indistinguishable from* a manufactured green. **This is the one place in the slice where the reviewer must look
hardest.** Justify it on the measurement in §1.3 (a service that resolves identity, closes over its own
`PrismaService`, and cannot take a `tx`), state the before/after enumerated count explicitly, and expect to defend
it. If the dev concludes the honest move is to leave those 6 UNCOVERED and record the seam as a finding instead —
**that conclusion is acceptable and should be taken**, with the reasoning written down. The brief's rule stands: a
sprint that reports a limit is doing its job.

### 5.3 The ratchet — DERIVED on both sides, and it must BITE

The wall is **set equality, not a count**:

* For every Layer-B file, **derive** the actual set of `<receiver>.<model>.<verb>(` statements from the source with
  the check script's existing matcher, and require it to equal the declared entry set **exactly**.
  * a statement in the file with **no** entry → **FAIL** (`unlisted`) — this is the hole the glob layer left open;
  * an entry matching **no** statement → **FAIL** (`dead`) — this is how a stale literal is caught;
  * an entry with an empty/missing `reason` → **FAIL** (`unreasoned`, the existing branch, extended to Layer B).
* Keep `scoped + enumerated === total` unchanged as the top-level verdict.
* **No ratio floor.** A floor is a knob and a knob here is a bypass flag wearing a different hat (`DNC-10`). This is
  recorded verbatim in the ledger and is not open for re-litigation.
* Extend the existing gate spec's mutant family in `tenant-adversarial-gate.spec.ts`: a mutant that adds an
  unlisted statement to a Layer-B file, and a mutant that deletes a reason, must each make the verdict
  non-affirmative.

**AC-7 requires the ratchet to be shown biting for real, not only in a spec:** add a statement to a Layer-B file, run
the check, capture the FAIL output verbatim in the PR, then restore and capture the PASS. A ratchet that has only
ever been green has never been tested.

## 6. PART 3 — `PF-217`, the `classSessionId` ownership gap

### 6.1 The defect, and why RLS does not close it

`lessons.controller.ts:263` writes `classSessionId: body.classSessionId` **straight from the request body with no
ownership validation**. Measured in `schema.prisma:1156`:

```prisma
classSessionId String? @unique @map("class_session_id") @db.Uuid
classSession   ClassSession? @relation(fields: [classSessionId], references: [id], onDelete: SetNull)
```

Mono-column, **nullable**, **`@unique`**, FK to the tenant-scoped `class_session`. PostgreSQL evaluates referential
integrity **outside** row security: `tenant_isolation`'s `WITH CHECK` sees only `lesson_entry.tenant_id`, and the FK
trigger runs as the owner of `class_session` with policies off. **A foreign `classSessionId` inserts under a
perfectly correct policy.** This is `PF-204`'s shape (closed for `calendar_event` by `S-E01-5` / `ADR-049`)
recurring in a second module.

### 6.2 The fix — `ADR-049`'s pattern, applied

Inside `create`'s `this.scope.run(...)` callback, **before** the `lessonEntry.create`, and **after** the
`teaching_assignment` guard (order matters: the caller learns nothing about its body until it has proven it owns the
path row):

```ts
if (typeof body.classSessionId === 'string' && body.classSessionId.length > 0) {
  const owned = await tx.classSession.findFirst({
    where: { id: body.classSessionId, tenantId },
    select: { id: true },
  });
  if (owned === null) throw new BadRequestException(/* the SAME message as "unknown" */);
}
```

* **`findFirst`, not `findUnique`** — `findUnique` cannot carry the non-unique `tenantId`, so the composite predicate
  would be applied *after* the foreign row was fetched.
* **`tenantId` EXPLICIT in the `where`** even where RLS makes it redundant (`ADR-042 §D1`): on every deployment
  today the scope is `degraded_no_app_url`, running as the OWNER, and this clause is the **only** thing working.
* **One 400 for both failure modes, byte-identical** — "foreign tenant" and "does not exist" must be
  indistinguishable *by construction*, not by careful wording (`ADR-048 §D9`).
* **Truthiness, never key presence** — `null` and `''` are live "clear this field" values from clients, and
  `findFirst({ where: { id: null } })` is a Prisma validation error, i.e. a 500. **`null` must keep succeeding:** the
  column is nullable and this slice must not turn an optional FK into a required one.
* Convert `:252`'s `teachingAssignment.findUnique` + manual tenant compare into the same
  `findFirst({ where: { id, tenantId } })` shape inside the scope, keeping the **404** it throws today (that is an
  existing refusal semantic; do not change it under G-AUTHZ).

### 6.3 The other write paths — measured

* **`update`: NOT exposed.** `UpdateLessonDto` (`:50-57`) has **no `classSessionId` field** — measured. So `update`
  cannot write the FK and needs no probe. **Pin that premise with a source assertion** (the `PF-206` technique): a
  test that reads the DTO and asserts the field is absent, so adding it later turns a silent hole into a red test.
* **`remove`: no FK write.** Nothing to probe.
* `teacherProfileId` (`:262`) is derived from the *already-validated* assignment row, not from the body — safe.

### 6.4 The `@unique` consequence — a HYPOTHESIS to measure, not to assert

`classSessionId` is `@unique` and `calendar_event`'s scope FKs were not. Two effects to prove **separately**:

* **Cross-tenant REFERENCE** — tenant A's `lesson_entry` points at tenant B's `class_session`.
* **Cross-tenant SQUAT / denial (hypothesis)** — because the column is `@unique`, once A has taken B's session id, B
  can **never** link its own `lesson_entry` to its own session: the unique index refuses it. Unique-index
  enforcement, like FK enforcement, sits **below** row security, so B would receive a **`P2002`** for a row it cannot
  see — a denial *and* an existence oracle.

**Measure this before asserting it.** If it does not reproduce, say so and keep the correction — that is the habit.
Note also that a nullable `@unique` column permits **many NULLs** (Postgres does not treat NULLs as equal), so the
"no class session" case is unaffected; confirm that too.
