**Epic** `V3-E01` — Tenant isolation and identity resolution · **Layer** L0 · **Risk tier** **P0**
**Closes** `PF-02` half (a) *as far as it can honestly be closed* — see §9, the row does **not** flip to `closed`
**Gates** G-TENANT, G-MIGRATION, G-DNC · **DNC** DNC-10
**Touches** backend (`apps/api`) only — **no UI, no worker, no controller, no guard, no DTO, no contracts type**
**Author** John (BMAD PM) · **Written** 2026-08-13

## 0. Read this first — what this slice is, in four sentences

The repository claims RLS (ADR-002) and has none: **zero** `ENABLE ROW LEVEL SECURITY`, **zero** `CREATE POLICY`,
anywhere, `0_baseline` included. This slice writes them, for the 44 tenant-scoped tables, and proves by **execution
against the real PostgreSQL** that a real non-owner login role sees tenant A's rows and cannot see tenant B's.

**It does NOT make the running application RLS-isolated**, and no artefact you write may imply that it does. The API,
the seeds and `prisma migrate` all connect as `pilotage`, which **owns all 55 tables**, and a table owner is exempt
from RLS unless `FORCE ROW LEVEL SECURITY` is set — which this slice deliberately does **not** set (§3). The remaining
step is a **connection cutover**, not more policy work, and it belongs to `S-E01-1`.

## 2. The problem, stated without softening

`ADR-002` says multi-tenancy is "shared DB + `tenant_id` + RLS". Two of those three are true. The third has been a
claim in prose for the life of the project, and `PF-02` — the **oldest open L0 trust finding** — records exactly that
gap. `S-E01-2` (2026-08-11) closed half (b), the SQL-injection half, on a seam nobody calls. Half (a), "RLS claimed,
not implemented", is still literally true: F5.

The failure mode this slice must not commit is **shipping green while protecting nothing**. There are five distinct
ways to do that here, and each has a dedicated acceptance criterion:

1. Policies applied but the connection under test is the **owner** → everything passes, isolation nil (AC-8, AC-14).
2. A denial test that passes because the role has **no grants at all** (F8) rather than because RLS denied it (AC-6).
3. `current_setting(...)` **without** `missing_ok` → 42704 on every context-free connection: migrations, seeds, health
   checks, every BullMQ job break on day one (AC-2).
4. The obvious repair for (3), `current_setting(...) IS NULL OR tenant_id = ...` → **fails open for the entire
   application** (AC-4, DNC-10).
5. `tenant_id::text = current_setting(...)` → matches **zero rows** for an upper/mixed-case tenant id, because
   PostgreSQL renders `uuid` lowercase while `assertTenantId` deliberately preserves case. Fail-closed, but
   **invisible**: the dashboard is simply empty and the investigation starts three layers away (AC-3).

## 3. The central design decision — already taken; implement it, do not relitigate it

**`ENABLE ROW LEVEL SECURITY` + a `tenant_isolation` policy on the 44 tables, and DML `GRANT`s to `app_user`.
NO `FORCE ROW LEVEL SECURITY` in this slice.**

This reasoning must be written into **both** the migration header **and** ADR-032's amendment. It is not a footnote:

- **`FORCE` makes the table owner subject to the policies.** Today the API, every seed script and `prisma migrate`
  connect as the owner `pilotage` (F6), and there are **zero** `withTenant` call sites (F13) — so no connection sets
  the GUC. `FORCE` today would make **every query in the entire application return zero rows**. That is a local
  outage, and the routine is required to leave the stack healthy.
- **The correct fix for owner-bypass is not `FORCE`, it is that the application must stop connecting as the table
  owner.** `app_user` exists for exactly that (F7), and `DATABASE_URL_APP` is already declared (F14).
- Therefore: this slice makes the policies **exist**, be **correct**, and be **proven to deny for a real, non-owner,
  login-capable role**. The remaining step is a **connection cutover**.

**The honesty rule, and it is a hard acceptance criterion (AC-16).** Not one sentence in the migration, the ADR,
`PROGRESS.md`, `OPEN.md`, the PR description or any code comment may be readable as *"the app is now RLS-isolated"*.
That overclaim **is** the defect `PF-02` records. Write instead: *"the policies exist and deny for `app_user`; the
running application still connects as the table owner `pilotage` and is therefore still NOT isolated by RLS."*

## 5. Acceptance criteria

All sixteen are **criteria**, not notes. AC-1…AC-12 come from the intake brief verbatim in substance; AC-13…AC-16
were added by this spec after measurement, and each names the false-green it exists to prevent.

### AC-1 — the migration exists and is generated from one source

`apps/api/prisma/migrations/20260813120000_tenant_rls_policies/migration.sql`, hand-authored and reviewed, **never**
`db push` (G-MIGRATION). For **each of the 44** tables: `ENABLE ROW LEVEL SECURITY` **and**
`CREATE POLICY tenant_isolation … USING (…) WITH CHECK (…)`.

**Shape.** A single `DO $$ … $$` block iterating a **literal `text[]` array of the 44 table names**, executing
`format('ALTER TABLE public.%I ENABLE ROW LEVEL SECURITY', t)` and the `CREATE POLICY` via `format(… %I …)`.

- The array is a **literal list**, never a discovery query over `information_schema`. A discovery-driven migration
  applies differently on different databases and is unreviewable — a reviewer must be able to **count 44**.
- `%I` (quote_ident), never `%s` — the names are ours, but `format('%I')` is the shape that stays correct when
  somebody adds a table whose name needs quoting.

### AC-2 — the predicate, and `missing_ok` is mandatory

The predicate is exactly:

```sql
current_setting('app.current_tenant_id', true)::uuid = tenant_id
```

The second argument `true` (`missing_ok`) is **mandatory**. Without it every connection that never set the GUC raises
`42704` (and `22P02` on empty string), breaking migrations, seeds, health checks and every BullMQ job on day one.
**Prove the `missing_ok` behaviour by execution** (AC-7c) — do not assert it in prose.

### AC-3 — CAST, never compare as text

Write `current_setting(…)::uuid = tenant_id`. **Never** `tenant_id::text = current_setting(…)`: PostgreSQL renders
`uuid` lowercase, `assertTenantId` deliberately preserves case, so the text form silently matches **zero rows** for an
upper/mixed-case tenant id — fail-closed but **invisible**. A spec assertion must pin the cast direction so the text
form cannot be reintroduced.

### AC-4 — NULL context means SEE NOTHING, decided deliberately

With `missing_ok` the GUC is `NULL` when unset, the predicate evaluates `NULL`, and no row passes — fail-closed **by
construction**, no extra clause required.

**You must NEVER write `current_setting(…) IS NULL OR tenant_id = …`.** That fails **open** for the whole
application and is DNC-10 ("hard-coded bypass") committed in SQL. A spec assertion must scan the migration text for
that shape and any `OR`-widened variant, and fail on it.

Add an executed test: a connection with **no** context sees **zero rows** **and raises no error**. Both halves.

### AC-5 — grants, conditional on the role existing

The migration `GRANT`s `SELECT, INSERT, UPDATE, DELETE` on **the 44 tables** to `app_user`, plus `USAGE ON SCHEMA
public`.

- **Only the 44.** Do **not** write `GRANT … ON ALL TABLES IN SCHEMA public`: that would hand `app_user` unrestricted
  access to the 11 unprotected reference/global tables (`tenant`, `role`, `permission`, `user_role`, `branding`,
  `outbox_event`, …) which carry **no** policy. Each of those 11 needs its own decision, and that decision belongs to
  the cutover slice. Say so in the migration header.
- **No sequence grants** — F12: there are none.
- **Conditional on the role existing.** Wrap the grants in a `DO` block testing
  `EXISTS (SELECT 1 FROM pg_roles WHERE rolname = 'app_user')`, and `RAISE NOTICE` when absent. Roles are
  **cluster-wide** while the schema-drift gate creates **scratch databases** and runs `migrate deploy` on them; a
  fresh cluster without `app_user` must still deploy successfully. **The `ENABLE`/`CREATE POLICY` half is
  unconditional** — only the grants are guarded.

### AC-6 — THE POSITIVE CONTROL. The criterion that stops this slice being a false green.

`app_user` today has **zero** grants (F8), so a test asserting *"foreign-tenant rows are not visible"* would pass for
**entirely the wrong reason** — `permission denied` is not RLS.

The suite **MUST**, connected **as `app_user`**, first prove that with the GUC set to tenant A, **tenant A's rows ARE
VISIBLE**. Only a suite that shows rows **appearing and disappearing** as the GUC changes is evidence of RLS.

**State this explicitly, in the test file, in a comment a reviewer cannot miss.** A `permission denied` error anywhere
in the visibility path must fail the suite loudly rather than be caught and read as "denied, therefore isolated".

### AC-7 — the executed two-tenant adversarial proof

Connected **as `app_user`**, against the real PostgreSQL, all five:

| | Case | Expected |
|---|---|---|
| (a) | GUC = A | tenant A's rows **visible** (the AC-6 positive control) |
| (b) | GUC = A | tenant B's rows **NOT visible** |
| (c) | GUC unset | **zero rows**, **no error** |
| (d) | `INSERT` carrying tenant B's id while GUC = A | **rejected** by `WITH CHECK` (SQLSTATE `42501`) |
| (e) | `UPDATE` moving a row across tenants | **cannot** succeed |

Build fixtures in the test; **clean them up**; leave the server clean (§7).

### AC-8 — the recorded limit, tested rather than hidden

A test named so nobody can mistake it for a defect — e.g.
`« la limite ENREGISTREE de cette tranche : le PROPRIETAIRE contourne les policies (pas de FORCE) »` — that, connected
as the **owner** `pilotage`, **all rows remain visible regardless of the GUC**.

This is the deliberate, documented limit of the slice (§3). It is the test that makes the honesty in §3 executable
instead of rhetorical.

### AC-9 — narrow `withTenant`'s `fn` to `Prisma.TransactionClient`

`apps/api/src/shared/prisma/prisma.service.ts` ~lines 152, 158, 221: change `fn: (tx: PrismaClient) => Promise<T>` to
`fn: (tx: Prisma.TransactionClient) => Promise<T>` and drop the `as unknown as PrismaClient` cast at :158.

Prisma 5.22 exports it. It drops `$transaction`/`$connect`, so **both** a nested transaction **and** the "closed over
the injected service instead of `tx`" mistake become **compile errors**. This is `PROGRESS.md` obligation 3, and it
must land **before** the first call site exists. With zero callers (F13) it breaks nothing.

### AC-10 — the GUC name cannot drift between TypeScript and SQL

`TENANT_GUC = 'app.current_tenant_id'` (`prisma.service.ts:18`) and the policy predicate must be tied together by a
**check**, not by discipline. `PROGRESS.md` obligation 2 records that the existing ratchet reads
`apps/api/src/shared/prisma/**` only and therefore **cannot see** a `.sql` file.

Extend the existing source ratchet (`prisma.service.spec.ts` §"Cliquet de source") to read
`apps/api/prisma/migrations/**/*.sql` and assert the policy predicate contains `TENANT_GUC` **as an interpolated
constant, not a re-typed literal** — i.e. `expect(sql).toContain("current_setting('" + TENANT_GUC + "', true)::uuid")`.
Renaming the constant without editing the SQL must turn the suite **red**.

### AC-11 — rewrite the docblock at `prisma.service.ts:181-220`

Its propositions **2** (*"il n'existe AUCUNE policy RLS dans cette base"*) and **5** (*"Activer RLS est une story
ULTÉRIEURE"*) become **FALSE** with this diff. An accurate comment that decays into a false claim is the exact failure
mode that cost this programme three separate slices.

Rewrite it to say precisely **what is now true** (policies exist on 44 tables; they deny for `app_user`; the read-back
and bound-parameter properties are unchanged) **and what is still not** (the API connects as the owner, so RLS does
not constrain it; `withTenant` still has zero callers; no `FORCE`). Keep proposition 4 — *a well-formed UUID is a
FORM, not a RIGHT* — it is still true and still load-bearing.

### AC-12 — a stated, tested rollback (G-MIGRATION)

The migration header must carry the **DOWN path in full**, copy-pasteable:
`DROP POLICY IF EXISTS tenant_isolation ON public.<t>;` + `ALTER TABLE public.<t> DISABLE ROW LEVEL SECURITY;` for the
44, plus the matching `REVOKE`s. It must be **tested**, not merely stated: a test that executes the down SQL against a
scratch database (or against the live database, restoring the up-state afterwards) and asserts `pg_policy` returns to
its prior count and `relrowsecurity` is `f` again.

State the **expand/contract** reasoning explicitly: this migration is **pure expand** — it adds policies and grants,
alters no column, drops nothing, and rewrites no data. It is therefore reversible without data loss, which is why a
`DROP`/`DISABLE` down path is sufficient.

### AC-13 *(added by this spec)* — the 44-table list cannot silently drift

The literal array in the migration (AC-1) is a snapshot. A model added later **with** `tenantId` would get no policy,
silently, and the gap would be invisible until an audit.

Add a ratchet — no database required — that parses `apps/api/prisma/schema.prisma`, collects the `@@map` name of every
model declaring `tenantId String`, and asserts that set is **equal** (set equality, both directions) to the 44 names in
the migration array. F11 confirms this parse is reliable today: 44 with, 10 without.

**Assert that the two sets AGREE — do not weaken either side to make it pass.** If a future table legitimately has
`tenantId` but must not carry a policy, that is a decision requiring its own named, commented exemption entry, not a
loosened assertion.

### AC-14 *(added by this spec)* — the proof must prove *whom it connected as*

**The single most dangerous false green available in this slice.** If the DSN the suite uses is ever pointed at the
owner `pilotage` — by an edited `.env`, by a copy-paste, by a future refactor of the URL helper — then AC-6 and AC-7
would **all pass on an unprotected database**, because the owner sees everything and can write anything.

Before any visibility assertion, the suite must query, **over the very connection it is about to test**:

- `select current_user` → **not** the owner of the tables under test;
- `select rolbypassrls from pg_roles where rolname = current_user` → **`f`**;
- `select count(*) from pg_class c join pg_roles r on r.oid = c.relowner where c.relname = 'student' and r.rolname = current_user` → **0**.

Any of these failing must **fail the suite**, never skip it. This is not defence in depth; it is the assertion that
gives every other assertion in the file its meaning.

## 6. Implementation notes a developer will otherwise have to rediscover

**The policy statement.**

```sql
CREATE POLICY tenant_isolation ON public.<t>
  FOR ALL
  TO PUBLIC
  USING      (current_setting('app.current_tenant_id', true)::uuid = tenant_id)
  WITH CHECK (current_setting('app.current_tenant_id', true)::uuid = tenant_id);
```

`TO PUBLIC` is deliberate and must not become `TO app_user`. A policy restricted to one named role leaves **every
other** non-owner role — present or future — unconstrained: that is a role exemption, i.e. fail-open, i.e. DNC-10.
The only exemption in this design is the **ownership fact**, which §3 documents and AC-8 tests.

`FOR ALL` gives one policy covering `SELECT`/`INSERT`/`UPDATE`/`DELETE`. `USING` governs which existing rows are
visible/modifiable; `WITH CHECK` governs which rows may be written — AC-7(d) and AC-7(e) exercise the second, and
without `WITH CHECK` an `INSERT` carrying a foreign `tenant_id` succeeds.

**DNC-10, restated for this diff.** No superuser escape. No `IS NULL OR`. No environment flag that disables the
policy. No role exemption beyond the ownership fact being documented. The existing DNC-10 ratchet in
`prisma.service.spec.ts` already scans for `SYSTEM_TENANT`, `SKIP_`, `ALLOW_`, `skipTenant` — **extend the same token
set over the migration SQL**.
