## 1. The slice in five sentences

`S-E01-2b` policied the **44** tables carrying a `tenant_id` column. `S-E01-2c` policied the **five** that derive a
tenant by **foreign key**. That left exactly **one** base table in `public` outside both classes: `outbox_event`,
which holds **no foreign key at all** — its `aggregate_type` (text) + `aggregate_id` (uuid) pair is polymorphic and
unconstrained, so there is no parent to predicate on and none may be invented.

This slice gives it a **denormalised `tenant_id`** — a column, a foreign key to `tenant`, a leading index, the
**ordinary** `tenant_isolation` policy shared word-for-word with the 44, and a `SELECT, INSERT, UPDATE` grant — and
proves by execution that tenant A sees its own event and not tenant B's.

**It does NOT make the running application RLS-isolated.** The API still connects as `pilotage`, which owns all 55
tables, and an owner is exempt from its own policies while `FORCE ROW LEVEL SECURITY` is absent — deliberately, per
`ADR-032 §D5`. What remains is the **connection cutover** (`S-E01-1`). No sentence here may read as "the app is
isolated"; that over-claim *is* the `PF-02` defect.

## 2. Why this blocks roadmap work — the RULE 0 justification, stated once

`PF-185` is a `PF-58+` id and is therefore **not itself roadmap work**. It was selectable only under RULE 0 clause 3,
which requires naming the roadmap story it blocks:

> **`S-E01-1` — the identity seam and the `DATABASE_URL` cutover to `app_user`, which closes `PF-01` and completes
> `PF-02`.**

Until `outbox_event` has a tenant path, that cutover forks two ways and **both are bad**: grant the table without a
policy and `app_user` receives an **unfiltered, cross-tenant event log** — every aggregate of every tenant; leave it
ungranted and the day a writer lands, the feature fails with `permission denied` that will read like a bug in the
feature rather than a deliberate fail-closed state. Neither branch is acceptable, which is why run 53 sequenced this
**before** the cutover rather than during it.

`S-E01-1` is not hypothetical downstream work: its first half is already in flight as **PR #246** (`S-E01-1a`, held).

## 5. Acceptance criteria — as shipped

### AC-1 — the column, the key, the index
`tenantId String @map("tenant_id") @db.Uuid` with `tenant Tenant @relation(..., onDelete: Cascade)`, and
`Tenant.outboxEvents`. The migration emits **exactly the names Prisma generates** —
`outbox_event_tenant_id_fkey`, `outbox_event_tenant_id_status_created_at_idx` — because `prisma migrate diff` compares
them and a mismatch would be a drift RED.

### AC-2 — R-11, created here rather than asserted
Unlike the 44 (`tenant_id` already led an index) and the five derived (the FK column already led one), `outbox_event`'s
`tenant_id` **did not exist**, so nothing could lead by it. The migration **creates**
`(tenant_id, status, created_at)` and, before enabling the policy, **verifies on `pg_index` that an index leads by
`tenant_id`, raising if not**. `(status, created_at)` is kept — the relay drains by status, and removing it would be a
behaviour change disguised as cleanup. **This is the first slice in the sequence where R-11 is real work.**

### AC-3 — the predicate, identical to the 44
`nullif(current_setting('app.current_tenant_id', true), '')::uuid = tenant_id`, in **both** `USING` and `WITH CHECK`,
declared explicitly (a NULL `with_check` silently falls back to `USING`, which looks right until someone adds a
permissive one), `FOR ALL TO PUBLIC`. **`nullif` is not decorative:** after a `COMMIT`, `set_config(…, true)` leaves
the GUC at `''` and not `NULL` on this cluster, so a bare cast raises `22P02` on the **second** query of every pooled
connection (measured run 52). It is also not a disguised `IS NULL OR` — `''` becomes `NULL`, and `NULL` passes no rows.

### AC-4 — `SELECT, INSERT, UPDATE`, and **not** `DELETE` — *this overrules the brief*
The routine's brief proposed full DML on the reasoning that a worker drains the queue. **The implementation refused
`DELETE` and it is right.** `INSERT` is the pattern itself (the producer writes the event in the same transaction as
the aggregate); `UPDATE` is the relay marking `status`/`sent_at`/`attempts`/`last_error`. `DELETE` is **retention**,
which is an **owner** job — granting it to the application role would let it erase **undelivered** events, i.e. exactly
the loss the outbox pattern exists to prevent. The absence is **asserted** (`OUTBOX_DELETE = 0`) so it cannot widen
quietly, and the privilege string is validated at migration time against a **closed set** that contains no `DELETE`.

### AC-5 — one migration, not two — *this also overrules `PF-185`*
`PF-185` prescribed `NOT NULL` in a **second** migration. Expand/contract in two steps exists to protect against a
**live writer** inserting rows without the column between deployments. **There are zero writers**, so that window does
not exist — and splitting would leave a **security discriminant nullable in production for a whole deploy cycle**,
which is strictly worse. `ADR-044 §D2` records when the split becomes mandatory again: the day a writer exists.

### AC-6 — the backfill is fail-loud, never complacent
Mono-tenant database → the assignment is **forced by the catalog**, not guessed. Any other shape with orphan rows →
`RAISE EXCEPTION` carrying the exact count, and `migrate deploy` **fails**. The two complacent answers are refused by
name: deleting orphans (silent data loss of undelivered events) and assigning them to the first tenant (fiction with a
policy around it).

### AC-7 — the census stays an AGREEMENT
`outbox_event` **leaves** `NON_DERIVED_EXPECTED`, and both terms stay computed from the catalog:
`RLS_ON == TENANT_COLS + DERIVED_EXPECTED` → `50 == 45 + 5`. **No `50` is hard-coded and no frozen list is
subtracted** — that is precisely how a later unprotected table would ship invisibly. The AC-5b residue assertion still
names every unreached table with a written reason, and no longer names `outbox_event`.

### AC-8 — proven by execution, and `permission denied` regains its meaning
The separate `OUTBOX_SQL` invocation is **removed**, not merely re-pointed: `outbox_event` now takes the same
two-tenant proof as every other table — visible under GUC A, invisible under GUC B, invisible with no context,
reappearing under GUC B, foreign-tenant `INSERT` rejected by `WITH CHECK`, and the **silent** case (marking a foreign
tenant's event delivered raises nothing and touches nothing) measured from the owner connection. Because there is no
longer any place where `permission denied` is expected, the file-wide guard that treats that string as a loud failure
**is meaningful everywhere again** — which it was not while block 7b existed.

## 6. Pre-mortem — assume this shipped and caused an incident

1. **The cutover happens and the outbox returns nothing.** Cause: `withTenant` was not used, so the GUC is unset and
   the policy correctly denies everything. Reads as "the outbox is broken". Mitigated by the no-context assertion,
   which fixes the expected value at **zero** and says so.
2. **A writer lands and inserts without `tenant_id`.** `NOT NULL` rejects it at the database. Loud, correct.
3. **Someone grants `DELETE` to silence a retention job.** Caught by the `OUTBOX_DELETE = 0` assertion and by the
   closed privilege set in the migration. The correct fix is an owner-run purge.
4. **A restore loses the column.** **The attribution is not recomputable** — `aggregate_type`/`aggregate_id` are
   polymorphic, so no join recovers it. Recorded in `restore-drill-baseline.json`; the migration's backfill is
   explicitly *not* a repair path for a bad restore.
5. **A tenant is deleted and events vanish via `ON DELETE CASCADE`.** Accepted: this is a **queue**, not an audit
   trail, and a queue for a deleted tenant has no addressee. `ADR-044` says which it is and why — the same question
   `PF-186` answers *differently* for `grade_revision`, which is why that one stays open.
