## §0 The ledger disagreed, and where it is wrong

Three corrections are load-bearing. Two overrule the finding ledger; one overrules the brief that commissioned
this story. **All three were measured at HEAD, not inherited.**

### §0.1 `PROGRESS.md` points at a different slice — the SLICE wins

`docs/spec/features/v3-e01/PROGRESS.md` closes with *"The pointer is now `S-E01-1`"* and asserts
`PrismaService.withTenant` has **"0 production call sites out of 722"**. Both statements are stale: `calendar`
(S-E01-1d) and `lessons` (S-E01-1e) are converted, and the counter measures **803** call sites today, not 722.
The operator override selects **S-E01-1f**; implement this story. Do not substitute `S-E01-1`.

### §0.2 PF-208's recorded blast radius is WRONG — correct it, do not repeat it

`OPEN.md:137` records that a foreign `userProfileId` "writes an `announcement_receipt` **and a notification** into
**another tenant's** user feed." **Measured, it does not render in the victim's feed.** Every victim-side read path
filters on the *victim's* tenant while the injected rows carry the *attacker's* `tenantId`:

| Read path | File:line | Filter |
|---|---|---|
| `list()` non-staff branch | `announcements.controller.ts:139-148` | `announcement: { tenantId: me.tenantId }` |
| `unreadCount` | `announcements.controller.ts:194-200` | `announcement: { tenantId: me.tenantId }` |
| notification feed | `notifications.controller.ts:40-45` | passes `tenantId: me.tenantId` into `notifications.list` |
| the write itself | `announcements.controller.ts:604-616` | `tenantId: a.tenantId` — the **attacker's** — with the **victim's** `userProfileId` |

**The honest severity is TWO things, and both must be stated wherever this is described:**

- **(a) INTEGRITY.** Tenant-mismatched rows are written into `announcement_receipt` and `notification`, referencing a
  `userProfileId` that belongs to another tenant. The rows are real, persistent, and invisible to the victim — they
  are *dark data*. They also become live the instant any read path stops filtering on the reader's own tenant.
- **(b) DISCLOSURE RENDERED TO THE ATTACKER.** `getOne` (`:415-440`) returns `stats.total`, `readRate`,
  `_count.recipients` (list, `:115`/`:132`) and the **raw `userProfileId` UUID list** at `:433-438`. Because the
  attacker owns the announcement, they read all of it. So the attacker learns **the cardinality of a foreign
  class's guardian + teacher + linked-student set**, and can **confirm that a foreign profile id exists**. That is a
  cross-tenant counting-and-existence oracle.

**Do not overclaim.** Names and e-mails are correctly suppressed: the profile lookup at `:361-363` **is**
tenant-filtered (`tenantId: me.tenantId`), so a foreign recipient renders as `userProfile: null`. There is **no PII
leak**. **Do not underclaim either** — the cardinality oracle is real and it is larger than a single id.

### §0.3 The commissioning brief's AC-3 premise is FALSE — measured, and this overrules it

The brief asserts *"a preview endpoint that leaks the count is the identical oracle with no write at all."*
**`GET /announcements/preview-recipients` does NOT leak a cross-tenant count.** Traced at
`announcements.controller.ts:262-310`: `computeRecipients` returns the foreign ids, but the returned `count` is
**`profiles.length`** (`:308`) — the length of a lookup that **is** tenant-filtered (`:274-275`,
`where: { id: { in: ids }, tenantId: me.tenantId }`). For a foreign scope that is `0`, and the early-return at
`:263-268` also yields `0` with an all-zero breakdown. The two responses are **byte-identical**, so there is no
observable difference and therefore **no cross-tenant oracle on this endpoint**.

**But the preview has a DIFFERENT, real hole the brief did not name, and it is intra-tenant horizontal:**
`previewRecipients` (`:230-236`) refuses a teacher only for `school_wide` / `individual_user`. It **does not carry
the teaching-assignment check** that `create` applies at `:466-485`. So **a teacher can preview the recipient count
and role breakdown of any class in their own school, including classes they do not teach** — the exact enumeration
the docblock at `:216-219` claims is prevented ("*so the composer can't be used to enumerate the school via the
preview*"). That docblock is **false as written** and is a G-DNC / DNC-06 expectation-debt instance.

## §1 What is broken, measured at HEAD

### §1.1 The controller writes five unverified ids

`apps/api/src/modules/announcements/announcements.controller.ts`

- **`:45-49`** — `CreateAnnouncementDto` declares `cycleId`, `gradeLevelId`, `classSectionId`, `studentId`,
  `userProfileId` as bare `@IsOptional() @IsUUID()`. A UUID is a *format*, not a *permission*.
- **`:622-646`** — `validateScope` checks only that the field required by the declared scope is **present**. It never
  checks that the id belongs to the caller's tenant.
- **`:489-509`** — `create` persists all five **verbatim** from the DTO.
- **`:459-486`** — the **only** ownership-ish check in the handler: a non-admin teacher's `classSectionId` is
  validated against `teachingAssignment` **with `tenantId`**. It applies to **one role** and **one scope**. An admin
  (`super_admin` / `school_admin`) reaches the write with **zero** ownership checks on any of the five ids.

### §1.2 Five untenanted queries in the service — FOUR scope branches leak, not one

`apps/api/src/modules/announcements/announcements.service.ts`

| # | Line | Query | Tenant predicate? |
|---|---|---|---|
| 1 | `:43-44` | `individual_user` → returns the supplied `userProfileId` **verbatim** as the recipient set | none — no query at all |
| 2 | `:91-93` | `guardiansOfStudents` → `guardianship.findMany({ where: { studentId: { in }, status: 'active' } })` | **NO** |
| 3 | `:109-111` | `studentsOwnProfiles` → `student.findMany({ where: { id: { in }, userProfileId: { not: null } } })` | **NO** |
| 4 | `:120-122` | `teachersOfClasses` → `teachingAssignment.findMany({ where: { classSectionId: { in } } })` | **NO** |
| 5 | `:129-131` | `recipientsForClassSections` → `enrollment.findMany({ where: { classSectionId: { in }, status: 'active' } })` | **NO** |

Only `allTenantUsers` (`:82-84`) and the two `classSection.findMany` calls (`:61-63`, `:69-71`) carry `tenantId`.

**Consequence — this is the part PF-208 missed.** `class_section_scope` (`:57-58`) hands its `classSectionId`
straight through with no tenant check, so a single foreign class id enumerates the **victim tenant's guardians +
teachers + linked students in bulk**. `grade_level_scope` and `cycle_scope` are protected only *incidentally*,
because their `classSection.findMany` is tenanted and yields an empty list — that protection is **accidental, not
designed**, and it disappears the moment anyone reorders that code. `individual_student` leaks through queries 2
and 3. **PF-208 recorded the smallest of the four branches.**

### §1.3 What is *not* wrong, so nobody re-fixes it

- `list`, `unreadCount`, `getOne`, `update`, `publish`, `remove` all carry a correct `tenantId` guard.
- The `getOne` profile lookup (`:361-363`) and the `list` author lookup (`:173-176`) are tenant-filtered.
- `materialiseReceipts` (`:145-156`) writes only what `computeRecipients` returned — fix the source, not the sink.

## §2 Acceptance criteria

> Priority order. **AC-1 … AC-4 are the P1 security fix and its honest description; they must not be partially
> done.** If the budget forces a cut, cut from the BOTTOM: AC-7, then AC-6, then AC-5. A cut item is **recorded as a
> new finding starting at `PF-228`** with a priority and a one-line reason — never silently dropped.

### AC-1 (MANDATORY) — every supplied scope id is proven owned BEFORE the write

`POST /announcements` proves all five ids belong to the caller's tenant before the `announcement` row is written:
`cycleId`→`cycle`, `gradeLevelId`→`gradeLevel`, `classSectionId`→`classSection`, `studentId`→`student`,
`userProfileId`→`userProfile`.

**Shape — copy ADR-049 exactly** (working reference: `calendar.controller.ts:630-670`):

- one `findFirst({ where: { id, tenantId }, select: { id: true } })` per **supplied** id;
- `findFirst`, never `findUnique` — so "foreign tenant" and "does not exist" are the **same branch**;
- **sequential `await` in a `for` loop — never `Promise.all`.** An interactive transaction is ONE connection;
- **`tenantId` EXPLICIT in the `where`**, even where RLS would make it redundant (see §5 — today it does not);
- refusal **byte-identical** between "foreign tenant" and "does not exist". Distinguishing them is itself a
  cross-tenant existence oracle;
- the `switch` is **CLOSED** with a `default: { const exhaustive: never = ref.field; throw unknownScopeRef(exhaustive); }`
  so a sixth field **does not compile**, and if it somehow reached runtime it **refuses** (fail closed);
- "supplied" is decided by `isSuppliedScopeId` from `apps/api/src/shared/prisma/scope-fk.ts` — **never by key
  presence**. `@IsOptional()` lets `null` through despite `?: string`, and
  `findFirst({ where: { id: undefined, tenantId } })` makes Prisma **omit the filter**, returning the first row of
  the tenant and passing the check **vacuously**.

**Refusal wording** — a 400 with a French message naming only the **field** (the caller's own data): never a tenant,
a school, a table, or a Postgres string. `unknownScopeRef` already produces exactly this.

**Ordering** — the ownership probes run **after** the role/scope refusals at `:459-486` (a teacher must not learn
anything about a body they were never allowed to send) and **before** the `announcement.create`.

### AC-2 (MANDATORY) — `computeRecipients` cannot return a foreign `userProfileId`

The five untenanted queries of §1.2 each gain a tenant predicate, **or** the service is restructured so the ids
reaching them are already proven owned. Either way the invariant is: **`computeRecipients` is incapable of returning
a `userProfileId` outside the announcement's tenant.**

**Recommended shape** (defence in depth, and it survives a future caller who forgets AC-1): thread
`announcement.tenantId` into the four private helpers and add the predicate at each — `guardianship`:
`{ tenantId }`; `student`: `{ tenantId }`; `teachingAssignment`: `{ tenantId }`; `enrollment`: `{ tenantId }`; and
for `individual_user` (`:43-44`) replace the verbatim pass-through with a
`userProfile.findFirst({ where: { id, tenantId }, select: { id: true } })` that returns an **empty set** when it
misses. AC-1 alone is not sufficient here: it guards *one entry point*, and `computeRecipients` is also reached from
`publishInternal` (`:588`) and `previewRecipients` (`:251`).

**Proof — required, per branch.** A test that supplies a foreign id and asserts the recipient set is **EMPTY** (or
that the call refuses), for **each of the four leaking branches**: `individual_user`, `individual_student`,
`class_section_scope`, and one of `grade_level_scope`/`cycle_scope`. A test that only covers `individual_user`
repeats PF-208's own mistake.

### AC-5 — the ownership-plan helpers are EXTRACTED; announcements is consumer #2 of ONE implementation

**Measured at HEAD.** `SCOPE_ID_FIELDS` (`:116`), `ScopeIdField` (`:117`), `OwnedScopeField` (`:119`),
`CREATE_OWNED_SCOPE_FIELDS` (`:126`), `ScopeIdCarrier` (`:136`), `assertSingleScopeId` (`:160`),
`scopeOwnershipPlan` (`:174`) and `unknownScopeRef` (`:201`) are all defined in **`calendar.controller.ts`** —
exported, but module-local. `lessons.controller.ts` imports **only** `isSuppliedScopeId` from
`shared/prisma/scope-fk.ts` (repo grep: zero hits on the plan helpers outside calendar and its spec).
announcements would be the **third** consumer of the pattern.

Run 61 already ruled on exactly this shape when it moved `mapWriteRefusal` out of `calendar.controller.ts` into
`shared/prisma/write-refusal.ts`, on the argument that *a second copy at module two IS the drift*. Follow that
precedent: **extract to `apps/api/src/shared/prisma/scope-fk.ts`** (the shared home that already exists for this
family) and have **calendar consume the shared copy**. Its spec
(`apps/api/src/modules/calendar/calendar-scope-ownership.spec.ts:17-22`) imports them by name — update the import,
do not fork the assertions.

**A third hand-written copy is a refusal condition for this story.**

**Design note — the extraction must generalise the field type.** `OwnedScopeField` is calendar's four fields.
announcements needs `studentId` and `userProfileId` too. Make the plan **generic over a caller-supplied field
tuple** (it already is: `scopeOwnershipPlan<F extends OwnedScopeField>(body, fields)`) and widen the base union, or
invert it to `scopeOwnershipPlan<F extends string>` keyed on the caller's `as const` tuple. Each module keeps its
**own** `as const` field list and its **own** inline `switch` — **the `findFirst` loop stays written IN LINE in each
callback.** That is not superstition: `classifyCallSite`
(`scripts/tenant-adversarial-check.js:1898`) is **lexical** and does not follow `this`. A probe hidden behind a
shared method would count **not covered** while looking converted — or worse, run on the **owner** connection while
a counter credits it to the callback (PF-200).

**Why this AC is worth more than dedup — see §4.** The plan is what makes a systematic detector *possible*.

### AC-6 — `announcements` is converted to `withTenant` (module #3)

Advances **PF-02 half (a)**. Requirements:

- `this.scope.run(tenantId, async (tx) => { … })` written **LEXICALLY** in each converted handler;
- `tx` — not `this.prisma` — for every statement inside;
- identity resolved **OUTSIDE** by necessity: `this.users.ensureUser(jwt)` and `this.ctx.forUser(me)` produce the
  `tenantId` a scope would need, so they cannot run inside one (PF-199, and both are already on the enumerated
  bootstrap allow-list);
- pure validation stays **outside** the scope — a body refused before the scope opens costs no transaction.

**THE COUNTER IS RE-DERIVED BY THE SCRIPT, NEVER EDITED AS A LITERAL.**
**Measured before (this run, `node scripts/tenant-adversarial-check.js`):**

```
AC-9 CUTOVER READINESS: the tenant scope covers only PART of the corpus (24 scoped + 120 enumerated / 803)
```

State the **after** value from a re-run. **`announcements.controller.ts` holds 23 `this.prisma.*` sites and
`announcements.service.ts` holds 8** — so the number that moves is large enough that a wrong-direction move is
unmissable.

**PF-217 is the failure mode to avoid:** `classifyCallSite` returns **`owner-inside-scope`**, *not* `scoped`, for a
`this.prisma.*` statement sitting inside a scope callback. A half-converted handler therefore moves the counter the
**wrong way** while looking converted. If you convert a handler, convert **every** statement in it, or leave the
handler alone.

### AC-7 — the boot-probe closure gains this module's entries, each with a real `why`

`APP_ROLE_REQUIRED_PRIVILEGES` (`apps/api/src/shared/prisma/tenant-scope.ts:146+`) is walked by `appRoleVerdict`
**at boot**. A missing entry does **not** fail the probe — it certifies `enforcing: true` over a closure nobody
checked, and then **every announcements request answers `42501` on all four portals**. It has already drifted once
(`academic_year`, S-E01-5).

Tables this module touches, which must gain **verb-by-verb** entries for whatever you actually convert:
`announcement`, `announcement_receipt`, `notification`, `user_profile`, `guardianship`, `student`,
`teaching_assignment`, `teacher_profile`, `enrollment`, `class_section`, `grade_level`, `cycle`.

Each `why` must be a **real reason**. The anti-vacuity guard **refuses** a reason that merely repeats the handler
verb — that is how S-E01-1e caught three inherited 6-character reasons (`create` / `update` / `remove`). A good
`why` names the user-visible consequence of the entry's absence.

**Worth more than the conversion itself:** if you can **DERIVE** the closure corpus-wide instead of extending the
third hand-maintained list, that closes **PF-219**. But only if the derivation is **corpus-wide and measured** — a
fourth list wearing a new name is the disease, not the cure.

### AC-8 — every claim is evidenced by something that RAN

Assertions written but never executed are **NOT evidence**. Run 61 shipped two that could never have passed. If

## §4 The enumeration (delivered, and it changes what AC-5 is for)

The commissioning brief asked, if it could be done cheaply, for an enumeration of the other controllers whose DTOs
accept bare scope-FK UUIDs — *"that enumeration is worth more than any prose about the class being closed."*
**It was run. Here it is, and its most useful result is a negative one.**

**Measured:** across `apps/api/src/modules/**/*.controller.ts`, **11 controllers** declare **27** scope-FK DTO
fields as bare `@IsUUID()`:

| Controller | scope-FK DTO fields |
|---|---|
| `announcements.controller.ts` | `classSectionId, cycleId, gradeLevelId, studentId, userProfileId` |
| `attendance.controller.ts` | `classSessionId, studentId` |
| `calendar.controller.ts` | `academicYearId, classSectionId, cycleId, gradeLevelId` |
| `enrollments.controller.ts` | `classSectionId, studentId` |
| `grades/assessments.controller.ts` | `termId` |
| `grades/grades.controller.ts` | `assessmentId, studentId` |
| `guardians.controller.ts` | `guardianId, studentId, userProfileId` |
| `lessons.controller.ts` | `classSessionId` |
| `school-structure/classes.controller.ts` | `academicYearId, gradeLevelId` |
| `school-structure/subjects.controller.ts` | `gradeLevelId, subjectId` |
| `teaching/teaching-assignments.controller.ts` | `classSectionId, subjectId, teacherProfileId` |

**And now the result that matters: no textual heuristic can triage this list. Both error directions were
observed.**

- **File-level** ("does the file contain a `findFirst` with `id` + `tenantId`?") marks **announcements as covered** —
  a **false green on the very defect this story fixes** — because the teacher branch at `:472-479` *is* such a
  probe, for a different field, on a branch that admins never reach.
- **Field-level** ("does `body.<field>` appear inside a tenant-qualified `find*`?") marks **all four calendar
  fields BARE** — a **false red on the module that already fixed this** — because calendar's ids reach the probe
  indirectly, as `ref.id` through `scopeOwnershipPlan`, never as `body.X`.

**Therefore, and this is the design conclusion to carry forward: AC-5 is not cosmetic de-duplication — it is the
enabling step for closing the class.** As long as ids may reach a write by any route, "is this field proven owned?"
is a **data-flow** question that a grep cannot answer. Once the shared plan is the **only** sanctioned route from a
DTO scope-FK to a persisted id, the question collapses into **list membership**: *is this field in the module's
`as const` plan tuple, and does the plan's closed `switch` have a case for it?* That is decidable by exactly the
kind of lexical checker this repo already runs, and it is how the remaining 9 controllers get triaged **by
machine** instead of by hand, one lucky finding per run.

**Record this as `PF-228` (P2)** — *"the scope-FK ownership class has no systematic detector, and the two cheap
heuristics were measured to fail in both directions; a detector becomes possible only once the shared ownership
plan is the mandated route"* — carrying the 11-controller table above so the next run starts from data instead of
from a grep. **The table is a CANDIDATE list, not a defect list**: `enrollments` (`:185-186`) and `guardians`
(`:250-251`) were spot-checked and do guard, via fetch-then-compare (`!x || x.tenantId !== me.tenantId`), which
refuses correctly. Each remaining entry needs its own reading.

## §5 DNC rules that bind here (verbatim, and what they forbid in this diff)

- **DNC-10** — *"Hard-coded demo-account billing bypass — backdoor by string comparison."* **No bypass flag, no
  allow-listed id, no env knob that turns an ownership check off. A ratio with a floor is a knob wearing a
  different hat.** The cutover-readiness counter gets **no floor**.
- **DNC-07** — *"WhatsApp templates/state in localStorage; one hard-coded client template — no central audit or
  delivery truth; TENANT LEAKAGE."* The leakage half is the class of defect this story closes. **Do not introduce a
  second instance while closing the first** — in particular, do not "simplify" any of the five new predicates away.
- **DNC-06** — *"Guides promise deeper behaviour than runtime delivers — expectation debt."* **Do not write that
  the module is isolated, converted or closed beyond what executed.** Specifically, and this must appear in the ADR:
  **the application still connects as the table OWNER, which escapes its own policies without
  `FORCE ROW LEVEL SECURITY`, so the explicit `tenantId` predicate is doing ALL the work today and RLS is not
  doubling it.** The adversarial suite proves this as a *present* leak, in its own words: *"THE APPLICATION IS NOT
  ISOLATED: as the OWNER (pilotage) with GUC = tenant A, tenant B's `user_profile` row IS STILL VISIBLE."*
  The `previewRecipients` docblock (`:216-219`) is a live instance of this rule — see AC-3.3.
- **DNC-08** — *"AI health audit missed manually reproduced defects — automation is a signal, never a release
  gate."* The counter moving is a signal. It is not proof the branches are closed; AC-2's four per-branch tests are.

## §6 Portal impact (G-PORTAL — all four, and they are not symmetric)

| Portal | Reads announcements? | What this change can break |
|---|---|---|
| **admin** | yes — `list` admin branch (`:106-119`), `getOne` stats + roster (`:415-440`), the composer's preview | the composer must still publish every **legitimate** scope; a probe that refuses a *valid* own-tenant id is an outage on the primary authoring surface |
| **teacher** | yes — `list` with `mine=true` (`:123-136`), composer restricted to the teaching footprint | AC-3.3 tightens the preview for teachers; the refusal message must match `create`'s existing one so the composer surfaces one consistent hint |
| **parent** | yes — `list` non-staff branch (`:139-188`) + the notification bell | **the core of the product.** A missing `APP_ROLE_REQUIRED_PRIVILEGES` entry (AC-7) turns every parent announcement read into a `42501` |
| **student** | yes — the student's own linked account is a recipient per **E8-S3 / FR-S3-7** (`announcements.service.ts:107-116`, `:140`) | the `student` and `user_profile` predicates added in AC-2 must **not** drop the linked-student union; assert a linked student still receives a receipt |

**G-TRUTH.** `stats.total`, `stats.readRate`, `stats.unread` and `_count.recipients` are **rendered projections**,
and this story changes what they count: after the fix, a foreign id contributes **zero** recipients instead of one.
That is the intended correction — but it means these numbers **change for existing rows only if those rows were
already poisoned**. State whether any remediation of already-written cross-tenant `announcement_receipt` /
`notification` rows is in scope (**recommendation: it is NOT — record it as a separate finding**, because a
data-repair migration is a different risk tier and would trigger G-MIGRATION, which this story does not).
