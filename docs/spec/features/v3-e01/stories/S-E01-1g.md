## §0 What the ledger and the commissioning brief got wrong

### §0.1 `PROGRESS.md` is stale on the two numbers this story moves — the SLICE wins

`docs/spec/features/v3-e01/PROGRESS.md` still asserts `PrismaService.withTenant` has **"0 production call
sites out of 722"** and that the pointer is `S-E01-1`. Both are false today: `calendar` (S-E01-1d),
`lessons` (S-E01-1e) and `calendar_event`'s scope-FK work (S-E01-5) are converted, and the corpus measures

floor**" — **do not do that.** A floor is DNC-10's knob wearing a different hat, and S-E01-1f already
refused it (`§5`). Implement **this** story; `PROGRESS.md` is context and is out of date.

### §0.2 The brief's closure list is INCOMPLETE in one direction and OVER-BROAD in the other

The brief says `APP_ROLE_REQUIRED_PRIVILEGES` "does NOT carry **announcement, announcement_receipt,
student** — and check whether `notification` is reached via a `tx` receiver too." Measured against
`apps/api/src/shared/prisma/tenant-scope.ts:146+`, the first half is right and **incomplete**, and the
second half resolves to **no**:

- **Also missing, and the brief did not name them: `user_role` and `role`.** `getOne` reads
  `userProfile.findMany({ … select: { userRoles: { where: { revokedAt: null }, select: { role: { select:
  { slug, name } } } } } })` at `announcements.controller.ts:515-518`. That nested `include` traverses
  **two more tables**. Both are grantable — `user_role` is a *derived* child of `user_profile` with
  `SELECT, INSERT, UPDATE`
  (`20260813180000_tenant_rls_derived_policies/migration.sql:375`), and `role` carries `SELECT` from the
  reference surface (`20260814180000_role_reference_surface_rls/migration.sql:400`). A converted `getOne`
  with no `user_role` / `role` entry is exactly the `academic_year` defect of S-E01-5, on the **admin
  detail page**.
- **`notification` must NOT be added.** It is reached only from `publishInternal` (`:821`), through
  `NotificationsService`, which is **excluded** by AC-3. Adding an entry for a table no `tx` receiver
  reaches certifies a closure nobody exercises — **that is PF-219's shape**, and it is the failure this
  story must not commit while fixing PF-232.
- **`teacher_profile` and `teaching_assignment` must NOT gain announcements entries either.** They are
  reached only from `assertTeacherScope` (`:868`, `:873`), which runs **before** the scope opens, by
  design (a role refusal must cost no transaction). They already carry entries from `lessons`; leave them.
- **`guardianship` and `enrollment` likewise.** Reached only by `AnnouncementRecipientsService`, excluded.

### §0.3 `announcement_receipt` has **no `tenant_id`** and **no `DELETE` grant** — both are load-bearing

`schema.prisma:1237-1249`: `AnnouncementReceipt` carries `announcement_id`, `user_profile_id`, `read_at`,
`created_at` — **no `tenant_id` column**. It is therefore not one of the 44 directly-policied tables. It is
covered by the **derived** migration as a child of `announcement`:

```
ARRAY['announcement_receipt', 'announcement_id', 'announcement', 'SELECT, INSERT, UPDATE']
```
`20260813180000_tenant_rls_derived_policies/migration.sql:371`

Two consequences the implementer must not discover the hard way:

1. **`app_user` holds SELECT, INSERT, UPDATE on `announcement_receipt` — and no DELETE.** The closed
   privilege set of that migration contains no string with `DELETE` (ADR-042 §D5). **Do not add an
   `announcement_receipt` / `DELETE` entry to `APP_ROLE_REQUIRED_PRIVILEGES`** — `appRoleVerdict` walks
   that list at boot and would then correctly refuse, 503-ing announcements on all four portals for a
   privilege the schema deliberately withholds. This is the S-E01-5 boot-probe hazard **inverted**.
2. **`remove` (`:799`) deletes an `announcement`, which `ON DELETE CASCADE`s into `announcement_receipt`
   (`0_baseline/migration.sql:1737`).** PostgreSQL runs referential-integrity actions with the privileges
   of the constraint owner and RI checks are not subject to RLS, so the cascade is expected to succeed
   without a child `DELETE` grant — **expected, not proven.** Treat this as a named risk on `remove` (AC-2
   §"handler ledger"), not as a settled fact.

### §0.4 **G-AUDIT is not triggered.** Measured, against the brief

The brief says "announcements writes audit rows. Any audit row must stay in the SAME transaction as the
mutation it audits (ADR-035)." **Measured: `grep -c audit` returns `0` in
`announcements.controller.ts`, `announcements.service.ts` and `announcements.module.ts`.** This module
writes no audit rows at all. ADR-035's rule is therefore vacuous here and **no transaction may be split
citing it**. The rule the brief was reaching for still binds in its other half and is restated as a hard
constraint in §4: **do not split a transaction to make a scope fit.**

### AC-7 (NICE — cut first) — PF-234: collapse the duplicated `switch (ref.field)` dispatch

Four hand-written copies of the same dispatch exist today: `announcements.controller.ts:358` and `:664`,
`calendar.controller.ts:360` and `:588`. **Converting `create` to `tx` makes this worse, not better** —
`create`'s copy now takes `tx` while `previewRecipients`' copy keeps `this.prisma`, so the two copies
**diverge in their receiver** inside the same file.

If budget remains, collapse them into one `(field → delegate)` resolver that takes the client as a
parameter, so one dispatch serves both `this.prisma` and `tx`.

**Two hard constraints if you touch it:**

- **The `findFirst` loop must stay LEXICALLY inside each callback.** ADR-053 §D2 and PF-200 both bind:
  attribution is lexical and does not follow `this`. A resolver that *returns a delegate* which the
  in-line loop then calls is acceptable; a resolver that *performs the query* on the caller's behalf is
  not — it would count the sites at the resolver's location, not the handler's.
- The closed `default: { const exhaustive: never = ref.field; throw unknownScopeRef(exhaustive); }` must
