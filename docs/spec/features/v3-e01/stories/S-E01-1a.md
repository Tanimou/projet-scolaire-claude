## 1. Premises, measured. Three of them were wrong.

Everything in this section was re-measured on the checkout at `38f1c06`. Statements the brief made that survived
measurement are marked ✅; statements that did not are marked ⚠️ with the correction, and **the correction governs**.

### ✅ P1 — the defect reproduces at exactly two addresses

```
apps/api/src/shared/auth/user-sync.service.ts:9    const DEMO_TENANT_SLUG = 'demo';
apps/api/src/shared/auth/user-sync.service.ts:40   where: { slug: DEMO_TENANT_SLUG },
apps/api/src/shared/auth/user-sync.service.ts:42   create: { slug: DEMO_TENANT_SLUG, name: 'Demo Tenant' },
apps/api/src/modules/identity/register.controller.ts:60/366/368   (the deferred half)
```

`ensureUser` (`:17-59`) looks the subject up by `authProviderId`, then by `email`; if **both miss**, `:38-56` upserts a
`demo` `Tenant` **into existence** and creates a `UserProfile` in it with `status: UserStatus.active`. A login is
performing a provisioning decision, and choosing its own tenancy while doing it.

### ✅ P2 — there is no spec for this file

`apps/api/src/shared/auth/` contains six `*.spec.ts` files; **`user-sync.service.spec.ts` is not one of them.** The
tenant origin of the entire API has never had a test.

### ✅ P3 — the three realm identities are real, enabled, and unseeded

`infra/keycloak/realm-export.json` `users[]` (`:106-135`) ships `admin@pilotage.local` (`school_admin`),
`teacher@pilotage.local` (`teacher`), `parent@pilotage.local` (`parent`) — all `"enabled": true`,
`"emailVerified": true`, password `Changeme123!`. `grep -rn "pilotage.local" apps/api/prisma/` returns **only**
`student@pilotage.local` (`seed-demo.ts:1509`, `:1536`, `:1552`). The three are profile-less, and under the current
code each becomes an `active` member of a self-created `demo` tenant on first login, carrying its realm role.

### ⚠️ P4 — CORRECTED: the realm export declares **no user ids**, so `authProviderId` cannot be taken from it

The brief said *"their `authProviderId` must match the realm export's user ids — read
`infra/keycloak/realm-export.json` and use the real values; do not invent them."* **There are no such values.** The
three `users[]` entries carry `username`, `email`, `firstName`, `lastName`, `enabled`, `emailVerified`, `credentials`
and `realmRoles`, and **no `id` field**. Keycloak mints the UUID at import time, per cluster.

This is confirmed a second way, from the repository's own tooling:
`apps/api/prisma/seed-keycloak-users.ts` never hard-codes an id — it calls `findUserByEmail` (`:108-113`) to
**discover** the id at runtime and only then patches it onto the profile (`:211-214`). And the existing student seed
(`seed-demo.ts:1506-1514`) creates its `UserProfile` with **no `authProviderId` at all**.

**Therefore, exactly as the brief's own escape clause anticipated: the seed uses the email-linking path.** The three
profiles are seeded with `email` and no `authProviderId`; `ensureUser`'s surviving `findFirst({ where: { email } })`
branch adopts them and stamps `authProviderId` on first login. This is the established pattern in this repository, not
a workaround, and **AC-5 requires this sentence to be stated in the shipped doc** — it is stated here.

### ⚠️ P5 — CORRECTED: `UserStatus` has no `pending`, so the `pending` state is out of scope by construction

`schema.prisma:31-35` — `enum UserStatus { active suspended deleted }`. `PROGRESS.md`'s `S-E01-1` step 1 says
*"introduce the `pending` state"*; that is an **enum change**, i.e. a migration, i.e. `G-MIGRATION`. This slice's brief
says `G-MIGRATION` must not trigger. The two are only compatible if `pending` is **not** in this slice. It is not.
`S-E01-1a` refuses; it does not park.

### ⚠️ P6 — CORRECTED: the call-site count is bigger than "~200 across every controller", and that is the point

`grep -rn "ensureUser" apps/api/src --include=*.ts` → **242 lines across 50 files** (definition and specs included).
The number is not the argument; the shape is: every one of them is `const me = await this.users.ensureUser(jwt)`
followed by scoping on `me.tenantId`. **Whatever `ensureUser` returns *is* the tenancy of the request.**

### ⚠️ P7 — CORRECTED: the "real seeded tenant" is `voltaire-demo`, not anything called `demo`

`seed-demo.ts:260-263` upserts `slug: 'voltaire-demo'`, `name: 'Lycée Voltaire (Démo)'`; `:289` binds `const T =
tenant.id`, which every seeded row uses. The three new profiles go into **`T`**. The string `demo` does not appear as a
tenant slug anywhere in the seed — so the `demo` tenant that exists on developer machines today was created **by
`ensureUser` itself**, which is the finding restated as an artefact.

### ✅ P8 — the deliberate-behaviour comment is real

`invite.controller.ts:130-136` already documents the lazy-provisioning behaviour and its consequences in prose, and
`invite.controller.spec.ts:26/53/411` repeats it. This slice makes those comments describe history rather than
behaviour; **the implementer must update them in place, not delete them** (they carry the reasoning for why the
adoption branch was withdrawn, which remains true).

## 3. Functional requirements

**FR-1 — delete the creation branch.** In `apps/api/src/shared/auth/user-sync.service.ts`, remove
`const DEMO_TENANT_SLUG` (`:9`) and the whole `if (!user) { … }` block (`:38-56`). `ensureUser` must contain **zero**
`tenant.*` calls of any kind after this slice.

**FR-2 — refuse.** When both lookups miss, throw the exported error type (FR-3). No sanitising, no defaulting, no
"best-effort" fallback — `ADR-032`'s refuse-don't-repair discipline, applied one seam over.

**FR-3 — an exported, nameable error type.** Export from the same file, modelled on `TenantContextError`
(`shared/prisma/prisma.service.ts:52-56`) so callers and tests can name it:

```ts
export class UnprovisionedUserError extends ForbiddenException {
  constructor() {
    super(UNPROVISIONED_USER_MESSAGE);
    this.name = 'UnprovisionedUserError';
  }
}
```

Extending `ForbiddenException` (not `Error`) is deliberate: Nest maps it to the wire without an exception filter, so no
new cross-cutting mechanism is introduced (**no new ADR is owed**).

**FR-4 — the status code is `403`, and here is the argument, both ways.**

*For `401`:* the subject is not a known user of this system, and `401` leaks less — it does not confirm that the bearer
token was accepted.

*For `403`, which is what ships:* the token **is** valid — `JwtAuthGuard`/`jwt.strategy.ts` already verified its
signature and issuer and refused a missing `sub` with the only `401` in this seam (`jwt.strategy.ts:60`). Emitting a
second `401` says *"your credentials are missing or invalid"*, which is false, and RFC 9110 pairs `401` with
`WWW-Authenticate` — every portal client reads that as **"refresh and retry"**. A refreshed token cannot conjure a
`UserProfile`, so `401` produces a re-authentication loop against Keycloak on every request of every page, for exactly
the identities this slice is meant to stop. `403` is terminal and truthful: **authenticated, not authorised, because
not provisioned**. The information-leak objection is accepted and judged negligible — the caller already holds a valid
realm token, so it has already learned that the realm accepted it.

**FR-5 — French, actionable, non-stigmatising, and it names no internals.** One exported constant, one message:

```ts
export const UNPROVISIONED_USER_MESSAGE =
  "Votre compte n'est rattaché à aucun établissement. Contactez l'administrateur de votre établissement.";
```

It must not reveal whether an account, an email or a tenant exists locally, and it must not name `UserProfile`,
`Tenant`, a slug or a subject id. GUARDRAILS §1 tone: factual, kind, leads to a next step.

> **⚠️ Superseded by what shipped (annotated at land, 2026-08-14).** The constant carries a trailing sentence
> this spec does not: *« …de votre établissement **pour activer votre accès**. »* Added during implementation
> because the last clause of FR-5 asks for a next step and the spec's own wording does not give one. The
> **code** is the reference; `ADR-043` §D4 was corrected to quote it. The spec line is annotated, not
> rewritten, so the divergence stays visible.

**FR-6 — the linking path is untouched.** `findUnique({ authProviderId: sub })`, then
`findFirst({ where: { email } })` + `update({ data: { authProviderId: sub } })` + the existing `logger.log`, exactly as
today (`:23-36`). Only the creation branch goes. This branch is what makes FR-7 work.

> **⚠️ NOT what shipped, and this is the one divergence a reader must not implement literally (annotated at
> land, 2026-08-14).** The implementation replaced `findFirst` with
> `findMany({ where: { email }, take: 2 })` and added **two refusal legs** FR-6 does not describe:
> `candidates.length > 1` → refuse `ambiguous-email`, and a single candidate already bound to a *different*
> subject → refuse `email-bound-to-another-subject`. The reasons are recorded in `ADR-043` §D7b, and both are
> strictly tighter than this spec: `findFirst` returns an **arbitrary** row in unspecified order (so deleting
> the creation branch alone would have swapped tenancy-by-constant for tenancy-by-arbitrary-row), and the old
> `update` was **unconditional**, so a subject presenting someone else's email string overwrote a live,
> permanent binding. `user-sync.service.spec.ts` now asserts the source contains **no `findFirst` at all** —
> a later run implementing FR-6 as written would turn that gate red.

**FR-7 — seed the three realm identities into the real seeded tenant.** In `apps/api/prisma/seed-demo.ts`, following
the shape of the student block (`:1500-1540`): three `userProfile` rows in tenant `T` (`voltaire-demo`), with
`email` = `admin@|teacher@|parent@pilotage.local`, the realm export's `firstName`/`lastName` (Sophie Durand /
Catherine Dupont / Jean Martin), `status: 'active'`, and **no `authProviderId`** (P4). Idempotent — the seed is re-run,
so use `upsert` on `email` or a `findFirst` guard, never a bare `create`.
The console block at `:1548-1554` gains a line naming the three accounts, so a developer who is refused knows why.

**FR-8 — the log line carries no PII.** On refusal, `logger.warn` with the `sub` only. No email, no
`preferred_username`, no name (RGPD minimisation, GUARDRAILS §1; same posture as `PF-176`). A refusal must not be
silent and must not be a data leak.

**FR-9 — no bypass, of any shape.** `DNC-10`. No `ALLOW_AUTO_PROVISION`, no `AUTO_PROVISION_TENANT`, no
`NODE_ENV !== 'production'` branch, no `SKIP_*`. If a local developer needs a profile, **the seed provides it**. A
bypass flag is this defect wearing a different hat, and the ratchet in AC-4 must be written so it would catch one.

## 6. Gate discharge

**G-TENANT.** This *is* the tenant seam. The proof required is not "the refusal happens" but "**the refusal wrote
nothing**": AC-1's assertion on the fake client's call record. After this slice, no code path reachable from a login can
choose or create its own tenancy — AC-4 holds that by ratchet rather than by review.

**G-AUTHZ.** The negative test is AC-1 and the default branch **refuses** — there is no fail-open leg, because the
branch that used to succeed is deleted rather than guarded. No permission is granted that the grantor lacks: this slice
grants nothing at all. FR-9 forbids the escape hatch.

**G-AUDIT — decided: no audit row on refusal, and the reason is structural, not economic.** `AuditLog.tenantId` is
**required** (`schema.prisma:1235`, `String @map("tenant_id") @db.Uuid`, non-optional; `actorId` is optional, `tenantId`
is not). A refused subject has **no tenant**. Writing the row would force this code to **invent a tenant id to record
that it refused to invent a tenant id** — the defect, re-entered through the door marked "observability". Second
reason: the seam is reachable by any holder of any valid realm token, so an audit write here is an append-only table an
outsider can inflate at will, against a hash chain `S-E01-2b` just made rewrite-proof on purpose. The refusal is
therefore recorded as a **`logger.warn` carrying the `sub` only** (FR-8). Provisioning *successes* continue to be
audited where they actually happen — `register.controller.ts:385+` and `invite.controller.ts` — in the same
transaction, unchanged.

**G-PORTAL — all four checked.** `ensureUser` serves `admin`, `teacher`, `parent` **and** `student`: the student portal
reads `me` from this same seam at `student-portal.controller.ts:53,61,70,79,90,107,116`. After this slice all four
portals refuse an unprovisioned identity identically, which is the intent. `student@pilotage.local` is already seeded
(`seed-demo.ts:1509`) and is adopted by email, so the student portal keeps working; FR-7 puts the other three on the
same footing.

**G-DNC.** `DNC-08` — AC-6, no skips. `DNC-10` — FR-9, no bypass, and AC-4 asserts the absence of `process.env` in the
file so a flag cannot be added quietly. `DNC-06` — AC-8, the comments that assert lazy provisioning are corrected in
the same diff, so no guide promises behaviour the runtime no longer has.

**G-MIGRATION — does not trigger.** No `schema.prisma` edit, no SQL, no new migration directory. Do not create one.
(This is also why `pnpm prisma generate` is **not** a prerequisite of this diff.)

## 7. Blast radius, stated so it is not discovered in production

Refusing profile-less logins is the correct behaviour and it **breaks things on purpose**. What breaks, and what
catches it:

| Who | Today | After | Mitigation |
|---|---|---|---|
| `admin@`/`teacher@`/`parent@pilotage.local` | silently become `active` in a self-created `demo` tenant | refused `403` | **FR-7 seeds them.** A developer who skips `pnpm prisma:seed:demo` is refused — correctly, and the seed console line tells them so |
| `student@pilotage.local` | adopted by email | unchanged | already seeded |
| `mme.dupont@`/`m.lefebvre@voltaire.fr` | adopted by email, or patched by `seed-keycloak-users.ts` | unchanged | already seeded |
| A production identity created in Keycloak by hand | auto-provisioned into `demo` | refused `403` | **This is the fix.** Provision through `invite.controller.ts` |
| Any realm identity, from any tenant (ADR-004: one realm) | reachable and auto-provisioned | refused | the finding, closed |

**Recorded, not fixed (track c's seam):** the four portals render the `403` through their generic error handling. The
message is correct and French, but no login page is designed for *"authenticated, and deliberately not admitted"*.
That is a `apps/web` change and it is out of scope (§5.6). It is a UX gap, not a security gap — the refusal is already
fail-closed — and it belongs with `PF-179`/`PF-180`, which are the same class of "the API's message never reaches the
user" finding, in `V3-E06`.
