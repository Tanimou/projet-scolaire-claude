## 1. The slice in six sentences

The application still connects as `pilotage`, the **owner** of all 55 tables, so it is exempt from every policy shipped
so far; the remaining work of `V3-E01` is the **connection cutover**, and a cutover is only safe once every statement
production already executes still works as a non-owner. Migration `20260814180000` granted `app_user` **`SELECT` and
only `SELECT`** on `role`, `role_permission`, `tenant`, `permission`, `_prisma_migrations`. Five statements in
`apps/api/src/modules/identity/roles.controller.ts` write two of those tables, and they work **today** only because the
connection is the table owner. This slice grants `INSERT, UPDATE, DELETE` on `role` and `role_permission` — **under
policies that make it structurally impossible for the application role to create, modify or delete a SYSTEM role, or to
change any system role's permission set**. It changes **no application code**, **no column**, and **no product
behaviour**: today's owner connection is unaffected by policies, so the observable system is byte-identical until
`S-E01-1` flips `DATABASE_URL`. What it produces is the write half of the cutover's AuthZ surface, proven by execution
as `app_user`, plus a **verb-aware** cutover-readiness check that enumerates every write blocker that remains.

### 2.1 The five writes, at their addresses

`apps/api/src/modules/identity/roles.controller.ts`:

| Line | Statement | Privilege needed |
|---|---|---|
| `:154` | `tx.role.create({ data: { …, isSystem: false, rolePermissions: { create: … } } })` | `INSERT` on `role` **and** `role_permission` |
| `:242` | `tx.role.update({ where: { id }, data: { name, description } })` | `UPDATE` on `role` |
| `:250` | `tx.rolePermission.deleteMany({ where: { roleId: id } })` | `DELETE` on `role_permission` |

| `:294` | `tx.role.delete({ where: { id } })` | `DELETE` on `role` (children cascade — see 2.3) |

Two application-level invariants already exist and are the ones this slice moves into the database:
`:190` `if (role.isSystem) throw new ForbiddenException('Les rôles système ne sont pas modifiables')` and `:278` the
same for delete. **There is no such guard on `create`** — `:161` hard-codes `isSystem: false`, which is a *literal in a
data object*, one edit away from being parameterised.

### 2.2 The column the whole design rests on

`0_baseline/migration.sql:550` — `"is_system" BOOLEAN NOT NULL DEFAULT false`. **NOT NULL** matters: `is_system = false`
can never evaluate to `NULL`, so the conjunct is *total* and there is no three-valued fail-open. This is why the
predicate must be written `is_system = false` and **never** `is_system IS NOT TRUE` / `IS DISTINCT FROM true` — those
laxer forms exist only to tolerate a `NULL` that cannot occur, and they read as a permission to make the column
nullable later.

### 2.3 Cascades, measured not assumed

`0_baseline/migration.sql:1653` — `role_permission_role_id_fkey … ON DELETE CASCADE`. So `tx.role.delete` at `:294`
removes the child rows through a referential action, and PostgreSQL runs RI triggers as the *referencing table's owner
with row security off*. It **should** therefore fire regardless of `app_user`'s policies — but that is a belief about
the engine sitting in a security path, and the harness already refuses to hold such beliefs (`rls-isolation-check.js`
step **(J)** executes the `user_profile → user_role` cascade for exactly this reason). Execute it here too (§6, AC-8).

## 3. The decision, and the three arguments (`ADR-047`)

**Decision.** Grant `INSERT, UPDATE, DELETE` on `role` and `role_permission` to `app_user`, bounded by policies that
make a SYSTEM role unwritable.

The ADR must carry all three of the following, because each is the reason a reader would otherwise object:

1. **This is a NARROWING, not a widening.** Today the application connects as the table OWNER and already performs all
   five writes, on **every** tenant's rows, under **no predicate at all**. After this slice the same writes are bounded
   by a policy. Refusing the grant does not keep the system safe — it keeps it owner-privileged, which is strictly
   worse.
2. **The escalation that matters is `role_permission` on a SYSTEM role.** Those are the roles real users hold.
   `is_system = false` inside the policy moves an invariant that today lives **only** in application code
   (`roles.controller.ts:190`, `:278`) into the database, where a future handler that forgets it cannot bypass it — and
   `create()` never had that guard at all (§2.1).
3. **The residual, stated plainly.** A tenant admin can still grant permissions to a **CUSTOM** role through the
   shipped API, bounded by `assertWithinCeiling` (`PF-09`). That is product behaviour, not a database defect, and this
   slice does not change it.

The ADR must **also** record, because a reader will otherwise assume they were overlooked:

- **Why not the two options `20260814180000`'s header floated.** A *separate administration role* means a second
  connection pool and a second `DATABASE_URL`, i.e. a second thing to get wrong at cutover, to protect five statements.
  A *narrow `SECURITY DEFINER` function* means privileged code whose body must itself re-implement the `is_system`
  check — the same invariant, in the same layer it already failed in (application logic), plus a permanent escalation
  surface. `ADR-046 §D4` refused a `SECURITY DEFINER` function with zero callers; this refuses one with five.
- **Why the existing `tenant_isolation` policy is NOT rewritten** (§4.1).
- **The explicit refusal to add `role.tenant_id`** (§7).

## 4. The design

### 4.1 Composition, not rewriting — and why

`role` and `role_permission` each keep their existing **permissive** `tenant_isolation` policy, **untouched, not
re-typed**. This slice adds **three RESTRICTIVE policies per table**, one per write command. PostgreSQL ANDs every
restrictive policy onto the OR of the permissive ones, so the effective predicate becomes exactly what AC-2 and AC-3
require:

| Command | Effective predicate on `role` |
|---|---|
| `SELECT` | `P_role` — **unchanged, verbatim, by non-modification** |
| `INSERT` | `WITH CHECK (P_role AND is_system = false)` |
| `UPDATE` | `USING (P_role AND is_system = false)` **and** `WITH CHECK (P_role AND is_system = false)` |
| `DELETE` | `USING (P_role AND is_system = false)` |

where `P_role` is today's predicate at `20260814180000_role_reference_surface_rls:400-410`. For `role_permission` the
same, with `P_rp` (the two-hop predicate at `:411-428`) and the parent conjunct
`EXISTS (SELECT 1 FROM public.role r WHERE r.id = role_permission.role_id AND r.is_system = false)`.

**The alternative was considered and rejected, and the ADR must say so.** Splitting `tenant_isolation` into
per-command policies would (a) require **retyping** today's predicate — the one thing AC-2 says must stay verbatim, and
the exact place a transposition would be invisible to a census that never reads a predicate; (b) break three census
assertions at once (`POLICIES` count, `WITH_CHECK_NULL` — a `FOR SELECT` policy *cannot* carry `WITH CHECK` in
PostgreSQL, so its `polwithcheck` is `NULL` by law — and `QUAL_MISMATCH`); and (c) make the DNC-10 discipline "inject
`WITH CHECK` from the same variable as `USING`" impossible to state for the SELECT half. Composition keeps all three
and touches nothing that already works.

Making the UPDATE guard appear in **both** `USING` and `WITH CHECK` is not redundancy: `USING` refuses editing a system
role, `WITH CHECK` refuses *promoting* a custom role into one. Drop either half and one of the two attacks lands.

### 4.2 Names

Three per table, identical across the two tables (policy names are per-relation):

- `system_role_immutable_insert` — `AS RESTRICTIVE FOR INSERT TO PUBLIC WITH CHECK (…)`
- `system_role_immutable_update` — `AS RESTRICTIVE FOR UPDATE TO PUBLIC USING (…) WITH CHECK (…)` (**same variable
  injected twice**)
- `system_role_immutable_delete` — `AS RESTRICTIVE FOR DELETE TO PUBLIC USING (…)`

`TO PUBLIC`, never `TO app_user` — naming a role silently exempts every *other* non-owner role (DNC-10).

### 4.3 Grants

`GRANT INSERT, UPDATE, DELETE ON public.role TO app_user` and the same on `role_permission`, table by table, guarded on
`has_app_user`, never `ON ALL TABLES IN SCHEMA public`. Resulting privilege string on both: `SELECT, INSERT, UPDATE,
DELETE`. **`tenant` and `permission` are not touched** (§7).

## 6. Acceptance criteria

**AC-1 — the migration is hand-reviewed.** `20260814210000_role_write_surface_rls/migration.sql` exists, sorts after
`20260814180000_…`, and neither `db push` nor `migrate dev` appears anywhere in the diff. Guard-spec assertions mirror
`rls-isolation-gate.spec.ts:1103-1120`.

**AC-2 — `role`.** SELECT predicate = today's, **verbatim and unmodified** (proven by the sibling migration file being
untouched in the diff). INSERT/UPDATE/DELETE = today's predicate `AND is_system = false`, achieved by composition
(§4.1). The UPDATE conjunct appears in **both** `USING` and `WITH CHECK`, injected from the **same variable**.

**AC-3 — `role_permission`.** SELECT predicate = today's two-hop predicate, verbatim. Write predicates = the two-hop
predicate `AND` the **parent** role's `is_system = false`, written out in full (never leaning on `role`'s own policy —
`ADR-042 §D1` clause 3: as the OWNER no policy applies, and the full predicate is then the only thing working).

**AC-4 — the census keeps working, and gets STRONGER.** Read `scripts/rls-isolation-check.js` first (§2.5). Required:

- `POLICIES`, `POLICIED_NAMES`, `WITH_CHECK_NULL`, `ROLE_SCOPED`, `QUAL_MISMATCH` keep their current values — the
  composition design means none of them moves. Assert this by running the check, not by reasoning.
- **New, and this is the AC-4 deliverable:** the census stops being name-blind. Add a term counting **every** policy in
  `public` and assert `TOTAL_POLICIES == POLICIES + 6`. A future policy under a third name now **fails** instead of
  being invisible.
- Assert, per new policy: `polpermissive = false` (all six restrictive — a permissive one would *add* permission and
  be a fail-open), `polroles = '{0}'` (TO PUBLIC), `polcmd` matches its name (`a` / `w` / `d`), and the predicate text
  contains `is_system = false`.
- Argue the change in `ADR-047`: a census that silently stops counting is the defect this programme exists to catch,
  so the fix is exhaustiveness, never an added exemption.

**AC-5 — the privilege set stays CLOSED.** `DERIVED_PRIVILEGE_SETS` gains exactly one string,
`'SELECT, INSERT, UPDATE, DELETE'`, with the reason written beside it; `DERIVED_TABLES`' `role` and `role_permission`
entries carry it. **`:2005`'s `DERIVED_DELETE == 0` must become a SET EQUALITY** — the set of derived tables holding
`DELETE` equals exactly `['role', 'role_permission']` — never a relaxed count or a `>= 0`. Grants stay table-by-table
and conditional on `has_app_user`; `ON ALL TABLES IN SCHEMA public` stays absent. `REFERENCE_PRIVILEGES` and
`AUTO_DISCRIMINANT_PRIVILEGES` are **not** touched.

**AC-6 — every guard the previous migration earned is kept.** `SET lock_timeout`; `has_app_user` computed once (assert
exactly one `FROM pg_roles WHERE rolname = 'app_user'` occurrence); `to_regclass` guard; the R-11 leading-index
precheck before any policy that walks an FK; `DROP POLICY IF EXISTS` before each `CREATE POLICY`; re-runnable.

**AC-7 — EXPAND-ONLY, and the rollback is EXECUTED.** No column created, dropped or moved; no data rewritten; no
application behaviour changed (the app still connects as the owner, `FORCE ROW LEVEL SECURITY` stays absent,
`DATABASE_URL` is untouched). This one **is** a pure expand — no constraint, no index — and the header must say so and
say why that differs from `20260814180000`. `scripts/rls-isolation-check.js` executes the header's rollback **before**
its existing generic rollback step, and asserts: the six guard policies are gone; `tenant_isolation` is **still
present** on both tables; `app_user` holds exactly `SELECT` on both again.

**AC-8 — the proof, as `app_user`, against a real scratch PostgreSQL with the GUC set.** `REFERENCE_WRITE_SQL` keeps
its name (`rls-isolation-gate.spec.ts:1381` pins it) and inverts its four expectations. First, the fixture fix of §2.4
plus a floor `SYSTEM_ROLE_IS_SYSTEM|1` read by the OWNER.

*POSITIVE CONTROLS — must SUCCEED (one transaction, markers printed inside, rolled back at the end):*

| Marker | Statement | Why this exact shape |
|---|---|---|
| `ROLE_INSERT_GLOBAL_OK` | `INSERT INTO role (id, name, slug) VALUES (…) RETURNING id` | `school_id` **NULL** is what the shipped API produces (`roles.controller.ts:114`, `:154` never sets `schoolId`). `RETURNING` is not decoration: Prisma always returns the row, and `INSERT … RETURNING` re-applies the SELECT policy. |
| `ROLE_INSERT_SCOPED_OK` | same, with `school_id = <SCHOOL_A>` | the shape a future school-scoped role takes; proves the tenant conjunct admits an OWN-tenant parent. |
| `ROLE_PERM_INSERT_OK` | attach `<SHARED_PERMISSION>` to the new custom role | `:252`. |
| `ROLE_UPDATE_OK` | `UPDATE role SET name = 'Renamed' WHERE id = <new>` then **read the name back** | `:242`. Assert the **value**, not the row count. |
| `ROLE_PERM_DELETEMANY_OK` | `DELETE FROM role_permission WHERE role_id = <new>` then read back `0` | `:250`. |
| `ROLE_DELETE_OK` | `DELETE FROM role WHERE id = <new>` with a child `role_permission` row present, then read back `0` for **both** | `:294` **and** §2.3 — the cascade, executed rather than believed. |

*MUST BE REFUSED — and each is classified as LOUD or SILENT, because the two need different evidence:*

| # | Statement | Expected | Evidence required |
|---|---|---|---|
| a | `INSERT INTO role (…, is_system) VALUES (…, true)` | LOUD (restrictive `WITH CHECK`) | marker absent; own transaction so the abort cannot let the marker print |
| b | `UPDATE role SET name='Escalated' WHERE id=<SHARED_ROLE>` | **SILENT** — `USING` filters the row, 0 rows, no error | `ROLE_SYSTEM_NAME_UNCHANGED\|1` read back |
| c | `UPDATE role SET is_system=true WHERE id=<custom>` | LOUD (`WITH CHECK`) | marker absent **and** read back `is_system = false` |
| d | `INSERT INTO role_permission (role_id, …) VALUES (<SHARED_ROLE>, …)` | LOUD | marker absent |
| e | `DELETE FROM role_permission WHERE role_id=<SHARED_ROLE>` | **SILENT** | `ROLE_PERM_SYSTEM_STILL\|1` read back |
| f | `UPDATE`/`DELETE` on tenant **B**'s custom role; `INSERT` a role with `school_id=<SCHOOL_B>` | UPDATE/DELETE **SILENT**, INSERT LOUD | the OWNER asserts `OWNER_FOREIGN_CUSTOM_ROLE_UNTOUCHED` — `app_user` under GUC=A cannot distinguish "row I cannot see" from "row I deleted" |
| g | any `INSERT`/`UPDATE`/`DELETE` on `tenant` | LOUD `permission denied` | markers absent; `PF-185` stays a blocker |
| h | any `INSERT`/`UPDATE`/`DELETE` on `permission` | LOUD `permission denied` | markers absent |

The stderr guard must be **sharpened, not disabled**: `permission denied for table role` / `role_permission` is now a
MISSING GRANT and a loud failure; `permission denied for table tenant` / `permission` remains the expected result. Do
not fold this block back into `PROOF_SQL` — half of it still expects denials (contrast `outbox_event`, folded back in
by `S-E01-2d` precisely because *none* of its expectations were denials any more).

**AC-8b — one mutant, killed by execution.** `S-E01-1b` measured a real cross-tenant defect that left the entire
harness green. Before trusting the six new policies: capture `system_role_immutable_update` on `role` via
`pg_get_expr`, `DROP` it, re-run probe **(b)**, assert `ROLE_SYSTEM_NAME_UNCHANGED` goes **RED**, re-`CREATE` it from
the captured expression, assert GREEN again. An assertion that cannot go red is not an assertion.

**AC-9 — silent no-ops are proven by READ-BACK, never by the absence of an error.** Every SILENT row of the table above
carries its read-back. Keep the `WRITE_PROBE_STILL_READS` / `WRITE_PROBE_RAN` floor so "no marker printed" cannot also
mean "the connection died". This is the `S-E01-2d` lesson and it is not optional.

**AC-10 — AC-9 CUTOVER READINESS becomes VERB-AWARE and RECEIVER-AWARE** (`scripts/tenant-adversarial-check.js`).

- Receivers come from a **named constant** with a written reason, covering `prisma`, `this.prisma` and `tx` — the last
  measured at 86 sites (§2.7), all currently invisible.
- Verb → privilege: `create` / `createMany` / `createManyAndReturn` → `INSERT`; `update` / `updateMany` → `UPDATE`;
  `upsert` → `INSERT` **and** `UPDATE`; `delete` / `deleteMany` → `DELETE`; `findX` / `count` / `aggregate` /

**Pre-mortem — assume this broke production; why?**

1. *A restrictive policy was written permissive.* It would then **add** permission instead of removing it, and every
   probe would still be green. → AC-4 asserts `polpermissive = false` on all six.
2. *The UPDATE guard was put in `USING` only.* Editing a system role is refused; **promoting** a custom role to system
   is allowed, and the next request that role serves carries the promotion. → AC-8 (c).
3. *`is_system` was written `IS NOT TRUE`.* Green today, fail-open the day the column becomes nullable. → §2.2, guard
   spec asserts the exact form and bans the laxer ones.
4. *The fixture was left at `is_system = false`.* Every "SYSTEM role refused" assertion tests a non-system row. → §2.4,
   floor `SYSTEM_ROLE_IS_SYSTEM|1`.
5. *A silent refusal was read as an error.* Probes (b), (e), (f) raise nothing and affect nothing. → AC-9 read-backs.
6. *The census stopped counting.* Six policies under a new name, invisible to five catalog terms. → AC-4
   exhaustiveness.
7. *`DERIVED_DELETE == 0` was "fixed" by deleting the assertion.* → AC-5 requires a set equality naming both tables.
8. *Someone grants `INSERT` on `tenant` "so registration keeps working" after AC-10 prints it as a limit.* → §7,
