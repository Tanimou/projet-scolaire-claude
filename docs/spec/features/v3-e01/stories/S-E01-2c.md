## 0. Read this first — the slice in five sentences

`S-E01-2b` (run 52) put a `tenant_isolation` policy on the **44** tables that carry a `tenant_id` column. **Five more
tables belong to a tenant by FOREIGN KEY** and carry no `tenant_id`, so they sit outside every policy: they are
fail-closed today only because `app_user` was never granted anything on them. This slice gives those five an **FK-path**
policy — `EXISTS (SELECT 1 FROM <parent> …)` — plus a per-table DML grant, and proves by **execution against the real
PostgreSQL** that tenant A's rows are visible and tenant B's are not, on **each of the five**.

**It does NOT make the running application RLS-isolated.** The API still connects as `pilotage`, which owns all 55
tables, and a table owner is exempt from its own policies while `FORCE ROW LEVEL SECURITY` is absent — which it
deliberately still is. The remaining step is the **connection cutover** (`S-E01-1`), and nothing you write may read as
"the app is isolated".

**A sixth table, `outbox_event`, is explicitly OUT.** It has no foreign key at all. It stays fail-closed, that stays
**asserted**, and it is recorded as `PF-185` so a later run cannot close the permission errors by widening the grant.

## 2. The problem, stated without softening

The 44 policies protect every table that *names* its tenant. Five tables *have* a tenant and do not name it. Right now
that is invisible and harmless at the same time, and the two facts are connected: `app_user` cannot read them because
nothing granted them, so nothing leaks — and nothing complains.

The `S-E01-1` connection cutover destroys that equilibrium, and it forks two ways with no third option:

- **Grant them, no policy.** `user_role` — the table that says *who holds which role in which school* — becomes an
  unfiltered cross-tenant read for the application role. `grade_revision` — the audit trail of every changed mark,
  carrying `previous_value` and `new_value` for named children — becomes the same. That is the leak this epic exists
  to prevent, shipped by the slice that was supposed to prevent it.
- **Leave them ungranted.** Six features break with `permission denied for table user_role`, which reads like a bug in
  the invite flow, not like a tenancy decision, and will be "fixed" by whoever is on call by adding a grant.

**Fix the policy, never the grant.** This slice is the third option, and it must land **before** the cutover, not
during it.

### 2.1 Why the census cannot catch a wrong FK path — the argument that sizes the proof

The census counts policies **by name**: `count(*) FROM pg_policy WHERE polname = 'tenant_isolation'`. A policy on
`grade_revision` whose subquery reads `announcement` instead of `grade` would still be counted. A policy whose join
column is `p.id = child.id` instead of `p.id = child.grade_id` would still be counted. **The census reads the name; it
never reads the predicate.**

For the 44 that was tolerable, because all 44 predicates are *identical* — one template, one column name, proven once
on `school`. Here **every one of the five has a different parent and a different column**, and four of them are
generated by the same `format()` call from a per-table tuple. A transposed tuple is a silent, fully-green cross-tenant
read.

That is why §4 AC-6 requires execution on **all five**, not one per shape. It is not thoroughness for its own sake; it
is the only mechanism in the repository that reads the predicate.

## 4. Acceptance criteria

> Every AC below is either a **file that must exist with a stated property** or an **assertion that must execute**.
> None of them may be discharged by a comment, and none may be satisfied by a skip (DNC-08).

### AC-1 — a new hand-reviewed migration
A new directory under `apps/api/prisma/migrations/` (suggested `20260813180000_tenant_rls_derived_policies`) holding
one `migration.sql`. **Never `prisma db push`. Never `prisma migrate dev`.** Its header follows the discipline of
`20260813120000_tenant_rls_policies`: it states what it does **and what it does not do**, and it **cites ADR-042 and
ADR-032 rather than taking any decision in a comment**. A migration comment cannot supersede a record — that lesson
cost runs 50, 51 and 52 three times each.

### AC-2 — the policy, and the exact predicate shape
Each of the five gets `ENABLE ROW LEVEL SECURITY` and a policy **named `tenant_isolation`** (same name as the 44 — the
census counts by name), `FOR ALL TO PUBLIC`, with `USING` and `WITH CHECK` **both declared explicitly and byte-identical
to each other**:

```sql
EXISTS (
  SELECT 1 FROM public.<parent> p
   WHERE p.id = <child>.<fk_col>
     AND p.tenant_id = nullif(current_setting('app.current_tenant_id', true), '')::uuid
)
```

- The `nullif` is **reused verbatim** and is not decorative. After `COMMIT`, `set_config(…, true)` leaves the GUC at
  `''`, not NULL, so a bare `::uuid` raises `22P02` on the **second** query of every pooled connection (F13, and the
  migration header of the 44 records the measurement). It is **not** a disguised `IS NULL OR`: `''` becomes NULL, and
  NULL lets no row through.
- `TO PUBLIC`, never `TO app_user`: a policy naming a role exempts every other non-owner role in silence.
- `WITH CHECK` explicit: a NULL `with_check` falls back to `USING`, which looks right today and breaks the day someone
  adds a permissive one. The existing census asserts `WITH_CHECK_NULL == 0` and `ROLE_SCOPED == 0` and both must keep
  passing over the enlarged set.
- **`user_role`'s tenant path is `user_profile_id`, never `role_id`** (F5). `role` is reference data with no tenant; a
  policy routed through it would evaluate `p.tenant_id` on a column that does not exist and fail to apply at all.

**Shape of the migration body.** One literal table, one row per derived table, each row carrying **four** literals —
child, FK column, parent, privilege string:

```sql
derived CONSTANT text[][] := ARRAY[
  ARRAY['announcement_receipt', 'announcement_id',  'announcement',  'SELECT, INSERT, UPDATE, DELETE'],
  ARRAY['branding',             'school_id',        'school',        'SELECT, INSERT, UPDATE, DELETE'],
  ARRAY['grade_revision',       'grade_id',         'grade',         'SELECT, INSERT'],
  ARRAY['import_row',           'batch_id',         'import_batch',  'SELECT, INSERT, UPDATE, DELETE'],
  ARRAY['user_role',            'user_profile_id',  'user_profile',  'SELECT, INSERT, UPDATE']
];
```

Names stay **literal and diffable**; only the loop is factored, exactly as the 44 did. Carrying the privilege as the
fourth literal rather than as an `IF … ELSE` is deliberate: there is no `ELSE` branch to forget, and a reviewer reads
each table's blast radius on the same line as its name. Guard the loop the way the 44 are guarded — refuse to apply
(`RAISE EXCEPTION`) if the row count is not 5, if a child or parent is missing from `to_regclass`, if a privilege
string is outside the closed set of three, or if a named parent does **not** carry a `tenant_id` column. **Refusing to
apply is always correct here; skipping a row is never correct** — a skipped row ships a missing policy under a green
`migrate deploy`.

Precede each `CREATE POLICY` with `DROP POLICY IF EXISTS` (PG 15 has no `IF NOT EXISTS`), so a partial application is
re-playable.

### AC-3 — the index prerequisite, verified then asserted
F6 measured that all five FK columns are already the leading column of an index. **Re-verify against the catalog before
trusting this spec**, add any that is missing, and then **assert it in the check**: for every derived table, an index
must exist whose leading column (`pg_index.indkey[0]`) is the FK column. An FK-path policy without an index on the FK
is a sequential scan of the parent on every row read — R-11 in its most direct form.

### AC-4 — the grants, and three privilege sets with named reasons
`GRANT` the five to `app_user` — **never** `ON ALL TABLES IN SCHEMA public`, which would hand over the unpolicied six
as well. Guard the grant half on `EXISTS (SELECT 1 FROM pg_roles WHERE rolname = 'app_user')` (roles are cluster state,
migrations are database state, and CI provisions a container with no `app_user`); keep the ENABLE/CREATE POLICY half
**unconditional**, because it is the security property and depends on no role.

| Table | Privileges | Reason, which must be written in the migration |
|---|---|---|
| `announcement_receipt`, `branding`, `import_row` | `SELECT, INSERT, UPDATE, DELETE` | Ordinary mutable rows. A receipt is marked read, branding is edited, an import row is re-classified and a rolled-back batch deletes its rows. |
| **`grade_revision`** | **`SELECT, INSERT`** | **G-AUDIT.** `schema.prisma` declares it *"Append-only audit log of grade modifications after publication"*. It is the evidentiary record of every changed mark, carrying `previous_value`, `new_value`, `reason` and `revised_by`. **It is more exposed than `audit_log`, not less**: `audit_log` carries a `hash`/`prev_hash` chain, so a rewrite is at least *detectable*; `grade_revision` carries no chain, so a rewrite leaves nothing behind at all. Measured safe (F10): the only write call site is a seed script running as the owner. |
| **`user_role`** | **`SELECT, INSERT, UPDATE`** — **no `DELETE`** | Revocation is a soft delete: `users.service.ts:228` does `updateMany` setting `revoked_at`, and grep finds **no** `userRole.delete` anywhere (F11). Withholding `DELETE` means a privilege can be revoked but never *erased*, which is what ADR-040's delegation ladder assumes. |

`user_role`'s missing `DELETE` carries one consequence that must be **proven, not assumed** (see AC-10).

Emit `GRANT USAGE ON SCHEMA public TO app_user` only if the earlier migration's grant is not already sufficient — it is;
do not re-emit it. Add **no** sequence grants: `public` holds zero sequences.

### AC-5 — THE HARD PART: the census stays an AGREEMENT, never a number

Adding five policied tables breaks all three of today's agreements (`RLS_ON == TENANT_COLS`, `POLICIES == TENANT_COLS`,
`GRANTED == TENANT_COLS`). **Do not repair that by hard-coding 49, and do not subtract a frozen list.** Either is how a
seventh derived table ships unprotected and invisible, and `rls-isolation-gate.spec.ts:371` already forbids the first
one textually.

**`DERIVED_EXPECTED` is computed from the catalog's STRUCTURE, with no reference to any policy:**

```sql
SELECT 'DERIVED_EXPECTED|' || count(DISTINCT child.relname)
  FROM pg_constraint k
  JOIN pg_class child  ON child.oid  = k.conrelid
  JOIN pg_class parent ON parent.oid = k.confrelid
  JOIN pg_namespace n  ON n.oid = child.relnamespace
 WHERE k.contype = 'f' AND n.nspname = 'public' AND child.relkind = 'r'
   AND NOT EXISTS (SELECT 1 FROM pg_attribute a WHERE a.attrelid = child.oid
                     AND a.attname = 'tenant_id' AND a.attnum > 0 AND NOT a.attisdropped)
   AND     EXISTS (SELECT 1 FROM pg_attribute a WHERE a.attrelid = parent.oid
                     AND a.attname = 'tenant_id' AND a.attnum > 0 AND NOT a.attisdropped);
```

Then the three agreements become:

```
RLS_ON   == TENANT_COLS + DERIVED_EXPECTED
POLICIES == TENANT_COLS + DERIVED_EXPECTED
GRANTED  == TENANT_COLS + DERIVED_EXPECTED
```

> **⚠ Correction to the intake brief — read this, it is the difference between a gate and a decoration.** The brief
> wrote the agreement as `RLS_ON == TENANT_COLS + DERIVED_POLICIED`, with the derived count "catalog-computed" from the
> tables that **have** a policy. That agreement is **self-satisfying**: a sixth derived table shipped with no policy is
> absent from `RLS_ON` *and* absent from `DERIVED_POLICIED`, the two sides still balance, and the gate passes on exactly
> the defect it was built to catch. The count must be **EXPECTED** — derived from FK structure alone — so that a new
> derived table raises the right-hand side while the left-hand side stays put, and the counts **disagree**. The whole
> value of AC-5 lives in that one word.

**AC-5b — the residue must be NAMED, never globbed.** The structural derivation above is one level deep, so a future
table with no `tenant_id` whose FK points at a *derived* table would fall outside both counts and be invisible again.
Close that with a **set-equality assertion in both directions**: the base tables in `public` that carry no `tenant_id`
**and** are not in the derived set must be exactly

```
_prisma_migrations   the migration ledger, not tenant data
permission           reference data by design (ADR-015)
role                 reference data by design (ADR-015)
role_permission      reference data by design (ADR-015)
tenant               its PRIMARY KEY is the discriminant; a policy here would break the identity seam,
                     which must read `tenant` BY SLUG before any tenant is resolved (S-E01-1)
outbox_event         PF-185 — no FK, no discriminant; needs a denormalised column + backfill (AC-8)
```

Six names, each with its reason in the source. Any new table landing in that residue **fails the gate** until someone
names it and says why. This is what "keep them outside NAMED and with reasons, never by a glob" means in executable form.

**AC-5c — the parents must stay readable.** A policy expression is evaluated **as the calling user**, so `app_user`
needs `SELECT` on each parent for the `EXISTS` subquery to run at all. All five parents are among the 44 and are
granted today — assert it, because the day someone narrows a parent's grant, every derived read starts failing with
`permission denied` from inside a policy, which is close to undiagnosable from the application side.

### AC-6 — POSITIVE CONTROL FIRST, on ALL FIVE, and it is not optional
`app_user` had **zero** privileges on these five before this migration (F7), so a proof showing only *absence* would be
**green for the wrong reason**. For **each** of the five, in this order:

1. with GUC = tenant A, the derived row **IS VISIBLE** (`count > 0`), **then**
2. with GUC = tenant B, it is **NOT** (`count = 0`), **and**
3. with the GUC unset on a fresh connection, and again on the same connection after `COMMIT` (the pooled case),
   `count = 0` **with no error raised**.

All five, not one per shape — see §2.1. A `permission denied` anywhere in the visibility path is a **loud failure**,
never read as isolation; the existing check already fails on that string and must keep doing so.

Extend `FIXTURES_SQL` with a two-tenant fixture for each derived table. The chains, measured (F8, F9), so the
implementer does not have to rediscover them — `tenant` and `school` for both tenants already exist in the fixtures:

| Derived table | Fixture chain to add, per tenant | Notes |
|---|---|---|
| `branding` | *(nothing)* — insert `branding(school_id, display_name)` directly | cheapest; `school_id` **is** the PK |
| `announcement_receipt` | `announcement(id, tenant_id, school_id, title, body, scope, author_id, updated_at)` → `announcement_receipt(id, announcement_id, user_profile_id)` | `author_id` and `user_profile_id` are `NOT NULL` with **no FK** — any uuid |
| `import_row` | `import_batch(id, tenant_id, school_id, type, file_name, updated_at)` → `import_row(id, batch_id, row_index, payload)` | `created_by` nullable |
| `user_role` | `user_profile(id, tenant_id, first_name, last_name, email, updated_at)` + one `role(id, name, slug)` **shared by both tenants** → `user_role(id, user_profile_id, role_id)` | `role` is empty in the ledger (F8). Sharing one role row across both tenants is the point: it proves the tenant path runs through `user_profile_id` and not through `role_id` |
| `grade_revision` | `academic_year` → `cycle` → `grade_level` → `class_section`; `subject`; `user_profile` → `teacher_profile` → `teaching_assignment` → `assessment`; `student`; → `grade` → `grade_revision(id, grade_id, reason, revised_by)` | the deep one — ~10 rows per tenant. Every intermediate carries `tenant_id`, so all of it is inserted by the **owner**, before any `app_user` connection |

All fixtures are built by the **owner**, as today: `app_user` has no grant on `tenant`.

### AC-7 — a cross-tenant INSERT through the FK path is REJECTED by `WITH CHECK`
This hazard has **no analogue in the 44**. There, a foreign INSERT is caught because the row itself carries the wrong
`tenant_id`. Here the child row **carries nothing tenant-shaped at all** — the only thing between a caller and a
cross-tenant write is the `EXISTS` subquery. Prove it executes: under GUC = tenant A, an `INSERT` into a derived table
whose **parent belongs to tenant B** must raise `new row violates row-level security policy`. Pair it with the positive
control — an own-tenant INSERT that **succeeds** — or the assertion is green on a database where the grant simply never
landed. Prove it on at least **two** shapes, one of which must be `branding` (where the FK **is** the primary key) and
one a child with its own surrogate key.

Also prove the silent one, as the 44 did: a `DELETE` of a foreign-parent row deletes **nothing** and raises **nothing**
— `USING` filters it away first. Code that reads "delete succeeded" as "row is gone" reports success for a delete that
never happened.

### AC-8 — `outbox_event` is PROVEN fail-closed
Assert by execution, with the reason named in the output:

- `outbox_event` carries **no** `tenant_isolation` policy and `relrowsecurity` is **false**;
- `role_table_grants` for grantee `app_user` on `outbox_event` returns **zero rows**;
- a `SELECT` from `outbox_event` as `app_user` fails with **`permission denied`** — and here, and *only* here, that
  string is the expected result rather than a failure.

This assertion is what stops the next run from "fixing" a permission error by widening the grant. It must name `PF-185`
in its label so a reader lands on the record instead of on a workaround.

### AC-9 — the harness, unchanged in shape, unchanged in honesty
Everything runs inside the existing scratch-database harness: create → `migrate deploy` the **full** ledger → connect as
`app_user` → assert → `DROP DATABASE`. **No skips, ever (DNC-08)**: no PostgreSQL, no `psql`, no `app_user`, no
`DATABASE_URL_APP` each stay exit 1 with a named reason. **No new flag, no new environment variable, nothing that lets
a caller choose what is compared (DNC-10).** Verify the scratch database is gone **independently of the script that
claims it** — a separate `psql -l` after the run, not the script's own log line.

### AC-10 — the `user_role` cascade, proven rather than assumed
`user_role` is granted no `DELETE` (AC-4), and `user_profile` → `user_role` is `ON DELETE CASCADE`. PostgreSQL runs
referential actions as the *table owner* with row security off, so the cascade **should** still work — but that is a
belief about the engine, and this repository's rule is that a belief in a security path gets executed. Prove it: as
`app_user`, under GUC = tenant A, delete a `user_profile` that has `user_role` rows, and assert the rows are gone.

If it fails, the correct fix is to add `DELETE` to `user_role`'s privilege string **and write the measured reason in
the migration** — not to remove the assertion. Either outcome is acceptable; an unasserted outcome is not.

### AC-11 — the rollback is written AND executed
Expand/contract reasoning stated: this is **pure expand** — policies and grants only, no column added, dropped, moved
or rewritten, no data reshaped, so there is no contract phase and a `DROP POLICY` / `DISABLE ROW LEVEL SECURITY` /
`REVOKE` is a **sufficient** reversal with no state to reconstruct. Write it in the header for the five, and make sure
`scripts/rls-isolation-check.js` **executes** it: the existing rollback block iterates every table with

## 8. The single most valuable targeted test

**`user_role` under GUC = tenant A, with a `role` row shared by both tenants.** It is the one fixture that fails
distinguishably for the two most likely implementation errors at once: route the policy through `role_id` and it
returns zero rows for *everyone* (the shared role has no `tenant_id`, the subquery cannot compile against it); route it
through `user_profile_id` correctly and tenant A sees exactly its own assignment while tenant B's — pointing at the
*same* role row — stays invisible. It is also the highest-consequence table in the set: it is the answer to "who is
allowed to do what, where".
