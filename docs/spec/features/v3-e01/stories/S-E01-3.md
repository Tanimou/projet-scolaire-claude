## 3. Where the brief was wrong, and what this story says instead

The slice brief carried three factual claims that were measured false. **Keep the measurement.**

### 3.1 The scratch database is built with `psql`, not `prisma migrate deploy`

The brief said *"same journey as `rls-isolation-check.js`: `CREATE DATABASE` → `prisma migrate deploy`"*.
**Measured false.** `rls-isolation-check.js:1043-1049` applies each `migration.sql` **file by file** through
`psql -f -`, in `sort()` order over the migration directories (`migrationFiles()`, `:521-529`). It never invokes the
Prisma CLI. This is load-bearing in two ways and you must copy it, not "improve" it:

- Prisma's CLI — **not** the SQL — creates `_prisma_migrations`. Because the ledger is applied with `psql`, that table
  is **ABSENT** from the scratch database, and `rls-isolation-check.js:1211-1223` branches its residue assertion on
  measuring whether it is present. Switching to `migrate deploy` silently changes that branch.
- `prisma migrate deploy` needs a generated client and Prisma's own env plumbing; a gate that can fail because
  `prisma generate` has not run is a gate that reports schema problems as tenancy problems.

**Your suite applies the ledger with `psql`, the same way, and reuses `migrationFiles()` by requiring it from the
sibling module's exports** (`module.exports` at the foot of `rls-isolation-check.js` already exports
`migrationFiles`, `lit`, `fid`, `isLoopbackHost`, `redact`, `SCRATCH_NAME_PATTERN`, `TENANT_GUC`, `POLICY_NAME`,
`MIN_EXPECTED_TABLES`, `VERDICT_EXIT_CODES`, `DERIVED_TABLES`, `NON_DERIVED_EXPECTED`, `OUTBOX_TABLE`). Requiring
that module is **read-only and side-effect-free** — its `main()` is behind `require.main === module` precisely so a
`require()` cannot create a database. Requiring it is **not** "touching" it (§7, constraint 2): you must not *edit*
it.

### 3.2 There are FIVE FK-derived tables, not six — and `outbox_event` is now a tenant-BEARING one

The brief's AC-4 listed *"grade_revision, announcement_receipt, branding, import_row, user_role, outbox_event"* as
*"the six FK-derived tables … covered THROUGH THEIR FK PATH"*. **Measured false, and dangerous if implemented as
written.** `outbox_event` is **polymorphic and unconstrained** on its aggregate: `aggregate_type` /
`aggregate_id` are bound by nothing, so there is no FK path to route a policy through and it is **not derivable**.
`ADR-042 §D7` records that, and it is still true.

**AMENDED after the rebase onto `e53f2d9`.** `S-E01-2d` (`ADR-044`, closes `PF-185`) has since merged and gives
`outbox_event` a **denormalised `tenant_id`**, an `ON DELETE CASCADE` FK to `tenant`, the ordinary
`tenant_isolation` policy and `SELECT, INSERT, UPDATE` — no `DELETE`. So it is neither derivable nor fail-closed
any more: it is an **ordinary tenant-bearing table**, the 45th, and this suite seeds it for both tenants and proves it
on four verbs like the rest. The FK-derived set stays at **five**.

### 3.3 "DELETE affects 0 rows" is not universally the right assertion

The brief's AC-2(c) asked for a `DELETE` proof on **every** tenant-bearing table. Measured, that is wrong for two
disjoint groups:

- **Append-only tables** — `audit_log` and `conversation_message` hold `SELECT, INSERT` **only** (`ADR-032 §D7`; the
  audit hash chain must stay unrewritable).
- **All five derived tables** — `ADR-042 §D5` grants **no `DELETE` to any of them**, asserted as
  `DERIVED_DELETE = 0` by the sibling check.

On those seven, a `DELETE` returns `permission denied` — which is **louder and strictly safer** than a silent
zero-row no-op. So the correct assertion is not one verb applied blindly; it is: **for each table, read the privilege
it actually holds from `information_schema.role_table_grants`, and assert the outcome that privilege implies** —
`0 rows affected` where `DELETE` is granted, `permission denied` where it is not. **Both outcomes are a pass; a
non-zero row count and a successful cross-tenant delete are the only failures.** The classification is read from the
**live catalog**, never from a list in your source.

## 4. Acceptance criteria (implement these, not the brief's)

Each is written so it can only be discharged **by execution**.

**AC-1 — the harness.** A new executable check `scripts/tenant-adversarial-check.js`:
- resolves `psql` through `scripts/lib/postgres-client-path.js` and the two addresses through
  `scripts/lib/default-database-url.js` (`defaultDatabaseUrl()` and `defaultAppDatabaseUrl()` / `APP_DATABASE_URL_VAR`).
  **No new environment variable, no new flag, no DSN literal** (`DNC-10`);
- refuses to run against a **non-loopback** address, with no override (reuse the exported `isLoopbackHost`);
- creates a **disposable scratch database** whose name matches its own generated pattern
  `/^tenant_adversarial_\d+_\d+$/`, checked before any `DROP`, and refused if it equals the source database;
- applies every `migration.sql` on disk with `psql`, in order, and **fails** if any does not apply;
- asserts the ledger built a real schema (`>= MIN_EXPECTED_TABLES` base tables) before any query below can pass
  vacuously;
- seeds **two real tenants A and B** with rows across the tenant-bearing seams, as the **owner**;
- performs every adversarial operation as **`app_user`**, and **asserts over that very connection**, before the first
  visibility query, that `current_user` owns **zero** of the tables under test, that `rolbypassrls` is **false**, and
  that `current_user` is not the owner named in `DATABASE_URL`. Any of those failing **fails** the run.

**AC-2 — breadth, enumerated FROM THE LIVE CATALOG.** The set of tenant-bearing tables is computed **on the scratch
database** — `information_schema.columns` for `tenant_id`, and the `pg_constraint` derivation for the FK-path set.
**No frozen list may appear on the enumeration side.** With the GUC `app.current_tenant_id` set to tenant A, prove by
execution, per table:
- **(a)** `SELECT … WHERE <pk> = <B's row>` returns **0**;
- **(b)** `UPDATE` targeting a B row reports **0 rows affected**;
- **(c)** `DELETE` targeting a B row reports **0 rows affected** **where `DELETE` is granted**, and reports
  **`permission denied`** where it is not — classification read from `role_table_grants` on the scratch database (§3.3);
- **(d)** an `INSERT` carrying **B's tenant id** is **REJECTED** by `WITH CHECK` (error `42501`,
  *new row violates row-level security policy*), inside a `SAVEPOINT` so the transaction survives.

A table that the enumeration finds but for which **no** assertion executed is a **failure**, printed by name. Silence
is never a pass.

**AC-3 — POSITIVE CONTROLS, and they are not optional.** For the same table set, with GUC = A, A's **own** rows must
be **visible**, **updatable** (`1 row affected`), **deletable where `DELETE` is granted**, and **insertable**. Run
the positive control **first**, before the matching denial. Without it, every assertion in AC-2 passes vacuously
against a broken connection, an empty database, or a revoked grant — a suite that only proves denial cannot
distinguish isolation from breakage. **`permission denied` anywhere in a positive-control path is a LOUD failure,
never read as isolation.**

**AC-4 — the FIVE FK-derived tables, through their FK path, in both directions.** `grade_revision`,
`announcement_receipt`, `branding`, `import_row`, `user_role` carry **no `tenant_id`** and sit outside the 45. Prove,
for each: A's child row is **visible** under GUC = A, and B's child row is **not**; then switch the GUC to B and
prove the mirror. Two shapes must both be covered because they fail differently: **`branding`**, whose FK **is** its
primary key, and one table with its own surrogate key. Seed B a **second parent with no child row** so that a
foreign-parent `INSERT` can fail for exactly one reason — the policy — and not for a unique violation.

**AC-4b — `outbox_event` is PROVEN, and named as such. REWRITTEN after the rebase onto `e53f2d9`.** It originally
read *"fail-closed … `permission denied` is the expected result, in its own `psql` invocation"*. `ADR-044` gave the
table a policy and a real grant, so that acceptance criterion became **false**: a `permission denied` here would now
be a MISSING GRANT, which is the false green every other phase of this suite treats as a loud failure. What is
required instead: `outbox_event` is enumerated as tenant-bearing, is **seeded for both tenants**, is proven on the
same four verbs as the other 44, and holds **exactly `SELECT, INSERT, UPDATE`** — the withheld `DELETE` of
`ADR-044 §D3` asserted by name so a widened grant fails instead of flipping one green assertion into another. The
separate `psql` invocation is deleted with the probe it existed for.

**AC-5 — no GUC at all means zero rows.** With **no** tenant GUC set, `app_user` sees **zero** rows — on the
tenant-bearing tables **and** on the derived ones, because a child predicate written without `nullif` raises `22P02`
only on the child. Assert **both halves**: zero rows **and no error**. Cover the three distinct states, because they
are not the same state and one of them is the steady state of every pooled connection in production:
- a **fresh** connection that has never set the GUC (`current_setting(…, true)` is `NULL`);
- the **pooled** case — same connection, after a `set_config(…, true)` transaction has **committed**, where the GUC
  is `''`, **not** `NULL`;
- the GUC set **explicitly** to the empty string.

**AC-6 — THE HONEST INVENTORY. This is the acceptance bar, not a footnote.** The application **today** connects as
`pilotage`, which **owns** the tables, and `FORCE ROW LEVEL SECURITY` was deliberately omitted (migration header,
`ADR-032 §D5`) — so the owner **bypasses every policy**. Prove that **by execution too**: as the **owner**, with
GUC = A, **B's rows ARE visible**. The suite must report this as a **named, explicit limit** — *the application is
not isolated yet* — printed on the **green** path (that is the only moment anyone is tempted to over-read the
result), and it must **not** be written so that this reads as a pass. Calling the app isolated on this evidence is
the `PF-02` defect one level down.

**AC-7 — DETERMINISTIC TEARDOWN.** `DROP DATABASE … WITH (FORCE)` must terminate every remaining session; the drop
runs as `pilotage`, which is a member of **neither** `app_user` **nor** `pg_signal_backend` (**measured**, §2), so a
leftover `app_user` backend makes the drop fail intermittently. Therefore: **close every `app_user` connection this
suite opens BEFORE dropping**, by construction — every `psql` invocation is a `spawnSync` that has already exited by
the time the next line runs, so the requirement is *"open no long-lived connection, and hold no handle across the
drop"*, and the suite must not open a pooled/`pg`-library connection at all. **Do NOT** buy a green teardown with
`GRANT pg_signal_backend TO pilotage` — that is a standing privilege escalation granted to the exact role the cutover
is about. The drop's own verdict is reported and never swallowed, and a failed drop never downgrades an isolation
verdict into a tooling one.

**AC-8 — FAIL-BEFORE / PASS-AFTER, executed and reported.** Show at least one assertion **RED** against a
deliberately weakened state, and **green** after. The weakening happens **inside the scratch database only** — e.g.
`DROP POLICY tenant_isolation ON public.school` — never on the live `pilotage` database, and never as a permanent
mode of the script. The evidence for this AC is the **transcript** in the PR, not a flag left in the code. An
assertion that was green before your change is not evidence.

**AC-9 — it FAILS, it never SKIPS (`DNC-08`).** No PostgreSQL, no `psql`, no `app_user`, no `DATABASE_URL_APP`,
no migrations on disk: every one is a **named** non-zero exit. There is no environment variable and no flag that
turns any verdict into a pass (`DNC-10`). `DATABASE_URL` and `DATABASE_URL_APP` name **where** and **as whom**, never
**whether**. Use three distinguishable exit codes, mirroring the sibling check's `VERDICT_EXIT_CODES`:
`0` = proven, `1` = could not run (tooling), `2` = **not** isolated.

**AC-10 — credentials never reach `argv` (`ADR-025 D6`).** Every `psql` invocation takes its password through
`PGPASSWORD` in the **child** environment and its address through `-h/-p/-U/-d` flags. No connection string is ever
an argument, and no address is ever printed unredacted (reuse the exported `redact`).

**AC-11 — the guard spec.** A new `apps/api/src/shared/quality/tenant-adversarial-gate.spec.ts` pins the properties
of the checker that a reader must not be able to erode, by **reading the checker's source and requiring its pure
exports** — never by running it:
- the enumeration side contains **no frozen table list** (a structural scan: no array literal of table names feeds
  the set the assertions iterate);
- no `SKIP_`/`ALLOW_`/`FORCE_`/`BYPASS_` variable, no `NODE_ENV` branch, and no `process.argv` flag can change a
  verdict (`DNC-10`), with a **non-vacuity floor** and a `__filename` self-exclusion;
- the scratch-name pattern rejects the live database name and any name the script did not generate;
- **no `GRANT … pg_signal_backend`** string anywhere in the checker (AC-7's forbidden shortcut, mechanised);
- the positive-control assertions exist and are reached **before** their paired denial;
- the honest-inventory sentence of AC-6 is present and printed on the **success** path;
- **and a case that shows the guard itself can go red** — feed a synthetic offending source through the same
  predicate and assert it fires (`PF-109`'s lesson: a guard never shown red is a guard we hope works).

**AC-12 — the CI stage is CONDITIONAL on determinism.** Wire the check into `scripts/ci-gate.sh` as its own stage
**only if** AC-7 is discharged and the check has been run **at least three times consecutively with identical
verdicts**. Record the three runs in the PR. If it is not deterministic, **do not wire it** — a flaky blocking stage
is worse than no stage — and say so explicitly, leaving the script runnable by hand. See §7, constraint 1, for the
**path** constraint that decides *where* the stage may be triggered from, and §6 for what wiring ripples into.

## 5. Implementation notes (the parts that will cost you an hour if you rediscover them)

- **The GUC is `app.current_tenant_id`** (`TENANT_GUC`, exported). It is a **custom** GUC, so
  `current_setting(guc, true)` returns `NULL` on a fresh session and `''` after a committed
  `set_config(guc, v, true)` — **two different states**, and a predicate that handles only one fails on the other.
- **Tenant A's id must carry UPPERCASE hex.** PostgreSQL renders a `uuid` in lowercase while the application's
  `assertTenantId` preserves case. A predicate written `tenant_id::text = current_setting(…)` matches **zero** rows
  for such a tenant — fail-closed but completely invisible, the worst shape a security control can have. Making A
  uppercase **executes** the cast direction instead of asserting it. Use ids **disjoint** from
  `rls-isolation-check.js`'s (`AAAAAAAA-1111-…` / `bbbbbbbb-2222-…`) so a stray row from one suite can never satisfy
  the other; e.g. `CCCCCCCC-3333-4333-8333-CCCCCCCCCCCC` and `dddddddd-4444-4444-8444-dddddddddddd`.
- **Fixture ids are GENERATED, not typed.** The `grade_revision` chain alone needs eleven rows per tenant, and a
  mistyped nibble surfaces as an FK violation in the **fixtures** — a red that costs an hour and proves nothing about
  RLS. `fid(tenantSlot, slot)` is exported by the sibling module; reuse it, with a distinct tenant slot.
- **Seed as the owner.** `app_user` has no grant on `tenant`, so the tenants and every intermediate row are inserted
  by `pilotage` before any `app_user` connection exists.
- **Every step prints `LABEL|value`** and the parser reads **facts, not row order**. `\pset footer off`.
  `psql -X` (skip `~/.psqlrc`, so a developer's local settings cannot change what a gate observes), `-A -t -q`.
- **`ON_ERROR_STOP` is a parameter, not a constant.** Most scripts must abort on the first error; the adversarial
  half deliberately provokes errors and must read them.
- **The refusal path needs `SAVEPOINT`.** A rejected `INSERT` aborts the transaction; wrap each provoked failure in
  `SAVEPOINT` / `ROLLBACK TO SAVEPOINT` so the run continues and later assertions still mean something.
- **A cross-tenant `DELETE` is a SILENT no-op**, not an error: `USING` filters the row away before the delete is
  considered. Code that reads *"deleted"* as success reports success for a delete that never happened. Assert the
  **row count**, and confirm the row still exists **as the owner** — the tenant-scoped connection cannot tell a row
  it cannot see from a row it deleted.
- **Ownership of the ordering:** read the derived tables' **totals before any `INSERT`** in the same transaction, or
  your own fixtures will move the number you are asserting.
- The suite is one `psql` **session** for the main proof (the pooled case of AC-5 is only reachable inside a reused
  connection) and one as the **owner** (AC-6). The third invocation this line used to require — the `outbox_event`
  fail-closed probe — is gone with AC-4b's rewrite above.
