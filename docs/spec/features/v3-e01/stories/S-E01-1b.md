## 1. The slice in six sentences

The running API connects as `pilotage`, the **owner** of all 55 tables, so it is exempt from its own RLS policies —
that is why 50 policied tables have not made the application isolated, and why the remaining work is a **connection
cutover**, not more policy.

The cutover is blocked by a fact written into the code: `apps/api/prisma/migrations/20260813120000_tenant_rls_policies/migration.sql`
§`LES GRANTS` says the grant set is *deliberately incomplete* — the first authorization join would fail because
`app_user` cannot read the privilege tables.

This slice grants `app_user` **exactly** the reads that join needs and nothing more, **SELECT-only**, table by table.

While doing so it corrects a **security-relevant misclassification**: `role` was filed as "genuinely global" and is
not — a `role` row with a non-null `school_id` belongs to exactly one tenant, so a bare `SELECT` grant would have let
tenant A read tenant B's **custom roles** the moment the cutover happened. `role` therefore gets RLS and an FK-path
policy in the same diff that grants it.

Everything is **proven by execution** against a real PostgreSQL as the non-owner role `app_user`, positive control
first, in a scratch database that is created and dropped.

**It does NOT make the running application RLS-isolated**, and no sentence in the diff, the ADR or the ledger may be
readable as though it did — that over-claim *is* the `PF-02` defect.

## 2. The discovery — `PF-191`, and the correction the brief itself got wrong

### 2.1 What the brief claimed, and what is actually true

`20260813120000_tenant_rls_policies/migration.sql:143-144` classifies four tables as
« **A. RÉELLEMENT GLOBALES** — aucun discriminant de tenant, aucune donnée d'un tenant : `permission`, `role`,
`role_permission`, `_prisma_migrations` ».

**That claim is FALSE for `role`** — confirmed by reading the schema:

| Fact | Location | Measured value |
|---|---|---|
| `Role.schoolId` is nullable | `apps/api/prisma/schema.prisma:905` | `schoolId String? @map("school_id") @db.Uuid` |
| `School.tenantId` is NOT NULL | `apps/api/prisma/schema.prisma:279` | `tenantId String @map("tenant_id") @db.Uuid` |
| the app creates school-scoped roles at runtime | `apps/api/src/modules/identity/roles.controller.ts:154` | `tx.role.create({...})` |

So a `role` row with a non-null `school_id` is **tenant-derived data**, of exactly the shape `S-E01-2c` / `ADR-042`
handled for the other five. Record this as **`PF-191`**.

### 2.2 Where the brief is WRONG, and it changes the design

The brief said `role` "was missed because its FK is NULLABLE". **There is no foreign key at all.** Measured:

```
$ grep -n 'ALTER TABLE "role"' apps/api/prisma/migrations/0_baseline/migration.sql
(no match — exit 1)
```

`role` carries `"school_id" UUID` (`0_baseline/migration.sql:546`) with **no** `role_school_id_fkey`, and
`schema.prisma`'s `model Role` declares **no** `school` relation field. `role.school_id` is a **dangling column**.

This is not a new observation — the harness already wrote it down and predicted this day, at
`scripts/rls-isolation-check.js:296-299`:

> `role` already carries a `school_id` column with no FK constraint, and the day `ADR-015` custom roles add
> `role_school_id_fkey`, `role` correctly ENTERS the derived set and the agreement correctly goes red.

**Consequence, and it is the load-bearing design decision of this slice:** `DERIVED_EXPECTED` is computed from
`pg_constraint` (`DERIVED_SET_SQL`, `scripts/rls-isolation-check.js:360-372`). With no FK, `role` is **invisible to
that derivation** — it will not move `5 → 6` on its own, no matter what policy is written. AC-4(e) is therefore only
satisfiable if the FK is **materialised**.

**Decision (`ADR-046 §D2`): materialise `role_school_id_fkey`.** Rejected alternative: teach the derivation a second,
convention-based clause ("a `school_id` column, FK or not"). Rejected because it re-introduces by the back door the
literal list `ADR-042 §D3` exists to abolish, and because it would leave the referential hole open — with no FK, a
`role` row can point at a school that does not exist, and under the new policy such a row becomes **invisible to
every tenant** (fail-closed, but silently). The FK closes the misclassification *and* the hole with one object.

**Measured on the live `pilotage` database (read-only, nothing written):**

```
ROLES|0                       ROLES_WITH_SCHOOL|0        ORPHAN_ROLES|0
USER_ROLE_ORPHAN_SCHOOL|0     TENANT_FK_PARENTS|tenant
```

Zero orphans locally. **Production may differ**, so the migration must *not* rely on this: it pre-checks and
`RAISE EXCEPTION`s with the offending count rather than letting `ADD CONSTRAINT` fail with an opaque message or —
worse — being written as `NOT VALID` and leaving the hole open under a green deploy.

### 2.3 The cost this decision arms, deliberately

Materialising the FK means `schema.prisma` changes (`Role.school School? @relation(...)` + `School.roles Role[]`),
which **arms the `prisma generate` RED trap (`P-05`)**: typecheck stays RED until
`pnpm --filter @pilotage/api exec prisma generate` is run — `exec` is mandatory, `pnpm --filter X prisma generate` is
a no-op that exits 0. It also means the drift gate can now see part of this slice, which is a gain: policies and
grants are invisible to `prisma migrate diff`, an FK is not.

## 3. Acceptance criteria

### AC-1 — ONE new reviewed migration

`apps/api/prisma/migrations/20260814<HHMMSS>_tenant_reference_surface/migration.sql`, hand-written and hand-reviewed
(`ADR-027`, G-MIGRATION). **Never `prisma db push`**; the strings `db push` and `migrate dev` must not appear in its
executable SQL. It grants `app_user` **`SELECT` only** on `permission`, `role_permission`, `role`, `tenant` and
`_prisma_migrations`, and nothing else. **No `GRANT ... ON ALL TABLES IN SCHEMA public`** — that form would hand over
every unpoliced table by the same gesture that claims to restrict.

Every GRANT is conditioned on `EXISTS (SELECT 1 FROM pg_roles WHERE rolname = 'app_user')`, computed **once** into a
`has_app_user` constant, exactly as the three prior migrations do: roles are **cluster**-scoped, migrations are
**database**-scoped, and both the drift gate and CI apply migrations to fresh databases where `app_user` does not
exist. The `ENABLE`/`CREATE POLICY`/`ADD CONSTRAINT` half stays **unconditional** — that is the security property and
it depends on no role.

The `_prisma_migrations` grant is additionally guarded on `to_regclass('public._prisma_migrations') IS NOT NULL`
(see AC-4(d) — the table genuinely does not exist in the proof harness's scratch database), with the branch taken
printed via `RAISE NOTICE`.

### AC-2 — `role` gets RLS and an FK-path policy, and the `IS NULL OR` is ARGUED

`role` receives `ENABLE ROW LEVEL SECURITY` and a policy **named `tenant_isolation`** (the census counts by name),
`FOR ALL TO PUBLIC` (never `TO app_user` — a policy naming a role exempts every other non-owner role silently), with
`WITH CHECK` written **explicitly and identically to `USING`**:

```sql
role.school_id IS NULL
OR EXISTS (
     SELECT 1 FROM public.school s
      WHERE s.id = role.school_id
        AND s.tenant_id = nullif(current_setting('app.current_tenant_id', true), '')::uuid
   )
```

**Why this is not DNC-10.** The banned fail-open shape is `current_setting(...) IS NULL OR ...` — a NULL **tenant
context** opening the table for every connection that never set the GUC. Here the NULL is `school_id`, a **data
fact** meaning "this row belongs to no school", i.e. a genuinely global system role. The tenant context is *not* on
the left of the `OR` and cannot open anything: with the GUC absent or `''`, `nullif(...)` is NULL, the comparison is
NULL, `EXISTS` is false, and **every school-scoped role is invisible**. Only `school_id IS NULL` rows survive, which
is the correct answer for a missing context, not a relaxation. This must be argued in the migration header and in
`ADR-046 §D3`, not copied.

`AND s.tenant_id = <GUC>` is **kept even though it is redundant for `app_user`** (school's own policy already filters
the subquery), because it is the only thing that works when the query runs as the **owner** — which is every
migration, every seed and the whole application today. `ADR-042 §D1` already ruled this; do not remove it as dead.

**Ratchet verification (do this by reading, before writing the SQL).** `apps/api/src/shared/prisma/prisma.service.spec.ts:483-489`
scans the executable SQL of **all** migrations with three regexes:

| Regex | Verdict on this predicate |
|---|---|
| `/current_setting\s*\([^)]*\)\s*IS\s+NULL\s+OR/i` | no match — `current_setting` appears **after** the `OR`, inside `EXISTS`, never before an `IS NULL OR` |
| `/IS\s+NULL\s+OR\s+tenant_id/i` | no match — the token after the `OR` is `EXISTS`, and the column before it is `school_id` |
| `/\bOR\s+true\b/i` | no match |

They **pass**. If any of them goes red, the predicate is wrong, not the test. `prisma.service.spec.ts:479-481`
additionally requires the corpus to contain the literal `nullif(current_setting('app.current_tenant_id', true), '')::uuid = tenant_id`
(already satisfied by earlier migrations) and forbids `tenant_id::text` anywhere — this predicate uses `::uuid`, so
both hold. The token ratchets (`SYSTEM_TENANT`, `SKIP_`, `ALLOW_`, `skipTenant`, `BYPASSRLS`, `FORCE ROW LEVEL SECURITY`)
must stay clean in executable SQL.

**Do NOT extend `rls-isolation-gate.spec.ts:583`** — that unqualified `expect(DERIVED_MIGRATION_CODE).not.toMatch(/IS\s+NULL\s+OR/i)`
is scoped to the `S-E01-2c` file, where no data column is nullable. Copying it onto this migration would fail on a
correct predicate. Say so in a comment at the new assertion site so the next reader does not "fix" it.

### AC-2b — the FK, and no orphan may pass

The same migration adds `role_school_id_fkey`: `role.school_id -> school.id`, **`ON DELETE CASCADE`** (a custom role
belongs to its school; ADR-015 role administration deletes roles explicitly, `roles.controller.ts:294`), matching the
other school children. Before adding it, the migration counts orphans and `RAISE EXCEPTION`s with the count if any
exist — never `NOT VALID`, never a silent skip.

`schema.prisma` gains the two relation fields, and `pnpm --filter @pilotage/api exec prisma generate` is run **inside
this diff** so typecheck is not left RED (`P-05`).

No new index is required: `role_school_id_slug_key` (`0_baseline/migration.sql:1314`, `UNIQUE (school_id, slug)`) has
`school_id` as its **leading** column, which is what `DERIVED_FK_INDEX_MISSING` checks (`indkey[0]`). Assert it,
don't create a duplicate.

### AC-3 — `tenant`: resolve the chicken-and-egg EXPLICITLY

The identity seam must read `tenant` **by slug before any tenant is resolved** — that is why `tenant` was left
policy-free (§`LE PÉRIMÈTRE` class B). The one live by-slug read is
`apps/api/src/modules/identity/register.controller.ts:366` (`tx.tenant.upsert({ where: { slug: DEMO_TENANT_SLUG } })`),
and it runs **as the owner** today.

**Preferred shape.** `tenant` gets `ENABLE ROW LEVEL SECURITY` and a `tenant_isolation` policy
`id = nullif(current_setting('app.current_tenant_id', true), '')::uuid` (same `USING`/`WITH CHECK`, `FOR ALL TO PUBLIC`),
plus **one narrow, named `SECURITY DEFINER` function** for by-slug resolution — e.g.
`public.resolve_tenant_by_slug(text) RETURNS uuid`, `STABLE`, `SECURITY DEFINER`, `SET search_path = pg_catalog, public`,
`REVOKE EXECUTE ... FROM PUBLIC` then `GRANT EXECUTE ... TO app_user`, returning **only the id** for an **exact** slug
match (no `LIKE`, no prefix, no list). A bare `SELECT` on `tenant` would otherwise be a tenant-**enumeration** oracle,
which epic §10 forbids.

**Note for the implementer:** `SECURITY DEFINER` on a function owned by `pilotage` is a genuine privilege-boundary
object. Its entire body must be one parameterised `SELECT id FROM public.tenant WHERE slug = $1`. No dynamic SQL, no
second statement, no `SET ROLE`.

**Fallback, only if MEASURED to be unworkable:** leave `tenant` grant-only (SELECT, no policy), **say so explicitly**
in the migration header and `ADR-046 §D4`, and record the enumeration exposure as **`PF-192`**. Do not leave it
silent and do not describe it as safe. Note that this fallback also keeps `RLS_ON` unchanged, which simplifies AC-4(e)
— that convenience is **not** a reason to choose it.

### AC-4 — PROVEN BY EXECUTION, by extending `scripts/rls-isolation-check.js`

Same harness, same posture: scratch database, ledger applied, proof run as `app_user`, database and role dropped.

**(a) POSITIVE CONTROL / fail-before-pass-after.** The authorization join

```sql
SELECT count(*) FROM user_profile up
  JOIN user_role ur ON ur.user_profile_id = up.id
  JOIN role r ON r.id = ur.role_id
  JOIN role_permission rp ON rp.role_id = r.id
  JOIN permission p ON p.id = rp.permission_id;
```

must raise `permission denied` as `app_user` **before** this migration's grants, and **succeed after**. Without the
before-half the grant is green for the wrong reason. The harness already applies migrations file by file
(`rls-isolation-check.js:1159`), so the "before" state is reachable by applying the ledger up to but excluding the new
file.

**(b) foreign custom role denied.** A `role` row with `school_id` = a school of **tenant B** is **not visible** under
`GUC = tenant A`. Reuse the existing `SCHOOL_A`/`SCHOOL_B` fixtures and `TENANT_A`'s deliberate **UPPERCASE** id —
that is the trap that executes the cast direction.

**(c) system role visible under both.** A `role` row with `school_id IS NULL` is visible under GUC = A **and** GUC = B.
Add the third case that (b) alone cannot catch: with **no GUC at all**, the system role is still visible and the
school-scoped one is **not**.

**(d) `_prisma_migrations` readable by `app_user`.** `apps/api/src/main.ts:81` calls `assertMigrationsClean(...)` at
boot and `apps/api/src/modules/health/health.controller.ts:44` calls `readMigrationState(...)` per request — both
read `_prisma_migrations` (`apps/api/src/shared/migrations/migration-state.ts`). **Verified: it does run at boot**, so
without this grant the API would refuse to start after the cutover.

**⚠️ The brief's premise here is FALSE and must be handled.** The harness does **not** run `prisma migrate deploy`; it
applies each `migration.sql` with `psql` (`rls-isolation-check.js:1159`), and Prisma's CLI — not the SQL — creates
`_prisma_migrations`. The script says so itself at lines 333-340 and branches on `LEDGER_TABLE` presence. So today
that table is **absent** from the scratch database and AC-4(d) is **unprovable as written**. Fix it in the harness:
create `_prisma_migrations` with Prisma's own DDL (owned by the scratch owner) **before** applying the ledger, so the
`ledgerTablePresent` branch becomes the real one, the residue expectation already handles it, and the grant is
exercised. Do **not** "fix" it by deleting the assertion.

**(e) the census agreement, with NO literal edited.** Today:
`RLS_ON == TENANT_COLS + DERIVED_EXPECTED` (`rls-isolation-check.js:1363-1367`), both terms catalog-computed. This
slice moves **two** things, and the second is not in the brief:

1. `role` joins the derived set once `role_school_id_fkey` exists → `DERIVED_EXPECTED` goes **5 → 6** through
   `DERIVED_SET_SQL` untouched, and `RLS_ON` goes 50 → 51. Balanced, no literal edited. `role` must also be **removed**
   from `NON_DERIVED_EXPECTED` (`rls-isolation-check.js:301-313` **and** `rls-isolation-gate.spec.ts:169-172`) or the
   residue set-equality fails printing its name — and the comment at `rls-isolation-check.js:296-299` predicting this
   day must be rewritten to say the day has come.
2. **If AC-3's preferred shape is taken**, `tenant` gets RLS → `RLS_ON` becomes **52** while the right-hand side is
   `45 + 6 = 51`, and the agreement **breaks**. It needs a **third catalog-derived term**, never a literal `1`: the
   set of tables that are the **parent** of a foreign key whose leading child column is `tenant_id`. Measured on the
   live database: `TENANT_FK_PARENTS = tenant`, exactly one. Derive it in SQL alongside `DERIVED_SET_SQL`, assert its
   **names** as well as its count, and make the agreement `RLS_ON == TENANT_COLS + DERIVED_EXPECTED + SELF_SCOPED`.

**(f) the grant surface stops being "exactly the policied tables".** `rls-isolation-check.js:1369-1373` asserts
`GRANTED == policiedExpected` where `GRANTED` counts **every** table `app_user` holds any privilege on. This slice
deliberately grants tables that are not policied, so that assertion **will go red** and must be **restructured, not
loosened**: assert **set equality by name** between the tables `app_user` is granted and
`policied ∪ REFERENCE_SURFACE`, where `REFERENCE_SURFACE` is a named, reasoned constant
(`permission`, `role_permission`, `tenant`, `_prisma_migrations`) — `role` is not in it, because `role` is policied.
Add a second assertion that **every** table in `REFERENCE_SURFACE` holds **exactly `SELECT`** and nothing else, so a
future `INSERT` cannot slip in under a count that still balances.

**(g) the derived privilege set opens by one.** `DERIVED_PRIVILEGE_SETS` (`rls-isolation-check.js:275`) is the closed
set `['SELECT, INSERT', 'SELECT, INSERT, UPDATE']`. `role` will hold **`SELECT`** alone, which that set rejects. Add
`'SELECT'` to it **with the reason written next to it** (the privilege surface is read-only this slice, see AC-7 §4).
`DERIVED_DELETE` stays `0`.

**(h) rollback executed, not written.** The harness already applies → proves → reverses → re-measures. Extend that
reversal to the new objects and re-assert that `pg_policy` returns to its prior count, `relrowsecurity` returns to
`f` on `role` (and `tenant`), the grants are gone, and the function is dropped.

**(i) the drop is verified independently.** After the run, confirm from a **separate** connection that the scratch
database and scratch role are gone — do not trust the script's own claim. The live `pilotage` database must be
byte-for-byte untouched (it deliberately has 0 policies and 2 migrations applied).

### AC-7 — `ADR-046`

`docs/adr/ADR-046-authorization-reference-surface.md`. **ADR-045 is taken by open PR #248 and is invisible from
`main`** — do not reuse it. The ADR extends `ADR-032` and `ADR-042`; it supersedes nothing. It must decide, with
reasons:

1. **Why grant the reference surface rather than keep the owner connection.** The owner connection is the defect
   (`PF-02`); keeping it to avoid grants would make the policies permanently decorative.
2. **The `IS NULL OR` distinction** of AC-2 — a NULL *data* column is not a NULL *tenant context*, with the three
   regexes and their verdicts as evidence.
3. **The `tenant` by-slug resolution** of AC-3 — the `SECURITY DEFINER` function, its narrowness, and why a bare

4. **SELECT-only on the whole privilege surface.** Privilege data the application role can edit is a
   privilege-escalation path.

   **⚠️ The brief's clause 4 states more than is true, and the ADR must not repeat it.** It is **not** true that the
   application never writes these tables: `apps/api/src/modules/identity/roles.controller.ts` calls `tx.role.create`
   (154), `tx.role.update` (242), `tx.rolePermission.deleteMany` (250), `tx.rolePermission.create` (252) and
   `tx.role.delete` (294) at runtime — that is ADR-015 custom-role administration. SELECT-only is correct **for this
   slice**, whose scope is reads; it is **not** a permanent statement about the system. The ADR must say so, and the
   write path must be a **named open decision**: after the cutover, custom-role administration will fail with
   `permission denied` until someone decides how it writes (a narrow `SECURITY DEFINER` administration function, a
   separate role, or a scoped `INSERT/UPDATE/DELETE` grant whose `WITH CHECK` on `role` is what stops a school admin
   from minting a role in another tenant's school). Record it as **`PF-193`** — *verify the number against `OPEN.md`
   and any open PR before allocating, per `TOOL-30`* — and do not silently widen this slice to solve it.
5. **Why `role_school_id_fkey` is materialised** (§2.2), including the `ON DELETE CASCADE` choice and the orphan
   pre-check.

Also worth one sentence in the ADR: `user_role.school_id` is the **same class of dangling column** as
`role.school_id` was (no FK, `0_baseline/migration.sql:568`). It is **out of scope** here — `user_role` already
derives its tenant through `user_profile_id` (`ADR-042 §D2`) and is already policied — but naming it prevents the
next reader from thinking it was checked and cleared.

### AC-8 — EXPAND-ONLY, with an executable rollback

No column dropped, no data rewritten, no behaviour change to the running app — it still connects as the **owner**,
and `FORCE ROW LEVEL SECURITY` is still deliberately absent (`ADR-032 §D5`; the ratchet at
`prisma.service.spec.ts:492` forbids it in SQL). Adding a foreign key is expand-only **provided** no orphan exists,
which AC-2b enforces by refusing rather than by hoping.

The rollback is stated in the header **and executed** by the harness (AC-4h), guarded on `pg_roles` the same way:

```
REVOKE SELECT ON permission, role_permission, role, tenant, _prisma_migrations FROM app_user
REVOKE EXECUTE ON FUNCTION public.resolve_tenant_by_slug(text) FROM app_user
DROP FUNCTION IF EXISTS public.resolve_tenant_by_slug(text)
DROP POLICY IF EXISTS tenant_isolation ON public.role      -- and ON public.tenant
ALTER TABLE public.role DISABLE ROW LEVEL SECURITY         -- and public.tenant
ALTER TABLE public.role DROP CONSTRAINT IF EXISTS role_school_id_fkey
```

Reversing the FK also requires reverting the two `schema.prisma` relation fields and re-running
`prisma --filter @pilotage/api exec prisma generate`; say so, because a rollback that leaves the datamodel ahead of
the database turns the drift gate red for the wrong reason.

## 5. Do-not-copy (G-DNC) — the concrete traps for this diff

- **DNC-10.** No `SYSTEM_TENANT`, no `SKIP_`/`ALLOW_` flag, no `OR true`, no hard-coded slug or email bypassing a

  `to_regclass`, orphan count) are fine and are what the prior three migrations already do.

## 7. Risks the pre-mortem must carry

1. **The FK fails on production data.** Orphan `role` rows would abort `migrate deploy`. Mitigated by the explicit
   pre-check with a counted, named error — a loud refusal at deploy time is the correct outcome, not a `NOT VALID`
   that ships the hole.
2. **`prisma generate` forgotten** → typecheck RED, and the reflex is to re-scope rather than run one command
   (`P-05`). Run `pnpm --filter @pilotage/api exec prisma generate` in the same diff; `pnpm --filter X prisma generate`
   is a no-op that exits 0.
3. **The census is "fixed" by editing a number.** Any diff that writes `6`, `51` or `52` as a literal into
   `rls-isolation-check.js` has destroyed the property `ADR-042 §D3` exists for. Reviewers: grep the diff for bare
   integers before anything else.
4. **`SECURITY DEFINER` written loosely** — a body with dynamic SQL or a second statement turns a narrow lookup into
   an owner-privileged execution surface. One parameterised `SELECT`, `STABLE`, pinned `search_path`, `EXECUTE`
   revoked from `PUBLIC`.
5. **The `tenant` policy silently breaks registration.** `register.controller.ts:366` runs as the owner today, so it
   is unaffected — but it will break at the cutover unless it goes through `resolve_tenant_by_slug`. Say so in the
   ADR; do not change the controller in this slice.
6. **Someone reads this slice as "the cutover is done".** It is not. The header, the ADR and PROGRESS.md must each
   carry the sentence that the running application is still not RLS-isolated.
