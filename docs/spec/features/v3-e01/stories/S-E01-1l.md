## 4. Design rules — the shape that is already shipped, and the four hazards specific to alerts

**Read first, before writing anything:** `apps/api/src/modules/remediation/remediation.service.ts` (lines 1–130 carry the whole doctrine in its docblock) and `apps/api/src/modules/student-portal/student-portal.service.ts`. Do not invent a new shape.

### 4a. The pattern

```ts
constructor(
  private readonly scope: TenantScopeService,      // replaces PrismaService
  private readonly notifications: NotificationsService,
) {}
```

- `TenantScopeService.run<T>(tenantId, (tx: Prisma.TransactionClient) => Promise<T>)` — signature at `apps/api/src/shared/prisma/tenant-scope.service.ts:127`. It is provided by the `@Global()` `PrismaModule`, so **no module wiring is due** — inject it and go.
- **`PrismaService` must stop being injected in both services.** As `remediation.service.ts` puts it: the property that no owner-connection statement can be reached from here becomes *"une propriété du CONSTRUCTEUR"*, not a review convention. A residual `this.prisma` inside a `run` callback is classified **`owner-inside-scope`** and reported by name — it does **not** count as scoped (`classifyCallSite`, `tenant-adversarial-check.js:2951`).
- **Keep every explicit `tenantId:` guard in every `where`.** They are not made redundant by RLS: on a deployment without `DATABASE_URL_APP`, `run` executes on the **owner** connection (ADR-056), which escapes its own policies. Removing them would make isolation a property of one deployment's env file.
- **The scope key is always `args.tenantId`** — the server-derived value already on every signature. Never `row.tenantId`, never `alert.tenantId`: that would make the scope key a function of the data the scope exists to filter.
- **Scope late, close early.** Do not wrap a handler end-to-end when only two statements need the connection.

### 4b. Caught errors must LEAVE their scope (ADR-058 §D1) — three sites

`run` opens an **interactive** transaction. Any error **aborts** it, and every subsequent statement on the same `tx` fails `25P02` (*current transaction is aborted*). The rule, applied verbatim from `remediation.service.ts`:

> the `try {` opens **BEFORE** `await this.scope.run(…)`, the `catch` closes **AFTER**, and the recovery statement opens a **FRESH** scope.

Three sites in this module:

1. **`recordMeetingIntent` (437 / 459)** — the `P2002` idempotency race. `meetingRequest.create` in one scope; on `P2002`, the winner re-read at 459 in a **second, fresh** scope. This is the exact shape of `promotePlan`.
2. **`loadMeetingRequestedAt` (868)** — the swallowed lookup failure that degrades to "not requested". The `try` must sit outside the `run`.
3. **`writeAuditEntry` (624) and the audit write at 481** — see §4c; these are the load-bearing ones.

**No unit test with a fake client can catch a violation of this rule** — a fake `run` that calls `fn(prisma)` has no transaction to abort. The property is provable **lexically only** (`PF-247`). State that in the ADR.

### 4c. G-AUDIT — the audit write must NOT be pulled into the mutation's transaction

**How it works today, measured:** `writeAuditEntry` (`alerts.service.ts:613-645`) and the inline write at `:481` are **best-effort, post-mutation, and in their own statement** — `alerts.service.ts` contains **no `$transaction` at all**. Each is wrapped in `try { … } catch { this.logger.error(…) }` that **swallows** and explicitly *"never rolls back the status change"*. `meeting-requests.service.ts:158` is the same shape.

**Therefore, for AC6: do not change that relationship, in either direction.**

- Pulling the audit write into the *same* scope as its mutation would make it transactional — which sounds stronger but is a **regression**: the swallowed error would abort the interactive transaction (§4b) and silently roll back the `acknowledge`/`resolve`/`dismiss` the audit row was merely recording. A best-effort trail would start deciding whether the mutation stands.
- Leaving each audit write in its **own** scope, with its `try`/`catch` outside the `run`, preserves the documented behaviour **exactly**: post-mutation, best-effort, never rolling back.

So: **`writeAuditEntry` opens its own scope; the mutation handlers open theirs.** The transactional relationship is unchanged — it was already "not in the same transaction", and it stays that way. **Say this plainly in the ADR**; do not let it read as "we made the audit trail transactional".

### 4d. `Promise.all` on one interactive transaction — sequentialise

`listInstances` (183 + 194) and `meeting-requests.list` (106 + 113) each issue two statements through `Promise.all`. An interactive Prisma transaction is **one connection**; concurrent awaits on the same `tx` are not a supported ordering. Inside a scope, replace each `Promise.all` with two sequential `await`s on `tx`. This is a real behaviour change in shape (two round-trips instead of one interleave) and is the correct one; note it in the ADR.

### 4e. `evaluateAll` — the scope must NOT swallow the rule evaluators or the notification fan-out

`evaluateAll` calls `RULE_FN[rule.code](ctx)` with `ctx.prisma: PrismaService` (`rules/rule-context.ts:8`), and the seven evaluators issue **8 reads through `ctx.prisma.`** (`grade`, `attendance_record`, `student`). It then calls `this.notifications.createMany(...)` — a **different, unconverted module** on the owner connection.

**Do not thread `tx` into `RuleContext` in this slice, and do not wrap the evaluator call or the notification fan-out in a scope.** Two independent reasons, both load-bearing:

1. **The derivation is POSITIONAL and single-file.** `derivePrivilegeClosure` attributes a call site by brace-matched range **in the file where the scope is opened**. A statement in `rules/high-absence.rule.ts` is not lexically inside a callback in `alerts.service.ts`, so threading `tx` through the context would run those 8 statements on the app connection **while the derivation never emits `grade.SELECT` / `attendance_record.SELECT` / `student.SELECT` for them** — a boot-green closure and a `42501` on the first evaluation after cutover. That is `TOOL-40 (a)`'s failure mode, reproduced by hand.
2. **The PF-200 inverse.** Calling `NotificationsService` (owner connection) from inside an open interactive app transaction holds two connections for the transaction's duration — precisely the hazard the `teacher-profile.service.ts` enumeration names.

**Correct shape for `evaluateAll`:** narrow scopes around this file's *own* statements — one for `alertRule.findMany` + `academicYear.findFirst` (660/673), and **one per detection** covering the dedup `findFirst` + the `create` (707/720) — each **closed before** the evaluator call and **closed before** `notifyGuardiansOfAlert`. `notifyGuardiansOfAlert` scopes only its `guardianship.findMany` (774) and closes it **before** `this.notifications.createMany`. An unbounded `for` loop of rules × detections inside one 5 s interactive transaction is the *"portée tardive, fermeture précoce"* rule of ADR-057 §D2 — do not violate it for a tidier diff.

The 8 `ctx.prisma.` sites are **invisible to the scan** (§10, `PF-256`) — they are not in the 818 and converting them would not move the gauge. Record that; do not chase it.

## 5. The ONE enumerated exception

`tenantsWithEnabledRules()` — `alerts.service.ts:919-926`:

```ts
async tenantsWithEnabledRules(): Promise<string[]> {
  const rows = await this.prisma.alertRule.findMany({
    where: { enabled: true },
    select: { tenantId: true },
    distinct: ['tenantId'],
  });
  return rows.map((r) => r.tenantId);
}
```

It takes **no `tenantId`** and returns the set of tenants the worker cron must evaluate. It **PRODUCES** the scope key; it cannot be issued from inside a scope, and inside one on `app_user` with no GUC it returns **zero rows** — the worker would then silently evaluate nothing, which is the `PF-199` failure shape exactly.

It must be added to `ENUMERATED_OUTSIDE_SCOPE` (`scripts/tenant-adversarial-check.js:2140`) as a **LAYER B / `kind: 'bootstrap'`** entry with a file glob, a file-level `reason`, and **one `statements` entry** (`model: 'alertRule'`, `verb: 'findMany'`) carrying its **own** reason — the exact shape of the `teacher-profile.service.ts` and `calendar-seed.service.ts` entries. `enumerationDrift` compares this list to the scan for **set equality in both directions**: an unlisted statement fails, a dead entry fails, a reasonless statement fails. A reason that merely repeats the method name is refused by the non-vacuity guard — say **why a scope cannot exist here**, not what the method is called.

**Every other one of the 37 sites converts.** If, while implementing, a site genuinely cannot enter a scope, it is enumerated with its own reason — **never silently left out** (AC2).

## 6. `PF-254` — the `RETURNING` rule, and why it belongs to THIS slice

### 6a. The defect

`VERB_PRIVILEGES` (`scripts/tenant-adversarial-check.js:2527`) maps `create → [INSERT]`, `update → [UPDATE]`, `delete → [DELETE]`, `upsert → [INSERT, UPDATE]`, `createManyAndReturn → [INSERT]`.

PostgreSQL requires **`SELECT` on every column named in a `RETURNING` clause**, and Prisma's singular writes all emit `… RETURNING`. So each of those verbs under-derives by one privilege.

### 6b. The fix

Split the table **by whether the verb returns rows**:

| verb | privileges | why |
|---|---|---|
| `create`, `update`, `delete`, `upsert`, `createManyAndReturn` | write privilege **+ `SELECT`** | emits `… RETURNING`; PostgreSQL requires `SELECT` on every returned column |
| `createMany`, `updateMany`, `deleteMany` | write privilege **alone** | returns a row **count**, no `RETURNING` |
| reads (`findFirst`, `findMany`, `count`, `aggregate`, `groupBy`, …) | `SELECT` | unchanged |

`upsert` becomes `['INSERT', 'UPDATE', 'SELECT']`. **Record the `RETURNING` rule as the REASON in a comment adjacent to the table**, so a future reader cannot read the added `SELECT`s back as mere symmetry between reads and writes and "simplify" them away.

### 6c. Why now — the accident this diff removes

Until this slice, **every** write table in the derived set (`announcement`, `announcement_receipt`, `calendar_event`, `lesson_entry`, `remediation_plan`) also had a **read** site contributing `SELECT`. The mapping was therefore **accidentally correct**. `tenant-scope.ts:453-456` already half-writes the rule by hand — it rationalises `remediation_plan.INSERT` by pointing at *"l'`include` de la création fait un `INSERT … RETURNING`, qui exige en plus le SELECT déclaré ci-dessus"* — but only in prose, on one entry, in one direction.

`alerts` writes `auditLog.create` at `alerts.service.ts:481` and `:624` (and `meeting-requests.service.ts:158`) and **never reads `audit_log`**. That makes `audit_log` the **first genuinely write-only table** to enter a tenant scope. Without the fix, the derivation emits `audit_log.INSERT` alone, the implementer declares exactly that on the gate's instruction, the gate reports 0 undeclared / 0 dead, and `appRoleVerdict` certifies `enforcing: true` on a closure that omits the `SELECT` the `INSERT … RETURNING` needs.

### 6d. Latent or live — verify by executing, then say which

**Measured on the running stack (`information_schema.role_table_grants`, 2026-08-23): `app_user` holds `SELECT, INSERT` on `audit_log`** — deliberately, per ADR-037 §D4 / GUARDRAILS §1, because the audit hash chain must not become rewritable.

So on **this** deployment the runtime is **expected to work**: `INSERT … RETURNING` finds the `SELECT` it needs even though nothing declared it. **The defect is in the DERIVATION, and on this deployment it is LATENT, not live.** Do not inflate it. What is *not* latent is the general case: the natural hardening of an append-only table is `GRANT INSERT` alone, and against such a grant the boot probe would still have said green while the first audit write raised `42501`. Re-run the grant query yourself and state the verdict from **your** execution, not from this paragraph.

### 6e. The test

Assert the rule **directly against `privilegesForVerb`** in `apps/api/src/shared/quality/tenant-adversarial-gate.spec.ts`. The existing block is at **lines 1843–1885** (`describe('AC-10 — le classifieur verbe -> privilège est PUR…')`) and currently asserts `create/createMany/createManyAndReturn → ['INSERT']` and `update/updateMany → ['UPDATE']` — **those assertions must change**, they are the ones encoding the defect. Add a case that names the row-returning vs row-counting split explicitly, and keep the unknown-verb `null` case intact. `privilegesForVerb` and `VERB_PRIVILEGES` are already exported (`tenant-adversarial-check.js:5013` region) and already typed in the spec's checker interface at `:216-217` — no new export plumbing.
