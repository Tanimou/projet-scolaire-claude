## 0. Read this first — what this slice is, and what it is not

This slice repairs **the gate**, not the application. Nothing a parent, teacher or admin can see changes. No
schema, no endpoint, no controller, no guard, no permission, no contract, no dashboard *value*, no production
worker code. The entire diff lives in one CI script and three test/doc files.

Two things are wrong, both **latent today** (nothing is red on `HEAD`), both **inside a blocking CI stage**
(`scripts/ci-gate.sh` stage 9 → `node scripts/observability-check.js`), and both confirmed by reading and driving
the shipped code on 2026-08-08 rather than by trusting a review claim (`R-30`):

1. **`PF-114` — the gate goes red on a correct tree.** Check 10 flags
   `sum by (queue) (max by (queue, state) (pilotage_queue_depth))`, which is correct PromQL and is *the exact
   idiom check 10's own error message recommends*. This is the mirror image of the defect `S-E02-18` closed. The
   script's own header states why it is equally corrosive: a gate that false-reds **teaches people to skip it**.
2. **`PF-115` — three vacuity gaps inside the mechanism `S-E02-18` shipped.** A failure message that names the
   wrong file; a shared-registry mutation whose restore nothing asserts; and a G-TENANT assertion that cannot
   fail.

**The whole method of this epic, restated because it is the acceptance bar:** *a check run only against a healthy
repository can demonstrate that the repository is healthy, and nothing else.* Every new rule in this slice must
be shown **failing before the fix** and **passing after**. An assertion that was green before your change is not
evidence.

## 2. PF-114 — stop rejecting correct replica-safe PromQL

### 2.1 The defect, precisely

`sumAggregationArguments(expr)` returns the **direct argument text** of each `sum` token.
`evaluateGaugeAggregation` then calls `metricNamesInExpr()` on that text and flags **any** gauge-typed family it
finds (`:799`–`:811`). It never asks whether an inner aggregation has already collapsed the replica dimension.

So for `sum by (queue) (max by (queue, state) (pilotage_queue_depth))`:
- `sumAggregationArguments` → `args: ['max by (queue, state) (pilotage_queue_depth)']`
- `metricNamesInExpr` on that arg strips `by (...)` and yields `['pilotage_queue_depth']`
- `types['pilotage_queue_depth'] === 'gauge'` → **PROBLEM**, on correct PromQL.

Why the expression is correct: `max by (queue, state)` produces **one** series per `(queue, state)` — the
`instance` dimension is gone, so the replica duplication that made `sum` wrong is already removed. Summing the
remaining states is ordinary, correct arithmetic.

### 2.2 Acceptance criteria

Each of AC-1…AC-5 must be a **new executed test case** in
`apps/api/src/shared/quality/observability-gate.spec.ts`. Each must be demonstrated **red before the fix**.

- **AC-1** — `sum by (queue) (max by (queue, state) (pilotage_queue_depth))` produces **no problem**.
- **AC-2** — `sum by (queue) (pilotage_queue_depth)` **still produces a problem**, and the message still names
  the metric family and the panel title. *This is the load-bearing criterion.* It is the `PF-108` defect the rule
  exists to catch. **If you widen the rule so this passes, you have deleted the gate, not fixed it.** Existing
  case `T18` covers the `sum by (queue, state)` variant; add the `sum by (queue)` variant explicitly.
- **AC-3** — the two existing acceptances stay green, unmodified: `max by (queue, state) (pilotage_queue_depth)`
  (no `sum` at all, `T18b`) and `sum by (queue) (rate(pilotage_queue_depth_collection_failures_total[5m]))`
  (a **counter** whose name is a prefix-superset of the gauge's — resolution goes through exact-name lookup, never
  `startsWith`, `T18c`). `T18d` (bare gauge) and `T18e` (histogram under `histogram_quantile`) likewise.
- **AC-4** — an inner aggregation that does **not** remove the replica dimension is **still flagged**. Two cases,
  both required:
  - `sum by (queue) (max by (queue, state, instance) (pilotage_queue_depth))` — the `by` list **retains**
    `instance`, so the `max` keeps one series per replica and the outer `sum` still double-counts.
  - `sum by (queue) (max_over_time(pilotage_queue_depth[5m]))` — `max_over_time` is a **range function over one
    series' samples in time**, not an aggregation across series. It removes nothing. A fix that shields on the
    string `max` rather than on aggregation semantics will wrongly accept this; that is the trap.
- **AC-5** — **DNC-08 preserved.** Anything the reader cannot parse stays a PROBLEM, never a silent accept. The
  existing `unbalanced` path (`T18g`, `evaluateGaugeAggregation:790`) must survive **and be extended to any new
  parsing you add**: if your shield analysis cannot scan a nested aggregation to its matching parenthesis, that is
  a PROBLEM with a message saying so — not a "cannot tell, assume safe".
- **AC-6** — `infra/grafana/dashboards/pilotage-slo.json` still produces **zero** problems, and
  `node scripts/observability-check.js` still exits **0** on `HEAD` (see §5 for the `apps/worker/dist` caveat).

### 2.3 Design guidance

Follow this unless you can justify better **in the story's PROGRESS entry** (an ADR is only warranted if you
deviate — see §6).

Make the walk **recursive**, not one-level. For each `sum` argument, decide whether each gauge reference inside it
is already **shielded** by an enclosing across-series aggregation whose grouping cannot retain a replica dimension.

1. **Name the replica dimension explicitly.** Add an exported constant — do not inline the list:

   ```js
   /** Label names that identify the PROCESS rather than the resource. */
   const REPLICA_LABELS = new Set([
     'instance', 'pod', 'job', 'replica', 'container', 'kubernetes_pod_name', 'host',
   ]);
   ```

2. **Name the shielding operators explicitly** — the PromQL operators that aggregate **across series**:
   `sum`, `min`, `max`, `avg`, `group`, `count`, `count_values`, `stddev`, `stdvar`, `topk`, `bottomk`,
   `quantile`. Anything not in this set (notably every `*_over_time` range function) shields **nothing**.

3. **The shield test, on the modifier:**
   - no `by`/`without` modifier at all → **shielded** (the aggregation collapses to a single series; there is no
     label left to duplicate);
   - `by (...)` → shielded **iff** the label list contains **none** of `REPLICA_LABELS`;
   - `without (...)` → shielded **iff** the removed set **explicitly contains** at least one replica label. A
     `without` that does not name one is **not** shielded — everything it does not remove is kept, including
     `instance`.

4. **Do NOT special-case the metric name `pilotage_queue_depth`.** The file's own header already forbids it:
   *"a rule that named `pilotage_queue_depth` would be a fix wearing a gate's clothes"*. The rule must stay stated
   over the **declared `# TYPE`**, so it catches the class and not the one line that was wrong.

5. **Suggested shape** — replace the `metricNamesInExpr(argument)` call inside `evaluateGaugeAggregation` with a
   new, named, unit-testable function, e.g.
   `unshieldedGaugeReferences(argument, types) → { families: string[], unscannable: boolean }`, and route
   `unscannable` into the same PROBLEM path the existing `unbalanced` flag uses (AC-5). Keeping it a separate pure
   function is what lets the spec drive it directly with the six AC expressions.

6. **Index alignment matters.** `matchingParen()` (`:310`) is already quote-aware; reuse it. If you mask any part
   of the expression before scanning (see AC-7), mask with **same-length** filler so `expr.slice()` still returns
   the original argument text — `metricNamesInExpr`'s `.replace(..., ' ')` does not preserve length, which is fine
   there because it never slices by index, and is **not** fine here.

### 2.4 AC-7 — an adjacent, cheap false-red in the same function (optional, explicitly flagged)

`sumAggregationArguments` scans the **raw** expression for its `sum` token, so a `sum` inside a quoted label value
— `pilotage_http_requests_total{job="sum"}`, or `label_replace(x, "sum", …)` — is read as an aggregation, fails to
find an argument, and returns `unbalanced: true` → **a hard PROBLEM on a correct tree**. The sibling
`metricNamesInExpr` in the same file already blanks quoted spans (`:220`–`:221`); this is the same discipline
applied inconsistently.

**Status: in scope, but droppable.** `PF-114`'s finding-index row does **not** name this; only
`bmad/roadmap.md`'s candidate-0 item (a) does. It is one masking step in the function you are already editing, in
the same defect class (a gate that false-reds), so it is included. If a reviewer calls it scope creep, drop it and
record it as still-open in PROGRESS.md — **do not** close it silently.

If you do it: add cases for `sum by (queue) (x_total{job="sum"})` (no problem, and `args` is the real argument)
and confirm `T19`'s existing negatives still hold — `sum_over_time(...)` → `args: []`,
`pilotage_http_request_duration_seconds_sum` → `args: []`, `sum pilotage_queue_depth` → `unbalanced: true`,
`sum by (queue) (pilotage_queue_depth` (truncated) → `unbalanced: true`.

## 3. PF-115 — the three vacuity gaps

### 3.1 (a) A failure message that names the wrong file

**Defect.** `readInstrumentedQueues()` (`:1221`) returns `null` when `readCollectorBoundQueues()` (`:1309`)
returns `null` — i.e. when `apps/worker/dist/shared/observability/queue-depth.collector.js` is missing, unloadable,
or carries no `self:paramtypes`. But the only message the caller emits
(`evaluateQueueInstrumentation:866`–`:872`) says the set *"could not be read from
`apps/worker/dist/shared/observability/queue-metrics.js`"*. **An operator following that message opens the wrong
file at the exact moment a blocking stage has failed.**

**AC-8 — the failure reason is explicit and correct.**

- Both readers return a **discriminated result**, not `null`. Do **not** throw: the script's crash path
  (`:1568`) already exits non-zero, but a throw would lose the per-cause detail that is the whole point.
  Suggested shape: `{ ok: true, … }` / `{ ok: false, reason: '<code>', file: '<repo-relative path>', detail?: string }`.
- **Every distinct `return null` site gets its own reason code**, and each names the file it actually read.
  Enumerate at minimum:

  | Reader | Cause | File named in the message |
  |---|---|---|
  | `readInstrumentedQueues` | queue-metrics module absent | `apps/worker/dist/shared/observability/queue-metrics.js` |
  | `readInstrumentedQueues` | metrics registry absent / carries no `registry` | `apps/worker/dist/shared/observability/metrics.registry.js` |
  | `readInstrumentedQueues` | `INSTRUMENTED_QUEUES` not an array | `…/queue-metrics.js` |
  | `readInstrumentedQueues` | `registerQueueDepthSources` / `observeJobCompleted` / `JOB_NAMES_BY_QUEUE` missing | `…/queue-metrics.js` |
  | `readInstrumentedQueues` | the driven write path threw | `…/queue-metrics.js` |
  | `readInstrumentedQueues` | **the registry was not restored** (AC-10) | `…/metrics.registry.js` |
  | `readCollectorBoundQueues` | collector module absent | `apps/worker/dist/shared/observability/queue-depth.collector.js` |
  | `readCollectorBoundQueues` | `reflect-metadata` unresolvable | (name the resolution root, `apps/api`) |
  | `readCollectorBoundQueues` | collector module unloadable (`require` threw) | `…/queue-depth.collector.js` + the error message |
  | `readCollectorBoundQueues` | no `QueueDepthCollector` export | `…/queue-depth.collector.js` |
  | `readCollectorBoundQueues` | no / empty `self:paramtypes` | `…/queue-depth.collector.js` |
  | `readCollectorBoundQueues` | no `BullQueue_*` token among the injected params | `…/queue-depth.collector.js` |

- **DNC-08 is unchanged and must be re-proven:** every one of these is still a **PROBLEM**, never a skip. An
  unrecognised or absent reason must **also** be a PROBLEM (fail closed on your own enum).
- The caller (`evaluateQueueInstrumentation`) maps reason → message. Keep the existing "That is a failure, not a
  skip: with nothing to compare against, a queue nobody instruments would pass unnoticed." sentence — it is what
  makes the message a *reason* rather than a *complaint*.

**AC-9 — `readCollectorBoundQueues()` is covered by executed tests.** It has none today. To make it drivable
without a build, give the reader an **optional path argument** defaulting to the real one
(`function readCollectorBoundQueues(collectorPath = join(REPO_ROOT, '…/queue-depth.collector.js'))`) and export
it. Then drive it from `observability-gate.spec.ts` against throw-away fixture files written to a temp directory
(the spec already reads the real repo via `REPO_ROOT`; follow `S-E06-5`'s throw-away-tree pattern). Cover at
minimum: absent file; a module that throws on `require`; a module exporting no `QueueDepthCollector`; a class with
no `self:paramtypes`; a class whose params carry no `BullQueue_*` token; and the **happy path** (a class with
`self:paramtypes` = `[{ index: 0, param: 'BullQueue_exports' }, …]` → the queue names, in the right order/shape).

> **An optional path parameter is a testability seam, not a flag.** DNC-10 forbids adding a **bypass** — a CLI
> flag, an env var or an argument *that turns any of this off*. A default-valued parameter that only changes
> which file is read, and cannot be reached from the command line, adds nothing to the script's flag surface.
> `main()` must keep calling it with no argument. Say this explicitly in PROGRESS.md so a reviewer does not have
> to re-derive it.

### 3.2 (b) An unguarded shared-registry mutation

**Defect.** `readInstrumentedQueues()` drives the **real write path**: it calls
`mod.registerQueueDepthSources([...])` with a synthetic source returning `{ waiting: 17 }`, and
`mod.observeJobCompleted(queue, { name })`, against the **process-wide prom-client registry**. It restores in a
`finally` (`:1263`–`:1269`) that **nothing asserts**. A leak would fabricate queue traffic that every later
`registry.metrics()` reader in the same process — including a future check — would treat as real. That is the
"green and false" shape this epic exists to close, relocated into the mechanism written to close it.

Measured at run 26: three consecutive script runs returned `PASS`/`FAIL`/`PASS` with no residue. **So it works.
It is simply not guaranteed.**

**AC-10 — the restore is asserted, and a failure to restore is a PROBLEM.**

- Capture the relevant exposition state **before** the drive.
- **After** the `finally` has run, re-render the registry and verify:
  1. the **depth sentinel is gone** — no `pilotage_queue_depth{…}` sample carrying the value `17`;
  2. the **driven job outcome is gone** — no `pilotage_queue_jobs_total{…}` sample for the driven
     `(queue, job, outcome)` triple;
  3. the **depth-source list is empty** — `pilotage_queue_depth_sources_bound` reports no bound source.
- Residue → return the `registry-not-restored` reason (AC-8) → the caller emits a PROBLEM. **A silent pass here
  is the exact defect.**
- **Keep the restore total.** It must still run when the driven call throws. Structure it as: `try { drive } catch
  (error) { driveError = error } finally { restore() }`, then verify restore on **both** paths. If there is both a
  drive error and residue, report the **residue** first — a poisoned registry misleads every later reader in the
  process, which is strictly worse than one failed read.
- Add an executed test for the guarantee. Because the reader talks to a real built module, prefer driving the
  **restore-verification predicate** as its own exported pure function over an exposition string (e.g.
  `registryResidue(expositionAfterRestore) → string[]`), with cases for: clean exposition → `[]`; a `17` depth
  sample present → names the depth family; a driven outcome sample present → names the outcome family; a bound
  source present → names it. That is executable in `apps/api`'s jest without `apps/worker/dist`.

### 3.3 (c) A vacuous tenant assertion

**Defect.** `apps/worker/src/shared/observability/queue-metrics.spec.ts:679`, `T-STALL-6`:

```ts
const JOB_ID = 'clx9q7r4t0001wxyz5678ijkl';
observeJobStalled('exports');
const exposition = await registry.metrics();
expect(exposition).not.toContain(JOB_ID);
```

`JOB_ID` is declared and **never passed to anything**. `'exports'` is what is driven, so
`not.toContain(JOB_ID)` **cannot fail** — no mutation of the production code could make it red. The comment
claims it is *"driven anyway with the values BullMQ really hands the handler"*, which is **false** (`DNC-06`).

**AC-11 — the assertion is made able to fail, and the comment is corrected.**

- **Do not delete the test.** Drive the identifier through the seam that can actually carry it.
  `observeJobStalled`'s single parameter is the **queue name**, so pass the identifier **as the queue name** and
  assert it collapses to the `<other>` sentinel:

  ```ts
  observeJobStalled(JOB_ID);
  const exposition = await registry.metrics();
  expect(sample(exposition, 'pilotage_queue_stalled_total', { queue: OTHER_JOB })).toBe(1);
  expect(exposition).not.toContain(JOB_ID);
  expect(observeJobStalled.length).toBe(1);
  ```

  Now removing the build-time queue whitelist makes the case **red**, which is the property that was missing.
- **Correct the comment to what is actually proven, and no more (`DNC-06`).** Honest wording, roughly: *"the
  signature has arity 1 and that parameter is the QUEUE name, so a job-id label is unrepresentable rather than
  merely untaken; driven here with a real cuid in the one parameter that exists, to prove the whitelist collapses
  it to `<other>` and it never reaches the exposition. This is `T-STALL-4`'s mechanism driven with a
  tenant-shaped input — the added value is the input, not a new mechanism. The end-to-end driven G-TENANT proof
  is case `C9` in `queue-depth.collector.spec.ts`."*
- **`G-TENANT`: this must strengthen, never weaken, the proof.** `/metrics` is unauthenticated by construction,
  so no job id, tenant id or resolved URL may reach a label. If your edit makes any existing tenant assertion
  weaker, stop and re-scope.
