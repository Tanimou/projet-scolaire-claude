## Why

recorded: metrics (`S-E02-13`), traces (`S-E02-14`), web coverage (`S-E02-15`), and the restore rehearsal

deferred residual in three consecutive rows of the traceability matrix.

It is not a guess. `apps/worker/src/shared/observability/metrics.registry.ts` says so in its own header:

> *« **Non couvert, et dit franchement :** profondeur de file, taux d'échec et DLQ ne sont pas exposés. Ils demandent
> d'instrumenter les processeurs BullMQ un par un ; c'est un slice à part, pas un oubli. »*

## Step 2 — the finding still reproduces, and it is slightly wider than recorded

Measured on `main` at `6dad0d9`, before any edit:

1. **Zero queue series exist.** The worker registry contains `collectDefaultMetrics` output and nothing else. The API
   registry has an HTTP histogram and counter. Neither knows a queue exists.
2. **Three queues are registered on both sides** — `exports`, `notifications-email`, `imports` — by
   `apps/api/src/shared/queue/queue.module.ts` (producer) and `apps/worker/src/shared/queue/queue.module.ts`
   (consumer), and **three processors** consume them (`ExportsProcessor`, `ImportsProcessor`,
   `NotificationsEmailProcessor`).
3. **The queue-name constants are declared twice**, once per module, as two independent literal blocks with a comment
   in each pointing at the other. Nothing compares them. That is the R-26 shape — a declared invariant trusted because
   it is written down — and it is the reason a fourth queue can be added on one side and instrumented on neither.
4. **Job payloads carry `tenantId`** (`ExportJobPayload.tenantId`, and the same for imports). Any instrumentation that
   labels a series by job data leaks a tenant identifier onto an endpoint that is unauthenticated by construction.

## Design decisions, and why the obvious implementation is wrong

**D1 — depth is collected in the worker, not in the API.** Both processes hold a BullMQ connection to all three queues,
so both *could* report depth. Two scrape sources for one number is `DNC-01`'s shape (one dataset, two totals) applied
to operations: a graph that disagrees with itself teaches operators to distrust the graph. Depth, being a property of
the queue rather than of the process, is reported by exactly one process — the worker — and the API keeps only what is
a property of itself (its HTTP surface).

**D2 — "DLQ" is not claimed, because BullMQ has none.** BullMQ has no dead-letter queue; a job that exhausts
`attempts` stays in the `failed` set. Exposing a series called `dlq_depth` would be a metric that describes a mechanism
this system does not have — the *"UI exists ⇒ feature delivered"* move at the observability layer. What is exposed is
what exists: the `failed` set size, and a counter that separates a **retryable** failure from a **terminal** one
(`attemptsMade >= attempts`), which is the operational question a DLQ panel is actually asked.

**D3 — cardinality is the security control, again.** `/metrics` is unauthenticated by construction (`S-E02-13` design
record). Labels are therefore drawn from a **closed set known at build time** — the queue name and the job name — and
never from job data, job id, or an error message. A job id is unbounded cardinality *and*, for these payloads, one
join away from a tenant. G-TENANT is discharged by a test that drives the label function with a job carrying
`tenantId`, `exportJobId` and a cuid, and asserts none of the three reaches the exposition.

**D4 — the depth collector must not be able to wedge the worker.** Depth is read by a prom-client `collect()` callback
that calls `getJobCounts()` against Redis at scrape time. A Redis stall must degrade to a stale or missing data point,
never to a hung scrape or an unhandled rejection: the collector is time-bounded and swallows its own errors, the same
rule `S-E02-13`'s HTTP middleware follows.

**D5 — the drift guard is the durable half of the slice.** Metrics that exist today and silently miss the fourth queue
added next quarter are worth less than a gate. `scripts/observability-check.js` gains a check that the set of
**instrumented** queues equals the set of **registered** queues, read from both modules, and fails in **both**
directions — an uninstrumented queue and an instrumented queue nobody registers. This is also what finally compares the
two constant blocks that D-Step-2-3 found nobody compares.

## Acceptance criteria

1. The worker exposition carries, for **every** registered queue, the depth of each BullMQ state
   (`waiting`, `active`, `delayed`, `failed`, `completed`, `paused`), labelled by queue name only.
2. The worker exposition carries a job-outcome counter (`completed` / `failed`, with retryable vs terminal
   distinguished) and a job-duration histogram, labelled by queue and job name only.
3. **No label carries an identifier.** Proven by driving the instrumentation with a real job payload containing
   `tenantId` and a cuid, then asserting the rendered exposition contains neither.
4. The metric names are reachable in a dashboard: `infra/grafana/dashboards/pilotage-slo.json` gains queue panels, and
   the existing coherence check (*every dashboard query names a metric the applications really register*) passes over
   them — so a renamed metric breaks the gate rather than the dashboard.
5. **Instrumented queues ≡ registered queues**, enforced by `scripts/observability-check.js`, exercised in **both**
   directions against synthetic inputs.
6. A Redis failure at scrape time yields a served exposition, not a hung or 500 response. Executed.
7. No bypass flag, no `SKIP_*`/`ALLOW_*` env var, and a check that cannot run **fails** rather than skips (DNC-08,
   DNC-10). Locked by test.
8. The full `scripts/ci-gate.sh` passes, and its verdict line is reported (R-23) — not a selection of stages.

## Out of scope, stated plainly

- **Alert rules and SLO thresholds remain undefined.** What "too deep" or "too slow" means is a product decision about
  what good looks like, not a build. `PF-56` stays open for that reason among others.
- **Job-level tracing is not added.** There is no official OpenTelemetry BullMQ instrumentation; hand-rolling span
  propagation through job data is a separate slice with its own G-TENANT argument (job data crosses a process boundary
  through Redis).
- **Nothing is ingested.** As with `S-E02-13`/`S-E02-14`/`S-E02-15`, the exposition is proven to *serve* the series;
  whether a Prometheus scrape lands is proven only if this run's evidence rebuilds the `obs` profile and observes it.
  Whichever of the two happened is stated in the evidence, not implied.
- **The API is not given queue depth**, by D1. If an operator wants producer-side confirmation, that is a second
  decision, not an omission.

## DNC rules that apply

- `DNC-01` — one number, one source. Depth is reported by one process (D1).
- `DNC-06` — never describe a mechanism the system does not have (D2: no DLQ series).
- `DNC-08` / `DNC-10` — a check that cannot run fails; no flag turns it off (AC-7).

## 3 — Label safety: the closed set, and where each member comes from (D3, G-TENANT)

New module `apps/worker/src/shared/observability/queue-metrics.ts` owns both the metrics and the label functions.

```
INSTRUMENTED_QUEUES  : readonly string[]   // the three names, exported for the gate (§8)
JOB_STATES           : readonly string[]   // the six BullMQ states
JOB_OUTCOMES         : readonly string[]   // completed | failed_retryable | failed_terminal
OTHER_JOB            = '<other>'           // mirrors UNMATCHED_ROUTE = '<unmatched>' in the API registry
JOB_NAMES_BY_QUEUE   : Record<queue, readonly string[]>
jobLabel(queue, name): string              // pure; returns name iff it is in the queue's set, else OTHER_JOB
```

`jobLabel` is **the security control**, and it is a whitelist, not a sanitiser. A cuid job name is lowercase
alphanumeric and would survive any plausible character-class filter; only membership in a build-time set stops it.
Nothing derived from `job.data`, `job.id`, or an error message may ever reach a label — not as a value, not as a
label *name*, not in a help string.

**Where each allow-list comes from — say it in the file, do not silently copy** (R-26: a fourth un-compared literal
block is the defect this slice exists to close, and re-creating it here would be the finding writing itself):

- `exports` — **compared, not copied.** A test asserts `JOB_NAMES_BY_QUEUE.exports` equals `Object.keys(GENERATORS)`
  from `exports.processor.ts`, so adding a generator without instrumenting it fails.
- `notifications-email` — **compared** against `Object.values(NotificationKind)` from `@prisma/client` if that import
  is acceptable in the spec (it is: the worker already depends on `@prisma/client` and `prisma generate` is stage 1 of
  the gate). If measurement shows the import is not viable, hand-declare it **and state in the header that this one
  set is hand-held, and what the consequence is** (an un-listed kind is bucketed as `<other>`, never leaked).
- `imports` — hand-declared `['apply', 'rollback']` with a comment naming the producer file and lines; the producer
  lives in `apps/api` and cannot be imported from the worker. Same honesty rule: say it is hand-held.

An un-listed job name is a **loss of detail** (`<other>`), never a leak. That asymmetry is the point, and it is why
the allow-list not being perfectly synchronised is survivable while a missing whitelist is not.

## 4 — The depth collector (D4)

Registered as prom-client's `collect()` callback on the depth gauge, so it runs at scrape time and nowhere else.

Required properties, all four load-bearing:

1. **Time-bounded.** `Promise.race` against a timer of ~2 s (declare the constant, do not inline the number). The
   timer must be **cleared on the winning path** or the worker keeps a handle alive per scrape.
2. **Swallows its own errors.** `try/catch` around everything, plus a `.catch()` on the raced promise so a late
   rejection cannot surface as an unhandled rejection after the race resolved. Same rule as
   `metrics.middleware.ts:50` — *une panne d'instrumentation ne doit jamais dégrader le service*.
3. **Degrades to stale, not to blank.** On timeout or error, leave the gauge's previous samples in place and return.
   Do **not** `reset()` — an operator reading zero depth during a Redis outage is worse than one reading a stale
   number, because zero is a value they will act on.
4. **No Redis at import time.** The module must open no connection and start no timer when it is merely `require`d.
   This is not hygiene: `scripts/observability-check.js` **renders the worker registry in-process** (`readExposedMetricNames`,
   line 714) to read its `# TYPE` lines, so an import-time connection or an unregistered-source collector that
   dials Redis would hang or fail the gate itself.

The collector reads from a **structural** source type, not from `bullmq`'s `Queue`, so tests can drive it with plain
objects — the reason `RouteLabelSource` exists in the API registry:

```
interface QueueDepthSource { readonly queue: string; getJobCounts(...states): Promise<Record<string, number>> }
registerQueueDepthSources(sources: readonly QueueDepthSource[]): void   // idempotent; replaces, never appends twice
```

With zero sources registered the collector is a no-op that resolves immediately — that is the state the gate renders in.

## 5 — Wiring into the worker

- New `apps/worker/src/shared/observability/observability.module.ts` — a Nest module whose provider (`OnModuleInit`)
  injects the three queues with `@InjectQueue(QUEUE_EXPORTS)` etc. (the existing `QueueModule` already
  `exports: [BullModule]`, so no queue-module edit is needed) and calls `registerQueueDepthSources`.
- Import it in `apps/worker/src/app.module.ts` **after** `QueueModule`.
- **Outcome + duration** are recorded with `@OnWorkerEvent('completed')` / `@OnWorkerEvent('failed')` from
  `@nestjs/bullmq`, added to each of the three processor classes, each handler a two-line call into a shared
  `observeJobOutcome(job, outcome)` helper in `queue-metrics.ts`. The handlers must be individually
  exception-proof — a throw inside a worker event handler is an unhandled rejection in the worker process.
- **Retryable vs terminal** (D2): terminal iff `job.attemptsMade >= (job.opts?.attempts ?? 1)`. Compute it in a pure
  exported function, `isTerminalFailure(attemptsMade, attempts)`, so the boundary is testable without BullMQ
  (`attempts` undefined, `attempts: 1`, `attemptsMade` 1 of 3, 3 of 3).
- **Duration**: `job.finishedOn - job.processedOn`, in seconds, guarded — both are optional in BullMQ's types, and a
  missing one means *no observation*, not `0` (a zero-second bucket is a lie that shifts the p95).

## 8 — The gate: check 9 in `scripts/observability-check.js` (D5, AC-5)

**Extend the existing script — do not add a new one.** Same subject, and extending is what keeps `ci-gate.sh` and
`ci.yml` in step (S-E02-2 AC-4); a new stage would be two more places to drift.

**Two new readers in the I/O half** (both return `null` on any failure; `null` is a problem, never a skip):

- `readInstrumentedQueues()` — `INSTRUMENTED_QUEUES` from `apps/worker/dist/shared/observability/queue-metrics.js`.
- `readRegisteredQueues()` — requires **both** built queue modules
  (`apps/api/dist/shared/queue/queue.module.js`, `apps/worker/dist/shared/queue/queue.module.js`) and takes every
  export whose key matches `/^QUEUE_[A-Z0-9_]+$/` and whose value is a string. Returns `{ api: [...], worker: [...] }`.
  Reading the module's **exports** rather than grepping its source is R-26 rule (a), and it means **neither
  `queue.module.ts` has to be edited** — which keeps this diff out of PF-80's blast radius. Measure the require:
  it must not open a Redis connection or leave a handle (`BullModule.forRoot`/`registerQueue` build metadata; the
  connection is made by Nest DI at bootstrap, not at import). If measurement contradicts that, fall back to a
  dedicated import-free constants module and **write down in the header which one you are reading and why**.

**Pure evaluation in `evaluateObservability`**, from `input.instrumentedQueues` and `input.registeredQueues`:

1. Either input `null`/absent → problem containing `That is a failure, not a skip`.
2. Either side's registered set smaller than a floor of 3 → problem. An empty or truncated read must not pass
   vacuously (this is the same escape-by-omission rule checks 4/6/8 each had to add).
3. `api` set ≠ `worker` set → problem naming both sides and the two files. *This is the assertion that finally
   compares the two constant blocks nobody compares.*
4. `registered \ instrumented` ≠ ∅ → problem naming each queue: registered on both sides and instrumented by
   nothing, so it is invisible on the dashboard while looking healthy.
5. `instrumented \ registered` ≠ ∅ → problem naming each queue: instrumented but registered by no module, so the
   series is permanently zero and reads as an idle queue.
6. On success, a `note` naming the queues compared, so a pass is readable rather than merely silent.

Wire the collected values into `collectFromRepo()`'s returned object. No new `run_stage` in `ci-gate.sh` and no new
step in `ci.yml` — but **do update the stage-9 comment in both files** to say the stage now also holds
instrumented ≡ registered, because those comments are what the next reader trusts.

## 11 — Traps measured in this repository (each one has already cost a run somewhere)

1. **The gate renders the registry in-process.** `readExposedMetricNames` calls `await mod.registry.metrics()` on the
   built worker registry. Anything the depth collector does at scrape time, `scripts/observability-check.js` does to
   itself. Import-time Redis, an unbounded wait, or a rejection = the gate hangs or fails on a healthy repository.
2. **A near-identical name already appears in the guard spec.** `observability-gate.spec.ts:352` uses
   `pilotage_queue_depth_total` as its example of *a metric no application registers*. That test drives **synthetic**
   `exposedMetrics`, so it stays valid — but the reader will trip over the resemblance. Either leave it and add a
   one-line comment saying the fixture is synthetic and the real metric is `pilotage_queue_depth` (no `_total`), or
   rename the fixture's example to something plainly non-existent. Do not let the two look like the same metric.
3. **`version-server.ts` turns a registry rejection into a 500.** So "the collector swallows its errors" is not
   defence in depth — it is the only thing standing between a Redis blip and a scrape endpoint that reports the
   worker as broken. T-D4-3 is the case that proves it.
4. **No `@OnWorkerEvent` exists in the worker yet.** There is no local precedent to copy; check the `@nestjs/bullmq`
   v10 signature before writing three of them, and make each handler exception-proof.
5. **Worker jest matches `<rootDir>/src/**/*.spec.ts` only** (`apps/worker/jest.config.js`) — a spec placed anywhere
   else runs nowhere and reports as coverage that does not exist.
6. **`apps/api/dist` is already a precondition** of check 6, so requiring the API's built queue module in §8 adds no
   new failure mode — the same absent-build path already exists and already fails loudly.
