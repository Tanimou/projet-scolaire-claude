## Why

`node scripts/schema-drift-check.js` printed, on this machine:

> ✗ no PostgreSQL server answered at the resolved address. Start the local stack — `docker compose …` — and re-run.
> The route back to green is starting a database, never editing code (ADR-027)

That sentence is **false here**, and it is the sentence that parked `S-E01-2b` (RLS), `VAL-03` and `TOOL-13`'s drift
half for **eight consecutive runs**. Measured 2026-08-13 (run 50), all three independently:

1. `127.0.0.1:5432` **accepts** a TCP connection in 3 ms (`5433` refuses in 9 ms — nothing has listened there for
   weeks; `TOOL-22` already repaired the address half).
2. `C:\Program Files\PostgreSQL\15\bin\psql.exe` **exists**, and that directory **is** in the persisted Windows user
   PATH — but no running process sees it, because every one of them inherited an older environment block, so
   `spawnSync('psql', …)` answers `ENOENT`.
3. Executed, exit 0:
   `PGPASSWORD=… "/c/Program Files/PostgreSQL/15/bin/psql.exe" -h 127.0.0.1 -p 5432 -U pilotage -d pilotage -A -t -c "select current_database(), version();"`
   → `pilotage|PostgreSQL 15.3, compiled by Visual C++ build 1914, 64-bit`. **Route B is fully functional.** The only
   thing missing was DISCOVERY of the binary.

## The two defects — one seam, both P1

**TOOL-23 — the client was resolved only through the inherited PATH.** `schema-drift-check.js` did `run('psql', …)`;
`restore-drill.js` did the same at four sites. Worse than the miss: both files recorded *"there is no host `psql`
here"* as a **fact about the host**, in comments a reader would trust.

**TOOL-24 — the verdict contradicted evidence the run already held.** `check()`'s reachability catch set
`state.serverReachable = false` **unconditionally**, and only then inspected `error.routeFailure`. `routeFailure`
means *"no CLIENT could run the query"*; it says nothing about whether a server answered. The script already owns the
instrument that separates the two — the three-state TCP preflight — and printed the opposite of what it measured. We
knew the preflight had not returned `refused`, because `query()` only descends to `psql` when it has not.

## What shipped

- **`scripts/lib/postgres-client-path.js`** — one module, mirroring `scripts/lib/default-database-url.js` (the
  `TOOL-22` precedent, which shipped without an ADR). Ladder: **inherited PATH** first, returning the **bare name** so a
  checkout where this already works spawns exactly today's argv; then **well-known install roots**, Windows *and*
  POSIX, highest major first; then unavailable, naming everything it searched. Resolution is a **filesystem walk**, not
  a `--version` spawn.
- **A root qualifies only if it holds the whole client set.** Resolving each binary independently lets the drill dump
  with one major and restore with another, and `pg_restore` on a newer archive reports corruption on a healthy backup.
- **Numeric, filtered enumeration.** `C:\Program Files\PostgreSQL\` on this host holds `15` **and `psqlODBC`**;
  `['9','10','15'].sort()` puts `9` last. Both are fixture cases, because both would have selected the wrong directory.
- **`serverReachable` is `true | false | null`.** A `routeFailure` with a non-`refused` preflight leaves it **`null`** —
  absence of evidence — which `REQUIRED_EVIDENCE` reports as an extra `unknown` finding. `evaluateDrift` now **refuses**
  a non-boolean, non-null value, so the sentinel shortcut (`'unknown'`) cannot be taken later.
- **`ADR-027` amendment**, not a new ADR: it narrows `D3.1`'s prose, which is what made both verdicts print the same
  "start a database" remedy.

Route B was really attempted on the second run — its failure line reads
`psql: error: could not translate host name "schema-drift-gate.invalid" to address: Unknown host`, i.e. the discovered
binary ran. Before this slice it read `spawnSync psql ENOENT`.

## DNC-10, stated because it is the objection that parked TOOL-15 three times

**No environment variable and no CLI flag names a client binary.** A `PSQL_PATH`-style variable would let a caller
substitute the program a gate reaches its verdict with — a bypass wearing a different hat. `parseArgs` stays exactly
`['--help','-h']`. The module reads `PATH` and `PATHEXT` and nothing else — the two variables `spawnSync` already
consults to perform today's bare-name lookup — and the Windows roots are **fixed literals**, never the program-files
variable, which *is* caller-settable. Because the two consumer specs scan each script's own text, the new module
carries the **mirror ratchet** in `postgres-client-path-gate.spec.ts`: set-equality on its env reads, no `process.env[`,
none of the forbidden tokens, and a call-site extraction proving neither production site passes the injectable
`options` seam.

## Explicitly out of scope

Route C (`docker exec`) is untouched (`TOOL-19`: the engine is wedged on this host). No RLS, no end-to-end restore
drill, the skipped-count ratchet stays disarmed, and **the drift check was not run end-to-end against the live
`127.0.0.1:5432`** — the first such run creates and drops a real database on the operator's server and belongs to
`S-E01-2b` / `VAL-03`. Getting the route reachable is the deliverable; using it is the next story.
