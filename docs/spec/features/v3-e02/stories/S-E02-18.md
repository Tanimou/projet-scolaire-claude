## 4. Acceptance criteria

### AC-1 (`PF-106`) — nothing executes the wiring

`grep -rn 'OnWorkerEvent' --include=*.spec.ts apps/` returns **zero** hits today, and
`QueueDepthCollector.onModuleInit` has no reference outside its own module. All 39 `S-E02-17` tests
call `observeJobCompleted` / `observeJobFailed` / `registerQueueDepthSources` **directly** — they
prove the helpers and never the seam. So dropping `ObservabilityModule` from `app.module.ts`,
drifting an `@InjectQueue` token, or misspelling an event name ships **green on every gate** while
panels 6–8 render "No data" for ever, indistinguishable from an idle system.

Add **`apps/worker/src/shared/observability/queue-depth.collector.spec.ts`** containing:

1. **The collector seam.** `Test.createTestingModule({ providers: [QueueDepthCollector, …stubs] })`
   where each stub is `{ provide: getQueueToken(name), useValue: { name, getJobCounts: async () => counts } }`
   for each of `INSTRUMENTED_QUEUES`. `getQueueToken` is exported by `@nestjs/bullmq` and returns
   `BullQueue_<name>` (verified). **Do not import `QueueModule` or `ObservabilityModule` here** —
   `BullModule.forRoot` in the test process is a Redis handle and jest would report an open handle;
   providing the three tokens directly is the whole point of the seam.
   - `await moduleRef.init()` (this is what invokes `onModuleInit`; `compile()` alone does not).
   - Assert `queueDepthSourceCount() === INSTRUMENTED_QUEUES.length` — **one depth source bound per
     `INSTRUMENTED_QUEUES` entry**.
   - Render `await registry.metrics()` and assert a `pilotage_queue_depth{queue="…",state="…"}`
     sample **equals the number the stub returned** — parse the sample value out of the exposition
     (reuse the `sampleValue`-style parser already in `queue-metrics.spec.ts`; prom-client renders
     the registry's default labels **after** the metric's own, so a `toContain` on a formatted line
     asserts prom-client's formatter, not the exposition). Use a distinctive value (e.g. `41`) so the
     assertion cannot pass against a zero-seeded sample or against a helper's return value.
2. **The three processor seams.** For each of `ExportsProcessor`, `ImportsProcessor`,
   `NotificationsEmailProcessor`: construct the class (its constructor dependencies may be plain
   stubs — the event handlers touch none of them), **invoke the decorated method** (`onCompleted`,
   `onFailed`, and the new `onStalled` from AC-4) with a synthetic job, render the registry, and
   assert the rendered `queue="…"` label is that processor's **own** queue. This is the assertion
   that catches `observeJobCompleted(QUEUE_EXPORTS, job)` pasted inside `ImportsProcessor`.
3. **The event-name metadata.** `@nestjs/bullmq`'s `OnWorkerEvent` is `SetMetadata('bullmq:worker_events_metadata', { eventName })`
   on the **method** (verified in `apps/worker/node_modules/@nestjs/bullmq/dist/decorators/on-worker-event.decorator.js`
   and `dist/bull.constants.js`). Read it with
   `Reflect.getMetadata('bullmq:worker_events_metadata', ExportsProcessor.prototype.onCompleted)`
   and assert `eventName === 'completed'` (idem `'failed'`, `'stalled'`). **A misspelled `'complete'`,
   which BullMQ never emits, must make this red.** Prefer importing the key from `@nestjs/bullmq`'s
   constants if it is exported at the package root; otherwise inline the literal with a comment
   naming the file it was read from.
4. **The module import.** Assert `Reflect.getMetadata('imports', AppModule)` **contains**
   `ObservabilityModule`. Requiring `app.module.ts` builds metadata only — it opens no connection
   (the same property `scripts/observability-check.js` `readRegisteredQueues` already relies on and
   documented as measured).
5. **The negatives, executed — not asserted.** Two halves, both required:
   - **Durable, in-spec companion cases**, mirroring the `DNC-10` "the guard can actually fail" pair
     already in `observability-gate.spec.ts`: extract the two predicates as small local functions
     (`importsObservability(moduleClass)` and `workerEventName(proto, method)`), then feed each a
     **throw-away** subject — a `@Module({ imports: [] })` class, and a class whose method carries
     `@OnWorkerEvent('complete')` — and assert the predicate reports the defect. A guard never shown
     to fire is a guard we hope works.
   - **A one-off measured red, recorded in the PR/PROGRESS evidence.** Physically remove
     `ObservabilityModule` from `apps/worker/src/app.module.ts`, run the spec, record the failing
     output; restore. Do the same for one processor's `@OnWorkerEvent('completed')`. **Both reds must
     be executed and pasted into the evidence.** The diff that lands restores both.

### AC-2 (`PF-106` residual) — partial binding is silent

`QueueDepthCollector.onModuleInit` filters with `typeof queue.getJobCounts === 'function'` and drops
a failing queue with only a `logger.log` count **nobody compares against `INSTRUMENTED_QUEUES.length`**,
while `pilotage_queue_depth_collection_failures_total` is zero-seeded for that queue and therefore
renders it as *healthy*. Make a partial binding observable:

- **In the exposition** — add **one** new gauge in `queue-metrics.ts`,
  `pilotage_queue_depth_bound{queue}`, value `1` when a depth source is bound for that queue and `0`
  when it is not. Written by **exactly one implementation**: inside `registerQueueDepthSources`,
  which already knows both `INSTRUMENTED_QUEUES` and the sources it was handed. It must **reset every
  instrumented queue to `0` and then set `1` for each bound one**, so the function stays idempotent
  and "replaces, never stacks" (its existing contract). Zero-seed all of `INSTRUMENTED_QUEUES` at
  import, exactly as the failure counter does, so the shortfall is legible with no Redis.
  Cardinality cost: **+3 series**; update the cardinality budget paragraph in the file header
  (currently "≈ 312 séries") to the new total rather than leaving a number that is now false.
- **In the log** — the collector's `logger.log` becomes a `logger.error` **naming the missing
  queues** whenever `sources.length < INSTRUMENTED_QUEUES.length`, keeping the existing success
  `logger.log` for the healthy path. French, matching the file.
- **Asserted by test** — in `queue-depth.collector.spec.ts`, build the module with one stub whose
  `getJobCounts` is **not a function**, `await moduleRef.init()`, and assert both
  `queueDepthSourceCount() === INSTRUMENTED_QUEUES.length - 1` **and** that the rendered exposition
  carries `pilotage_queue_depth_bound{queue="<the dropped one>"} 0`.

### AC-3 (`PF-105`) — rule 6 is a tautology

In `scripts/observability-check.js`, `readInstrumentedQueues` (near line 965) scrapes `rendered` from
`^pilotage_queue_[a-z_]*\{[^}]*queue="([^"]*)"`. In the gate's own process the **only** queue-labelled
samples that exist are the ones `queue-metrics.ts:319` zero-seeds from `INSTRUMENTED_QUEUES`
(`for (const queue of INSTRUMENTED_QUEUES) queueDepthCollectionFailures.inc({ queue }, 0)`), so
`rendered` is *derived from* `declared` and rule 6 (near line 751) reduces to `A ≡ A`.

Make `rendered` a value **only a real write path can produce**:

- Before rendering, for **each declared queue**: register a **synthetic depth source** through the
  module's own `registerQueueDepthSources` export (a plain object returning a fixed counts record —
  the seam `QueueDepthSource` exists for), **and** call the module's own `observeJobCompleted` with
  an **allow-listed** job name for that queue (`JOB_NAMES_BY_QUEUE` is exported; use its first entry,
  so the `<other>` sentinel cannot be what proves the label).
- Then render, and compute `rendered` as the queue label values carried by **both**
  `pilotage_queue_depth` **and** `pilotage_queue_jobs_total` — the *intersection*, not the union.
  Neither family is zero-seeded, so a declared queue with no write path appears in neither.
- **Correct the header comment** of `readInstrumentedQueues`, which today claims the rendered half
  confirms the declaration against *"what the process really publishes"*. Before this change that
  sentence was false; after it, say precisely what is driven (a synthetic depth source + one
  allow-listed completion per declared queue) and what that does and does not prove — it proves the
  **write path exists and is reachable**, not that production traffic uses it.
- Rules 3/4/5 are **real and unaffected** (they read the resolved `BullQueue_*` tokens). Do not touch
  them. Do not widen `rendered` into a union with anything.
- **EXECUTE the negative.** Add a fourth queue name to `INSTRUMENTED_QUEUES` in a throw-away copy of
  the built module (or a scratch tree), run `node scripts/observability-check.js`, and record that it
  **exits non-zero and NAMES the queue**. Rule 6's message must name it — extend the existing message
  so the missing set is printed, not only the two full lists. Paste the output into the evidence.
- Add fixture cases to `observability-gate.spec.ts` alongside T15c/T15d driving
  `evaluateObservability` with `{ declared: [a,b,c], rendered: [a,b] }` and asserting the problem text
  contains the missing name.

### AC-4 (`PF-104`) — a job that fails by stalling reaches no counter

Verified against the installed BullMQ, and these three facts are the justification — write them into
`queue-metrics.ts` so the next reader does not re-derive them:

- `dist/cjs/classes/worker.js:659` is the **only** `emit('failed', job, err)`, reached only from
  `handleFailed` — i.e. the processor threw.
- `worker.js:908` emits `('stalled', jobId, 'active')` for **every** id returned by
  `moveStalledJobsToWait`.
- The Lua script `moveStalledJobsToWait-8` lines **154–162** move a job past `maxStalledCount` into
  the **FAILED set** with reason `'job stalled more than allowable limit'` **and still emit only
  `'stalled'`**.

So an OOM-killed or SIGKILLed worker leaves panel 6 flat at zero while
`pilotage_queue_depth{state="failed"}` climbs — the green-silent-false shape this epic exists to close.

- Add `@OnWorkerEvent('stalled')` to **all three** processors, each a **one-line** call site matching
  the existing `observeJobCompleted` / `observeJobFailed` shape (DNC-01: **one** write implementation
  in `queue-metrics.ts`, three one-line call sites).
- Record `pilotage_queue_stalled_total{queue}` — a **SEPARATE counter**. **NOT** a fourth `outcome`
  value on `pilotage_queue_jobs_total`, and **NOT** labelled by `job`. Both reasons must be written
  into `queue-metrics.ts`, because both are measured, not stylistic:
  1. the event carries a **bare `jobId`** with no job name — there is nothing to put in a `job` label
     that is not an identifier (and identifiers are forbidden: G-TENANT);
  2. the event **does not distinguish** "moved back to wait" from "moved to failed" — folding it into
     the `outcome` enum would assert a **terminality the event cannot support**, next to
     `failed_retryable`/`failed_terminal`, whose whole value is that they *are* terminal-accurate.
- The write implementation is `observeJobStalled(queue: string): void` — total (try/catch, like
  `observeJobOutcome`; a throw in a BullMQ listener is an uncaught rejection in the worker process),
  applying the existing `queueLabel()` so an unknown queue collapses to the `<other>` sentinel.
  **Its signature takes no job id at all** — the handler receives one and deliberately drops it.
- **Do not zero-seed** this counter. It is empty until the first stall; that is honest and it keeps
  AC-3's `rendered` intersection clean.
- **Plot it** so the signal is legible: a **second target on panel 6** (which is exactly the panel
  that under-reports today), `sum by (queue) (rate(pilotage_queue_stalled_total[5m]))`, legend
  `{{queue}} · bloqués (stalled)`. Update panel 6's **title and description** to state that a stalled
  job is a *third* shape — a worker that died or lost its lock, never routed through the `failed`
  event — and say that the series does not distinguish requeued from failed-out. **DNC-06**: every
  sentence in that description must be true of an expr in the same file.
- Add the paragraph to `queue-metrics.ts` stating that **BullMQ's `failed` event does not cover
  stalled jobs**, citing the two emit sites and the Lua branch by file and line.

### AC-6 (`PF-108`) — a gauge summed across replicas

`infra/grafana/dashboards/pilotage-slo.json:85` uses `sum by (queue, state) (pilotage_queue_depth)`.

absolute number and `docker compose up --scale worker=2` **doubles every line**.

- Change to `max by (queue, state) (pilotage_queue_depth)`.
- Add a description line saying **why** the gauge aggregates with `max` while the counters beside it
  aggregate with `sum` (a counter `rate()` **is** additive across replicas; an absolute gauge of a
  shared resource is not). This is `ADR-028` D1's "one number, two sources" arriving one dimension

- **Panels 6–8 are CORRECT as written. Do not touch their exprs.**
- **Add a gate rule that catches the class, not the line.** In `scripts/observability-check.js`:

    the **type** as well (`^# TYPE (\S+) (\S+)$`) and surface a `input.exposedMetricTypes` map

  - Inside check 6, for every dashboard `expr`, fail when a metric family whose declared type is
    **exactly `gauge`** appears as the direct argument of a `sum(...)` / `sum by (...) (...)` /
    `sum without (...) (...)` aggregation. Resolve names through the existing `metricNamesInExpr` +

    (declared `counter`) do **not** trip it. `nodejs_eventloop_lag_p99_seconds` on panel 4 is a gauge

  - **Fail closed (DNC-08)**: if the type map is missing or empty, that is a **failure**, not a skip —

  - Prove the rule both ways in `observability-gate.spec.ts`: a fixture summing a gauge → problem
