## 4. The rule for axis 4 — verified, and stated as the implementer must apply it

### 4.1 The rule

> **When `scope.studentIds` is an EXPLICIT id set (parent / teacher / student-self), that set is already the
> authority and is already tenant-keyed, so intersecting it with a *heuristic* "biggest school" adds no
> security and manufactures the contradiction. When `scope.studentIds === null` (admin, unrestricted), the
> school context is a deliberate working scope and MUST be preserved.**
>
> **Therefore: the `schoolId` filter applies to the UNRESTRICTED path only.**

The proposed rule was checked against the source and **is adopted**, with one refinement the implementer must
not miss (§4.3). `ADR-076` must state the check, not just the conclusion:

- *Does removing `schoolId` widen beyond the tenant?* **No.** `tenantId: me.tenantId` stays in the `where`,
  and every branch of `scopeForUser` is itself filtered on `user.tenantId` (§2.1). The widening is bounded
  **twice**, independently.
- *Does it widen beyond what the caller may see?* **No.** For the explicit-set path the result is exactly
  `id: { in: scope.studentIds }` ∩ `tenantId` — the same predicate `canAccessStudent` uses to authorise the
  detail page. **That identity is the whole point:** the list and the detail page become two projections of
  one predicate.
- *Does it widen the ADMIN path?* **No** — that branch is untouched. `AC-3` proves it.
- *Does it widen the TEACHER path across schools?* **Yes, and correctly.** A teacher's set is derived from
  their own `TeachingAssignment` rows; a teacher assigned in two schools of one tenant should see both
  rosters. Today the biggest-school filter silently truncates that, which is the same defect wearing a
  teacher's badge. Call this out in `ADR-076` under **G-PORTAL**; do not treat it as collateral.
- *Does it widen the STUDENT-SELF path?* **No** — that set holds exactly one id, their own.

### 4.2 The edit

`apps/api/src/modules/students/students.controller.ts:193-196`. **One condition, not two.** Fold the school
key into the *same* ternary that already discriminates the sentinel, so there is a single place where the
distinction is made and no second predicate to drift:

```ts
const where: Prisma.StudentWhereInput = {
  tenantId: me.tenantId,
  // S-E03-3d / ADR-076 — le filtre école s'applique à la SEULE branche NON
  // RESTREINTE. Un jeu d'ids EXPLICITE (parent / teacher / student-self) est
  // DÉJÀ l'autorité et DÉJÀ clos sur `tenantId` ; l'intersecter avec « l'école
  // du tenant qui a le plus d'élèves » (`school-context.service.ts:104-129`)
  // n'ajoute AUCUNE sécurité et FABRIQUE la contradiction PF-356 : la liste
  // rend vide pendant que `GET /students/:id` rend l'enfant en entier.
  // Même principe que `canonicalYearBySchool` seize lignes plus bas.
  ...(scope.studentIds === null ? { schoolId } : { id: { in: scope.studentIds } }),
  ...(status ? { status } : {}),
  ...searchClause,
};
```

**Everything else in the handler is unchanged**, including the `AND` intersection of caller filters
(`ADR-065 §D5`) and the fact that `count` receives the *same* `where` object.

### 4.3 The refinement the implementer must not miss: `[]` is an explicit set

`scope.studentIds === []` is the **DENY** (`ADR-065 §D5`) and yields `id: { in: [] }`, which already matches
nothing. Under the single-ternary form above, the deny branch also loses `schoolId`. **That is intentional and
harmless** — an impossible predicate is impossible with or without a school key — and it is what keeps the
rule to one condition. **State it in `ADR-076`.**

**It also breaks an existing assertion, which must be updated deliberately and never deleted:**
`apps/api/src/modules/students/students-list-teacher-scope.spec.ts:229-237` currently asserts

```ts
expect(whereOf()).toMatchObject({ tenantId: TENANT, schoolId: SCHOOL, id: { in: [] } });
```

Under the new rule that case must become `expect(whereOf()).not.toHaveProperty('schoolId')` while keeping
`id: { in: [] }` and keeping `expect(count).toHaveBeenCalledWith({ where: whereOf() })`. **Do not weaken the
case to `toMatchObject` without the `schoolId` key** — a `toMatchObject` that simply omits a key proves
nothing about its absence. Record the change in the PR body as a *stated behaviour change*, exactly as
`students-list-teacher-scope.spec.ts:155` did for `?status=`.

> **AC-1** In a multi-school tenant, `GET /students` and `GET /students/:id` agree about which children exist
> for one parent: a child the detail page renders is a child the list returns. Proven by a red-before /

apps/api/src/modules/students/students.controller.ts` and re-running: the case must fail on the
`schoolId` key. Record both runs.

> **AC-2** The widening is BOUNDED and proven bounded: the list is still constrained by `tenantId` AND by
> `scope.studentIds`; a foreign-tenant student and a same-tenant student the parent does not guard are BOTH
> still denied. This is the `PF-11` class — removing a key from a where-clause — so it needs an explicit
> negative test, not an argument.

*Proof.* Two cases, both asserting on the captured `where`:

2. A same-tenant non-guarded id is **not** in `where.id.in`, and a foreign-tenant id is excluded by

*Proof.* `build(null)` → assert `where.schoolId === SCHOOL` **and** `where` has no `id` key. This is the
existing `:248` case extended with the positive `schoolId` assertion it never made. It must be **green before
and after** — an AC-3 that goes red-before means the edit widened the admin path and the slice is wrong.

> **AC-4** A one-way ratchet asserts the rule cannot silently re-diverge: no parent-reachable student read may
> intersect `SchoolContextService.forUser`'s `schoolId` with an ABAC id set. Ship it with a genuine RED-BEFORE
> against `origin/main` sources and an anti-vacuity floor (a ratchet that matches nothing must FAIL, not pass).

*Proof.* New file `apps/api/src/shared/quality/parent-school-scope-gate.spec.ts`, modelled on
`academic-year-resolution-gate.spec.ts` (walk-derived inventory, **no hand-written path list** — this repo has

rule, stated on **form**:

> A Prisma **read** on `student` whose `where` object literal carries **both** a bare `schoolId` shorthand
> **and** an id-set clause derived from `StudentAccessService` is a violator.

Required properties, each with its own assertion:
