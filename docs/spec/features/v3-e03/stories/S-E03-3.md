## 1. Why this slice

The audit observed **one seeded child** described as *"actively enrolled in 2nde A"* by the parent dashboard
and the child-detail page, and as *"no active enrolment"* by the children list and the « Ma famille » settings
tab. **Nothing is broken.** Each surface asks a *different question*, and every answer is locally correct.

That is the whole finding. `PF-12` is not a bad query — it is the **absence of a canonical one**, which is
precisely what `ADR-041 §D4` forbids: *"Portals import the predicate; they never re-derive it."*

It is simultaneously two do-not-copy patterns, and the diff's own reasoning must name both (G-DNC):

- **`DNC-01`** — a KPI diverging from its ledger. `children/page.tsx:109-124` counts "active classes" with one
  predicate while `:186` badges each card with the same predicate re-typed; the dashboard counts a third way.
- **`DNC-06`** — the interface promising more than the runtime delivers. `children/[id]/page.tsx:343` renders
  `StatusBadge label="Inscription active" tone="success"` over a row the runtime never checked was active.

### 2.4 Four corrections to the authoritative story — measured, load-bearing

**A. "Four parent surfaces" is six; nine sites carry the shapes.** §2.2. `children/[id]/report/page.tsx:166`
and `messages/new/page.tsx:37` are byte-equivalent re-derivations the story does not list, and three admin

**C. Admin is not "mostly untouched".** `B3` and `B4` are the *same endpoints* the admin portal reads, so

**D. The schema comment at `schema.prisma:669-670` is false, and the story inherited it.**
The comment reads *"A student can have at most one active enrollment per academic year. We enforce uniqueness
on (studentId, academicYearId) when status='active' via a partial unique index in migration SQL."*
**No migration creates it.** `grep -n unique apps/api/prisma/migrations/*/migration.sql` over `enrollment`
returns exactly one row — `0_baseline/migration.sql:1272`,
`CREATE UNIQUE INDEX "enrollment_student_id_class_section_id_academic_year_id_key"` — the plain three-column
index, which permits **two `active` rows for the same student in the same year in different class sections**.

Consequence for AC-1: the total order **must not assume** at-most-one-active-per-year. It must be total over
that case too. Consequence for the ledger: this is a new finding, `PF-361`, **recorded not fixed** —
`schema.prisma` and migrations are hard out of scope (§9).

## 3. The ruling — already made, do not re-open

`ADR-041 §D2`, row *Class roster*, verbatim:

> **Effective-dated as of today**, not "current" as a mutable attribute — *Removes the `PF-12`
> self-contradiction between child and enrollment views*

`ADR-041 §D4`: *"Definitions live in one module, not in each query. A single registry in `packages/contracts`,
each entry carrying id, definition, scope label and the predicate. Portals import the predicate; they never
re-derive it."*

**Therefore, and `ADR-072` records this verbatim:**

> A child is **actively enrolled** when they hold an `Enrollment` whose `status` is `active` **and** whose
> `academicYear` is the tenant's canonical active year as resolved by `resolveActiveAcademicYear`
> (`packages/contracts/src/academic-year/`, `ADR-070`). Where more than one such row exists, the canonical one
> is chosen by a **single total order stated once in the contract module** — never by the caller. Where none
> exists, the answer is **"not actively enrolled"**, and it is **never** softened by falling back to an
> arbitrary row.

Two consequences the ADR must state rather than let a later run discover:

1. **Numbers change in the UI on the day this lands.** A child whose only enrolment is `graduated` reads
   "Inscription active" today and reads honestly after. `ADR-041 §D3`: *"Some numbers will change in the UI on
   the day this lands. That is the point."*
2. **`ADR-070`'s residual `PF-328` is inherited, not solved.** With no "at most one active year" DB invariant
   — and, per §2.4.D, no "at most one active enrolment per year" invariant either — the canonical row is
   chosen **deterministically, not correctly**. The module docblock must say so, and must carry `ADR-041`'s
   `confirmed: false` posture, rather than appear stronger than the resolver it is built on.

## 5. Acceptance criteria

### AC-1 (G-TRUTH) — one contract module, mirroring `ADR-070`'s shape exactly

Create `packages/contracts/src/enrollment/` as `index.ts` re-exporting one implementation file, and re-export
it from `packages/contracts/src/index.ts` (which today lists `./academic-year`, `./enums`, `./audit`, `./dto`,
`./events`, `./release`, `./observability`, `./security`).

It exports **at minimum**:

1. **The Prisma predicate** for "actively enrolled", parameterised by `tenantId` and the canonical
   `academicYearId` — so server queries import it instead of spelling `{ status: 'active' }` inline. `tenantId`
   is **required in the type**, not merely in the options, exactly as `AcademicYearWhere` makes the
   `school-context.service.ts:32` leak inexpressible.
2. **The total order**, stated **once**, as an *array* (two separate objects do not break ties). It must be
   total **without assuming** at-most-one-active-row-per-year (§2.4.D). The tie-break of last resort is `id`,
   which is the primary key — the `ADR-070` precedent (`[{ startDate: 'desc' }, { id: 'desc' }]`).
   Nominate the leading key deliberately and justify it in the ADR: `enrolledAt desc` is what `B1`/`B2`/`B4`
   already use, so choosing it changes no currently-correct answer.
3. **`selectActiveEnrollment(rows, ctx)`** — a pure function over an **already-fetched** array, which is what
   the nine web surfaces consume. It must return the *absence* honestly; it must never fall back to `rows[0]`.
4. **A scope label** per `ADR-041 §D3`, so a surface can state what it is showing next to the number.

The docblock must record: the `PF-328` inheritance; the `PF-361` inheritance from §2.4.D; the
`confirmed: false` posture; and — as `resolve-academic-year.ts` does — **no `new Date(` and no `Date.now(`**
in the file (`hermetic-spec-writers-gate.spec.ts` exists; a default clock makes the branch untestable).

### AC-2 (G-TRUTH) — the server answers the question instead of shipping the ingredients

`B1`, `B2`, `B3`, `B4` and `B5` each carry an **explicit canonical field** — `activeEnrollment` plus its scope

**`B4` (`GET /students/:id`) keeps returning the full, unfiltered enrolment history.** The detail page's
history section is a legitimate consumer and truncating it is a regression. What changes is that the history

### AC-4 — RATCHET, MANDATORY (this is what closes a CLASS)

A one-way gate in the `apps/api/src/shared/quality/` family, same shape as
`academic-year-resolution-gate.spec.ts` and `student-authz-locality-gate.spec.ts`.

- **Parse, never grep** — `require('typescript')`, per `notification-tenant-scope-gate.spec.ts:35-41`.
- **Walk roots must include `apps/web/src`** — six of nine offending sites live there. The gate **reads** those
  files as source/AST from the API test tree; it does **not import** them, so no `rootDir`/TS6059 problem
  arises. `apps/web` has no unit runner (`project_web_has_no_unit_test_runner`) — **do not try to add one.**
  Roots: `apps/api/src`, `apps/web/src`, `apps/worker/src`, `packages/<pkg>/src`.
- **Use the shared `scripts/lib/walk-read.js` seam** (`mapWalkedFiles` / `maxVanishedFor` / `warnSkipped`),

  them produces a self-red that gets "fixed" by an exclusion, i.e. an allowlist in disguise.
- **The three rules**, applied outside the declaring module:
  1. an `enrollments`-shaped array indexed `[0]` used as an **activity claim**;
  2. a `.find()` / `.filter()` whose predicate tests `status === 'active'` **or**
     `academicYear.status === 'active'` over enrolments;
  3. a **student-anchored** Prisma `enrollment` read whose `where` spells `status: 'active'` literally instead
