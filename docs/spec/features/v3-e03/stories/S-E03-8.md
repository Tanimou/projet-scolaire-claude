## 1. Le défaut, mesuré en source le 2026-08-27

`PF-40` se lit comme un défaut d'*asynchronisme*. **Ce n'en est pas un.** Rien ici n'est asynchrone :
les événements arrivent en une seule prop, déjà résolue côté serveur. Les quatre mécanismes ci-dessous
sont **structurels et permanents**, et le mot « interim » de l'audit désigne en réalité le §1.4
(le patch d'hydratation React). Nommer correctement la cause est la moitié du remède.

### 1.1 (A1) Le prédicat « ce mois-ci » DIVERGE selon le portail, sur le même endpoint

Les trois portails lisent le **même** `GET /api/v1/calendar/events`. Ils ne posent pas la même question.

| Surface | Fichier:ligne | Prédicat « l'événement est-il dans le mois M ? » |
|---|---|---|
| admin | `apps/web/src/app/admin/calendar/CalendarManager.tsx:73-83` | `start = new Date(y, m, 1)` ; `end = new Date(y, m+1, 1)` ; garde **si et seulement si** `startsAt ∈ [start, end)`. **`endsAt` n'est jamais lu.** |
| parent + teacher | `apps/web/src/components/calendar/PortalCalendarView.tsx:218-226` | `start = new Date(y, m, 1)` ; `end = new Date(y, m+1, 0, 23,59,59)` ; garde si `startsAt <= end && endsAt >= start` — **CHEVAUCHEMENT**. |

**Conséquence mesurable :** un congé du 28 octobre au 10 novembre est « de novembre » pour un parent
et pour un enseignant, et **n'est pas de novembre** pour l'administrateur qui l'a saisi. C'est
littéralement le *« totals differ by role »* de l'audit, et la violation directe du contrat
*« shared effective date/year filters »*.

**Et le code admin se contredit LUI-MÊME.** `CalendarManager.tsx:250-261` construit `byDay` ainsi :

```
const startDay = s.getMonth() === month.getMonth() ? s.getDate() : 1;
const endDay   = en.getMonth() === month.getMonth() ? en.getDate() : daysInMonth;
```

Ces deux branches `: 1` et `: daysInMonth` n'existent **que** pour peindre un événement qui a commencé
*avant* le mois ou qui finit *après*. Le rendu de la grille admin est donc écrit **pour la sémantique
de chevauchement**. Mais son appelant (`monthEvents`, §1.1 ligne 1) a déjà éliminé exactement ces
événements-là : **les deux branches sont du code mort, rendu mort par le filtre situé au-dessus
d'elles.** L'admin possède déjà le rendu de la bonne réponse et se prive de la donnée qui l'alimente.

Deux écarts secondaires, à corriger par la même dérivation et non un par un :

* `PortalCalendarView` ferme le mois à `23:59:59` — il **perd les 999 dernières millisecondes** du mois.
  `CalendarManager` utilise un intervalle semi-ouvert correct. La forme canonique sera **semi-ouverte**.
* `CalendarManager.tsx:254` compare `s.getMonth() === month.getMonth()` **sans comparer l'année** :
  un événement de novembre de l'année *précédente* serait traité comme intra-mois. Défaut réel,
  aujourd'hui inatteignable (le filtre le masque) ; il redeviendrait atteignable dès que le filtre
  passe au chevauchement. **Il doit être corrigé dans la même tranche**, sinon ce remède l'active.

### 1.2 (A2) La bande de KPI IGNORE le filtre actif pendant que l'en-tête de grille lui OBÉIT

Dans `PortalCalendarView.tsx`, un seul écran, deux populations :

| Nombre rendu | Ligne | Population comptée |
|---|---|---|
| KPI « TOTAL » | `:257` | `events` — **NON filtré** |
| KPI « CE MOIS-CI » | `:249` (`thisMonthCount`) | `events` — **NON filtré** |
| KPI « CETTE SEMAINE » | `:248` (`thisWeekCount`) | `events` — **NON filtré** |
| KPI « PROCHAIN » | `:266-282` (`nextEvent`) | `events` — **NON filtré** |
| en-tête de grille « N événement(s) » | `:349` via `monthEvents` `:218` | `filteredEvents` — **FILTRÉ** |
| liste « À venir » | `:365` via `upcomingEvents` `:228` | `filteredEvents` — **FILTRÉ** |

Choisir un type dans la rangée de puces (`:280-306`) fait bouger la moitié des nombres de l'écran
pendant que l'autre moitié ne bouge pas, **sans qu'aucune donnée n'ait changé**. Deux nombres portent
le mot « événement » et comptent des populations différentes : c'est le *« totals differ by filter »*
de l'audit, et l'instance exacte de `DNC-01` (un KPI de synthèse en désaccord avec le registre détaillé
placé sous lui).

### 1.3 (A3) Un compte dérivé d'un `.length` BORNÉ — dans les DEUX surfaces

* `PortalCalendarView.tsx:228-233` : `upcomingEvents = [...].slice(0, 12)` ; `:365` rend
  `` `${upcomingEvents.length} prochains` ``. Avec 39 événements à venir, l'en-tête annonce
  **« 12 prochains »**.
* `CalendarManager.tsx:86-92` : le même `.slice(0, 12)` ; l'admin n'en rend pas le compte
  (`:174` ne teste que `=== 0`), mais **il tronque en silence** : 27 événements à venir disparaissent
  sans que rien à l'écran ne le dise. C'est `DNC-06` — une promesse plus large que ce que le runtime
  livre.

C'est la **classe identique** à celle que le run 91 a fermée sous `PF-20` et ré-enregistrée sous
`PF-377`. La forme du remède maison est déjà écrite : lire
`docs/spec/features/v3-e03/PROGRESS.md` §`S-E03-6` et
`apps/api/src/modules/alerts/alert-rule-population.ts` **avant** d'en inventer une autre.

**Ce qui N'EST PAS une violation de cette classe, et doit être déclaré tel quel** :
`PortalCalendarView` et `CalendarManager` rendent tous deux `+{dayEvents.length - 3}` dans une cellule
de jour. C'est un **indicateur de débordement**, pas un total tronqué : il annonce précisément ce
qui n'est pas montré. Il reste, et le cliquet du §5 doit l'exclure **explicitement**, par une règle
écrite — pas par un accident de motif.

### 1.4 (A4) L'horloge est lue PENDANT LE RENDU d'un composant client rendu par le serveur

* `PortalCalendarView.tsx` porte `'use client'` (ligne 1) ; `:187` exécute
  `const today = startOfDay(new Date())` **au scope de rendu** ; `:229` appelle `Date.now()` dans un
  `useMemo`. `today` alimente `month` (`:192`), `weekStart`/`weekEnd`/`monthStart`/`monthEnd`
  (`:236-239`) et `nextEvent` (`:266`).
* `CalendarManager.tsx:70` : `const today = new Date()` ; `:87` : `Date.now()` dans un `useMemo`.

Next.js **rend les composants clients sur le serveur** : chaque compteur dérivé d'une fenêtre est
calculé une première fois sur l'horloge et le fuseau du **serveur**, puis une seconde fois sur ceux du
**navigateur**. React remplace silencieusement le nœud de texte. **L'utilisateur voit un compteur
changer après le chargement, sans avoir rien fait** — c'est exactement le *« interim/final »* de
l'audit, et c'est le seul mécanisme des quatre qui mérite le mot « interim ».

Le fuseau aggrave le mois : `new Date(y, m, 1)` utilise le calendrier **local du runtime**. Serveur en
UTC et navigateur en UTC+1 ne délimitent pas le même mois.

**Le précédent maison qui NE s'applique PAS ici.**
`apps/web/src/components/freshness/FreshnessChip.tsx:66-76` accepte délibérément une divergence
serveur/client de `now`, avec `suppressHydrationWarning`. La raison y est écrite : *le suffixe est
purement décoratif et `aria-hidden`*. **Un KPI n'est pas décoratif** : il est lu, cité, et il pilote une
décision. Réutiliser cette exemption ici transformerait une exception motivée en règle générale.
`ADR-078` doit dire pourquoi les deux cas diffèrent, sans quoi le prochain run lira `FreshnessChip`
comme une permission.

## 2. Exigences fonctionnelles

**FR-1 — un seul prédicat déclaré.** Un module canonique unique, sans dépendance, déclare : la
résolution de l'instant de référence, la fenêtre « mois M », la fenêtre « cette semaine », le prédicat
de chevauchement, et le prédicat « à venir ». Toutes les surfaces calendrier l'importent. **Aucune
surface calendrier ne redéclare une fenêtre.**

**FR-2 — sémantique tranchée : CHEVAUCHEMENT, intervalle semi-ouvert.** Un mois M contient un
événement **ssi** `[startsAt, endsAt]` intersecte `[début de M, début de M+1)`. Idem pour la semaine.
Justification écrite dans l'ADR : *un congé qui court aujourd'hui est un congé de ce mois-ci* ; et la
grille admin est **déjà écrite** pour ce rendu (§1.1), sa branche `: 1 / : daysInMonth` étant du code
mort que ce choix ressuscite.

**FR-3 — l'instant de référence traverse la frontière en prop.** Chaque page serveur résout l'ancre
une fois (`Date.now()` côté serveur, sur une page déjà `export const dynamic = 'force-dynamic'`) et la
passe en prop. **Aucun composant client calendrier n'appelle `new Date()` ni `Date.now()` au scope de
rendu.** SSR et hydratation produisent des compteurs **identiques au caractère près**.

**FR-4 — la bande de KPI obéit au filtre, et le dit.** Tous les nombres d'un même écran comptent la
même population. Quand un filtre est actif, chaque tuile nomme la portée qu'elle compte. Le total non
filtré reste visible et étiqueté (la puce « Tous » le porte déjà).

**FR-5 — une liste plafonnée annonce son plafond ou ne rend aucun nombre.** Aucun en-tête ne rend la
longueur d'une liste tronquée comme si c'était un total.

**FR-6 — un cliquet à sens unique**, sous `apps/api/src/shared/quality/`, qui juge du **code** et non
de la prose, et qui porte un **contrôle positif**.

**FR-7 — aucune régression fonctionnelle.** La navigation ±1 mois, le bouton « Aujourd'hui »,
l'export ICS, le tiroir de détail, la création/édition/suppression admin, l'import de vacances et
l'accessibilité existante restent inchangés.

## 3. Les décisions, tranchées ici — `ADR-078` les argumente

### D1 — Où vit le prédicat canonique : `packages/contracts/src/calendar/`

L'orchestrateur signalait un **conflit** entre deux artefacts du dépôt. Il a été **mesuré**, et il
est **tranché en faveur de `packages/contracts`**.

| Ce qui a été mesuré | Résultat |
|---|---|
| `apps/web/next.config.mjs:12-17` | `transpilePackages` contient bien `@pilotage/contracts`. |
| `apps/web` a-t-il un runner unitaire ? | **Non** — ni jest ni vitest, seulement Playwright. Un module posé dans `apps/web` **ne peut pas** avoir de test comportemental. |
| Un composant client importe-t-il déjà une **VALEUR** de `@pilotage/contracts` ? | **OUI.** `apps/web/src/app/admin/audit/audit-labels.ts` (module **neutre**, sans `'use client'`, son docblock l'exige) importe et ré-exporte les **valeurs** `auditActionTone`, `classifyAuditAction`, `auditVocabularyExplanation`… depuis le **barrel racine** `@pilotage/contracts` ; `AuditDetailDrawer.tsx` porte `'use client'` (ligne 1) et les importe (`:9-17`). **Le barrel CJS est donc déjà dans le graphe du bundle navigateur, depuis `S-E04-2` / `PF-14`.** |
| Import par sous-chemin (`@pilotage/contracts/calendar`) ? | **Interdit.** `apps/api/tsconfig.json` étend `@pilotage/tsconfig/node.json` → `moduleResolution: "Node"` (node10), **qui ignore la table `exports`**. Et le dépôt ne contient **aucun** import de sous-chemin `@pilotage/contracts/*` aujourd'hui. Ce serait une convention neuve et cassante. |
| Les tests liront-ils la source ou `dist/` ? | La **source** : `apps/api/jest.config.js` mappe déjà `^@pilotage/contracts$` → `packages/contracts/src/index.ts` (raison écrite sur place : `dist/` est git-ignoré et non reconstruit par le runner). |

**Verdict.** Le commentaire de `apps/web/src/app/admin/enrollments/EnrollmentsPageTabs.tsx:20-28`
— *« y importer la valeur … ce qu'aucun composant client du dépôt ne fait aujourd'hui »* — est
**mesurablement PÉRIMÉ** : `audit-labels.ts` le fait déjà. Le développeur **corrige ce commentaire
dans le même diff** (précédent maison explicite : `PROGRESS.md` §968, *« il a corrigé le commentaire
qu'il falsifiait, dans le même diff »*). Il ne supprime pas le raisonnement de `EnrollmentsPageTabs`,
qui reste juste sur son propre point (une liste **dérivée côté serveur** y est plus forte qu'une
itération côté client) ; il en retire seulement l'affirmation de fait devenue fausse.

**Donc :**

* Le module vit dans **`packages/contracts/src/calendar/`**, il est **sans dépendance** (**pas de
  `zod`**, pas de `lucide`, pas de React), et il est ré-exporté depuis le barrel racine
  (`packages/contracts/src/index.ts`) — **spécificateur nu `@pilotage/contracts` partout**.
* `packages/contracts/package.json` **n'est pas modifié** : aucune entrée `exports` nouvelle.
* Les composants clients l'importent directement. C'est déjà ce que fait le graphe du portail admin.
* `pnpm --filter @pilotage/contracts build` reste un **pré-requis de land** (les consommateurs runtime
  passent par `dist/`). Le noter dans la PR.

### D2 — La sémantique du mois : CHEVAUCHEMENT (FR-2)

Tranchée. Argument en §1.1 : la grille admin **est déjà écrite pour ce rendu**. Conséquence assumée et
à écrire dans l'ADR : *un congé de deux semaines à cheval sur octobre et novembre est compté **une
fois dans chaque mois**.* Ce n'est pas un double comptage : « combien d'événements concernent
novembre » et « combien d'événements commencent en novembre » sont deux questions, et c'est la
première que la grille pose. Le KPI « CE MOIS-CI » posera **exactement** la même.

### D3 — Comment l'ancre traverse la frontière sans dépendre du fuseau du lecteur (FR-3)

L'ancre est une valeur **plate et sérialisable**, résolue une fois côté serveur :

```
CalendarAnchor = { nowMs: number; tzOffsetMinutes: number }
```

* `nowMs` = `Date.now()` du serveur ; `tzOffsetMinutes` = décalage du fuseau **DÉCLARÉ de
  l'école** à cet instant, lu par `resolveCalendarAnchorInZone(now, timeZone)`.

> **CORRECTION DE SPEC (`PF-406`, 2026-08-27).** Cette ligne disait *« décalage civil du
> **serveur** à cet instant »*, et l'implémentation a obéi : `-now.getTimezoneOffset()`. Le
> défaut est donc né **ici**, dans la spec, pas dans le code. Le conteneur `web` livré
> (`node:22-alpine`, aucun `TZ` dans `infra/docker-compose*.yml`) tourne en **UTC** alors que
> l'école est à `Europe/Paris` : toutes les bornes glissaient d'une heure — assez pour qu'un
> congé « toute la journée » s'affiche **la veille** sur les trois portails, et pour qu'un férié
> isolé du 1er novembre chevauche octobre ET novembre. Le fuseau du **serveur** est un ambiant
> au même titre que celui du **navigateur** ; le déplacer de l'un à l'autre n'était pas le
> corriger. Voir `ADR-078 §D3.1` et §7 (`PF-406`).
* **Toute** arithmétique de borne dans le module canonique se fait en **millisecondes absolues** à
  partir de l'ancre. **Aucun constructeur `new Date(y, m, d)` local, aucun `getMonth()` local, aucun
  `getDay()` local n'est autorisé dans le module** — c'est ce qui rend le résultat indépendant du
  fuseau du navigateur et donc identique en SSR et à l'hydratation.
* La navigation ±N mois est un **entier** (`monthOffset`) appliqué à l'ancre ; le client n'ajoute
  jamais d'horloge.

**Limite DÉCLARÉE, pas découverte plus tard.** Un décalage figé au moment de l'ancre peut décaler une
borne de mois d'une heure lors d'un changement d'heure d'été. Pour des événements scolaires
majoritairement `allDay`, l'effet est nul en pratique ; il n'est pas nul en principe. **Résidu
`PF-402`** (§7). Une implémentation exacte IANA (ancre = échelle de bornes précalculées côté serveur)
est l'alternative ; elle est **hors périmètre** de cette tranche et l'ADR doit dire pourquoi.

### D4 — La bande de KPI OBÉIT au filtre (FR-4)

Tranchée : la rangée de puces est **immédiatement adjacente** à la bande de KPI, et le modèle mental
de l'utilisateur qui clique « Examens » est *« j'ai filtré cet écran »*. Une bande qui reste immobile
lui apprend que l'écran ment. Choisir l'autre branche (« la bande est le total, étiqueté comme tel »)
laisserait un écran où deux nombres portant le mot « événement » divergent — c'est-à-dire
`DNC-01` conservé sous un nouveau libellé.

Le total non filtré **ne disparaît pas** : la puce « Tous » le porte déjà (`:283-287`) et chaque puce
de type porte déjà son propre compte non filtré (`:290`). Aucune information n'est perdue ; ce qui
change, c'est **quel nombre porte quel mot**.

## 4. Le changement, surface par surface

### 4.1 Nouveau — `packages/contracts/src/calendar/`

Module pur, sans dépendance. Les **noms** ci-dessous sont indicatifs ; la **sémantique** ne l'est pas.

* `CalendarAnchor` — `{ nowMs, tzOffsetMinutes }` (D3).
* `calendarAnchorOf(nowMs, tzOffsetMinutes): CalendarAnchor` — **le seul** constructeur d'ancre du
  module canonique, et il ne devine rien. La résolution du fuseau vit **hors** du module (elle
  exige `Intl` + un import, tous deux interdits par R4) :
  `resolveCalendarAnchorInZone(now: Date, timeZone: string)` dans
  `packages/contracts/src/school-time/anchor.ts`, appelée **uniquement** depuis un composant
  serveur, via `apps/web/src/lib/school-calendar-anchor.ts`. Il n'existe **aucun**
  `resolveCalendarAnchor(now)` : voir la correction `PF-406` en D3.
* `CalendarWindow` — `{ startMs, endMs }`, **semi-ouvert** `[startMs, endMs)`.
* `monthWindow(anchor, monthOffset: number): CalendarWindow`
* `weekWindow(anchor): CalendarWindow` — semaine **ISO, lundi premier**, 7 jours (préserve
  `startOfWeek` de `PortalCalendarView.tsx:142-147`).
* `dayWindow(anchor, monthOffset, dayOfMonth): CalendarWindow` — alimente les cellules de jour.
* `eventOverlapsWindow(e: { startsAt; endsAt }, w): boolean` — `startMs(e) < w.endMs && endMs(e) >= w.startMs`.
* `eventsInWindow(events, w)` — filtre par le prédicat ci-dessus.
* `upcomingEvents(events, anchor)` — `endsAt >= anchor.nowMs`, **trié par `startsAt` croissant**,
  **JAMAIS tronqué**. La troncature est la décision de l'appelant, et elle est **appariée à son total**
  (§4.5).
* `monthLabelParts(anchor, monthOffset): { year: number; month0: number }` — l'étiquette de mois est
  dérivée de la **même** ancre que la fenêtre, sinon l'en-tête et le compte peuvent désigner des mois
  différents.

Contraintes dures du module, à asseoir par le cliquet : **zéro import**, **aucun `new Date(` à
arité > 1**, **aucun `Date.now()`**, **aucun `getMonth`/`getDay`/`getDate` local**. Il est
**totalement déterministe** : mêmes entrées ⇒ mêmes sorties, sur n'importe quel hôte.

* `month`, `monthEvents`, `weekStart/weekEnd`, `monthStart/monthEnd`, `upcomingEvents`, `nextEvent` :

### 4.5 La règle de troncature, une fois pour toutes

Partout où une liste calendrier est plafonnée :
1. le **vrai total** est calculé **avant** la troncature ;
2. l'en-tête rend soit `${cap} affichés sur ${total}` (si `total > cap`), soit `${total} prochains` ;
3. le nombre rendu n'est **jamais** `truncatedList.length` lorsque `total > cap`.

`+{dayEvents.length - 3}` dans les cellules de jour **reste** : c'est un indicateur de débordement
(§1.3), pas un total.

`new Date(<expr>, <expr>, …)` à arité ≥ 2, aucun `getMonth() + 1`, aucun `, 0, 23, 59, 59`, aucun

**R2 — aucune horloge au scope de rendu d'un composant client.** Dans tout fichier du corpus portant

après cette tranche. Un gestionnaire d'événement qui en aurait un jour besoin **écrira la dérogation
dans le cliquet**, pas dans une allowlist.

**R3 — aucune longueur tronquée rendue comme un total.** Un identifiant affecté depuis une chaîne
se terminant par `.slice(0, N)` (N littéral) ne peut pas voir son `.length` interpolé dans du JSX sans
que le même élément JSX porte aussi le total non tronqué. **Portée déclarée** : la règle suit
l'affectation `const X = … .slice(0, N)` **dans le même fichier**, et apparie `X.length` dans un
littéral de gabarit ou une expression JSX. Elle **ne** poursuit **pas** une valeur tronquée passée en
prop à un autre fichier — cette limite est **écrite** et porte son propre contrôle négatif.

**R4 — le module canonique reste pur.** `packages/contracts/src/calendar/**` : **zéro** déclaration
`import`, zéro `Date.now()`, zéro `new Date(` à arité ≠ 1, zéro `getMonth`/`getDate`/`getDay`. Un
module qui redevient dépendant du fuseau ré-ouvre `A4` en silence.

contrevenante** tenue sous `apps/api/src/shared/quality/__fixtures__/`, et **exige un échec**. Un

cliquet** et sa dette **chiffrée par un test dédié** — exactement comme `S-E03-6` l'a fait pour
`PF-398` (`PROGRESS.md` §1088-1100). Une portée rétrécie sans trace se relit six semaines plus tard
comme « tout est couvert ».

**Aucun interrupteur (`DNC-10`).** Aucun `SKIP_*`, `ALLOW_*`, `NODE_ENV`. Un test le vérifie **sur le
propre texte du fichier**.
