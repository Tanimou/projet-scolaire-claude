## 1. The defect, in one paragraph

The parent children page renders two components stacked on top of each other. The list above is built from
`GET /students`, which reads **`Guardianship`** — the fact. The panel below is built from
`GET /parent/child-claims`, which reads **`GuardianshipClaim`** — the request. On the live local stack there
are **2488 guardianships (2460 `active`, 28 `pending`, 2459 distinct guardians with an active link) and
0 claims**. So for every parent in the data, the page lists their children and then, three centimetres lower,
states *« Vous n'avez pas encore rattaché d'enfant »*. Reproduction rate: **100 %**. This is `DNC-01` (a
panel disagreeing with its own page) in its purest observed form, and it is the third clause of the audit's
`PF-12` sentence, verbatim: *"children list, 'My family' and claim panel say none"*.

The inverse holds too: an `approved` claim whose `Guardianship` was later revoked still renders
`STATUS_CHIP.approved` = **« Validé »** with a `success` tone. The badge asserts a link that no longer exists.

## 3. The design

### 3.1 Row identity — why the `@unique` join key alone is not enough

`AC-2` names `GuardianshipClaim.guardianshipId` as the join key, and it is. But it does **not** by itself
satisfy *"no row appears twice"*, and the counter-example is a shipped code path: `withdraw()`
(`child-claims.service.ts:~388-398`) sets the claim to `withdrawn` **and nulls `guardianshipId`** while
revoking the link. After one withdrawal the caller therefore owns a revoked `Guardianship` with no claim
attached **and** a `withdrawn` claim with no link attached — two rows, one child, one story.

**Decision (ADR-073 §D1).** A row's identity is the **child**, not the record:

```
identity(entity) = entity.studentId            // Guardianship.studentId
                 ?? entity.matchedStudentId    // GuardianshipClaim
                 ?? entity.id                  // a match_failed claim resolves no child
```

`@@unique([guardianId, studentId])` guarantees at most one `Guardianship` per identity, so the fact side of a
row is unambiguous by construction.

### 3.2 The union, stated as a derivation and not as a literal

Two tenant-keyed, guardian-keyed reads:

```ts
const links  = await tx.guardianship.findMany({ where: { tenantId, guardianId }, … });
const claims = await tx.guardianshipClaim.findMany({ where: { tenantId, guardianId }, … });
```

Then:

1. Build `byIdentity` from `links` — every `Guardianship` of the caller is a row. **This is AC-1.**
2. For each claim, resolve `identity(claim)`. If a row already exists at that identity, the claim becomes
   that row's **provenance**. Otherwise the claim **is** a row of its own. **This is AC-2.**
3. Attach provenance by preference: the claim whose `guardianshipId === link.id` first; failing that, the
   caller's most recent claim with `matchedStudentId === link.studentId`, ordered `[createdAt desc, id desc]`.

> **Step 3's fallback is load-bearing, not a tidiness measure.** Without it, the revoked link left behind by
> `withdraw()` looks *admin-created* (no provenance), loses the `claimed*` values the parent typed, and is
> therefore dropped as unnameable (§3.4) — so the parent's own withdrawn request would silently VANISH from
> the panel instead of resolving to `request_withdrawn`. **FM-1 in §7.** Do not simplify it away. Record:
> `PF-369`. *(Before §3.4 was corrected at the review pass, the same omission was a leak rather than a
> disappearance — see `ADR-073 §R.6`.)*

Never write `where: { guardianshipId: null }` to find the "orphan" claims. Derive membership from the
identity map (the paired-lists lesson: *measure both sides, fix by deriving, never by one more literal*).

### 3.3 The state vocabulary — five members, stated ONCE

`AC-3` requires one module. It goes in `packages/contracts` because the **server** evaluates it; the
component consumes a value, never a predicate.

```ts
export const PARENT_CHILD_LINK_STATE = [
  'linked',              // the fact: an active Guardianship
  'requested',           // in flight — pending link OR an un-decided claim
  'request_rejected',    // the admin refused; decisionReason surfaces
  'request_withdrawn',   // the parent cancelled
  'ended',               // the link existed and was revoked
] as const;
```

The derivation is a **total function of the pair** `(linkStatus | null, claimStatus | null)`, evaluated in
this precedence order. `(null, null)` is unreachable — assert it with an exhaustive `never`.

| # | link | claim | state |
|---|---|---|---|
| 1 | `active` | anything or none | `linked` |
| 2 | `pending` | anything or none | `requested` |
| 3 | any | `rejected` | `request_rejected` |
| 4 | any | `withdrawn` | `request_withdrawn` |
| 5 | `revoked` | none / `submitted` / `match_failed` / `approved` | `ended` |
| 6 | none | `submitted` **or** `match_failed` | `requested` |

**Row 2 and row 6 must collapse, and this is the single most dangerous line in the slice.** A matched
`submitted` claim drives a **`pending` Guardianship**; a `match_failed` claim drives **nothing**. If `pending`
were its own wire state, the parent could read *"the school has a child by that name"* straight off the
badge — a fresh, worse leak than the one the current code carefully avoids. `'requested'` therefore covers
both, whatever the provenance. `ChildClaimsStatusStrip.tsx:40-41` maps `submitted` and `match_failed` to the
same label **on purpose**; this design makes the distinction **unrepresentable on the wire** rather than
merely unprinted. That is a strengthening of `AC-6`, and the diff must say so.

**The word « Validé » leaves the vocabulary entirely.** `linked` says *« Rattaché »* about the fact. There is
no state whose name or label is derived from a claim's `approved` status, so the *"approved claim over a
revoked link"* bug is not fixed — it is **inexpressible** (`AC-3`).

### 3.4 When the child’s identity may be projected

> ⚠ **CORRECTED AT THE REVIEW PASS OF RUN 83 — the three-disjunct predicate below was a LEAK.** The version
> this section shipped with is struck through and kept for the record; `ADR-073 §D5` + `§R.6` govern. Do not
> re-widen it.

~~`mayProjectChildIdentity = link !== null && (link.status === active || provenance === null ||
provenance.status === approved)`~~ — only the first disjunct was gated on the link being live.
`StudentAccessService` (`student-access.service.ts:111`) authorises `status: active` guardianships ONLY, and
**2460 of 2460 live links carry zero claims**, so `provenance === null` fired for `revoked` and `pending`
links as the ordinary case: the panel handed the child’s real name and internal `studentId` to a guardian the
admin had just revoked (`DELETE /guardians/guardianships/:id`) or had not yet authorised.

**The rule, as implemented.** One predicate plus the nameability rule it composes, both in the same module,
both consumed by the projection only:

```ts
mayProjectChildIdentity = link !== null && link.status === active;
isNameableForGuardian  = provenance !== null || mayProjectChildIdentity(link, provenance);
```

Everything else — a pending link, a revoked link, any claim-born row — projects `child: null` and falls back
to the parent’s **own typed** `claimed*` values, which leak nothing because the parent supplied them.

**And the corollary, which gating the predicate alone does not give you.** A link that is not `active` with
**no** claim behind it has neither source of a name, and `displayName`’s last fallback used to read
`link.student` — so the same identity went out by a second path. Such a row is therefore **not projected at
all** (`isNameableForGuardian`), restoring `ADR-073 §D4`. This is not a lost capability: the pre-slice panel
read `GuardianshipClaim` alone and rendered nothing for these rows, and the children list above the panel is
`active`-only too, so the two surfaces still agree — which is all `PF-357` asks.

`AC-6` asks this claim to be *proved, not asserted*: **listing an active link reveals nothing `GET /students`
does not already return on the same page** — asserted as a test (§6, T-8), by checking that every `studentId`
the panel projects lies in the **`active` subset** of the same guardian’s `Guardianship` set (⊆ against the
whole set would pass while the panel leaked), plus a whole-payload check that no non-active child’s name or
id appears anywhere in the response. T-8b / T-8c / T-8d cover the claim-less revoked, claim-less pending and
claim-backed revoked shapes.

### 3.5 The wire shape — the component is given no predicate to re-derive

`packages/contracts/src/dto/child-claim.ts` gains the new response; the old `ChildClaimStatusRowSchema` /
`ChildClaimListResponseSchema` are **replaced, not kept alongside** (two shapes is two truths — `DNC-01`).

```ts
export const ParentChildLinkRowSchema = z.object({
  id: z.string(),                        // guardianship id when a link exists, else claim id
  state: z.enum(PARENT_CHILD_LINK_STATE),
  displayName: z.string(),               // resolved SERVER-side (§3.4) — the FE never chooses
  relationship: z.enum(GUARDIAN_RELATIONSHIP),
  child: z.object({ studentId: UuidSchema, firstName: z.string(), lastName: z.string() }).nullable(),
  claimedBirthDate: z.string().nullable(),   // the parent's own typed DOB, or null
  decisionReason: z.string().nullable(),     // non-null ONLY on request_rejected
  claimId: UuidSchema.nullable(),            // the withdraw action needs it
  canWithdraw: z.boolean(),                  // see the WARNING below
  resubmit: z.object({ firstName: z.string(), lastName: z.string(),
                       birthDate: z.string().nullable(),
                       relationship: z.enum(GUARDIAN_RELATIONSHIP) }).nullable(), // request_rejected only
  createdAt: z.string(), updatedAt: z.string(),
});
export const ParentChildLinksResponseSchema = z.object({ links: z.array(ParentChildLinkRowSchema) });
```

**The raw `GuardianshipClaimStatus` is NOT on the wire.** Not as `status`, not nested under a `claim` object.
Every downstream decision (`displayName`, `child`, `decisionReason`, `canWithdraw`, `resubmit`) is already
taken. This is what makes *"do not write a second predicate in the component"* structural instead of
aspirational.

> ⚠ **`canWithdraw` keeps today's exact semantics — `provenance?.status === 'submitted'` — and this
> deliberately preserves a leak that is already shipped.** A `match_failed` row gets no *« Annuler la
> demande »* button while a matched `submitted` row does, so the affordance discriminates matched from
> unmatched even though the label does not. Closing it means widening `withdraw()`'s from-status guard, which
> is a **mutation** change and would trigger `G-AUDIT` — explicitly out of this slice. **`AC-6` says preserve
> every existing property; RULE 0 clause 6 says record, don't fix.** Recorded as **`PF-367`** (§9). Do not
> "improve" it here.

### 3.6 Ordering

Deterministic total order, stated once (`ADR-072`'s precedent — three orderings for one question was axis 3
of `PF-12`): **`[state rank asc, createdAt desc, id desc]`**, rank = `linked(0) · requested(1) ·
request_rejected(2) · request_withdrawn(3) · ended(4)`. `createdAt` is the **fact's** `createdAt` when a link
exists, else the claim's.

## 4. The four states of the panel (AC-4 and AC-5)

`AC-4` invites distinguishing two zero-states. **The union removes the second one**: *"links exist but no
request was ever made"* is no longer empty — it is `n` rows in state `linked`. So there is exactly **one**
emptiness state, and no new ambiguity is traded for the wrong denial. That is the judgement call `ADR-073`
records (§D3).

| # | Condition | Render |
|---|---|---|
| 1 | read ok, `links.length > 0` | the list |
| 2 | read ok, `links.length === 0` — **neither a guardianship nor a claim** | the existing `EmptyState` *« Vous n'avez pas encore rattaché d'enfant »* + the `ChildClaimDrawer` CTA. **Unchanged copy** — it is now true when it renders |
| 3 | read failed **403 / 404** (`isAccessDenied`) — incl. the **422** *"account is not a parent"* | `ReadErrorState variant="denied"`, `retryable={false}`. Copy must not assert a school fact: *« Vos rattachements ne sont pas accessibles depuis ce compte. »* / *« Cela vient d'un droit d'accès, pas d'un compte sans enfant. L'établissement peut rétablir l'accès. »* |
| 4 | read failed 5xx / network / unknown | `ReadErrorState variant="failure"`, `retryable`. *« Nous n'avons pas pu charger vos rattachements. »* / *« Ceci ne veut pas dire qu'aucun enfant n'est rattaché à votre compte : c'est l'affichage qui a échoué. »* |
| 5 | 404 / 501 / 503 — backend not migrated | keep the existing calm *« Le rattachement en ligne n'est pas encore disponible »* banner |

Rows 3 and 4 replace `fetchClaims`'s `return { claims: [], available: true }`. **Note the collision between
rows 3 and 5:** a `404` currently means *"not migrated"*. Keep `available:false` for `501/503` and for a
`404` **only** when the response carries no JSON body; route a `404` with a body to row 3. State the rule in
the code comment; it is the kind of overlap that silently re-creates the bug.

`ADR-071 §D5` is binding on the copy: *a portal never renders a failed read as a fact about the school* — and
`PF-346` (fixed at run 81's land pass) proves the **inverse** polarity is just as wrong. Do not write
*"vos enfants sont bien rattachés"* on a failure branch. The page knows nothing.

### 12.1 — `FM-4` discharge: the `select` each field of §3.5 actually needs

`FM-4` says *"check every field of §3.5 against the `select`/`include` the service actually writes."* Done. The
trap is concrete and it is on the **new** read: today's `listForGuardian` (`:321-328`) includes
`student: { id, firstName, lastName }` on the **claim**, and nothing on a bare `Guardianship`. **2460 of the
2460 live active links have no claim at all**, so a `guardianship.findMany` that omits the student relation
leaves `displayName` and `child` with **no source** for every row the slice exists to produce — a declared type
the payload cannot carry, i.e. `FM-4` reproduced inside its own fix.

| §3.5 field | source when a link exists | source when only a claim exists |
|---|---|---|
| `id` | `guardianship.id` | `claim.id` |
| `state` | derived (§3.3) | derived (§3.3) |
| `displayName` | `guardianship.student.{firstName,lastName}` **only when §3.4 permits (link `active`)**, else the provenance claim's `claimed*`. **No third fallback** | `claim.claimed{First,Last}Name` |
| `relationship` | `guardianship.relationship` | `claim.relationship` |
| `child` | `guardianship.student.{id,firstName,lastName}`, **gated by §3.4 — `active` links only** | always `null` (§3.4: `link === null` ⇒ false) |
| `claimedBirthDate` | provenance `claim.claimedDob`, else `null` | `claim.claimedDob` |
| `decisionReason` | provenance `claim.decisionReason`, `request_rejected` only | `claim.decisionReason`, `request_rejected` only |
| `claimId` | provenance `claim.id`, else `null` | `claim.id` |
| `canWithdraw` | `provenance?.status === 'submitted'` (unchanged semantics — `PF-367`) | same |
| `resubmit` | provenance `claim.{claimedFirstName,claimedLastName,claimedDob,relationship}` | same |
| `createdAt` / `updatedAt` | `guardianship.{createdAt,updatedAt}` (§3.6) | `claim.{createdAt,updatedAt}` |

So the two reads owe, minimally:

- `guardianship.findMany` → `{ id, studentId, relationship, status, createdAt, updatedAt }` **plus**
  `student: { select: { id: true, firstName: true, lastName: true } }`.
- `guardianshipClaim.findMany` → `{ id, status, relationship, guardianshipId, matchedStudentId,
  claimedFirstName, claimedLastName, claimedDob, decisionReason, createdAt, updatedAt }`. It **no longer needs**
  `include: { guardianship: { select: { status } } }` — the link now arrives from the other read — and it does
  **not** need `student`, because a claim-only row can never project `child` (§3.4).

**`displayName` is total, and here is the proof, because a reviewer will ask.** §3.4 is
`link !== null && link.status === 'active'`, and every draft failing `isNameableForGuardian` has already been
dropped, so on entry `provenance !== null || (link !== null && link.status === 'active')`. If the identity is
not projected, `provenance !== null`, so `claimed*` exists. There is no `(no link, no claim)` row — that pair is
unreachable and T-9 asserts it throws. Every **reachable** branch therefore has a name to print, and there is
deliberately **no** third fallback onto `link.student`: that was the second path by which a non-active link
printed the child's name, and reaching it now throws.

### 12.5 — `R1`'s literal: typographic apostrophes, and what "an identifier named `claim`" means

`apps/web/src/components/parent/ChildClaimsStatusStrip.tsx:127`; the bytes are `E2 80 99` in `n’avez` and

unicode escapes rather than pasted characters, and assert the match count is **exactly one** so a zero match
fails loudly instead of passing.

**not** match `claimId`, `claimedBirthDate`, `ChildClaimDrawer` or `ChildLinksPanel` — all of which legitimately
remain in the file (`claimId` powers the withdraw flow that §5 requires be kept). Say so in the docblock: a
reader who assumes substring matching will "fix" a passing gate into a broken one.
