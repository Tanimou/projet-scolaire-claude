## 1. Le défaut, mesuré en source le 2026-08-27

L'audit (`02_Internal_Platform_Audit.md:140`) dit : *« The demo teacher has two classes and a
physics/chemistry assignment. Counts disagree: 48 students in one context, 46 cumulative in another, 43
distinct in another, and one class alternates between 25 and 26. »* Il s'agit d'effectifs d'ÉLÈVES sur des
surfaces enseignantes, **jamais** d'un nombre d'enseignants.

Docker est à l'arrêt sur cette machine et `pilotage@5432` rend `enrollment = 0` : **aucun des chiffres
43 / 46 / 48 / 25 / 26 n'est re-mesuré ici, et aucun n'est revendiqué.** Ce qui est mesuré, c'est la
SOURCE — et elle suffit, parce que les quatre dérivations vivantes forment une chaîne monotone qui
IMPOSE l'ordre des trois magnitudes de l'audit sans qu'aucune donnée soit nécessaire (§1.4).

### 1.1 (A) « Combien d'élèves dans cette classe ? » a QUATRE réponses, et deux vivent dans le même endpoint

| # | Forme | Population comptée | Sites (vérifiés à la ligne) |
|---|---|---|---|
| **V-A** | `_count: { select: { enrollments: true } }` sur une **section** | **les SIX** valeurs d'`EnrollmentStatus` (`pending`, `active`, `transferred_in`, `transferred_out`, `graduated`, `dropped` — `schema.prisma:176-183`) | `school-structure/classes.controller.ts:171` · `grades/assessments.controller.ts:123` |
| **V-B** | `_count: { select: { enrollments: { where: { status: 'active' } } } }` | `active` seule | `classes.controller.ts:103`, `:297` · `structure.controller.ts:95`, `:195` · `analytics.service.ts:1803`, `:2002`, `:2538`, `:3527`, `:3982` · `enrollments.controller.ts:714`, `:921` · `teachers.controller.ts:147` |
| **V-C** | `new Set(rows.map(e => e.studentId)).size` | élèves DISTINCTS, année active épinglée | `teaching/teachers.controller.ts:405-415` (`GET /teachers/:id/load`) |
| **V-D** | `Map<classSectionId, size>` puis somme des valeurs | classes dé-dupliquées, **élèves non dé-dupliqués** | `apps/web/src/app/teacher/settings/page.tsx:100-106` (client) |

**V-A et V-B se contredisent DANS UNE SEULE CHARGE UTILE.** `GET /classes` (liste, `:103`) compte
`active` ; `GET /classes/:id` (détail, `:171`) compte **tous les statuts** — la même classe, deux
endpoints, deux nombres. Une classe de 25 élèves actifs portant un `dropped` s'affiche **25 dans la liste
et 26 dans le détail**. C'est, à la lettre, le *« one class alternates between 25 and 26 »* de l'audit,
et c'est la forme que `PF-12` nomme : une contradiction interne, pas un désaccord entre deux écrans.

**Le détail se contredit même lui-même** : `classes.controller.ts:150-152` charge `enrollments`
filtré `status: 'active'` et `:171` compte SANS filtre, dans le même `include`.

### 1.2 (B) Les DEUX sommes cumulatives : « les élèves de cet enseignant » comptés autant de fois qu'il les voit

`analytics.service.ts:1821` (`teacherDashboard`) :

```ts
stat.studentCount += a.classSection._count?.enrollments ?? 0;   // une itération PAR AFFECTATION
```

`analytics.service.ts:2697` (roll-up admin par cycle) fait le même `+=` sur les classes d'un cycle.
En face, `teachers.controller.ts:418` fait `new Set(...).size`. **Les deux sont étiquetées « élèves de
l'enseignant ».** La somme sur-compte deux fois :

1. **par AFFECTATION** — l'enseignant de physique-chimie de l'audit tient DEUX affectations sur UNE
   classe : la classe est comptée deux fois (`teacherDashboard` itère `assignments`, pas `classSections`) ;
2. **par ÉLÈVE** — un élève inscrit dans deux classes du même enseignant est compté deux fois, et rien
   dans la base ne l'interdit (§1.5).

### 1.3 (C) Le comptage de LIGNES rendu comme un comptage d'ÉLÈVES — jusqu'à un pourcentage qui peut dépasser 100

`analytics.service.ts:3406` et `:3425` (`studentsAggregate`, KPI `/admin/students`) :

```ts
totalStudents  = prisma.student.count({ where: { tenantId, schoolId, status: 'active' } });   // TÊTES, clé école
activeStudents = prisma.enrollment.count({ where: { tenantId, status: 'active',              // LIGNES, PAS de clé école
                                                    academicYearId: activeYear.id,
                                                    student: { status: 'active' } } });
activePct = totalStudents === 0 ? 0 : (activeStudents / totalStudents) * 100;                 // :3406
```

Un numérateur en LIGNES sur un dénominateur en TÊTES, et deux portées différentes (l'un keyé école,
l'autre pas). Dans un tenant multi-écoles, ou avec une seule double-inscription, `activePct` **dépasse
100 %**. Rien ne le borne dans le code.

Même asymétrie dans `structure.controller.ts` : `:106-107` comptent élèves et parents `where: { schoolId }`,
`:108-110` compte les inscriptions `where: { tenantId, status:'active' }` **sans clause d'école**, pendant
que `:131` calcule le même total par somme des `_count` de classes, elles, keyées école.

### 1.4 Pourquoi 48 ≥ 46 ≥ 43 se déduit de la SOURCE, sans données

Sur une même population, les quatre dérivations sont ordonnées par construction :

```
V-A (tous statuts, par affectation)  ≥  V-B sommée (active, par affectation)
                                     ≥  V-D (active, par classe)
                                     ≥  V-C (active, élèves distincts)
```

`≥` #1 vaut parce que `active ⊂ {les six statuts}` ; `≥` #2 parce qu'une classe portant *k* affectations
est comptée *k* fois à gauche et une fois à droite ; `≥` #3 parce qu'un élève inscrit dans *m* classes du
même enseignant est compté *m* fois à gauche. **Les trois magnitudes de l'audit se rangent dans cet
ordre exact.** Cette tranche ne prétend PAS avoir re-mesuré 48/46/43 ; elle démontre que la source
produit nécessairement trois nombres décroissants pour une seule question, ce qui EST la constatation.

### 1.5 L'invariant qui aurait fait s'accorder V-B-sommée et V-C n'existe pas — re-mesuré CONTRE LA BASE VIVANTE

`schema.prisma:669-670` affirme, en commentaire, juste au-dessus de l'`@@unique` :

> *A student can have at most one active enrollment per academic year. We enforce uniqueness on
> (studentId, academicYearId) when status='active' via a partial unique index in migration SQL.*

Exécuté le 2026-08-27 contre `postgresql://…@localhost:5432/pilotage` (la base que `DATABASE_URL` désigne,
schéma migré, `enrollment` à **0 ligne**) :

```
select indexname, indexdef from pg_indexes where tablename='enrollment';
 enrollment_academic_year_id_status_idx  | CREATE INDEX ... (academic_year_id, status)
 enrollment_class_section_id_status_idx  | CREATE INDEX ... (class_section_id, status)
 enrollment_pkey                         | CREATE UNIQUE INDEX ... (id)
 enrollment_student_id_class_section_id_academic_year_id_key
                                         | CREATE UNIQUE INDEX ... (student_id, class_section_id, academic_year_id)
 enrollment_tenant_id_idx                | CREATE INDEX ... (tenant_id)
(5 rows)

select conname, pg_get_constraintdef(oid) from pg_constraint where conrelid='public.enrollment'::regclass;
 enrollment_academic_year_id_fkey | FOREIGN KEY (academic_year_id) REFERENCES academic_year(id) ...
 enrollment_class_section_id_fkey | FOREIGN KEY (class_section_id) REFERENCES class_section(id) ...
 enrollment_pkey                  | PRIMARY KEY (id)
 enrollment_student_id_fkey       | FOREIGN KEY (student_id) REFERENCES student(id) ...
(4 rows)
```

**Aucun index partiel. Aucun index sur `(student_id, academic_year_id)`.** `PF-361` est donc confirmée
d'un cran plus haut qu'au run 82 : elle était mesurée contre le SQL de migration, elle l'est désormais
contre le catalogue de la base migrée. Deux inscriptions `active` d'un même élève, la même année, dans
deux sections, sont **légales**.

**Trois faits de plus, tirés de la même sortie, et chacun porte une décision de §3 :**

* **L'index à trois colonnes, lui, EXISTE.** `(student_id, class_section_id, academic_year_id)` est
  unique. Donc **à l'intérieur d'UNE section ET d'UNE année, compter des LIGNES, c'est compter des TÊTES** :
  l'effectif d'une classe est honnête *par construction*, à condition d'être épinglé sur une année.
  C'est ce qui rend la question « effectif d'UNE classe » séparable de la question « élèves distincts sur
  UN ENSEMBLE de classes » — §3 D2.
* **Rien ne lie `Enrollment.academicYearId` à `ClassSection.academicYearId`.** Deux colonnes, deux FK
  indépendantes, aucune contrainte de cohérence. Une année « impliquée par la section » n'est donc pas
  une année : c'est une hypothèse. → **`PF-409`**.
* **`enrollment.tenant_id` n'a NI FK NI contrainte.** Les `_count` imbriqués n'énoncent jamais de
  `tenantId` : ils sont scopés au tenant **par la convention du `where` parent**, jamais par prédicat, et
  la base ne le rattrape pas. C'est le résultat de la vérification G-TENANT demandée — la réponse est
  « supposé », pas « vrai ». → **`PF-415`**.

  `:235`, `:359`, `:419` et `analytics.service.ts:842`, `:996` sont des `_count` **ancrés sur l'ÉLÈVE**,

* **`PF-63` n'est plus un pré-requis.** La ligne `PF-36` d'`OPEN.md` avertit que les 7 specs

## 2. Exigences fonctionnelles

**FR-1.** Il existe **exactement un** module qui répond « combien d'élèves sont inscrits ici ? ».
Il vit dans `packages/contracts/src/roster/` ; son adaptateur Prisma et sa spec dans
`apps/api/src/shared/roster/` ; son cliquet dans `apps/api/src/shared/quality/`. Aucun second foyer.

**FR-2.** Le module distingue **par le NOM** deux questions aujourd'hui confondues :
`classRosterSize` (l'effectif d'UNE section) et `distinctStudentsAcrossSections` (les élèves DISTINCTS
sur un ENSEMBLE de sections). **La seconde ne doit jamais être obtenue en sommant la première**, et
cette interdiction est portée par le TYPE, pas par un commentaire (FR-6).

**FR-3.** Le prédicat de population est énoncé **une fois**, dans ce module, sous des noms
(`seated`, `onTheBooks`, `awaitingDecision`, `everRegistered`). Un site qui veut une autre population la
demande **par son nom** au même module ; il n'écrit plus de `where` à la main.

**FR-4.** Les listes d'états sont **DÉRIVÉES de l'énum Prisma**, jamais recopiées. Le cliquet assied que
l'union des populations nommées est byte-identique à `enum EnrollmentStatus` de `schema.prisma` : un
septième membre ajouté à l'énum **fait rougir** au lieu de se ranger silencieusement quelque part.

**FR-5.** Chaque site converti énonce sa portée d'année **explicitement** — soit `{ academicYearId }`,
soit le marqueur `ROSTER_YEAR_IMPLIED_BY_SECTION` qui DÉCLARE l'hypothèse que `PF-409` mesure comme non
garantie. Aucun site ne peut rester muet là-dessus.

**FR-6.** `distinctStudentsAcrossSections` **lit** (une requête sur `studentId`), elle ne somme pas. Le
type de retour est distinct de celui de `classRosterSize`, si bien qu'une somme d'effectifs ne peut pas
être passée là où un nombre d'élèves distincts est attendu : `+=` sur un effectif **ne compile plus**
comme un nombre d'élèves.

**FR-7.** Toute lecture d'inscriptions du module **exige `tenantId` dans son TYPE** (patron `ADR-070 §D3`
/ `ADR-072`), y compris quand le tenant paraît impliqué par le parent — `PF-415` mesure que la base ne
l'impose pas.

**FR-8.** Aucun nombre affiché ne change **en silence**. Les changements de valeur sont énumérés,
page par page, avant/après, en §6 (`AC-7`).

**FR-9.** Un cliquet à sens unique interdit l'apparition d'un NOUVEAU `_count … enrollments` ancré sur
une section, ou d'une NOUVELLE somme cumulative d'effectifs, hors du module déclarant. Son allowlist est
**dérivée de l'arbre** et exprimée en PLAFOND décroissant, jamais en liste de fichiers écrite à la main.

**FR-10 (non-but explicite).** Cette tranche **n'ajoute pas** l'index unique partiel manquant, et
**ne touche pas** `schema.prisma`. Voir §3 D5.

## 3. Les décisions, tranchées ici — `ADR-079` les argumente

> `ADR-079` (`docs/adr/ADR-079-canonical-class-roster-size.md`) doit reprendre D1..D6 ci-dessous
> **avec leurs contre-arguments**. Le texte ci-dessous est la décision ; l'ADR en est l'exposé.

### D1 — Le foyer : `packages/contracts/src/roster/class-roster-size.ts`

Trois raisons, dont la troisième est décisive :

1. **La famille est déjà là** — cinq modules frères (`academic-year`, `enrollment`, `guardianship`,
   `calendar`, `school-time`). Un sixième foyer sous `apps/api/src/shared/` créerait la divergence que
   `PF-365` enregistre, dans le run même qui prétend supprimer une divergence.
2. **`apps/web` en a besoin** — `teacher/settings/page.tsx` porte la dérivation V-D. Elle est pinnée et non
   convertie dans cette tranche (§7), mais la convertir un jour depuis un module vivant sous `apps/api/`
   est impossible (`apps/worker/tsconfig.json` fixe `rootDir: ./src`, et `apps/web` ne peut pas importer
   `apps/api`).
3. **Le module ne doit PAS importer Prisma** (GUARDRAILS §2 : `@pilotage/contracts` est consommé par
   `apps/web` et construit en CJS). Il produit un **fragment de `where`** et un **argument de `_count`**
   structurels, que le vrai `PrismaClient` accepte tels quels, et **n'émet aucune requête**.
   L'adaptateur qui lit (`prismaRosterReader`) vit, lui, dans `apps/api/src/shared/roster/`.

⚠ **Conséquence de build** : `packages/contracts` construit en CJS et **doit être rebâti** avant que
`apps/api` ne typecheck (`project_prisma_generate_red_gate`, même famille). C'est le test-architect qui
lance `pnpm typecheck` ; aucun agent ne construit.

### D2 — DEUX questions, DEUX noms, et l'asymétrie est fondée sur ce que la base garantit VRAIMENT

C'est le cœur de la tranche, et l'argument est asymétrique **parce que la base l'est** :

| Question | Nom | Ce qui la rend honnête |
|---|---|---|
| « Combien d'élèves dans CETTE section ? » | `classRosterSize` | **Un index qui EXISTE** : `@@unique([studentId, classSectionId, academicYearId])`. À section + année fixées, une ligne = un élève. Compter des lignes EST compter des têtes. |
| « Combien d'élèves distincts sur CES sections ? » | `distinctStudentsAcrossSections` | **Aucun index.** L'invariant qui rendrait la somme correcte (`PF-361`) n'existe pas. La seule dérivation honnête est un `DISTINCT studentId` **lu**, jamais additionné. |

Le commentaire obligatoire d'`AC-2`, dans le module, dit exactement pourquoi sommer est faux :

> Sommer des effectifs de sections ne rend un nombre d'élèves que si aucun élève n'apparaît dans deux
> sections. Cette hypothèse est écrite dans `schema.prisma:669-670` et **n'est pas tenue par la base**
> (`PF-361`, re-mesurée contre `pg_indexes` le 2026-08-27). Une somme sur-compte donc silencieusement,
> et sur-compte d'autant plus que l'établissement est gros. `distinctStudentsAcrossSections` LIT les
> `studentId` ; elle n'additionne pas.

### D3 — Les populations NOMMÉES, et une seule liste positive

```
ROSTER_SEATED_STATUSES        = ['active']                    LISTE POSITIVE, jamais dérivée
ROSTER_EXIT_STATUSES          = ['transferred_out','graduated','dropped']
ROSTER_ON_THE_BOOKS_STATUSES  = TOUS LES ÉTATS  \  ROSTER_EXIT_STATUSES     (dérivée)
ROSTER_AWAITING_STATUSES      = ['pending']                   LISTE POSITIVE
ROSTER_EVERY_STATUS_IS_DELIBERATE                             marqueur, aucun filtre
```

L'asymétrie est reprise verbatim de `ADR-074` : `seated` est **positive** — un septième état ne doit
JAMAIS entrer dans un effectif affiché par le seul fait d'avoir été ajouté à une énum ; `onTheBooks` est
**dérivée** — « tout sauf les sorties » — pour ne pas créer une deuxième liste tenue à la main face à
`schema.prisma` (`project_paired_lists_drift` : c'est ce couple qui a déjà coûté un 503 sur quatre
portails). Le cliquet assied `SEATED ∪ AWAITING ∪ {transferred_in} ∪ EXIT === enum EnrollmentStatus`,
byte à byte, **lu dans `schema.prisma`**.

### D4 — La portée d'année est DÉCLARÉE, jamais devinée

`rosterCountArg` exige l'un des deux :

* `{ academicYearId }` — l'effectif est épinglé, et la garantie de D2 tient ;
* `ROSTER_YEAR_IMPLIED_BY_SECTION` — la section est censée porter l'année. **`PF-409` mesure que rien ne
  le garantit** ; le marqueur existe pour que l'hypothèse soit LUE, et pour que le cliquet puisse compter
  combien de sites en dépendent encore.

**Aucun site converti ne se voit AJOUTER une clause d'année qu'il n'avait pas.** Ajouter un filtre est un
changement de valeur ; cette tranche en déclare trois (§6 `AC-7`) et n'en cache aucun. Les lectures
d'appartenance de `student-access.service.ts` restent **hors périmètre par l'énoncé** (`ADR-063 §D1`,
`ADR-066 §D1`) : y toucher serait une modification d'AUTORISATION.

### D5 — On N'AJOUTE PAS l'index unique partiel manquant. Et c'est un choix, pas un évitement

**Décision : la dérivation devient correcte PAR CONSTRUCTION ; l'invariant absent reste enregistré
(`PF-361`) et non corrigé. `schema.prisma` n'est pas ouvert. `G-MIGRATION` n'est pas déclenché.**

Trois raisons, la troisième étant celle qui tient seule :

1. `CREATE UNIQUE INDEX … WHERE status='active'` **échoue sur des données existantes en violation**. La
   base locale est vide (`enrollment = 0`) ; **la production ne l'est pas** (l'audit mesurait 2 460 liens
   de garde vivants). Ajouter l'index sans mesurer les violations en production transforme une tranche de
   vérité de lecture en migration de données à l'aveugle.
2. Un index unique est un changement de **contrat d'écriture** : `POST /enrollments` et l'import en lot se
   mettraient à échouer sur un cas aujourd'hui accepté, sans qu'aucun message d'erreur ne l'explique.
   C'est une décision produit (« un élève peut-il être inscrit dans deux classes ? » — pensez aux options,
   aux groupes de langue), pas une décision de routine.
3. **Décisive** : une dérivation qui n'est correcte QUE parce qu'un invariant tient est exactement la
   fragilité dont `PF-36` est faite. `distinctStudentsAcrossSections` rend le MÊME nombre que l'invariant
   tienne ou non. **Si l'index était ajouté demain, aucune ligne de ce module ne changerait** — et c'est
   le test de la décision : la correction ne dépend pas de la migration, la migration ne dépend pas d'elle.

*Contre-argument, à porter dans l'ADR :* sans l'index, `classRosterSize` reste vrai mais
« un élève peut être assis dans deux classes » demeure une bizarrerie métier. **Réponse :** c'est un
défaut de DONNÉES, `PF-361` le porte, et le rendre visible (un effectif honnête) est un préalable à le
trancher, pas un substitut.

### D6 — Ce que la tranche NE fait pas au dénominateur du rang

`classSize` désigne aujourd'hui **au moins trois populations différentes** : l'effectif inscrit
(`attendance.controller.ts:378` — `enrollments.length` après `where status active`), le nombre d'élèves
**AYANT UNE NOTE** (`analytics.service.ts:1571` — `new Set(classGrades.map(g => g.studentId)).size`) et le
nombre d'élèves **classés** (`snapshot-recompute.service.ts:287`, `:353` — `means.length` / `ranks.length`).
Le dénominateur du rang affiché au PARENT est le deuxième.

**Décision : on n'y touche pas dans cette tranche.** Changer un dénominateur de rang change un rang
affiché à une famille — c'est un changement de sens sur la page qui porte la promesse nord (« cinq
questions en moins de 2 s »), et il exige une décision produit (« être classé 12/26 quand 3 élèves n'ont
pas de note, est-ce 12/23 ? »). Le fait est **enregistré (`PF-411`)** et le cliquet interdit qu'une
NOUVELLE dérivation d'effectif se glisse là. Le module expose néanmoins le nom
`gradedPopulationSize` **en TYPE seulement**, sans implémentation, pour que la prochaine tranche ait un
nom à remplir plutôt qu'un quatrième à inventer.

## 7. `AC-6` — le cliquet : `apps/api/src/shared/quality/class-roster-size-derivation-gate.spec.ts`

Marche AST (TypeScript, `ScriptKind.TSX` pour les `.tsx`) sur les **quatre racines** — `apps/api/src`,
`apps/worker/src`, `apps/web/src`, `packages/*/src` — patron `enrollment-activity-derivation-gate.spec.ts`.

### Les règles

**R1 — tolérance ZÉRO.** Hors du module déclarant, un `_count: { select: { enrollments: … } }` **ancré sur
une section** dont l'argument n'est pas un APPEL à `rosterCountArg` est un contrevenant. L'ancrage est
**structurel** (le modèle Prisma de l'appel englobant), jamais nominatif — même discipline qu'en
`S-E03-3`. Préfixes à tolérance zéro : `apps/api/src/modules/school-structure/`,
`apps/api/src/modules/analytics/`, `apps/api/src/modules/teaching/`.

**R2 — la SOMME CUMULATIVE est interdite partout, sans plafond.** Est un contrevenant tout
`x += <expr>._count…enrollments`, tout `reduce((s, c) => s + <expr>._count…enrollments)` et tout
`Set(...).size` sur des `studentId` **hors du module déclarant**. C'est la forme d'`analytics:1821` et
`:2697`, et c'est la forme que `AC-2` déclare fausse : elle ne peut pas revenir.

**R3 — plafond DÉCROISSANT** sur les `where` de population d'inscription écrits à la main sous une clé
d'appartenance (`_count` / `some` / `none` / `every`) hors du module. Mesuré AVANT conversion : la marche
en compte **N** ; le plafond est posé à la valeur mesurée APRÈS, et un test assied
`CEILING < MEASURED_BEFORE_CONVERSION` — épingler sans convertir est un échec. Les résidus pinnés sont
**énumérés dans `OPEN.md` avec un id**, jamais allowlistés en silence.

**R4 — l'énum ne peut pas dériver.** `SEATED ∪ AWAITING ∪ {transferred_in} ∪ EXIT` est byte-identique à
`enum EnrollmentStatus` **lu dans `apps/api/prisma/schema.prisma`**. Un septième membre fait rougir et
exige d'être classé. (Patron `guardianship-liveness-derivation-gate.spec.ts`.)

### Les garde-fous d'anti-vacuité (sans eux, le cliquet ne prouve rien)

* plancher de fichiers **PAR RACINE** (les quatre) ;
* **du TSX a bien été parsé** (sinon la moitié du portail est invisible) ;
* **compteur de RECONNAISSANCE > 0** : zéro contravention sur zéro construction reconnue ne prouve rien ;
* **exactement UN foyer déclarant** ;
* l'**allowlist manuelle expédie VIDE** — le foyer est DÉRIVÉ, jamais énuméré ;
* les fichiers convertis sont **toujours vus** par la marche (un vert obtenu par disparition n'en est pas
  un — leçon `PF-366`) ;
* **contrôles NÉGATIFS** : injecter chacune des quatre formes interdites (V-A, `+=`, `reduce(+)`, `where`
  à la main) **doit** les signaler, avec fichier, ligne et règle ;
* **contrôles POSITIFS** : un `_count` **non filtré ancré sur l'ÉLÈVE** (`totalEnrollmentCount`,
  `ADR-072`) **PASSE** ; `student-access.service.ts` **PASSE** ; une somme de `maxStudents` (des PLACES,
  pas des élèves) **PASSE**.

### ⚠ L'interaction avec le cliquet de `S-E03-3` — vérifiée, et elle CONTRAINT le design

`enrollment-activity-derivation-gate.spec.ts:638` assied que la **famille ancrée sur la section existe
encore** (`hasMembershipFamily`, plancher **≥ 5**), et son commentaire interdit d'« arranger » un zéro en
baissant le plancher. `hasMembershipFamily` est vrai dès qu'une **clé `enrollments` apparaît sous
`_count`/`some`/`none`/`every`** (lu en source : `classify()`, `apps/api/src/shared/quality/enrollment-activity-derivation-gate.spec.ts:384-405`).

**Conséquence de design, normative :** l'appel canonique doit être posé **À la clause `enrollments:`**
(`_count: { select: { enrollments: rosterCountArg(...) } }`), **jamais** en remplaçant la clé par un
helper qui la masquerait. Ainsi le cliquet de `S-E03-3` continue de voir la famille, son plancher ≥ 5
tient, et `PF-362` est fermée **par arbitrage sémantique** (la famille a désormais un sens nommé) sans
qu'aucun test existant ne soit relâché. **Vérifier ce plancher fait partie de l'`AC-6`** ; s'il rougissait,
c'est le design qui est faux, pas le plancher.

## 10. Ce qui ferait échouer cette tranche

1. **Ajouter l'index unique partiel** parce qu'il « manque ». C'est `G-MIGRATION`, un contrat d'écriture
   et une décision produit — §3 D5. Si l'implémenteur conclut qu'il est indispensable, il doit **le dire
   explicitement, l'argumenter, fournir la migration relue ET le `DROP INDEX` de retour arrière**, et
   jamais `db push`.
2. **Convertir les sept sites ancrés sur l'ÉLÈVE** vers `active` : cela casse `ADR-072`
   (`out_of_scope` deviendrait `none`) et rendrait `PF-12` à un état déjà fermé.
3. **Toucher `student-access.service.ts`** : ce serait une modification d'AUTORISATION (`ADR-063 §D1`,
   `ADR-066 §D1`).
4. **Obtenir l'accord d'`AC-4` en re-sommant** au lieu de lire des `studentId` distincts — l'assertion 3
   d'`AC-4` existe précisément pour l'interdire.
5. **Changer le dénominateur du rang PARENT** (§3 D6) : un rang affiché à une famille ne change pas sans
   décision produit.
6. **Baisser un plancher d'anti-vacuité** ou ajouter une allowlist écrite à la main pour faire passer un
   cliquet (`academic-year-resolution-gate.spec.ts:20-32`, R-30).
7. **Un septième nombre qui change** sans figurer dans le tableau `AC-7`.
