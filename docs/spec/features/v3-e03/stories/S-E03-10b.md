
## 2. AC-1 (`PF-380`, **P1, bloquante**) — le tableau gagne une borne de rétention

**Fichier** `apps/worker/src/modules/analytics-snapshots/snapshot-drain-cron.service.ts`.

### 2.1 Ce qu'il faut écrire

Un balayage de rétention **borné, scopé par tenant, à cadence grossière**, qui supprime les lignes
**TERMINALES** (`done` ou `failed`) dont le `processedAt` est plus vieux qu'un TTL.

**Le gabarit n'est pas à inventer : c'est `pruneOrphanSnapshots` (`:292-354`) et son site d'appel dans
`tick()` (`:137-140`). LIRE CES DEUX BLOCS ET LES DÉCALQUER.** Ils fournissent déjà, exactement :

1. une constante d'env avec défaut (`ORPHAN_PRUNE_TAKE`, `:39`) ;
2. une borne `take` ;
3. une cadence grossière `EVERY_TICKS` (`:41`, `:138`) ;
4. l'invocation via `this.safe(label, fn, 0)` — un échec ne doit **jamais** avorter le tick (`:139`) ;
5. la forme *« `findMany({ select: { id: true }, take: N })` puis `deleteMany`»* — Prisma n'a **pas** de
   `take` sur `deleteMany` ;
6. la boucle `byTenant` qui garantit qu'aucun `deleteMany` ne nomme des ids de deux tenants (`:325-348`).

### 2.2 Les trois constantes, avec leurs défauts TRANCHÉS

À placer dans le bloc de constantes en tête de fichier (`:9-57`), chacune avec un docblock.

| Constante | Variable d'env | Défaut | Justification (à recopier dans le docblock) |
|---|---|---|---|
| `TERMINAL_RETENTION_DAYS` | `SNAPSHOT_TERMINAL_RETENTION_DAYS` | **30** | Un mois scolaire. Assez long pour qu'un opérateur post-mortem un incident de drain (`FAILED_RETRY_AFTER_MIN` vaut 60 **minutes** : 30 jours, c'est 720× la fenêtre de revive) ; assez court pour que la minimisation ait un sens sur une ligne par enfant. **Aucun chemin de lecture ne consomme une ligne terminale** — voir §6.3. |
| `TERMINAL_SWEEP_TAKE` | `SNAPSHOT_TERMINAL_SWEEP_TAKE` | **500** | Plus haut qu'`ORPHAN_PRUNE_TAKE` (200) parce que l'ingest est ici **une ligne par recalcul**, pas un échantillon. |
| `TERMINAL_SWEEP_EVERY_TICKS` | `SNAPSHOT_TERMINAL_SWEEP_EVERY_TICKS` | **10** | Même cadence que le prune orphelin — cadence déjà éprouvée dans ce fichier. À `INTERVAL_MS = 60 s`, c'est un balayage toutes les 10 minutes, soit **3 000 lignes/heure**. |

**Arithmétique à écrire noir sur blanc dans le docblock (et dans l'ADR) :** le plafond d'ingest terminal est
`BATCH_SIZE (25) × tenants × 60 ticks/h`. Sur un déploiement multi-tenant saturé en continu, cela peut
dépasser 3 000/h. **Ce balayage est une borne de RÉTENTION, pas un mécanisme de contre-pression** : il
garantit qu'aucune ligne ne survit indéfiniment, il ne garantit pas un plafond de cardinalité instantané.
Si le compteur du §2.5 ne redescend pas, l'opérateur monte `SNAPSHOT_TERMINAL_SWEEP_TAKE`. **C'est
précisément pourquoi le compteur du §2.5 est obligatoire et non décoratif.**

### 2.3 Le `where`, et l'invariant qu'il ne doit JAMAIS violer

```
status:      { in: ['done', 'failed'] }     // JAMAIS pending / processing
processedAt: { lt: cutoff }                 // cutoff = new Date(Date.now() - TTL_DAYS * 86_400_000)
```

**Une ligne dont `processedAt` est `null` ne doit JAMAIS être balayée.** En SQL, `processed_at < cutoff`
est `NULL` — donc non vrai — pour une ligne nulle, et la ligne est déjà exclue. **Ce n'est pas une raison
de ne pas l'écrire** : `reclaimStaleProcessing` (`:227-232`) prouve que ce fichier contient déjà des
lignes `processing` avec `processedAt: null` (*« a pre-S5 legacy claim »*), et une future réécriture du
`where` en `OR` réintroduirait le trou en silence. **Écrire l'exclusion explicitement** (un commentaire qui
la nomme, et le test n° 4 du §5 qui la mesure) fait partie de l'AC.

### 2.4 La forme, en deux temps, pour `G-TENANT`

1. `findMany({ where: <ci-dessus>, orderBy: { processedAt: 'asc' }, take: TERMINAL_SWEEP_TAKE, select: { id: true, tenantId: true } })`
   — sélection la plus vieille d'abord, bornée.
2. Regrouper les ids **par `tenantId`**, puis **un `deleteMany` par tenant** :
   `deleteMany({ where: { tenantId, id: { in: idsDeCeTenant } } })`.

**Aucun `deleteMany` ne doit jamais nommer des ids appartenant à deux tenants.** C'est la forme exacte de
`pruneOrphanSnapshots:325-348`, et c'est ce que `G-TENANT` exige d'un `DELETE`. La *sélection* est
volontairement transverse aux tenants (comme `reclaimStaleProcessing` et `reviveFailedTriggers` le sont
déjà) ; c'est le *statement de suppression* qui porte la clé.

### 2.5 Le site d'appel et le compteur

Dans `tick()`, juste après le bloc du prune orphelin (`:137-140`), à l'identique :

```
if (this.tickCount % TERMINAL_SWEEP_EVERY_TICKS === 0) {
  sweptTerminal = await this.safe('terminalSweep', () => this.sweepTerminalTriggers(), 0);

```

Déclarer `let sweptTerminal = 0;` à côté des autres compteurs (`:126-133`) et **ajouter `sweptTerminal` à

La méthode s'appelle `sweepTerminalTriggers()` et retourne le nombre de lignes supprimées.

## 6. AC-4, ADR et gates

### 6.1 `ADR-083` — le fichier à écrire

`docs/adr/ADR-083-snapshot-trigger-terminal-key-and-retention.md`.

- **(d)** l'**interaction avec `reviveFailedTriggers`**, qui est un arbitrage réel et pas un détail :
  une ligne `failed` de plus de 30 jours **est supprimée**, donc son travail est perdu. C'est acceptable
  **parce que `backfillLaggingTenants` (`:371`) est le filet** : son ensemble `tenantsWithOpen` (`:376-384`)
  ne compte que `pending`/`processing`, donc une ligne `failed` **ne bloque déjà pas** le backfill, et un
  scope dont le snapshot retarde sur la dernière note est ré-enfilé par ce balayage-là. Le dire, plutôt que
  de laisser le lecteur le redécouvrir.
- **(e)** la conséquence `G-AUDIT` : `lastError` est effacé au succès, et le texte d'erreur brut d'une ligne
  parkée a désormais une **durée de vie bornée**.
