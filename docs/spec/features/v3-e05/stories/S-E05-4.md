- **Epic:** `V3-E05` — AuthN/AuthZ hardening and permission integrity · **Layer:** L0

## 1. The finding, re-measured before a line was written

`PF-11` — *"Notification fan-out dedup query is not tenant-scoped"* — had an empty Evidence column
since the register was written. **It still reproduced.**

`NotificationsService.createMany` filtered its source-dedup query on
`(userProfileId, sourceType, sourceId)` with no `tenantId` anywhere, under a docblock claiming the
dedup ran *"within the same tenant"*. Parsed across both applications, it was the **only** one of the
eleven `Notification` filter queries that carried no tenant — including four worker siblings whose
comment says they *"mirror NotificationsService.createMany"*.

The same parse found the softer form one file over: four `preferences.service.ts` batch resolvers
took `tenantId?: string` and spread it as `...(tenantId ? { tenantId } : {})` — the absent-key
fail-open `ADR-065 §D5` forbids — and a fifth had no tenant parameter at all.

Severity is stated in `ADR-068 §1.1` rather than inherited from the label: every `OR` branch also
constrained `userProfileId`, and a profile belongs to one tenant, so the realistic leak was narrower
than the classification suggests. What makes it worth closing is that **nothing in the code said so**,
and `PF-02` (RLS) is being built on the premise that application queries are already tenant-keyed.
