## 1. Why — the defect, stated precisely

`PF-175` is **not** "the ceiling is wrong". It is: *the ceiling bounded what can be granted from now on, and
grandfathered everything already granted, and nobody has looked.*

The live chain, all of it already measured by `S-E05-2` and unchanged by this slice:

1. Before `S-E05-2` landed, `POST /roles` validated only that a requested code **exists** in the catalogue. A
   `school_admin` could mint a custom role carrying all 89 codes and self-assign it.
2. `effectivePermissions` unions that role's codes into the actor's effective set (`user-sync.service.ts:80-84`).
3. `exceedsGrantor` compares against that union. The escalated codes are *in* it. **The ceiling permits, correctly,
   by its own rule.**

So the only question that can be answered today is a **data** question: *does any custom role in a real deployment
carry a code a `school_admin` does not hold?* Empty ⇒ `S-E05-2`'s closure label is earned and `PF-175` downgrades to
monitoring. Non-empty ⇒ a human revokes, in that window.

**What this slice ships is the instrument, not the verdict.** The local database is seed data; an empty result here
proves nothing about anywhere else. The slice is done when the detector is tested and runnable — the verdict comes
from an operator running it against production.

**Why `school_admin` is the baseline, and not something else.** `PF-09` — the P0 the ceiling closed — was reachable
by a `school_admin`, because `school_admin` is the level that holds **both** `roles.write` and `roles.assign`
(`permissions.constants.ts:209-211`). Any code above that level, sitting in a **minted** (non-seeded) role, is a
grant `PF-09` produced. `super_admin` is not the baseline (it holds the whole catalogue, so it would flag nothing),
and `teacher`/`parent`/`student` are not (they are not grantor levels).

## 2. What changes

Three new files and one script line. Nothing existing changes behaviour.

### 2.1 `apps/api/src/shared/auth/legacy-escalation-sweep.ts` — the pure detector (NEW)

Same posture as `privilege-ceiling.ts`, and for the same reason: **no `@Injectable`, no Nest module, no Prisma
import, no decorator, no options bag, no barrel export.** There is no `index.ts` in `shared/auth/` (fifteen files,
none of them a barrel); consumers import the module directly.

**Exported surface — exactly these five symbols, and no more:**

```ts
/** A role as the sweep needs to see it. Shaped at the caller, so the module never touches Prisma. */
export interface CandidateRole {
  readonly id: string;
  readonly slug: string;
  readonly isSystem: boolean;
  /** Nullable by schema (`Role.schoolId String?`) — a global role is legal. */
  readonly schoolId?: string | null;
  readonly permissionCodes: readonly string[];
}

export interface RoleFinding {
  readonly roleId: string;
  readonly slug: string;
  readonly schoolId: string | null;
  /** De-duplicated, sorted ascending by UTF-16 code unit. Never empty in a finding. */
  readonly codesOutsideBaseline: string[];
  /** true when the entry itself could not be read, not merely when it exceeds. */
  readonly malformed: boolean;
}

export interface SweepReport {
  readonly examined: number;      // entries inspected, including skipped system roles
  readonly skippedSystem: number; // subset of `examined`
  readonly baselineSize: number;  // 0 is a loud condition, not a quiet one
  readonly findings: RoleFinding[];
  readonly clean: boolean;        // findings.length === 0
}

/** The 75 codes of `REALM_ROLE_PERMISSIONS.school_admin`, frozen into a set at module load. */
export const SCHOOL_ADMIN_BASELINE: ReadonlySet<string>;

export const MALFORMED_ROLE_SENTINEL = '<rôle illisible>';
export const MALFORMED_CODE_SENTINEL = '<code de permission invalide>';

export function sweepLegacyEscalations(
  candidates: readonly CandidateRole[],
  baseline: ReadonlySet<string> | undefined,
): SweepReport;

export function formatSweepReportFr(report: SweepReport): string;
```

**The algorithm, decided here so it is not re-invented:**

1. `if (!Array.isArray(candidates))` → return a report with `examined: 0`, `clean: false` and **one** finding whose
   `roleId`/`slug` are `MALFORMED_ROLE_SENTINEL`, whose `codesOutsideBaseline` is `[MALFORMED_CODE_SENTINEL]` and
   whose `malformed` is `true`. Never `clean: true`.
2. `const held = baseline ?? EMPTY_BASELINE` where `EMPTY_BASELINE` is a module-level frozen empty `Set`. An
   `undefined` or empty baseline therefore reports **everything**. It is never read as "unknown, therefore clean".
3. For each entry (`examined++`):
   - `null`, or `typeof entry !== 'object'` → malformed finding (sentinels for `roleId`/`slug`, `schoolId: null`).
   - **`entry.isSystem === true` — strict — skips** (`skippedSystem++`, no finding). Anything else (`undefined`,
     `'false'`, `0`) is treated as **not** system and is evaluated normally: only an explicit `true` may silence a
     role. Skipping system roles is **structural, never by name**: a seeded role's permissions come from
     `seed.ts`, not from a grant, so it cannot be a `PF-09` artefact. The string `'super_admin'` appears nowhere in
     the module, and there is no name-based exemption of any kind (§AC-2).
   - `!Array.isArray(entry.permissionCodes)` → malformed finding carrying `[MALFORMED_CODE_SENTINEL]`.
   - Otherwise walk the codes: a non-`string` element contributes `MALFORMED_CODE_SENTINEL` and sets
     `malformed: true`; a `string` not in `held` is collected. Both are de-duplicated with a `Set`.
   - **Zero collected codes ⇒ no finding.** This includes a role with zero permissions. *This is the ONE
     permit-on-empty and it must carry the comment saying so*, in the same words as `privilege-ceiling.ts:52-54`: a
     role carrying zero permissions grants zero privilege. It is not a fail-open branch.
4. Sort, so the report is a function of the *set* of inputs and not of the database's row order:
   - within a finding: `codesOutsideBaseline.sort()` — the **default** comparator (UTF-16 code units). **Not**
     `localeCompare`: locale ordering differs between machines, which would make "deterministic" false in exactly the
     environment (an operator's laptop vs. the VPS) where the report is compared.
   - between findings: ascending on `` `${schoolId ?? ''} ${slug} ${roleId}` ``, default comparator.
5. `clean = findings.length === 0`.

`formatSweepReportFr(report)` is a pure `SweepReport → string`. It is in this module, not in the CLI, so the French
strings are covered by unit tests and the CLI stays I/O-only.

### 2.2 The baseline (AC-2)

```ts
import { REALM_ROLE_PERMISSIONS } from './permissions.constants';

export const SCHOOL_ADMIN_BASELINE: ReadonlySet<string> = new Set<string>(
  REALM_ROLE_PERMISSIONS.school_admin ?? [],
);
```

Derived, never copied. If a future slice adds a permission to `school_admin`, the baseline follows and the sweep
stops flagging it — which is correct, because it is then a code a `school_admin` legitimately holds. The `?? []` is
deliberate: a missing key must yield an **empty** baseline (report everything), never `undefined` treated as clean.

### 2.3 Tenancy (AC-6)

The sweep **never filters by school and cannot**: `schoolId` is carried through to the finding and printed, and there
is no school parameter on either exported function. A silent single-tenant filter would under-report, which on this
finding is the same as lying. The CLI reads **all** roles, prints each finding's `schoolId` (or the global marker for
`null`), and says so in its docblock. Cross-tenant reading is correct **here and only here**: this is a read-only
operator diagnostic run from a shell, not a request handler, and it has no `tenantId` to scope to. That exception is
stated in the docblock so it is not copied into a handler.

## 3. Functional requirements

- **FR-1** A pure function reports, per candidate role, the permission codes outside a supplied baseline.
- **FR-2** The baseline is derived at runtime from `REALM_ROLE_PERMISSIONS.school_admin`.
- **FR-3** Seeded (`isSystem === true`) roles are skipped structurally, and counted in the report so the reader knows
  how many were skipped.
- **FR-4** The report is total and fail-closed: unknown codes, malformed entries, a missing baseline and a non-array
  input all produce a *reported* outcome, never a silent clean one.
- **FR-5** The report is deterministic: the same set of roles in any order yields a deep-equal report, with
  de-duplicated codes.
- **FR-6** The report names the `schoolId` of every finding and is never filtered to one tenant.
- **FR-7** An operator can execute the detection against a real database with one pnpm script, read a French report,
  and gate on the exit code.
- **FR-8** The detection performs no write of any kind and revokes nothing.

## 8. Gates — every row answered

**8.1 G-AUTHZ (triggers — permission code).** Evidence = §5's matrix, and specifically its **negative** half: T-3b,
T-5, T-6, T-8 and T-9 are the inputs on which a well-meaning "if we can't tell, call it clean" branch would report an
empty sweep while every positive test stayed green. Plus the mutation check in §5.3, which produces the
fail-before half rather than asserting it. No fail-open guard is added: the module is not a guard at all, and it
denies nothing — but the *reporting* posture is fail-closed in the same shape the gate asks for.

**8.2 G-DNC (always triggers).** DNC-10 is answered by T-12: mechanised source scan of both files plus fixed arity on
both exports. No env read, no bypass flag, no dev escape, no options bag. DNC "no hard-coded bypass" is also answered
structurally — there is no allow-list of role names anywhere, and `'super_admin'` is a token the spec forbids.

**8.3 G-AUDIT does NOT trigger.** The sweep performs no mutation, so there is nothing to audit. Deliberately **no**
`auditLog` row is written for a *read* — the house posture (`privilege-ceiling.ts:152-155`, and the two cross-tenant
guards in `users.service.ts`) is that a non-mutation writes nothing. Note the second-order reason: this CLI is run by
an operator from a shell with no authenticated actor, so any row it wrote would be provenance-less, which
`ADR-035`/`PF-176` already name as the failure mode to avoid.

**8.4 G-MIGRATION does NOT trigger, and no ADR is needed — argued, not skipped.** The brief invites the counter-case,
so here it is answered. An ADR is required when a change introduces a *new architectural decision*: a new HTTP style,
a new state library, an off-convention path, a new cross-cutting pattern. This slice introduces none of those. It is a
**diagnostic script** in the same posture, in the same directory, with the same "pure function, explicit call site, no
provider" shape that `ADR-015`'s `S-E05-2` amendment already documented for `privilege-ceiling.ts`; the CLI is the
fifth `tsx` script in the package, alongside seven existing `prisma:seed:*` entries. Two things *would* have flipped
this to "ADR required" and are deliberately not taken: an HTTP surface (§7.4) and any automated revocation (§7.3) —
either would be a new cross-cutting pattern (machine-decided permission removal) and both belong in `ADR-015`, not in
a script. **If the implementer adds either, stop and write the ADR.**

**8.5 G-TENANT.** Not one of this slice's triggered gates, but §2.3 answers it head-on: the deliberate cross-tenant
read is a shell-run diagnostic with no request context, it is documented in the docblock as the exception it is, and
T-10 proves it reports every tenant rather than silently collapsing to one.

**8.6 G-PORTAL / G-TRUTH.** Do not trigger — no UI, no user-visible product claim.
