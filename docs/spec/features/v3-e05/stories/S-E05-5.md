## 1. The measurement, re-taken against `HEAD` before a line was written

`PF-07` reproduces. It also **undercounts on both axes**, and that undercount is why this story is P1.

### 1.1 It is FOUR handlers, not two

`apps/api/src/modules/attendance/attendance.controller.ts` (539 lines) carries seven handlers under
`@UseGuards(JwtAuthGuard, PermissionsGuard)`. `assertOwnership` — the controller's own ABAC, defined at
`:451` — is called on **exactly three**, all WRITE-shaped (`:110` `listSessions`, `:217` `openSession`,
`:282` `batch`). Four READ handlers carry a **tenant check and nothing else**:

| # | Handler | Route | Permission | Guard today | What it returns to an unauthorised caller |
|---|---|---|---|---|---|
| 1 | `sessionDetail` `:250` | `GET /class-sessions/:id` | `class_sessions.read` | `s.tenantId !== me.tenantId` (`:264`) | `teachingAssignment.classSection.enrollments{ include: { student: true } }` **and** `attendanceRecords{ include: { student: true } }` — the whole roster as full `Student` rows |
| 2 | `roster` `:410` | `GET /class-sessions/:id/roster` | `attendance.read` | `session.tenantId !== me.tenantId` (`:431`) | `roster[].student` — a full `Student` row per active enrolment |
| 3 | `studentAttendance` `:346` | `GET /attendance/students/:studentId` | `attendance.read` | tenant (`:354`) + a **parent-only** guardianship branch (`:357`) | one student's entire attendance history + summary |
| 4 | `overview` `:471` | `GET /attendance/overview` | `attendance.read` | `tenantId: me.tenantId` only | the **establishment-wide** 50 most recent records, each with `student.firstName/lastName`, class and subject |

A full `Student` row is `firstName`, `lastName`, `birthDate`, `email`, `phone`, `gender`, `nationality`,
`address`, `photoUrl`, **`medicalNotes`**, `notes`, `customFields` (`apps/api/prisma/schema.prisma:488`).
That is not "a roster"; it is the children's dossier.

Handler 3 is the subtle one: it *has* ABAC, and that is what hid it. The branch reads
`if (roles.includes('parent')) { …guardianship… }`. A caller who is **not** a parent skips the check
entirely, so the constraint is not "prove your relationship to this student" but "prove it *if you
volunteered that you are a parent*". Every other audience falls through to the full history of any student
in the tenant.

### 1.2 The exposed audience includes `parent`, not only `teacher`

The audit says *"any teacher"*. The catalogue (`apps/api/src/shared/auth/permissions.constants.ts`) says
more:

- `teacher` holds `class_sessions.read` (`:235`) **and** `attendance.read` (`:237`);
- **`parent` holds `class_sessions.read` (`:264`) and `attendance.read` (`:265`).**

So handlers 1, 2 and 4 are reachable **today** by any authenticated parent of the establishment. A parent
calling `GET /class-sessions/:id/roster` receives the full `Student` row of every child in that class —
other families' children. A parent calling `GET /attendance/overview` receives the establishment's 50 most
recent attendance records with names attached. This breaches the project's hardest stated constraint
(`bmad/GUARDRAILS.md` §1 — children's data, minimal access) with a read that has no ABAC at all.

`PF-07`'s severity is therefore **raised, not merely confirmed**: it is a cross-family PII read by the
audience least entitled to it, not only an over-broad teacher read. **The ADR must say this**, because the
audit sentence it supersedes is what a future reader will otherwise trust.

### 1.3 The caller census, re-run over `apps/web/src` (this is what makes the fix cheap)

| Route | First-party callers | Consequence |
|---|---|---|
| `GET /attendance/overview` | `apps/web/src/app/admin/attendance/page.tsx:80` — **admin only** | narrowing to privileged roles breaks **no** caller |
| `GET /attendance/students/:id` | `parent/attendance/page.tsx:219`, `parent/children/[id]/page.tsx:178`, `parent/children/[id]/report/page.tsx:159` — **parent only** | the parent branch must keep passing **byte-identically** |

| `GET /class-sessions/:id` | **none** | requiring ownership breaks no caller |

Every narrowing this story applies lands on a route whose only first-party caller already satisfies the

being changed. `scripts/boot-route-baseline.json:53,54,59` lists these routes: no route is added or
removed, so **that file must not change**. If it does, something outside this slice moved.

## 2. The design — resolve outside, compare purely

### 2.1 The house pattern this story follows

`apps/api/src/modules/lessons/lessons.controller.ts:114` `assertOwnedByTeacher` + its spec
`apps/api/src/modules/lessons/lessons-scope-ownership.spec.ts`. The shape is: the controller resolves the
caller's identity (a query), then hands **plain values** to an **exported pure function** that compares and
throws. The pure function is what the spec tests directly — no Nest testing module, no DI container.

Identity resolution uses `TeacherProfileService.findForUser`
(`apps/api/src/modules/teaching/teacher-profile.service.ts:94`) — a `findFirst` with an **explicit
`tenantId`**, returning `{ id } | null`. **Never `ensureForUser`** (which the controller's existing
`assertOwnership` uses at `:458`; that is `PF-265`, out of scope — see §6). `null` is not an error: a caller
with no teacher profile owns no session by construction of the foreign key, and is refused with the *same*
403 and the *same* message.

### 2.2 The five exported symbols to add to `attendance.controller.ts`

Place them above the `@Controller()` class, as `lessons.controller.ts` does. Docblocks in **French** — that
is the idiom of this codebase's newer security seams; match it.

```ts
/** Le contexte d'autorisation de l'appelant, résolu DEHORS, comparé PUREMENT. */
export interface AttendanceReadContext {
  /** `super_admin` / `school_admin` : la propriété n'est pas exigée d'eux. */
  readonly isPrivileged: boolean;
  /** `null` = l'appelant n'a AUCUN profil professeur (donc aucune séance). */
  readonly teacherProfileId: string | null;
}

/** 1 — le seul endroit qui nomme les deux rôles privilégiés de ce contrôleur. */
export function isPrivilegedAttendanceCaller(roles: readonly string[]): boolean;

/** 2 — AC-1 + AC-2 : la séance appartient-elle à l'appelant ? Même 403, même message. */
export function assertSessionReadable(
  context: AttendanceReadContext,
  sessionTeacherProfileId: string,
): void;

/** 3 — AC-5 : la vue établissement est réservée à l'administration. */
export function assertEstablishmentOverviewReadable(context: { readonly isPrivileged: boolean }): void;

/** 4 — AC-3 : l'assiduité d'UN élève. `ForbiddenException` NUE (AC-4). */
export function assertStudentAttendanceReadable(decision: {
  readonly isPrivileged: boolean;
  readonly isGuardian: boolean;
  readonly teachesStudent: boolean;
}): void;

/** 5 — AC-3 + AC-8 : le `where` de la sonde « ce professeur enseigne-t-il à cet élève ? ». */
export function teacherOfStudentWhere(input: {
  readonly tenantId: string;
  readonly studentId: string;
  readonly teacherProfileId: string;
}): Prisma.EnrollmentWhereInput;
```

**Bodies, pinned.** Deviations are findings, not style.

- `isPrivilegedAttendanceCaller` → `roles.includes('super_admin') || roles.includes('school_admin')`.
  Identical to the short-circuit at `:457`. Do **not** widen it; do **not** add an options bag or a
  `bypass` / `allow` / `skip` parameter (`DNC-10`).
- `assertSessionReadable` → `if (context.isPrivileged) return;` then
  `if (context.teacherProfileId === null || sessionTeacherProfileId !== context.teacherProfileId) throw new ForbiddenException('Vous ne pouvez consulter que les séances de vos affectations.');`
  One message for both handlers — AC-2 says *same* message.
- `assertEstablishmentOverviewReadable` → `if (!context.isPrivileged) throw new ForbiddenException("La vue d'ensemble de l'assiduité est réservée à l'administration de l'établissement.");`
- `assertStudentAttendanceReadable` → `if (decision.isPrivileged || decision.isGuardian || decision.teachesStudent) return;` then `throw new ForbiddenException();`
  **Naked, no message** — byte-identical to the parent refusal at `:361`, which AC-4 freezes.
- `teacherOfStudentWhere` returns exactly:
  ```ts
  {
    tenantId: input.tenantId,
    studentId: input.studentId,
    status: 'active',
    classSection: {
      teachingAssignments: {
        some: { tenantId: input.tenantId, teacherProfileId: input.teacherProfileId },
      },
    },
  }
  ```
  **Both `tenantId` clauses are explicit and neither is redundant.** Today's deployments run the
  `degraded_no_app_url` path, where the owner connection escapes its own RLS policies (`ADR-032 §D5` /
  `ADR-042 §D1`): these clauses are the only thing that filters. The relation hop is
  `Enrollment.classSection → ClassSection.teachingAssignments → TeachingAssignment.teacherProfileId`
  (`schema.prisma:666`, `:474`, `:1009`) — verified against the schema, not assumed.

### 2.3 Which column carries "the owner of this session" — decided, not left open

`ClassSession` carries **both** `teachingAssignmentId` and a denormalised `teacherProfileId`
(`schema.prisma:1129-1130`), the latter written from `a.teacherProfileId` at creation
(`attendance.controller.ts:238`). They can drift if an assignment is later reattributed.

**Use `classSession.teacherProfileId`** — the same column `batch` (`:282`) already trusts to authorise the
attendance **write**. The reason is a correctness argument, not a preference: the teacher attendance
workspace calls `POST /class-sessions/open` and then `GET /class-sessions/:id/roster` on the same session
(`actions.ts:19` then `:28`). If the read predicate were computed from a *different* column than the write
predicate, a drifted row would 403 the roster of a session the same teacher may legally write — turning a
hardening slice into an outage on the only caller it has. Read and write must refuse on the same bit.
Record the drift itself as a residual in the ADR; do not repair it here.

### 2.4 Refusal ORDER — 404 before 403, always

Every changed handler keeps the existing order: **tenant/existence first (`NotFoundException`), ownership
second (`ForbiddenException`)**. That is the order `listSessions` and `batch` already use (`:109`→`:110`,
`:281`→`:282`). Inverting it would make the 403 an existence oracle for another tenant's session ids —
`ADR-048 §D9`'s rule, and precisely the class of leak this epic exists to close. A foreign-tenant id must
still return a **bare 404**, indistinguishable from a nonexistent id.

## 3. The change plan, handler by handler

### 3.1 `sessionDetail` (`:248-266`) — AC-1

Split into **guard query, then payload query**. AC-1 says the refusal happens *before the payload is
assembled*: the deep `include` **is** the PII, and materialising it into the process for a caller who is
about to be refused is the defect, not a detail of ordering.

```ts
const me = await this.users.ensureUser(jwt);
const guard = await this.prisma.classSession.findUnique({
  where: { id },
  select: { id: true, tenantId: true, teacherProfileId: true },
});
if (!guard || guard.tenantId !== me.tenantId) throw new NotFoundException();
await this.assertSessionOwnership(guard.teacherProfileId, me, jwt);   // §3.5
// …le findUnique existant avec son include profond, INCHANGÉ, puis sa re-vérification tenant…
```

Keep the second query's `if (!s || s.tenantId !== me.tenantId) throw new NotFoundException();` as it stands.
It is now unreachable in practice; it costs one comparison and removes any argument about a TOCTOU window
between the two reads. Say so in a French comment rather than deleting it.

**Cost:** one extra primary-key `findUnique` selecting three scalar columns. Negligible — and this route has
no first-party caller at all.

### 3.2 `roster` (`:408-449`) — AC-2

Same two-step shape, same helper, same message. The guard `select` is
`{ id: true, tenantId: true, teacherProfileId: true }`; the existing deep query follows unchanged.

### 3.3 `studentAttendance` (`:344-405`) — AC-3 **and** AC-4

The parent block (`:356-362`) is **frozen**: same `roles` read, same `findFirst`, same `where` object, same
naked `throw new ForbiddenException()`, same position — before the records query. Do not extract it into a
helper, do not "harmonise" it with the new pure function, do not reorder it. AC-4 is the regression surface
of this whole story (three parent pages) and the cheapest way to keep it is to not touch it.

Add the teacher branch as an `else`:

```ts
const roles = jwt.realm_access?.roles ?? [];
if (roles.includes('parent')) {
  // …BLOC EXISTANT, INCHANGÉ À L'OCTET (AC-4)…
} else {
  const isPrivileged = isPrivilegedAttendanceCaller(roles);
  let teachesStudent = false;
  if (!isPrivileged) {
    const tp = await this.teachers.findForUser(me);          // JAMAIS ensureForUser (AC-6)
    if (tp) {
      const link = await this.prisma.enrollment.findFirst({
        where: teacherOfStudentWhere({ tenantId: me.tenantId, studentId, teacherProfileId: tp.id }),
        select: { id: true },
      });
      teachesStudent = link !== null;
    }
  }
  assertStudentAttendanceReadable({ isPrivileged, isGuardian: false, teachesStudent });
}
```

`isGuardian: false` is not a shortcut: on this branch the caller is not a parent, so guardianship was never
consulted. The parameter exists so the pure function states the **complete** rule in one place and can be
tested on all eight input combinations.

**A collision this story resolves in favour of AC-4, and records.** A caller holding *both* `parent` and
`teacher` realm roles (a teacher whose own child attends the school) takes the parent branch and is refused
unless they are a guardian of the requested student — even for a pupil they teach. That is **today's**
behaviour, unchanged, and no first-party caller reaches it (only parent pages call this route, §1.3).
Freezing it is what AC-4 requires. Recorded as **PF-266**, not fixed here.

### 3.4 `overview` (`:469-538`) — AC-5

One statement, and it goes **before `this.users.ensureUser(jwt)`**:

```ts
assertEstablishmentOverviewReadable({
  isPrivileged: isPrivilegedAttendanceCaller(jwt.realm_access?.roles ?? []),
});
const me = await this.users.ensureUser(jwt);
```

The decision needs only the token, so it is decidable before any database contact. Placing it first also
means a refused caller no longer reaches `ensureUser`, whose adoption branch can **write**
(`user-sync.service.ts:158`+) — a free reduction of the same "write on a refusal path" class that `PF-265`
records. This ordering is deliberate; keep a French docblock saying why, so a later reader does not "tidy"
it back below `ensureUser`.

### 3.5 The private helper (new, beside the existing `assertOwnership` at `:451`)

```ts
/**
 * S-E05-5 — la RÉSOLUTION d'identité pour les chemins de LECTURE. Lecture seule
 * (`findForUser`), jamais `ensureForUser` : un refus ne doit PROVISIONNER rien
 * (ADR-051 §D1). Non fusionnée avec `assertOwnership` (:451) délibérément — ce
 * dernier reste sur `ensureForUser` et ses trois sites d'appel sont hors de la
 * portée de cette tranche (PF-265).
 */
private async assertSessionOwnership(
  sessionTeacherProfileId: string,
  me: { id: string; tenantId: string },
  jwt: KeycloakJwtPayload,
): Promise<void> {
  const isPrivileged = isPrivilegedAttendanceCaller(jwt.realm_access?.roles ?? []);
  const tp = isPrivileged ? null : await this.teachers.findForUser(me);
  assertSessionReadable({ isPrivileged, teacherProfileId: tp?.id ?? null }, sessionTeacherProfileId);
}
```

The privileged short-circuit skips the query entirely: an admin never needs a teacher profile, and not
asking for one is one fewer statement on the hot admin path.

## 4. Acceptance criteria

- **AC-1** — `sessionDetail` refuses a caller who is neither privileged (`super_admin` / `school_admin`) nor
  the owner of the session, with `403`, **before** the deep-include payload query is issued.
- **AC-2** — `roster` refuses on the same rule, same `403`, same message string.
- **AC-3** — `studentAttendance` gains a **teacher** branch: a teacher may read only when the student holds
  an `active` enrolment in a `classSection` the caller is assigned to teach. A caller who is neither
  privileged, nor a guardian of the student, nor a teacher of the student is refused `403`.
- **AC-4** — the **parent** path of `studentAttendance` is unchanged to the byte: same query, same naked
  `403`, same payload. Proven by a test that **exercises** the parent branch, not by inspection.
- **AC-5** — `overview` is refused to any caller who is not `super_admin` / `school_admin`, `403`.
- **AC-6** — ownership resolution uses `TeacherProfileService.findForUser` (read-only), never
  `ensureForUser`. No refusal path provisions a `TeacherProfile` (`ADR-051 §D1`).
- **AC-7** — every new authorization decision is an **exported pure function** taking its inputs as
  parameters and tested directly, following `assertOwnedByTeacher` (`lessons.controller.ts:114`).
- **AC-8** — the fake Prisma / `tx` in the spec is **non-filtering**: it honours exactly the `where` it is
  given and applies no ambient tenant filter, so a test cannot pass on a query that lost its `tenantId`
  clause.
- **AC-9** — no permission code is added, removed or re-granted in `permissions.constants.ts`.
- **AC-10** *(added by this authoring pass — the failure mode a pre-mortem surfaces first)* — refusal
  **order** is preserved: a foreign-tenant or nonexistent session/student still returns a bare `404`, never
  a `403`. A test asserts the foreign-tenant id yields `NotFoundException` on each of the three
  id-addressed handlers, so the new 403 can never become a cross-tenant existence oracle.
- **AC-11** *(added by this authoring pass)* — `scripts/boot-route-baseline.json` is **unchanged**: this
  story adds and removes no route. A diff there means the change escaped its blast radius.
- **AC-21** *(added by the land pass, 2026-08-23 — **defined here because four shipped documents already cite
  it**: `traceability/OPEN.md:53`, the `PF-269` row at `OPEN.md:59`, `audit-findings-index.md:156` and
  `NEXT.md:56`. It was allocated in the 20-block, not as `AC-12`, so that a later authoring pass of this same
  story may still take `AC-12`… without colliding with a criterion the traceability layer already references.
  A criterion cited from four places and defined in none is the `TOOL-01` dangling-id class — the very class
  this slice invoked as its reason for declaring `PF-264`…`PF-274` in the same commit.)* — **`PF-07` may not
  be recorded as `closed` on the strength of this slice.** This story closes the **WHO** axis only: it decides
  *which caller* may read, and changes **nothing** about *what is returned*. `roster` and `sessionDetail` keep
  `include: { student: true }`, so the owning subject-teacher still receives `medicalNotes`, `address`,
  `notes`, `customFields`, `birthDate`, `email` and `phone` for every child in the class on every
  attendance-taking page load. That **WHAT** axis is carried forward as **`PF-269`**, and `PF-07`'s row must
  read `in-progress` with the qualifying sentence attached until `PF-269` lands. The failure mode this
  criterion exists to prevent is not a leak on day 1 — it is `PF-07` being ticked `closed` and the maximal
  payload thereby losing its only advocate.

### 5.2 The test file

**New:** `apps/api/src/modules/attendance/attendance-read-abac.spec.ts`, modelled on
`apps/api/src/modules/lessons/lessons-scope-ownership.spec.ts` (881 lines — read its `makeDb()` and its
header block before writing).

Two layers, both required:

1. **Pure-function tests** — `assertSessionReadable` over the four `(isPrivileged, teacherProfileId)` ×
   owner / not-owner combinations; `assertStudentAttendanceReadable` over all **eight** boolean triples;
   `assertEstablishmentOverviewReadable` both ways; `isPrivilegedAttendanceCaller` on `super_admin`,
   `school_admin`, `teacher`, `parent`, `[]`. Assert the **exact message string** where one exists, and
   assert that `assertStudentAttendanceReadable`'s refusal carries **no** message (AC-4).
2. **Controller tests against a non-filtering fake** (AC-8) — instantiate `AttendanceController` directly
   with hand-rolled doubles for `PrismaService`, `UserSyncService` and `TeacherProfileService` (no Nest
   testing module). The fake honours the scalar `where` it is given and applies **no** ambient tenant
   filter; relational members are recorded and treated as satisfied, exactly as `lessons-scope-ownership`
   does. Then:
   - drive the §5.1 matrix through the real handlers;
   - assert `teachers.ensureForUser` is **never called** on any new path (AC-6) — spy, and assert
     `findForUser` *is* the one called;
   - assert on `sessionDetail` and `roster` that the **statement journal** shows the guard `findUnique`
     (three scalar columns) *before* any statement carrying `include`, and that on a 403 the deep query was
     **never issued** (AC-1);
   - assert the recorded `where` of the `enrollment.findFirst` **contains `tenantId`** — the half that
     proves the clause is in the code and not in the fixture;
   - drive the parent branch end-to-end, both outcomes, and assert the 200 payload is deep-equal to the
     pre-change payload for the same fixture (AC-4).

Allocate from **PF-264** upward — `main`'s maximum is `PF-255` and open PR **#263** already claims

| Id | Pri | Finding |
|---|---|---|
| **PF-264** | P1 | **The catalogue over-grant.** `parent` holds `class_sessions.read` (`permissions.constants.ts:264`) and `attendance.read` (`:265`) — the reason the missing ABAC was exploitable by parents at all. Removing a grant is a four-portal decision touching Keycloak role sync, and `PF-53` owns catalogue drift. `AC-9` forbids doing it here. Three existing call sites (`:110`, `:217`, `:282`), out of this slice's blast radius. The fix is mechanical once someone owns the risk that `ensureForUser` also resolves the school and can 404 differently. |
| **PF-266** | P3 | **The `parent` realm role short-circuits the teacher branch of `studentAttendance`.** A caller holding both `parent` and `teacher` is evaluated on the guardianship rule only, so a teacher-parent is refused a pupil they teach. Pre-existing, frozen by `AC-4`, reachable by no first-party caller (§1.3). The honest fix is to evaluate all three predicates and OR them — which cannot be done while `AC-4` demands byte-identity. |
| **PF-267** | P3 | **A `DNC-06`-shaped doc/runtime mismatch in the same file.** `justify` (`:315`) is documented *"admin or teacher of the class"* but performs **no** ownership check, and `attendance.justify` is granted to `school_admin` only (`permissions.constants.ts:188`), never to `teacher` (`:221-255`). The docblock promises a rule the runtime does not implement, on a **write** handler; if a custom role ever grants `attendance.justify` to a non-privileged actor the missing check becomes live. Cheapest honest fix: correct the docblock **and** add the ownership check on the record's session. |
| **PF-268** | P2 | **"Privileged" is a realm-role-name test, blind to custom roles.** `isPrivilegedAttendanceCaller` (and the pre-existing `:457`) tests `super_admin` / `school_admin` by **name**, while the permission layer resolves custom roles through `UserSyncService.effectivePermissions` (`permissions.guard.ts:29`). Correct for this slice (its only caller is the admin page, §1.3) and deliberately not widened: the alternative is a new permission code, which `AC-9` forbids and `ADR-015` owns. |
