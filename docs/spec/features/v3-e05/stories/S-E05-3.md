## §1 — The defect, at the line

**File** `apps/api/src/modules/school-structure/subjects.controller.ts`
**Handler** `upsertCoefficients`, `@Put('coefficients/matrix')`, `@RequiresPermission('subjects.write')`

### 1.1 What the DTO proves, and what it does not

```ts
class CoefficientEntry {
  @IsUUID() gradeLevelId!: string;
  @IsUUID() subjectId!: string;
  @IsNumber() @Min(0.1) @Max(20) coefficient!: number;
}
class BulkCoefficientDto {
  @ValidateNested({ each: true }) @Type(() => CoefficientEntry) entries!: CoefficientEntry[];
}
```

`@IsUUID()` proves the id is *well-formed*. It proves nothing about *whose* it is. The handler never asks.

### 1.2 The write, verbatim

```ts
await this.prisma.$transaction(async (tx) => {
  for (const e of body.entries) {
    await tx.subjectCoefficient.upsert({
      where: { gradeLevelId_subjectId: { gradeLevelId: e.gradeLevelId, subjectId: e.subjectId } },
      update: { coefficient: e.coefficient },
      create: { tenantId: me.tenantId, gradeLevelId: e.gradeLevelId, subjectId: e.subjectId, coefficient: e.coefficient },
    });
  }
  await writeAudit(tx, { /* … action: 'coefficient.upsert' … */ });
});
```

`apps/api/prisma/schema.prisma:436-451` confirms the shape that makes this reachable:

```prisma
model SubjectCoefficient {
  tenantId     String @map("tenant_id") @db.Uuid
  gradeLevelId String @map("grade_level_id") @db.Uuid
  subjectId    String @map("subject_id") @db.Uuid
  @@unique([gradeLevelId, subjectId])   // ← NO tenant column in the key
}
```

**Three distinct harms, all live:**

| # | Branch | Harm |
|---|---|---|
| (a) | `update` | A caller in tenant A naming tenant B's `(gradeLevelId, subjectId)` pair **rewrites tenant B's coefficient row**. Every weighted average of every pupil of tenant B moves. **This is PF-10.** |
| (b) | `create` | A foreign pair with no row yet creates one stamped `tenantId: me.tenantId` while both FKs point at another tenant's `grade_level` / `subject` — a row whose tenant column **lies about its content**. Same "dark row" shape as PF-208. |
| (c) | post-commit | The recompute enqueue does `[...new Set(body.entries.map((e) => e.subjectId))]` and upserts `snapshot_recompute_trigger` rows under `me.tenantId` carrying a **foreign `subjectId`**. A third dark row. |

**(c) is fixed BY CONSTRUCTION and must not be fixed twice.** The enqueue block sits *after*
`await this.prisma.$transaction(...)`. A rejection from inside the transaction propagates out of the handler and the
`try { … } catch` around the enqueue is **never entered** — it is a sibling, not a wrapper. Refusing the request
first is the whole fix. **Do not add a second filter there.**

### 1.3 The siblings are CORRECT — do not touch them

* `GET coefficients/matrix` reads `subjectCoefficient.findMany({ where: { subject: { schoolId } } })` — scoped.
* `POST /subjects` (`create`) derives its levels from `tx.gradeLevel.findMany({ where: { schoolId } })` — derived,
  never accepted from the caller.
* `PATCH :id` / `DELETE :id` re-read the row and compare `subject.tenantId !== me.tenantId` — guarded.

**`upsertCoefficients` is the only leak in this file.** Leave `list`, `create`, `update`, `remove` and the GET matrix
untouched, byte for byte.

### 1.4 The one thing the handler is missing that every sibling has

`upsertCoefficients` is the **only** handler in this controller that never calls
`await this.ctx.forTenant(me.tenantId)`. That absence *is* the defect's enabling condition: with no `schoolId` in
hand there is nothing to compare the caller's ids against. AC-1 restores it.

## §2 — The design. Implement this; do not redesign it.

### 2.1 Scope by `schoolId`, not by `tenantId` — and know what that costs

Both probes filter on `schoolId`, the value the sibling GET and `create` already use. Not `tenantId`.

* `GradeLevel` and `Subject` both carry `schoolId` (`schema.prisma:388`, `:412`), and both carry `tenantId`.
* A tenant may own several schools (`SchoolContextService.forTenant` resolves the *active* one).
* The GET matrix only ever hands the UI subjects and levels of the **active school**, so the admin UI can only ever
  submit ids of the active school. Scoping the probe to `schoolId` therefore refuses nothing a real save produces.

**Named limit (state it, do not paper over it):** a save naming a grade level of *another school of the same tenant*
would now be refused. That is strictly narrower than tenant scoping, it matches what the read surface can produce,
and it matches the sibling handlers. If a multi-school workflow ever needs the wider form, it is a new slice with its
own evidence — not a quiet relaxation here.

### 2.2 The pure half — ONE new export in `apps/api/src/shared/prisma/scope-fk.ts`

```ts
export function distinctScopeIdPlan<F extends string>(
  rows: readonly ScopeIdCarrier<F>[],
  fields: readonly F[],
): { field: F; ids: string[] }[];
```

Contract, all four clauses load-bearing:

1. Returns **exactly one entry per field, in the order of `fields`** — so the caller may destructure positionally.
2. `ids` is **de-duplicated and order-preserving** (first occurrence wins). This is what makes AC-5 true.
3. A row whose `field` is **not** `isSuppliedScopeId` (i.e. not a non-empty string) **throws
   `unknownScopeRef(field)` immediately** — it is NOT skipped. Skipping is the vacuous path constraint 4 exists to
   forbid: `findMany({ where: { id: { in: [] } } })` returns `[]`, `0 === 0`, and the check passes having proved
   nothing. Refusing is the only safe reading of "there is an id here that I cannot verify".
4. It imports no Prisma, touches no database, and dispatches nothing by model name. `ADR-049` §D5's refusal of a
   generic `assertOwnedByTenant(tx, modelName, id, tenantId)` still stands and this does not contradict it.

**RATCHET — non-negotiable.** `prisma.service.spec.ts:317` builds its module list with
`readdirSync(__dirname).filter(name => name.endsWith('.ts') && !name.endsWith('.spec.ts'))`. **Every** non-spec file
in `apps/api/src/shared/prisma/` is under the AC-7 source ratchet, `scope-fk.ts` included. It refuses any template
literal containing an untagged `${}` — it does not distinguish SQL from a French error message, and that is
deliberate. **Use string concatenation for every message you write in that folder**, exactly as `assertSingleScopeId`
and `unknownScopeRef` already do. The same file also bans, *including inside comments* (it matches on `mod.source`,
not on stripped code), the tokens `SYSTEM_TENANT`, `SKIP_`, `ALLOW_` and `skipTenant`. Do not write them in your
docblock. **Never relax the ratchet to accommodate moved code — the code adopts the rule of its new home** (the
S-E01-1f ruling).

Keep the file's existing voice: French technical prose, ADR references, the *why* not the *what*. Say in the
docblock why clause 3 refuses instead of skipping — that sentence is the whole security value of the helper.

### 2.3 The impure half — INLINE in the handler, and it stays inline

```ts
/** Les deux FK de portée que porte une entrée de coefficient, dans l'ORDRE DE SONDAGE. */
const COEFFICIENT_SCOPE_FIELDS = ['gradeLevelId', 'subjectId'] as const;
```

Inside `upsertCoefficients`, in this exact order:

```ts
const me = await this.users.ensureUser(jwt);
const { actorRole, portal, ipAddress, userAgent } = deriveAuditProvenance(   // ← UNCHANGED, stays first
  jwt,
  extractAuditClientHints(req),
);
if (!Array.isArray(body.entries) || body.entries.length === 0) {             // ← UNCHANGED
  throw new BadRequestException('Aucune entrée à enregistrer.');
}
const { schoolId } = await this.ctx.forTenant(me.tenantId);                  // ← NEW (AC-1)

await this.prisma.$transaction(async (tx) => {
  // --- AC-1 : la preuve de propriété, AVANT que la boucle d'écriture n'ouvre ---
  const [levels, subjects] = distinctScopeIdPlan(body.entries, COEFFICIENT_SCOPE_FIELDS);

  const ownedLevels = await tx.gradeLevel.findMany({
    where: { id: { in: levels.ids }, schoolId },
    select: { id: true },
  });
  if (ownedLevels.length !== levels.ids.length) throw unknownScopeRef(levels.field);

  const ownedSubjects = await tx.subject.findMany({
    where: { id: { in: subjects.ids }, schoolId },
    select: { id: true },
  });
  if (ownedSubjects.length !== subjects.ids.length) throw unknownScopeRef(subjects.field);

  for (const e of body.entries) { /* …UNCHANGED… */ }
  await writeAudit(tx, { /* …UNCHANGED… */ });
});
```

Why each decision:

* **`forTenant` goes AFTER the provenance extraction and AFTER the empty-body guard, immediately before
  `$transaction`.** Nothing above it moves. `deriveAuditProvenance` / `extractAuditClientHints` stay extracted above
  `$transaction` — the S-E06-6 ordering rule: a failed `inet` cast must never roll back the record it traces.
  `audit-provenance-gate.spec.ts:672-689` asserts on `deriveAuditProvenance(\s*jwt,` and `extractAuditClientHints(req)`
  by regex; moving them is how you turn a green gate red for nothing.
* **Counting, not `Set` membership.** `id` is the primary key, `ids` is de-duplicated, so
  `owned.length === ids.length` holds **iff** every id is owned. One comparison, no second hand-maintained list —
  the `paired-lists-drift` lesson.
* **Probe order is `gradeLevelId` then `subjectId`, declared once in `COEFFICIENT_SCOPE_FIELDS`.** When both are
  foreign the message names `gradeLevelId`. That is deterministic, derived from the tuple, and asserted.
* **The field name in the message is `levels.field` / `subjects.field`, read back from the plan — never a literal.**
  Two hand-kept lists that drift is a repeated defect of this repository. Derive.
* **`select: { id: true }`** — the probe needs nothing else, and a `select` keeps a future `include` from making the
  probe expensive on a 30-entry save.

### 2.4 What must NOT happen

1. **Do not convert this module to `TenantScopeService` / `this.scope.run(...)`.** That is V3-E01's PF-02 work and is
   explicitly out of scope. `ADR-054` §D2 is the recorded refusal of exactly this reflex: threading the scope here
   moves the `tenant-adversarial-check.js` counter and widens a globally probed closure for zero security gain in
   this slice. This controller keeps using `this.prisma` / `tx` as it does today.
2. **Do not hide the two `findMany` behind a shared service method.** `PF-200`: `tenant-adversarial-check.js`
   attribution is **lexical** and does not traverse `this`. A probe behind a shared method counts as NOT COVERED
   while looking converted — the worst of both.
3. **No `catch` around the probe or the transaction.** A swallowed refusal is a fail-open and an automatic
   `G-AUTHZ` failure. The only `try/catch` in this handler stays where it is: around the post-commit enqueue, after
   the `await`, where it cannot see the refusal (§1.2).
4. **DNC-10.** No env flag, no `demo` tenant escape hatch, no `if (process.env.NODE_ENV === 'test')` in the probe.
5. **Do not reflow the existing docblocks** unless you check no spec asserts on their text (PF-237: a docblock reflow
   once broke a `toContain`). `audit-provenance-gate.spec.ts` and `provenance-callsites.spec.ts` both read this file.

## §3 — Acceptance criteria (verbatim, as commissioned)

**AC-1** Before ANY write, `upsertCoefficients` proves that every DISTINCT `gradeLevelId` and every DISTINCT
`subjectId` appearing in `entries[]` belongs to the caller's school
(`const { schoolId } = await this.ctx.forTenant(me.tenantId)`, which the handler does not currently fetch and must).
The proof runs INSIDE the same `this.prisma.$transaction` callback, on `tx`, and BEFORE the upsert loop opens.

**AC-2** An id that is foreign OR simply unknown is refused with the SAME 400, byte-identical in both cases
(ADR-049 §D2 indiscernability — distinguishing them would be a cross-tenant existence oracle). The message names only
the CALLER-SUPPLIED FIELD, never a tenant, a school, a table, a row count or a Postgres string. Reuse
`unknownScopeRef(field)` from `apps/api/src/shared/prisma/scope-fk.ts` — do NOT write a new message.

**AC-3** Refusal is ALL-OR-NOTHING. A 30-entry body containing ONE foreign id writes ZERO `subject_coefficient` rows,
ZERO audit rows and ZERO `snapshot_recompute_trigger` rows. Prove this with a spy assertion that
`tx.subjectCoefficient.upsert` was called EXACTLY ZERO times, not merely that the promise rejected.

**AC-4** The happy path is unchanged to the byte: same rows upserted in the same order, the SAME `writeAudit` row with
`action: 'coefficient.upsert'` in the SAME transaction (G-AUDIT must not regress), the same recompute-trigger enqueue,
the same `{ ok: true, count: body.entries.length }` response.

**AC-5** The probe is emitted per DISTINCT id, not per entry. A body of 6 subjects x 5 grade levels = 30 entries must
emit exactly 2 ownership queries (one `findMany` per model over the distinct id set), NOT 60 findFirsts. Assert the
emitted `where.id.in` arrays by content, and assert the CALL COUNT, so a later refactor to per-entry probes fails the
test.

**AC-6** MUTATION CONTROL, executed: after the suite is green, revert exactly one thing (delete the gradeLevel
ownership probe) and show the suite goes RED; restore and verify the file's sha256 is identical. Report both runs in
the evidence.

**AC-7** An entry whose `gradeLevelId` and `subjectId` are BOTH owned but which names a pair that already has a row
belonging to the caller still UPDATES normally — the fix must not turn ordinary saves into refusals. This is the
false-positive control.

**AC-8 (added by this authoring pass, §0.3)** The three existing `tx` doubles in
`apps/api/src/shared/audit/provenance-callsites.spec.ts` (~300, ~344, ~376) are extended with `gradeLevel.findMany`
and `subject.findMany` returning the ids they already send, and all three cases are green again. **No assertion in
that file is deleted, weakened or re-spelled.**

## §12 — AC-14, the merge condition the escalation panel imposed, and how it was discharged

*Added by the routine's land pass, 2026-08-22, after the escalation panel returned* **CONCERNS — conditional GO, do
not auto-merge** *on an otherwise green slice.*

### The objection, restated exactly

Every id this suite accepts came from constants the suite itself declares (`GL_A`, `S_A`). The suite therefore proved
that the PUT accepts ids **the test invented** — never ids the **sibling GET emits**. That is a second hand-kept list,
which is the defect class this repository re-hits more than any other (`project_paired_lists_drift`), and it mattered
here because the gap sits on the failure mode this diff **introduces** rather than the one it closes:

| Surface | Predicate on its axes |
|---|---|
| `GET /subjects/coefficients/matrix` | `{ schoolId }` — and `{ schoolId, active: true }` for subjects |
| `PUT /subjects/coefficients/matrix` (new probe) | `{ id: { in }, tenantId, schoolId }` |

`subject.tenant_id` and `grade_level.tenant_id` are denormalised beside `school_id` with **no constraint linking
them**. Any row where they disagree is therefore **rendered by the GET and refused by the PUT** — and because AC-3
makes refusal all-or-nothing, and `SubjectsManager.tsx` posts the whole dirty set and surfaces the raw 400, a single
drifted axis makes the coefficient matrix **unsavable** for an administrator who did nothing wrong. `ADR-055 §D3`
names this risk in prose. Nothing measured it, and `forTenant` is mocked to a fixed school in every other case, so the
suite **structurally could not** observe it.

### AC-14 (new)

> The matrix the sibling GET renders is accepted **verbatim** by the PUT, with the entries **derived** from the GET's
> own response and never from a constant declared in the spec file; both surfaces resolve the school through the
> **same** `forTenant(tenantId)` call; and the drift that separates them is pinned by a case that goes RED when it
> occurs.

### How it was discharged

Three cases were added under `aller-retour GET → PUT — les ids viennent de la surface sœur, pas du test`:

1. **the round trip** — `coefficientMatrix()` is called on the same fake database, `entries` are built by
   `matrix.gradeLevels.flatMap(... matrix.subjects.map(...))`, the PUT resolves `{ ok: true, count: 30 }`, and
   `forTenant` is asserted to have been called **twice, with the same argument** — so a later "improvement" swapping
   `forTenant` for `forUser` (which honours `preferences.activeSchoolId`) would diverge from the GET and redden here;
2. **the victim is not even reachable** — the GET renders neither `GL_B`/`S_B` nor the caller-tenant's *other* school's
   level, so the round trip cannot accidentally target them;
3. **the drift control** — one axis's `tenantId` is drifted away from its school; the GET still renders it and the PUT
   refuses the **whole body**. Recorded as **`PF-241`**, pinned rather than fixed: the honest remedy is `PF-239` (put
   the tenant in the key) or dropping `tenantId` from the probe, and either is its own diff.

The harness work AC-14 forced is the point, not overhead: the **non-`tx`** `prisma` double gained `gradeLevel`,
`subject` and `subjectCoefficient` reads backed by the **same** `db` and the **same** `matches()`, seed rows gained the
columns the GET projects, and the GET's nested relation filter `{ subject: { schoolId } }` is resolved by a **real
join through `db.subject`** — every other nested shape still throws `opérateur non supporté`, so the fake database
keeps its ability to fail.
