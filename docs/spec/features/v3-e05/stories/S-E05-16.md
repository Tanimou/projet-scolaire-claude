## 1. The defect, re-measured this run

`apps/api/src/modules/students/student-access.service.ts:36-38`, verbatim on the pre-diff tree:

```ts
if (roles.includes('teacher')) {
  // TODO Phase 4: when teaching assignments exist, filter by the teacher's class sections.
  return { studentIds: null, reason: 'teacher (unrestricted until teaching assignments land)' };
}
```

`studentIds: null` is **this service's own documented UNRESTRICTED sentinel**. Its docblock says so at `:21`:

```
 * The service returns a "scope" object that controllers fold into their `where` clauses.
 * `studentIds: null` means "no restriction"; a non-null array narrows the result set.
```

The `TeachingAssignment` rows the TODO waits for **shipped long ago** (`schema.prisma:1006`, with
`@@unique([teacherProfileId, classSectionId, subjectId])` and `@@index([tenantId, classSectionId])`).
`S-E05-14` and `S-E05-15` both walk them directly, and `enrollments.controller.ts:678-686` states in a docblock
**why it refused to delegate to this service**: delegating would have shipped a control that is a **no-op for
`teacher`** — *"tous les tests négatifs PARENT passeraient au vert pendant que la fuite survit, le pire résultat
possible pour une tranche `G-AUTHZ`."*

### 1.1 Consequence 1 — the list route, fail-open by absent key

`apps/api/src/modules/students/students.controller.ts:88-133`:

```ts
@Get()
@RequiresPermission('students.read')
async list(
  @CurrentJwt() jwt: KeycloakJwtPayload,
  @Query('q') q?: string,
  @Query('status') status?: StudentStatus,          // ← a CAST, not a check
  @Query('classSectionId') classSectionId?: string, // ← unvalidated, reaches a @db.Uuid column
  @Query('academicYearId') academicYearId?: string, // ← unvalidated, reaches a @db.Uuid column
  @Query('unenrolled') unenrolled?: string,
  @Query('limit') limit?: string,
  @Query('offset') offset?: string,
) {
  const me = await this.users.ensureUser(jwt);
  const { schoolId, activeAcademicYearId } = await this.ctx.forUser(me);
  const scope = await this.access.scopeForUser(me, jwt, schoolId);

  const where: Record<string, unknown> = {
    tenantId: me.tenantId,
    schoolId,
    ...(scope.studentIds ? { id: { in: scope.studentIds } } : {}),   // ← ADR-065 §D5 forbids this shape
    ...(status ? { status } : {}),
    ...
  };

  if (classSectionId) {
    where.enrollments = { some: { classSectionId, status: 'active', ...(academicYearId ? { academicYearId } : {}) } };
  } else if (unenrolled === 'true' && activeAcademicYearId) { ... }
```

Two defects in that spread, and they are **different defects**:

* `...(scope.studentIds ? … : {})` is the **absent-key fail-open**: `null` *and* `[]` both fall to `{}`. Today only
  `null` reaches it, but the shape means that the day any branch legitimately returns `[]` the key vanishes and the
  scope silently widens to the whole school. `ADR-065 §D5` names this exact shape and forbids it: **the empty array
  is the DENY, the absent key is the fail-open.**
* `teacher` holds `students.read` (`permissions.constants.ts:223`). So
  `GET /api/v1/students?classSectionId=<any section in the tenant>` lets **any** teacher enumerate **any** class's
  roster, and the response is **whole `Student` rows** (`firstName`, `lastName`, `birthDate`, `email`, `phone`,
  `gender`, `nationality`, `address`, `medicalNotes`, `notes`, `externalRef`, `photoUrl`, `customFields`) plus
  enrollments and guardianships — strictly wider than the four-column projection `/enrollments` now emits after
  `S-E05-15`. **The door `S-E05-15` closed is narrower than the one left open.**

### 1.2 Consequence 2 — `canAccessStudent` is unconditionally `true` for a teacher

`student-access.service.ts:66-75`:

```ts
async canAccessStudent(user, jwt, studentId, schoolId): Promise<boolean> {
  const scope = await this.scopeForUser(user, jwt, schoolId);
  if (scope.studentIds === null) return true;
  return scope.studentIds.includes(studentId);
}
```

This is the ABAC boundary for **~25 call sites** across `alerts`, `analytics`, `messaging`, `parent-exports`,
`remediation`, `student-portal`, `students`. For `teacher` it returns `true` for **every student in the tenant**.
The blast-radius table is `AC-5`, and a starting census is §5 below.

### 1.3 The divergence has started spreading

`alerts/meeting-requests.service.ts:8-14` already hand-rolls a workaround **around** this service, and says so:

```
 * teachers see only requests assigned to them OR unassigned within their school (they must NOT
```

Two decisions already arbitrated there, which this slice **inherits rather than re-litigates**:

* **No academic-year clause** (`ADR-063 §D1`): `ClassSection.academicYearId` is non-null, so the section id already
  carries the year; and `TeachingAssignment.academicYearId` can **diverge** from its section's (plain column, no
  composite FK), so filtering on it would refuse a teacher who really teaches the class today.
* **`new Set` and not Prisma `distinct`**: a teacher holds one assignment **per subject** on the same section
  (`@@unique([teacherProfileId, classSectionId, subjectId])`), so duplicates are normal; dedupe in JS because a jest
  double silently ignores `distinct` and would make the scope true for the wrong reason.

### 2.3 The pipe options, verified against the pinned source (not assumed)

Read this run at
`node_modules/.pnpm/@nestjs+common@10.4.22_…/node_modules/@nestjs/common/pipes/`:

* `parse-enum.pipe.d.ts` — `interface ParseEnumPipeOptions { optional?: boolean; errorHttpStatusCode?; exceptionFactory? }`.
  `parse-enum.pipe.js` — `if (isNil(value) && this.options?.optional) return value;` then
  `if (!this.isEnum(value)) throw this.exceptionFactory('Validation failed (enum string is expected)')`, default
  status `HttpStatus.BAD_REQUEST`. **`optional` exists and skips only on `null`/`undefined`.**
* `parse-uuid.pipe.d.ts` — `interface ParseUUIDPipeOptions { version?: '3'|'4'|'5'|'7'; errorHttpStatusCode?; exceptionFactory?; optional?: boolean }`.
  Same `isNil && optional` short-circuit; with **no** `version` it uses the `all` regex.

**Consequence to encode, not discover:** `?status=` (present but empty) is `''`, which is **not** nil, so it is
refused **400** — a behaviour change from today's `...(status ? { status } : {})`, which treats `''` as absent.
State it; do not claim the pre-state (`DNC-06`).

**Do not pass `{ version: '4' }`** to `ParseUUIDPipe`. Every id in `schema.prisma` is `@default(uuid()) @db.Uuid`
(52 occurrences, 0 `cuid()`), but imported/seeded rows are not guaranteed v4, and the `all` regex is the safe wall.

## 4. Acceptance criteria

**AC-1 (G-AUTHZ, the fix).** The `teacher` branch of `scopeForUser` returns a **non-null** `string[]`: exactly the
ids of students holding an `active` enrollment in a `ClassSection` the caller holds a `TeachingAssignment` for. The
`null` sentinel survives for `super_admin` / `school_admin` **only**. Shape to reach, stated as intent not as code:
resolve the profile → resolve the assigned `classSectionId`s (deduped) → resolve the distinct `studentId`s of
`active` enrollments in those sections. Follow §2.1: **no academic-year clause**, dedupe in JS.

**AC-2 (deny-by-default).** A `teacher` with **no** `TeacherProfile` resolves to `[]`, never `null`, and a teacher
with a profile but **zero** assignments also resolves to `[]`. Use `TeacherProfileService.findForUser`
(`teaching/teacher-profile.service.ts:94`) and **never** `ensureForUser` — the latter is an UPSERT and would
provision a `TeacherProfile` row on a **refusal** path (`PF-265` / `ADR-051 §D1`). `GET /api/v1/students` is a list
route hit on every page load; an upsert there is a sink.

**AC-3 (G-TENANT).** Every query the new branch issues carries `tenantId: user.tenantId` — the profile lookup, the
assignment lookup and the enrollment lookup, all three, **explicitly**, even where a `@unique` or a join would seem
to imply it (`ADR-042 §D1`: on `degraded_no_app_url` — i.e. every deployment today — the owner connection escapes
its own RLS policies and this clause is the only thing working). A foreign-tenant `classSectionId` must fall on an
**empty intersection**, never on an authorisation.

**AC-4 (no fourth copy of the teaching wall).** `PF-270` already records **three** divergent copies of the
teaching-wall predicate (`messaging.service.ts:90` `isTeacherOfStudent`, `remediation.service.ts:912`, and the
`S-E05-5` copy on a different join key). Do **not** add a fourth. Either reuse the exported `teacherSectionsWhere`
(`enrollments.controller.ts:405`) through a placement both modules can import, or write an ADR decision stating why
a service-local derivation is correct and record the consolidation as still-open. **Deciding this is part of the
slice; silently copying is a fail.**
**Ratchet hazard, named in advance:** moving code between folders has broken `scripts/ci-gate.sh` before *without
changing a line of logic* (the `AC-7` template-literal rule that applies inside `shared/prisma/`). If a move is
chosen, **adopt the destination folder's rules; never relax a ratchet.** A move out of `enrollments.controller.ts`
also changes that file's import surface, which `S-E05-15`'s specs assert against — re-read them before moving.

**AC-5 (blast radius, DECLARED not discovered).** Enumerate **every** `canAccessStudent` call site whose verdict
changes for a `teacher`, and say for each whether the new refusal is **INTENDED**. ~25 sites tighten at once. An
unintended tightening on the student or parent portal is a **regression, not a fix**. Any site whose refusal is not
intended must be **named and recorded as a finding**, never silently exempted. §5 below is the starting census,
measured this run — a starting point to verify, not a result to copy. **Specifically verify that
`student-portal.service.ts` (its `canAccessStudent(me, jwt, self.id, …)` sites, for the `student` role) is
untouched** — and read §5.3, which says why "untouched" is not automatic.

**AC-6 (PF-51 clause 3 — the roadmap half).** `GET /api/v1/students` validates its query parameters at the pipe:

* `status` → `ParseEnumPipe(StudentStatus, { optional: true })`. **This IS the surviving enum clause of `PF-51`**;
  it is today a bare `@Query('status') status?: StudentStatus`, a **cast not a check**, passed straight into a
  Prisma `where`.
* `classSectionId`, `academicYearId` → `ParseUUIDPipe({ optional: true })`, no `version`.

The `optional` option is **verified** against the pinned `@nestjs/common@10.4.22` source in §2.3 — quote that
verification in the ADR the way `ADR-065 §D4` did, rather than re-asserting it. State the `?status=` empty-string
behaviour change of §2.3 explicitly. Note what this **does not** fix: `?limit=`/`?offset=` still go through
`parseInt` with a silent fallback, and `?unenrolled=` is a string compared to `'true'` — both **out of scope**,
both recorded rather than widened.

**AC-7 (G-PORTAL).** State the effect on all four portals — admin, teacher, parent, student. In particular
`calendar.controller.ts:263-273` short-circuits `teacher` into `isPrivileged` **before** calling `scopeForUser`:


### 5.2 The rows that must be argued, not assumed

Rows 3–7 and 17–18 are **parent-shaped routes a teacher can currently call for any child in the tenant**.
Tightening them is almost certainly correct, but "almost certainly" is not the bar: for each, say whether any
first-party teacher UI calls it, and if one does, whether it calls it only for taught students. If a teacher screen
legitimately needs a non-taught student, that is a **finding to record**, not an exemption to add.

### 5.3 The precedence hazard the student portal inherits (`PF-297`)

`scopeForUser` resolves roles in strict order: `super_admin`/`school_admin` → `teacher` → `parent` → `student`. A
principal holding **both** `teacher` and `student` therefore takes the `teacher` branch and never reaches the
student-self branch. Today that is harmless (teacher → `null` → `canAccessStudent` true → the portal works by
accident). **After this slice it becomes harmful**: their own student id would only be in scope if they were
enrolled in a section they themselves teach, i.e. effectively never — so every `student-portal.service.ts` site
would 403 for that principal. The same ordering already shadows a `parent`+`student` principal.
This is a **pre-existing ordering defect that this slice makes reachable**. It must be named — record it as
**`PF-297`** — and the ADR must state whether the slice mitigates it (e.g. by resolving the student-self branch
before the teacher branch when the caller's own id is the subject) or accepts it. Do not discover it in review.
