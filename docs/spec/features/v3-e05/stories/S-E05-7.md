## §1 — The design. Implement this; do not redesign it.

### 1.1 No new dependency. A hand-written, in-process, fixed-window limiter.

Do **not** add `@nestjs/throttler` or any package. Three binding reasons:

1. `apps/api/package.json` + the lockfile are **outside this seam**, and a dependency bump is precisely how the
   **NestJS v10 pin** (GUARDRAILS §3 — `@nestjs/core` v11 crashes the process) gets broken by accident.
2. A `pnpm install` in this worktree costs ~7 min and the gate does not need it.
3. A DB-backed counter (the `child-claims` shape) would put the diff in `apps/api/prisma/**` = **track a's seam**,
   and would trigger `G-MIGRATION` for what is an authz concern.

### 1.2 The two tiers — this is the part that is easy to get wrong

A naive per-IP limiter is **not sound on this topology and would be a self-DoS**. Measured fact, already written
down at `register.controller.ts:195-214` and at `shared/audit/client-hints.ts:26-35`: this endpoint has exactly
**one caller repo-wide**, and it is a Next.js **server action** (`apps/web/src/app/parent/register/actions.ts`)
issuing a bare server-side `fetch`. Therefore `req.ip` is the **web container's egress address — one constant
address shared by every registrant on earth**. Keying on it puts every legitimate parent in one bucket. Do not
key on the address. Do not read `req.ip` at all.

**Tier 1 — per-identity bucket, keyed on the submitted email.**
Bounds the **rate** at which one address can be probed — the enumeration surface `S-E05-11` deliberately made
indistinguishable between its two 409 branches. **The docblock must state honestly that this key is
caller-chosen and therefore rotatable by an attacker: it is an enumeration-rate bound, NOT a security bound.**

**Tier 2 — a global ceiling for the endpoint.**
Because every request may share one source address, a global per-window cap on **admissions** is the only bound
that genuinely caps the Keycloak admin round-trips. **This is the amplification bound and the one that actually
holds.**

A request is refused if **either** tier is exceeded.

### 1.3 The algorithm, precisely

> ⚠️ **SUPERSEDED in shape, not in intent — see §0.5.** The shipped limiter is a class with `admit()` over an
> **epoch-aligned** window, not a free `consume()` over `windowStartedAt`. Steps 1-4 below describe the shipped
> ordering exactly; only the sweep predicate and the call signature changed.

One **fixed window**, shared by both tiers, swept **lazily on access** — no `setInterval`, no timers, nothing
left running for jest to tear down.

State (module-level, in `public-endpoint-throttle.ts`):

```
windowStartedAt : number | null   // null = no window open yet
admittedInWindow: number          // tier-2 counter
perKeyAdmitted  : Map<string, number>   // tier-1 counters, keyed by sha256 hex digest
```

`consume(key: string | null, now: number): { allowed: boolean; reason: ... }`:

1. **Sweep.** If `windowStartedAt === null || now - windowStartedAt >= WINDOW_MS` →
   `windowStartedAt = now`, `admittedInWindow = 0`, `perKeyAdmitted.clear()`.
2. **Tier 2.** If `admittedInWindow >= TIER2_MAX` → **refuse** (`'global'`). Touch no key: a refusal must not be
   able to create or grow a bucket.
3. **Tier 1** (only when `key !== null`):
   - not present **and** `perKeyAdmitted.size >= MAX_KEYS` → **refuse** (`'saturated'`) — fail closed, see §1.5;
   - present and `count >= TIER1_MAX` → **refuse** (`'identity'`).
4. **Admit.** `admittedInWindow += 1`; if `key !== null`, increment/create its entry. Return `allowed: true`.

**Counters count ADMISSIONS, not attempts — and that is deliberate.** A refused request performs no Keycloak
call, so it costs nothing to bound; counting refusals into tier 2 would hand an attacker hammering **one** email
a lever to exhaust the **global** bucket and lock out everyone else. Write that sentence into the docblock.

**A fixed window admits up to 2× the cap across a boundary.** Accepted, and stated rather than discovered: the
bound this slice needs is order-of-magnitude (cap the amplification), not exact. A sliding window needs a
per-key timestamp array, i.e. unbounded memory per key — exactly what §1.5 forbids.

### 1.4 The constants — named exports, no environment reads

> ⚠️ **SUPERSEDED, AND NOT RATIFIED — see §0.5 / `R-4`.** The shipped values are
> `60_000 · 5 · 30 · TIER2 × 2`, i.e. **16.7× looser per address** and **5× looser endpoint-wide** than the block
> below. The divergence is invisible to the gate (every spec reads the constants symbolically). **A human ratifies
> or reverts before merge.** The block below is kept verbatim as the number that was specified.

```ts
export const REGISTRATION_WINDOW_MS = 10 * 60 * 1000; // 10 min — the child-claims window
export const REGISTRATION_TIER1_MAX = 3;   // admissions per email per window
export const REGISTRATION_TIER2_MAX = 60;  // admissions per window, endpoint-wide
export const REGISTRATION_MAX_KEYS  = REGISTRATION_TIER2_MAX; // derived — see §1.5
```

`TIER1_MAX = 3` — a real registrant needs one; three tolerates a double-submit plus a genuine retry after a 500.
`TIER2_MAX = 60` per 10 min ≈ 6 admissions/min sustained, ~30× the platform's realistic peak. If a legitimate
onboarding wave (a whole class registering after one email blast) ever trips it, the answer is the **operator
bulk-invite path that already exists** (`invite.controller.ts`), not a higher ceiling — write that in the
docblock so the next author does not reflexively raise the number.

Both numbers change by code edit + PR review. That is the point (§1.6).

### 1.5 Key hygiene and memory safety

- **Never store the raw address.** The tier-1 key is
  `createHash('sha256').update(email.trim().toLowerCase(), 'utf8').digest('hex')`. A `Map` of plaintext
  registrant emails would otherwise sit in every heap snapshot of a platform whose GUARDRAILS §1 calls
  RGPD-level governance non-negotiable.
  `trim()` + `toLowerCase()` matches the handler's own `body.email.toLowerCase()` (`register.controller.ts:183`)
  so the guard and the handler agree on identity; the extra `trim()` is strictly *stricter* (two spellings share
  one bucket), which is the safe direction.
- **`MAX_KEYS` is derived, not chosen.** A key is created **only on admission** (step 4), at most `TIER2_MAX`
  admissions occur per window (step 2 refuses first), and the map is cleared on every sweep. Therefore
  `perKeyAdmitted.size` can never exceed `TIER2_MAX` — **saturation is unreachable by construction**. Say exactly
  that in a comment instead of picking a round number.
- **If saturation is somehow reached, refuse (fail closed).** Never LRU-evict: eviction would let an attacker
  flush their own counter by rotating keys, which is the bypass tier 1 exists to make expensive.
- **Read the email defensively.** Guards run **before** validation pipes, so the body is raw and may be
  anything. `typeof body?.email === 'string'` or treat it as absent. **Never throw on a malformed body** — a
  limiter that 500s on garbage is worse than no limiter. A request with **no usable email still counts against
  tier 2** (it is admitted with `key === null`; the DTO pipe will 400 it a moment later, but the guard cannot
  know that, and over-counting is the safe direction).

### 1.6 DNC-10 — hard rule, enforced for V3-E05

`DNC-10` = hard-coded bypass. **These files read no environment variable at all.** No `SKIP_*`, no `NODE_ENV`
branch, no "disabled" value, no off switch — following the precedent stated at `client-hints.ts:82-86`. Note the
anti-precedent deliberately **not** followed: `messaging.service.ts:62-72` makes its two knobs env-tunable. That
predates DNC-10 and is not a licence.

> **Implementation trap, stated so you do not trip your own test.** AC-9 asserts structurally on the **raw**
> source of both new files. Write the docblocks so they say *"reads no environment variable at all"* and never
> spell the literal tokens `process.env`, `NODE_ENV`, `ConfigService`, `SKIP_`, `ALLOW_`, `BYPASS_`, `FORCE_`,
> `DISABLE`. Asserting on raw source (no comment-stripping helper) is the strictest and simplest form, and it is
> self-enforcing.

If you ever believe a limit must be tunable, the rule is that **absence means the STRICTEST setting, never
disabled**. For this slice the correct answer is no environment reads at all.

### 1.7 Wiring

Apply the guard to `POST /auth/register-parent` **only**, with `@UseGuards(RegisterThrottleGuard)` on the
**handler method** (the controller has exactly one route; the handler is the precise placement). It runs before
the handler body and therefore **before any Keycloak call** — which is the entire point.

Do **not** register it as a global `APP_GUARD`: that silently changes every endpoint in the app and is a
cross-cutting architectural change requiring an ADR (GUARDRAILS §2).

`identity.module.ts` needs **no edit**: the guard has no constructor dependencies, so Nest instantiates the class
passed to `@UseGuards` without a provider entry. If the injector nevertheless objects, adding
`RegisterThrottleGuard` to `IdentityModule.providers` is in-seam and acceptable — nothing else in that file
changes.

### 1.8 The refusal

> ⚠️ **The message string is SUPERSEDED — see §0.5.** Everything else in this section shipped verbatim: 429 via
> `HttpException`, `body.message` as a top-level string, byte-identical across all three tiers, no `Retry-After`.

- **HTTP 429.** `ThrottlerException` does not exist here. Use
  `new HttpException(REGISTRATION_THROTTLED_MESSAGE, HttpStatus.TOO_MANY_REQUESTS)` from `@nestjs/common` —
  the exact shape `child-claims.service.ts:126-129` and `messaging.service.ts` already use. Nest serialises it
  as `{ statusCode: 429, message: "…" }`, so `body.message` is populated, which is the contract that matters
  (next bullet).
- **The message is user-facing French copy.** `apps/web/src/app/parent/register/actions.ts:41-45` returns
  `body.message` **verbatim** and `ParentRegisterForm.tsx` renders it **raw**. So this string is UI copy even
  though no `apps/web` file changes in this slice.

  ```ts
  export const REGISTRATION_THROTTLED_MESSAGE =
    'Trop de tentatives d’inscription — réessayez dans quelques minutes.';
  ```

  One sentence, factual and kind (GUARDRAILS §1), no jargon, mirroring the em-dash shape of the existing
  `child-claims` copy so the product speaks with one voice.
- **The message must NOT reveal which tier fired.** All three refusal reasons (`identity`, `global`,
  `saturated`) return the **byte-identical** string and the same status. A per-email refusal distinguishable
  from a global one is an enumeration oracle — it tells the caller the address is in the bucket — and would
  rebuild exactly what `S-E05-11` closed. AC-6 pins this.
- **No `Retry-After` derived from the per-email bucket**, for the same oracle reason. A constant window value
  would be acceptable; the simplest correct answer is to omit the header, and that is what this slice does.

### 1.9 G-AUDIT — reasoned, and the reasoning goes in the code

A throttled request performs **no mutation**, so G-AUDIT does not trigger for the refusal. **Do not write an
`auditLog` row per refused request**: that would be a DB write per blocked request — i.e. it would rebuild the
very amplification this slice removes, one table over. Use the Nest `Logger` (`warn`) instead.

**Write this reasoning into the guard's docblock** so the next author does not "fix" it.

The log line must **not** contain the raw email (RGPD, §1.5). Log the **first 12 hex characters of the digest**
plus the tier that fired — the tier is safe in a server log (it never reaches the caller) and it is exactly what
an operator needs to tell "one address being probed" from "the endpoint is under load".

The existing `user.register` audit row in `persistRegisteredParent` must keep working unchanged (AC-10).

### 1.10 Conventions that will turn the gate red if broken

- `writeAudit` must stay **one unconditional statement with an inline object literal** (`ADR-035` D1) —
  `scripts/audit-write-check.js` resolves `action`/`resourceType` from the call-site AST, and its **rule B**
  reddens on a `try` **anywhere** among a `writeAudit` call's AST ancestors, **function boundaries included**.
  That is why `persistRegisteredParent` and `compensateOrphanedKeycloakUser` are separate methods.
  **Do not restructure `register.controller.ts`'s methods.** The diff to that file should be almost exactly:
  **two imports and one decorator.**
- Do not touch the two French validation strings (`:175`, `:179`) or the 409 string (`:76-80`) — UI copy.
- Do not touch the `emailVerified` docblock at `:153-156` (§0.3).

### 3.1 `public-endpoint-throttle.spec.ts` — the limiter, with the clock injected

2. **AC-3** — `TIER2_MAX` admissions across `TIER2_MAX` **distinct** keys all succeed (no key ever reaches

## §7 — Residuals to register (name them; do not paper over them)

- **R-1 — a global ceiling *is* a global-DoS lever.** 60 cheap anonymous POSTs in 10 minutes suspend
  registration for everyone until the window rolls. This is inherent to any global cap and is the trade §1.2
  deliberately chose: **unbounded Keycloak admin amplification is worse**, because it degrades the identity
  provider that every portal's login depends on, not just registration. Bounded registration downtime beats an
  unbounded blast radius. The real fix is an upstream edge limiter (nginx `limit_req` in `infra/nginx/`), which
  is out of seam. **Recommend the orchestrator register R-1 as a new finding against `infra/**`.**
- **R-2 — per-process state.** The ceiling multiplies by the replica count and resets on deploy. Acceptable at
  the current single-replica topology; it is the same class of caveat as R-1 and has the same fix.
- **R-3 — `PF-46` stays open** on its `emailVerified` third (§0.3).
