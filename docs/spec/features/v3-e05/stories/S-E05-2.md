## 0. Corrections to the brief, measured before a line was written

The operator brief is right about the defect and right about the fix. Three of its *supporting facts* are wrong in
this checkout, and two of them change what the tests must assert. They are corrected here rather than absorbed
silently, because an implementer who writes a test against a fixture the brief invented will produce a green suite
that proves nothing.

**0.1 — `prisma/seed.ts` does NOT seed a `super_admin` Role row.** The brief calls this "the sharpest live
instance". Measured: `grep -rn "super_admin" apps/api/prisma/` returns **zero matches** across all ten seed files.
`seed.ts:189-199` seeds exactly four system roles — `school_admin`, `teacher`, `parent`, `student`. There is no
`super_admin` row to POST, so *that specific* exploit is not reproducible.

**The defect is nonetheless live, and at the mint site it is worse than the brief describes.** `school_admin` holds
**both** `roles.write` and `roles.assign` (`permissions.constants.ts:209-211`). So a school_admin can today:

1. `POST /roles` with `permissionCodes` = **every code in the catalogue** — `create()` validates only that the codes
   *exist* (`roles.controller.ts:116-122`), and every code exists because `seed.ts:184-188` upserts all of
   `PERMISSIONS`;
2. `POST /users/<ownProfileId>/roles` with that role's id — `assignRole` compares nothing
   (`users.service.ts:85-96`);
3. re-authenticate. `UserSyncService.effectivePermissions` (`user-sync.service.ts:71-84`) unions custom-role
   permissions into the effective set, and `PermissionsGuard:28-29` reads that union.

That is a complete, two-request self-escalation to **super_admin-equivalent** — without any `super_admin` row
existing. Consequence for the tests: **AC-6's positive control must be built from a full-catalogue fixture**
(a role whose permission set is the whole of `PERMISSIONS`), never from "the seeded super_admin role". A unit test
constructs its fixtures, so nothing is lost; the wording is what had to change.

**0.2 — `teacher` is not the only seeded role that exceeds a school_admin, and this enlarges §2.4.** The brief asks
for this to be verified against `permissions.constants.ts` before asserting the positive control. Verified — and
against `seed.ts`'s `ROLE_PERMISSIONS` too, because *that* is what lands in `role_permission` and therefore what the
ceiling actually compares. Both agree. Codes carried by each seeded Role row that a `school_admin` grantor does
**not** hold:

| Seeded Role row | Exceeds a `school_admin` grantor by | Assignable by a school_admin after this slice? |
|---|---|---|
| `school_admin` | *(nothing — 55 codes, all held)* | ✅ **yes** |
| `teacher` | `grades.write`, `grades.revise`, `attendance.write`, `lessons.write`, `exports.execute.teacher` | ❌ **no** |
| `parent` | `guardianships.claim`, `exports.execute.parent`, `remediation.book` | ❌ **no** |
| `student` | `grades.read.self`, `assessments.read.self`, `attendance.read.self`, `announcements.read.self`, `analytics.read.self` | ❌ **no** |

*(Against `permissions.constants.ts` the `teacher` list is the same five plus `lessons.delete`, which `seed.ts`'s
teacher row does not carry. The DB row is what the ceiling reads, so the five-code figure is the operative one.)*

So the honest positive control for a school_admin grantor assigning a **seeded system role** is
**`school_admin` itself**, not `teacher`. This is reported loudly, per the brief's instruction: **the ceiling changes
real admin behaviour for three of the four seeded system roles.** It is a genuine product consequence (§2.4), it goes
in the ADR and in the PR body, and it is **not** to be papered over by weakening the check.

**0.3 — AC-9's stated rationale is half wrong, and the divergence survives on a better argument.** The brief argues
a blanket `isSystem` ban "would stop a school_admin from assigning the teacher or parent role — the ordinary,
intended operation — while the ceiling ALREADY refuses super_admin". Measured (0.2): for a school_admin grantor the
ceiling **already refuses `teacher`, `parent` and `student`**, exactly as the ban would. The ban is therefore not
*broader* than the ceiling on those three; on today's data the two agree.

The divergence is still right, on two arguments that are actually true:

- **The ban is wrong on the one seeded role it would break.** `school_admin` → `school_admin` is within the ceiling
  (0 exceeding codes) and is an ordinary operation — promoting a colleague to an admin peer. A blanket `isSystem`
  refusal for non-super_admin grantors would refuse it. That is a live, concrete regression, not a hypothetical.
- **The ban is role-shaped where the defect is permission-shaped.** The escalation route that is fully live today
  (0.1) is *mint a custom role, then assign it*. Custom roles are created with `isSystem: false`
  (`roles.controller.ts:136`), so an `isSystem` ban does not touch the exploit at all, and `PF-09`'s mint site has no
  `isSystem` notion to ban. Only a permission-set comparison closes both findings with one mechanism.

Both arguments go in the ADR (§7 D4) and in a code comment (§4.3).

**0.4 — the ledger disagrees with this slice's existence, and the operator override wins.**
`docs/spec/features/v3-e05/PROGRESS.md:5-12` states `S-E05-12` is "the only one with a written story", lists
**`S-E05-2` as `⬜ unenumerated` — "matrix row only"**, and its "Next run" section says *"Not a `V3-E05` slice —
nothing in this epic is enumerated"*, preferring a `V3-E04` `epic-spec` run. That pointer is **stale and is not an

## 1. Why — the defect, reproduced

### 1.1 `PF-09` — minting (roles.controller.ts)

`create()` (`:104-155`), gated only by `@RequiresPermission('roles.write')` (`:105`):

```ts
const perms = await this.prisma.permission.findMany({
  where: { code: { in: body.permissionCodes } },      // :116-118
});
if (perms.length !== body.permissionCodes.length) {   // :119-122
  throw new BadRequestException({ message: 'Permissions inconnues', missing });
}
```

The only question asked is *does this code exist in the catalogue*. Never *does the caller hold it*. The role is then
created with those `rolePermissions` inside the `$transaction` at `:129-152`.

`update()` (`:157-209`) is the same defect and is worse, because it **rewrites**:

```ts
if (body.permissionCodes) {                                      // :185
  const perms = await tx.permission.findMany(…);                 // :186
  await tx.rolePermission.deleteMany({ where: { roleId: id } }); // :191
  for (const p of perms) await tx.rolePermission.create(…);      // :192-194
}
```

An existing, already-assigned role's permission set is replaced wholesale from arbitrary codes. Every holder of that
role gains the new set at their next `effectivePermissions` read — no second request needed.

### 1.2 `PF-156` — assigning (users.service.ts)

`assignRole` (`:74-125`) looks the role up (`:85`) and grants it (`:99-106`) with **no comparison against the
grantor's own permissions**. `users.controller.ts:50-61` gates only on `roles.assign`. The existing docblock
(`users.service.ts:58-66`) states this openly and says *"This slice does not close it"* — that paragraph is what
AC-7 now falsifies and must rewrite.

### 1.3 The live chain, end to end

`school_admin` holds `roles.write` ∧ `roles.assign` ⇒ mint a full-catalogue role (§0.1 step 1) ⇒ self-assign it
(step 2) ⇒ hold `grades.revise` (revise **published** grades — no admin is supposed to have it),
`attendance.write`, `lessons.write`, and every other code in the product. Two requests, both 2xx, both audited as
ordinary `role.create` / `role.grant` rows. **The audit trail records the escalation faithfully and refuses
nothing.** Legibility was `S-E04-6`'s contribution; refusal is this slice's.

## 2. What changes

### 2.1 One predicate

**NEW `apps/api/src/shared/auth/privilege-ceiling.ts`** — the single place the rule lives. There is **no barrel**
in `apps/api/src/shared/auth/` (measured: the directory holds eight files, no `index.ts`), so nothing is re-exported;
call sites import the module directly, exactly as they already import `permissions.guard` and `user-sync.service`.

```ts
/** The codes in `requested` that the grantor does not hold. Order-preserving, de-duplicated. */
export function exceedsGrantor(
  grantorPermissions: ReadonlySet<string> | undefined,
  requested: readonly string[],
): string[];

/** Thin throwing wrapper: the ONE place the refusal's HTTP shape is built. */
export function assertWithinCeiling(
  grantorPermissions: ReadonlySet<string> | undefined,
  requested: readonly string[],
): void;
```

Two exports, deliberately. `exceedsGrantor` is the predicate AC-1 specifies and is what the unit spec drives.
`assertWithinCeiling` exists so the three call sites cannot drift into three slightly different
`ForbiddenException` literals — AC-2, AC-3 and AC-4 each require the *same* body, and a wrapper is how that becomes
structural rather than reviewed. Neither call site reimplements the comparison; none of them constructs the
exception.

**Fail-closed rules, all three load-bearing (G-AUTHZ: "no fail-open guard"):**

- `grantorPermissions === undefined` or empty ⇒ **every** requested code is returned (deny). Never treated as
  "unknown, so allow".
- An unknown/unrecognised code is not in the grantor's set ⇒ it exceeds ⇒ deny. The predicate never consults the
  catalogue and never special-cases a code it does not recognise.
- `requested` empty ⇒ `[]` (allow). A role carrying zero permissions grants zero privilege; this is the one
  permit-on-empty and it is stated, commented and tested so it cannot be mistaken for a fail-open branch.

No `NODE_ENV`, no `process.env`, no `SKIP_*`/`ALLOW_*`, no `isDev`, no options object, no injectable service
(DNC-10, AC-10). Arity is exactly 2 on both exports, and the spec asserts it, so an options bag cannot appear later
without turning a test red.

### 2.2 The grantor's effective set is derived at the controller

Both controllers already inject `UserSyncService`. The set comes from the **same seam `PermissionsGuard:27-28`
uses**, and from nowhere else:

```ts
const grantorPermissions = await this.users.effectivePermissions(jwt.sub, jwt.realm_access?.roles ?? []);
```

For `assignRole` it is then **passed into `UsersService` as a parameter** (AC-5). **Do not inject `UserSyncService`
into `UsersService`; do not reimplement the union.** This mirrors the house pattern the `S-E04-6` docblocks in these
very files already state for `provenance` (derived in the controller, before the transaction, passed in) and
`ADR-035` D4 records.

### 2.3 The three call sites — insertion points and ordering, decided here

| # | Site | Insert exactly | Ordering decision |
|---|---|---|---|
| 1 | `roles.controller.ts create()` | **after** the `Permissions inconnues` check (`:122`), **before** `$transaction` (`:129`) | An unknown code keeps answering **400**, not 403. The existing message is preserved verbatim. |
| 2 | `roles.controller.ts update()` | **after** the `isSystem` refusal (`:166`), **before** `$transaction` (`:177`); guarded by `if (body.permissionCodes)` | AC-3 requires refusal *before* the transaction, and the `Permissions inconnues` check for `update` lives **inside** it (`:187-190`). **Do not move that check** — moving it is out of scope and would restructure the transaction body. Consequence, accepted and recorded: on `update()` an unknown code now yields **403** (it cannot be in anyone's effective set) where it used to yield 400. `create()` and `update()` therefore answer a typo differently. Deliberate, commented, and pinned by a test so it is a decision and not a surprise. |
| 3 | `users.service.ts assignRole()` | **after** the role lookup (`:86`), **before** the idempotency early-return (`:89-96`) and before `$transaction` (`:98`) | Before the idempotency return on purpose: a refused grant must never be answered with a 200 body. An "already granted" 200 for an over-privileged role is a probe oracle that tells a limited admin which users already hold escalated roles. |

For site 3 the role's permission set must actually be loaded. The lookup at `:85` becomes:

```ts
const role = await this.prisma.role.findUnique({
  where: { id: roleId },                                            // UNFILTERED — see §8, PF-153
  include: { rolePermissions: { include: { permission: true } } },
});
```

**`?? []` on `role.rolePermissions` is forbidden.** An absent include would produce an empty set, an empty set
exceeds nothing, and the ceiling would silently permit everything — the exact "guard that is green because it cannot
fire" shape this epic is named after. The include is pinned two ways: by the Prisma payload type, and by a test that
asserts the argument object passed to `findUnique` (§6, T-14).

### 2.4 The product consequence — stated, not smoothed

After this slice, a `school_admin` **can no longer assign the seeded `teacher`, `parent` or `student` roles**
(§0.2). They can still assign `school_admin`, and any custom role within their own set.

This is correct behaviour under the ceiling — a school_admin genuinely does not hold `grades.revise` — but it is a
real change to an everyday admin operation, and *"onboard a teacher"* is an everyday admin operation. **Do not
weaken the ceiling to restore it.** The three legitimate resolutions, none of which belongs in this slice:

1. widen `REALM_ROLE_PERMISSIONS.school_admin` (a deliberate, reviewed privilege grant — its own change, its own ADR
   amendment);
2. introduce an explicit *delegation* right (`roles.assign.system` or a per-role grantable flag) — schema/product
   work;
3. accept it: realm-role assignment moves to Keycloak/`super_admin`, and the app's `roles.assign` becomes a
   custom-role-only capability.

**Decision for this slice: accept and record.** The ADR states it (§7 D5), the PR body states it, and it is flagged
for human review. `requiresDecision: YES`.

### 2.5 The stale docblock (AC-7)

`users.service.ts:58-66` paragraph 1 currently asserts *"The grantor's own privileges are not checked … This slice
does not close it"*. That sentence becomes **false the moment this code lands**. Rewrite it to describe the ceiling:
what is compared, where the set comes from, that refusal happens before the transaction so no row is written, and
that the parameter is required rather than optional for the same reason `provenance` is. Leaving it is the `PF-164`
shape inverted — a comment asserting an invariant the code no longer lacks.

**Paragraph 2 (`:67-72`, the `PF-153` / tenant-scoping paragraph) is KEPT VERBATIM.** See §8.

## 3. Functional requirements

- **FR-1** A grantor may not create a role carrying any permission code absent from their own effective permission
  set. Refusal is `403 ForbiddenException`, before any write.
- **FR-2** A grantor may not rewrite a role's permission set to include any code absent from their own effective
  set. Same refusal, same timing.
- **FR-3** A grantor may not assign a role whose permission set is not a subset of their own effective set. Same
  refusal, same timing.
- **FR-4** A rename-only `PATCH /roles/:id` (no `permissionCodes` in the body) runs **no** ceiling check.
- **FR-5** A refused request writes **no** entity row and **no** audit row, and never opens a transaction.
- **FR-6** `super_admin` is unaffected: its realm role carries every code, so the ceiling is a no-op. Proven by
  test, not asserted.
- **FR-7** The effective set is computed once per request, at the controller, via
  `UserSyncService.effectivePermissions`.

## 5. Error contract

One shape, built once, in `assertWithinCeiling`:

```ts
throw new ForbiddenException({
  message: 'Permission(s) refusée(s) : vous ne pouvez pas accorder une permission que vous ne détenez pas',
  required: [...requested],
  missing: exceeding,
});
```

French, matching the neighbours (`'Rôle introuvable'`, `'Les rôles système ne sont pas modifiables'`,
`'Permissions inconnues'`, `'Permission(s) refusée(s)'`). Structurally identical to the guard's body, so a client
that already renders one renders the other.
