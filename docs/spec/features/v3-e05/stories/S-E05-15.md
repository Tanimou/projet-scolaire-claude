### 3.1 `AC-1` — the verdict, and why it is a **scope**, not a wall

The roster handler could answer allow/deny because it is keyed on **one** section. A list handler cannot: the
correct semantics differ per role, and three of the four roles have a legitimate non-empty answer.

| realm role | correct semantics | shipped |
|---|---|---|
| `super_admin` / `school_admin` | the whole tenant — they administer enrollments | **unrestricted within tenant** |
| `teacher` | the enrollments of the sections they actually teach | **scoped** to `classSectionId ∈ {sections they hold a `TeachingAssignment` on}` |
| `parent` | the enrollments of their own children, nothing else | **scoped** to `studentId ∈ StudentAccessService.scopeForUser(...).studentIds` |
| anything else (incl. `student`, incl. a caller with no relevant realm role) | nothing | **403** |

**Why a scoped read and not a blanket 403 for `teacher`** (`AC-1` asks for the justification either way): a
teacher reading the roll of their own class is the endpoint's *purpose*, the tenant already grants them
`enrollments.read`, and the refusal would have to be unpicked the moment a teacher-portal consumer arrives. The
census (§1.5) says zero consumers break either way, so "safer" is not a tiebreaker — correctness is.

**Why `parent` is scoped rather than refused:** GUARDRAILS §2 names `StudentAccessService` as *the* parent
access path, and it already returns exactly the right set. Refusing would be the cheaper diff and the wrong
product: the north star is a parent who can see their own child's situation.

**What a refusal would have needed, recorded as `AC-1` asks:** nothing — it is the *scope* that costs the extra
wiring (§3.6), not the refusal. If a reviewer forces the narrower slice, delete the `guardian` branch, return
`403` from `classifyEnrollmentListCaller` for `parent`, and drop file 2 from the set. Say so in the docblock and
raise it as a finding rather than leaving it silent.

### 3.2 The decision layer — **exported, pure, plain values** (`AC-3`)

Three exports. All in `enrollments.controller.ts`, above the class, in the house position.

```ts
export type EnrollmentListScope =
  | { readonly kind: 'tenant' }
  | { readonly kind: 'sections'; readonly classSectionIds: readonly string[] }
  | { readonly kind: 'students'; readonly studentIds: readonly string[] };
```

**The union has no `denied` member, deliberately.** A refused caller throws *before* a scope value can exist, so
"build a `where` for a denied caller" is not expressible — the same technique `teacherOfSectionWhere` uses on
`teacherProfileId` (`ADR-063 §D2`), applied one level up.

```ts
export function classifyEnrollmentListCaller(
  roles: readonly string[],
): 'privileged' | 'teacher' | 'guardian' | 'denied';
```

* `isPrivilegedEnrollmentsCaller(roles)` → `'privileged'` — **reused, not re-implemented** (`AC-3`).
* else `roles.includes('teacher')` → `'teacher'`
* else `roles.includes('parent')` → `'guardian'`
* else → `'denied'`. **Deny-by-default on the final branch**, and the test must include the empty-array case.

```ts
export function buildEnrollmentListWhere(input: {
  readonly tenantId: string;
  readonly scope: EnrollmentListScope;
  readonly filters: {
    readonly studentId?: string;
    readonly classSectionId?: string;
    readonly academicYearId?: string;
    readonly status?: EnrollmentStatus;
  };
}): Prisma.EnrollmentWhereInput;
```

**`tenantId` is the first key on every branch** and is never conditional (`G-TENANT`).

The fold, per scope kind — **intersection, never union**:

| scope | `classSectionId` key emitted | `studentId` key emitted |
|---|---|---|
| `tenant` | `filters.classSectionId` if defined, else **absent** | `filters.studentId` if defined, else absent |
| `sections` | **always present**: `{ in: filters.classSectionId ? intersect([filters.classSectionId], scope.classSectionIds) : scope.classSectionIds }` | `filters.studentId` if defined, else absent — safe, the section wall already bounds the result |
| `students` | `filters.classSectionId` if defined, else absent — safe, the student wall already bounds the result | **always present**: `{ in: filters.studentId ? intersect([filters.studentId], scope.studentIds) : scope.studentIds }` |

`academicYearId` and `status` fold exactly as today (present only when defined) — they are not access-bearing.

**Two traps that must be written into the docblock so nobody "simplifies" them away:**

1. **The empty array must survive.** `...(ids.length ? { classSectionId: { in: ids } } : {})` is the fail-open:
   Prisma drops the absent key and the caller gets the whole tenant. `{ in: [] }` is a *defined* key and matches
   nothing — that is the deny. The spec asserts `{ in: [] }` is **emitted**, not that the key is absent.
2. **Build one value per key, never spread twice.** `{ ...(f.classSectionId ? { classSectionId: f.classSectionId } : {}), classSectionId: { in: ids } }` and its mirror are both order-dependent and one of the two orders is a fail-open. Compute the key's value once, in a `switch` over `scope.kind`.

### 3.3 The handler — the ordered shape

```
1. pipes                (AC-7/AC-8 — 400 on a malformed uuid or a bogus status)
2. me = users.ensureUser(jwt)
3. kind = classifyEnrollmentListCaller(jwt.realm_access?.roles ?? [])
4. switch (kind):
     'privileged' → scope = { kind: 'tenant' }
     'teacher'    → tp = await teachers.findForUser(me)          // findForUser, NEVER ensureForUser
                    if (tp === null) throw ForbiddenException(ENROLLMENT_LIST_REFUSAL)   // ← AC-4
                    rows = await prisma.teachingAssignment.findMany({
                             where: { tenantId: me.tenantId, teacherProfileId: tp.id },
                             select: { classSectionId: true },
                           })
                    scope = { kind: 'sections',
                              classSectionIds: Array.from(new Set(rows.map(r => r.classSectionId))) }
     'guardian'   → scope = { kind: 'students',
                              studentIds: (await studentAccess.scopeForUser(me, jwt, '')).studentIds ?? [] }
     'denied'     → throw ForbiddenException(ENROLLMENT_LIST_REFUSAL)
5. where = buildEnrollmentListWhere({ tenantId: me.tenantId, scope, filters })
6. prisma.enrollment.findMany({ where, orderBy, include: { ... ENROLLMENT_LIST_CLASS_SECTION_SELECT ... } })
```

Notes the implementer must not get wrong:

* **`AC-4`, the null-profile path.** The `throw` at step 4 happens **before** `teachingAssignment.findMany` is
  reached. The spec asserts the ownership query was **never issued** (`expect(db.teachingAssignment.findMany).not.toHaveBeenCalled()`), not merely that a 403 came back. A 403 that arrives *after* the query is a different program.
* **`findForUser`, never `ensureForUser`** — `ensureForUser` is an upsert and would provision a `TeacherProfile`
  row for every caller probing this endpoint (`PF-265` / `ADR-051 §D1`).
* **Dedupe in JS, not with Prisma `distinct`.** A teacher can hold one assignment *per subject* on the same
  section (`@@unique([teacherProfileId, classSectionId, subjectId])`), so duplicates are expected. `new Set` is
  used rather than `distinct: ['classSectionId']` so the jest Prisma double does not have to implement `distinct`
  — a double that silently ignores `distinct` would make a green test prove nothing.
* **No academic-year clause on the teaching wall**, for the reasons already argued at length in
  `teacherOfSectionWhere`'s docblock (`ADR-063 §D1`): `TeachingAssignment.academicYearId` has no composite FK to
  `ClassSection.academicYearId`, and `ClassSection` is itself year-pinned. Do not re-litigate it; cite it.
* **`scopeForUser`'s third argument** is `_schoolId` and is **unused** in the implementation
  (`student-access.service.ts:30`). Pass `''` and say in the docblock that it is unused rather than inventing a
  school lookup — and record the dead parameter if you like, but do not change the service (`AC-9`).
* **The privileged short-circuit issues zero extra queries** — an administrator has neither a teacher profile nor
  a guardianship, and not asking for them is the point.
* **No `bypass` / `allow` / `skip` parameter, no environment variable, no `if (process.env...)`** anywhere on
  this path (`AC-5`, `DNC-10`). A control that can be switched off is not a control.

### 3.4 `AC-7` + `AC-8` — the pipes, and the measurement behind them

```ts
    @Query('studentId', new ParseUUIDPipe({ optional: true })) studentId?: string,
    @Query('classSectionId', new ParseUUIDPipe({ optional: true })) classSectionId?: string,
    @Query('academicYearId', new ParseUUIDPipe({ optional: true })) academicYearId?: string,
    @Query('status', new ParseEnumPipe(EnrollmentStatus, { optional: true })) status?: EnrollmentStatus,
```

**Measured this run, by reading the installed package** —
`node_modules/.pnpm/@nestjs+common@10.4.22/.../pipes/parse-uuid.pipe.js` and `parse-enum.pipe.js`:

* Both pipes open `transform` with `if (isNil(value) && this.options?.optional) return value;`. So
  `{ optional: true }` is **honoured by both**, and a request with no `?status=` and no uuid params passes
  through untouched. **A bare `ParseUUIDPipe` would 400 every caller** — `isUUID(undefined)` reaches
  `if (!isString(str)) throw ...`. This is the failure mode `AC-7` warns about and it must have its own green
  test.
* `ParseEnumPipe` in **10.4.22 does** expose `optional` (`ParseEnumPipeOptions { optional?: boolean; ... }`).
  This was verified in the installed `.d.ts` and `.js`, not assumed from the docs.
* `ParseUUIDPipe.isUUID` **throws** `'The value passed as UUID is not a string'` when the value is not a string.
  Express parses a repeated query param (`?studentId=a&studentId=b`) into an **array**, so that request yields a
  **400**, not a crash. Good outcome; note it, and give it a test.
* The default `version: 'all'` regex is `^[0-9A-F]{8}-...$` — it accepts any hex uuid, not only v4. That matches
  what Postgres `@db.Uuid` accepts. Do not tighten it to `4` — the seed data is not guaranteed v4.

**`AC-8`, handled honestly.** `status` is *typed* `EnrollmentStatus` and is a raw string at runtime; with the
pipe it can now only be one of the six `EnrollmentStatus` members (`pending`, `active`, `transferred_in`,
`transferred_out`, `graduated`, `dropped`, read from `schema.prisma`) or absent. **What Prisma did with a bogus
enum before this slice was NOT measured** — this author reached for a generated client and abandoned it on cost
(§1.6). The docblock must therefore say: *the pipe makes the question moot at the handler; the pre-state was
either a `PrismaClientValidationError` surfacing as a 500 (there is no global Prisma exception filter in this
app — `grep -rn "ExceptionFilter" apps/api/src` finds no filter class) or a silently empty result set, and this
slice did not distinguish them.* **Do not write a number you did not take** (`DNC-06`).

**`PF-51` clause (b) closes here** — the three uuid params of this handler are the last site the finding names.
Do not claim it closed until the whole clause is checked at land; `S-E05-13` and `S-E05-14` each advanced it on

**Order-of-execution sentence, stated correctly.** NestJS runs **guards before pipes**, and `PermissionsGuard`

`student` and `academicYear` already carry explicit `select`s and are **unchanged**. `orderBy: [{ enrolledAt: 'desc' }]`

decision, each revocable alone. It also carries `tenantId` and `maxStudents` and no `gradeLevel` — it is the

## 8. `ADR-065` — what it must argue (and what it must not re-argue)

This slice replays `ADR-063` on the sibling handler; the replay needs no ADR. **Three things are genuinely new**
and would otherwise read as oversights:

* **§D1 — a SCOPE, not a WALL.** Every ABAC this epic has shipped so far answers allow/deny on a single keyed
  resource. This is the first that returns a *narrowed list*. Argue why (§3.1), and argue the consequence: the
  security property is now *"the emitted `where` always carries a bounding key"*, which is a property of a
  **data structure**, provable by a pure unit test — not a property of an exception, provable by a throw.
* **§D2 — the empty array is the deny, and the absent key is the fail-open.** Prisma drops `undefined` keys from
  a `where`; `{ in: [] }` is the only representable empty deny. This makes `pnpm typecheck` **load-bearing
  security** in this file for the second time (`ADR-063 §D2` said the same about `teacherProfileId`), because the
  jest double fails *closed* on an absent key exactly where real Prisma fails *open*.
* **§D3 — the teacher wall deliberately does NOT go through `StudentAccessService`, while the parent wall
  deliberately DOES.** GUARDRAILS §2 mandates the service for parent access; `student-access.service.ts:36-38`
  makes it unusable for teachers (`PF-288`). Both halves must be written down, or the next reader will "unify"
  them and reopen the hole.

Do **not** re-argue in `ADR-065`: the missing academic-year clause (`ADR-063 §D1`), the module-local projection
rule (`ADR-062 §D3`), or the `findForUser`-not-`ensureForUser` rule (`ADR-051 §D1`). Cite them.
