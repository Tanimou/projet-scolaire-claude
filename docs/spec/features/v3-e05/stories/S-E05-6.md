# S-E05-6 — the attendance roster payload stops being MAXIMAL

> **Epic** V3-E05 · **Layer** L0 · **Closes** `PF-269` (P1) and `PF-274` (P2) · **Completes** `PF-07` (roadmap)
> **ADR** `ADR-062` · **Predecessor** `S-E05-5` (`ADR-061`, PR #264)

## 0. What this story is, in one sentence

`S-E05-5` narrowed **who** may read the attendance roster. It narrowed **nothing** about **what** the
roster returns. This story narrows the payload, and only then may `PF-07`'s row lose the `AC-21` qualifier
that forbids it from reading `closed`.

## 1. The measurement, re-taken against `HEAD` before a line was written

`PF-269` **reproduces**. Three sites, all in `apps/api/src/modules/attendance/attendance.controller.ts`:

| # | Line | Handler | Expression |
|---|---|---|---|
| 1 | `:463` | `sessionDetail` | `classSection: { include: { enrollments: { where: { status: 'active' }, include: { student: true } } } }` |
| 2 | `:467` | `sessionDetail` | `attendanceRecords: { include: { student: true } }` |
| 3 | `:728` | `roster` | `enrollments: { where: { status: 'active' }, include: { student: true }, orderBy: … }` |

`student: true` is the **whole `Student` row** as declared in `apps/api/prisma/schema.prisma`:
`birthDate`, `email`, `phone`, `gender`, `nationality`, `address` (Json), `photoUrl`, `medicalNotes`,
`notes`, `customFields` (Json), `status`, `userProfileId`, `schoolId`, `tenantId`, timestamps — for
**every actively enrolled child of the class**, on every attendance-taking page load.

`GUARDRAILS.md` §1 makes minimal access non-negotiable, and `medicalNotes` is special-category data about
a minor. This is the WHAT axis of `PF-07`.

### 1.1 The contract is already narrow — the FRONT END says so, and that is the decisive evidence

`apps/web/src/app/teacher/classes/[id]/attendance/AttendanceManager.tsx:12` **already declares**:

```ts
student: { id: string; firstName: string; lastName: string; externalRef: string | null };
```

The consumer's own type is the narrow projection. The backend has been over-delivering against a contract
the frontend never asked for. **The frontend therefore needs no change for the narrowing** — which is what
makes this slice cheap, and why the FE half of it is `PF-274` instead.

### 1.2 `photoUrl` is EXCLUDED, and this refutes the recommendation that produced the story

`NEXT.md` (run 71) recommended `select: { id, firstName, lastName, externalRef, photoUrl }`. **The
`photoUrl` half is refuted by measurement and must not be implemented.** The attendance list renders an
initials avatar — `AttendanceManager.tsx:220` composes `firstName[0]` + `lastName[0]` — and
`grep -rn photoUrl apps/web/src` returns **zero** hits in any teacher attendance file. Shipping a URL that
resolves to a photograph of a child, for every child in the class, inside the slice whose entire thesis is
payload minimisation, would contradict the story on its own terms.

`externalRef` **is** included: it is the school's own pupil identifier (the *matricule*), it is the only
homonym disambiguator in a class list, the consumer's declared type already carries it, and the gradebook
roster — the nearest analogue — already returns exactly this four-field shape
(`grades/assessments.controller.ts:157`).

### 1.3 The house form already exists inside this very file

`attendance.controller.ts:855` (`overview`) already reads
`student: { select: { id: true, firstName: true, lastName: true } }`. Twenty-plus sites across
`announcements`, `guardians`, `child-claims`, `enrollments`, `analytics` use the same form. This story
adopts the house pattern; it does not invent one, and it introduces **no** shared cross-module constant
(that would be a refactor, out of scope — see §6).

### 1.4 The four-portal consumer census (`G-PORTAL`), re-run over `apps/web/src`

`grep -rn "class-sessions" apps/web/src` returns **four** hits, all under `teacher/`:

| Portal | Consumes `GET /class-sessions/:id` (`sessionDetail`) | Consumes `GET /class-sessions/:id/roster` |
|---|---|---|
| admin | no | no |
| **teacher** | **no** | **yes** — `attendance/actions.ts:28` |
| parent | no | no |
| student | no | no |

Two consequences, both load-bearing:

1. **`sessionDetail` has ZERO first-party consumers.** Narrowing it cannot break a caller because it has
   none. It is nonetheless an authenticated endpoint that today emits full `Student` rows, so it is
   narrowed with the same select as `roster` rather than left alone.
2. `roster`'s single consumer already types the narrow shape (§1.1), so `G-PORTAL` is satisfiable by
   census plus the FE type, without a UI change.

## 2. The change plan

### 2.1 `attendance.controller.ts` — one projection, three sites

Introduce **one module-local constant** near the top of the file (module scope, not exported), and use it
at all three sites:

```ts
/**
 * S-E05-6 / `PF-269` — la PROJECTION d'une ligne de liste d'appel.
 *
 * `student: true` rendait la ligne `Student` ENTIÈRE — `medicalNotes`,
 * `address`, `notes`, `customFields`, `birthDate`, `email`, `phone` — pour
 * chaque enfant de la classe, à chaque chargement. `S-E05-5` a restreint QUI
 * lit ; cette constante restreint CE QUI est rendu (`GUARDRAILS` §1).
 *
 * `externalRef` est retenu : c'est le matricule de l'établissement, seul
 * désambiguïsateur d'homonymes dans une liste, et le type du consommateur le
 * déclare déjà (`AttendanceManager.tsx:12`).
 *
 * `photoUrl` est EXCLU délibérément : rien dans l'espace enseignant ne
 * l'affiche (l'avatar est composé des initiales, `AttendanceManager.tsx:220`).
 */
const ATTENDANCE_ROSTER_STUDENT_SELECT = {
  id: true,
  firstName: true,
  lastName: true,
  externalRef: true,
} as const;
```

Then, at each of `:463`, `:467`, `:728`, replace `include: { student: true }` with
`include: { student: { select: ATTENDANCE_ROSTER_STUDENT_SELECT } }`.

**`roster`'s `orderBy: { student: { lastName: 'asc' } }` is untouched** — Prisma's `orderBy` on a relation
is independent of the relation's `select`, and dropping the ordering would silently reshuffle the class
list a teacher reads down while marking.

### 2.2 `AttendanceManager.tsx:124` — `PF-274`, one attribute

```tsx
{error && <div role="alert" className="rounded-xl border border-red-200 bg-red-50 …">{error}</div>}
```

WCAG 2.2 AA §4.1.3 (Status Messages). 26 existing `role="alert"` sites in `apps/web/src` establish the
house form. This is folded in **declared, not silently**: `S-E05-5` made this banner reachable on a *new*
path (its 403 copy is funnelled verbatim through `actions.ts` into it), so a teacher on a screen reader
currently hears **nothing** when a refusal replaces the roster. It is the FE half of the same defect
family and it lives in the file this story is already reasoning about.

### 2.3 What must NOT change

- No handler signature, no route, no permission code, no guard, no refusal order — `S-E05-5`'s ABAC is
  frozen to the byte, and `attendance-read-abac.spec.ts` must stay green **unmodified** except for the
  additions in §4.
- No shared/exported cross-module projection constant (§6).
- `attendanceRecords` scalar fields on `roster` (`attendanceRecords: true`) stay as they are; only the
  `student` relation is projected.
- The deliberately-retained post-load `tenantId` re-checks in both handlers stay (`S-E05-5`'s comments say
  why; removing them is not this story's business).

## 3. Acceptance criteria

| id | criterion |
|---|---|
| **AC-1** | `sessionDetail` returns, for every active enrollment, a `student` object with **exactly** `id`, `firstName`, `lastName`, `externalRef` — and no other key. |
| **AC-2** | `sessionDetail`'s `attendanceRecords[].student` carries the same four keys and no others. |
| **AC-3** | `roster`'s `roster[].student` carries the same four keys and no others. |
| **AC-4** | `medicalNotes`, `address`, `notes`, `customFields`, `birthDate`, `email`, `phone`, `gender`, `nationality`, `photoUrl` are **absent** (not null — absent) from every student object returned by both handlers. A test asserts absence key by key, not shape equality. |
| **AC-5** | `roster` still returns rows ordered by `student.lastName` ascending. |
| **AC-6** | The `S-E05-5` ABAC behaviour is unchanged: `attendance-read-abac.spec.ts` passes with **no edit to any existing assertion**. Refusal order (404 tenant/existence, then 403 ownership) is untouched. |
| **AC-7** | `AttendanceManager.tsx`'s error banner carries `role="alert"`. |
| **AC-8** | No new `select`/`include` is added anywhere outside the three sites named in §2.1. |
| **AC-9** | `apps/web`'s `RosterRow` type is **not widened**; it may only be re-commented to name this story. |

| Gate | Triggered by | Evidence required |

| **G-AUTHZ** | the payload of two authorization-bearing read handlers | new `describe` in `apps/api/src/modules/attendance/attendance-read-abac.spec.ts` (or a sibling spec) asserting AC-1…AC-4 key-by-key, executed by the test-architect |

| **G-TENANT** | a Prisma read is edited | no `where` clause is touched; the `tenantId` guard reads and the post-load re-checks are unchanged — assert by diff, not by claim |
| **G-DNC** | always | no `DNC-06` (a docblock promising more than the runtime): the new constant's docblock states exactly what is and is not returned, including the `photoUrl` exclusion and why |

**Evidence must be executed, not asserted.** The local Docker stack is up (12 containers, `pilotage_api`
and `pilotage_postgres` healthy at Step 1), so nothing here is allowed to land as `deferred — needs a
deployment`.

## 6. Deliberately out of scope, recorded rather than done

1. **A shared `StudentSummary` projection across modules.** Twenty-plus sites declare a near-identical
   student select and they disagree on whether `id` and `externalRef` are present. Consolidating them is a
   cross-module refactor with its own blast radius (it has `PF-270`'s shape, one layer down), and doing it
   inside a payload-minimisation slice would make the diff unreviewable. Record as a new finding.
2. **`PF-267`** (`justify` has no ownership check) — a WRITE handler, out of a payload story.
3. **`PF-264`** (the `parent` catalogue over-grant) — a four-portal permission decision.
4. **`PF-272`** (same-tenant existence oracle) — accepted, and fixing it here alone would desynchronise
   this module from the `lessons` house pattern.
5. **The other `include: { student: true }` sites elsewhere in `apps/api`**, if any. This story's file set
   is `attendance.controller.ts` plus one line of `AttendanceManager.tsx`. A census may be **recorded** as
   a finding; it may not be fixed here.

## 7. Non-regression

The teacher attendance workspace must still: open a session, load the roster in `lastName` order, mark
every pupil, submit a batch, and render a refusal banner — now announced. `attendance/batch` validates
`studentId` against `enrollments` **without** the student relation, so the narrowing cannot affect the
write path.
