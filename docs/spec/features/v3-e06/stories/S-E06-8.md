## 1. Why — the defect, read from the source

### 1.1 Two server actions with no `catch`, called from a `try/finally` with no `catch`

`apps/web/src/app/admin/users/actions.ts` is **16 lines in total**:

```ts
export async function assignRoleAction(userId: string, roleId: string) {
  await api(`/api/v1/users/${userId}/roles`, { method: 'POST', body: { roleId } });
  revalidatePath('/admin/users');
}
```

`apps/web/src/app/admin/users/UsersTable.tsx:30-39` is its only caller:

```tsx
const assignRole = async (userId: string, roleId: string) => {
  setBusy(userId);
  setOpenMenu(null);
  try {
    await assignRoleAction(userId, roleId);
    router.refresh();
  } finally {
    setBusy(null);
  }
};
```

`api()` throws `ApiError` on any non-2xx (`apps/web/src/lib/api-client.ts:108-116`). Neither layer catches. So a
refused grant is an **unhandled promise rejection**: `setBusy(null)` runs (the `finally`), the menu is already closed
(`setOpenMenu(null)` ran *before* the await), `router.refresh()` is skipped because the rejection short-circuits it,
and **no message is rendered anywhere**. The admin clicks a role, the spinner blinks, the row does not change, and
nothing explains why.

### 1.2 The 403 is now real, not hypothetical

Track b's `S-E05-2` (`#218`) landed a privilege ceiling. `apps/api/src/shared/auth/privilege-ceiling.ts:175-179`:

```ts
throw new ForbiddenException({
  message: `${CEILING_REFUSAL_MESSAGE_PREFIX} (${nameCodes(exceeding)}).`,
  required: Array.isArray(requested) ? [...requested] : [],
  missing: exceeding,
});
```

and `apps/api/src/shared/auth/permissions.guard.ts:31-35` throws the same shape with
`message: 'Permission(s) refusée(s)'`. A `NestJS` `ForbiddenException` built from a plain string instead yields
`{ statusCode, message: string, error }`. **So `body.message` is a string on every 403 path in the code today.**

`POST /api/v1/users/:id/roles` is on that path. Measured by track b and recorded at
`docs/daily-improvement-v3/audit-findings-index.md:255`: a `school_admin` holds 75 permission codes; the seeded
`teacher` role exceeds that by 6, `parent` by 3, `student` by 5. **Three of the four other seeded system roles now
always 403 for a `school_admin`** — and `/admin/users` reports that as silence.

### 1.3 The contrast case proves this is a *local* defect

The routine counted `catch` clauses across every `'use server'` file in `apps/web/src`:
**`admin/users/actions.ts` is the only file in the whole web surface with zero catches.**
`admin/alerts/actions.ts` routes all six of its actions through one `callApi` helper that catches;
`admin/settings/preferences-actions.ts` uses `Promise.allSettled`; 14 further action files import the shared
`apiResultFromError` from `@/lib/api-client`. **This is an outlier to fix, not the tip of a class to sweep.
Do not widen into other action files.**

The direct model is `apps/web/src/app/admin/roles/actions.ts:24-31`, which renders the *identical* 403 correctly:

```ts
} catch (err) {
  if (err instanceof ApiError) {
    const body = err.body as { message?: string | { message: string; missing?: string[] } };
    const msg = typeof body?.message === 'string' ? body.message : body?.message?.message ?? `HTTP ${err.status}`;
    return { ok: false, error: msg };
  }
  return { ok: false, error: (err as Error).message };
}
```

### 1.4 Why the extractor must be *total*, not merely correct-today

`apps/api/src/shared/auth/privilege-ceiling.ts:147-152` states the hazard in writing, in the API source:

> `message` is a plain string and MUST stay one: `updateRoleAction`
> (`apps/web/src/app/admin/roles/actions.ts:45-47`) returns `body.message` with no type check and
> `RoleBuilderForm.tsx:236` renders it directly as a React child — nesting an object under `message` would unmount
> the role editor with « Objects are not valid as a React child ».

That is a **backend comment asking a frontend it does not own to keep being careful.** Read the three narrowing
sites in this repo and the inconsistency is visible: `createRoleAction` (`roles/actions.ts:26-28`) handles the nested
`{ message: { message } }` form; `updateRoleAction` (`:45-47`) and `deleteRoleAction` (`:59-62`) do not; the shared
`apiResultFromError` (`api-client.ts:154-164`) handles `string[]` but **not** the nested-object form — its
`body?.message ?? \`HTTP ${err.status}\`` returns the object while the declared return type says `string`. Four
hand-rolled narrowings, three different answers, one of them typed-but-untrue.

**AC-3 exists to make the hazard unreachable by construction rather than by everyone remembering.** A function whose
return type is `string` for *every* input cannot hand React an object, whatever the API later does to its body.

## 3. Acceptance criteria

### AC-1 — neither action can reject

`assignRoleAction` and `revokeRoleAction` return
`Promise<{ ok: true } | { ok: false; error: string }>` and **never reject**. Each:

1. re-throws a Next.js navigation signal **first** — see AC-1b, this is the one intentional improvement on the
   `roles/actions.ts` shape;
2. on `ApiError`, surfaces the API's own message via `apiErrorMessage` (AC-3), which falls back to `HTTP <status>`;
3. on any other thrown value, returns its message — also via `apiErrorMessage`, so a thrown non-`Error` cannot
   produce `undefined`;
4. calls `revalidatePath('/admin/users')` **only on success**.

Reference implementation (write it this way unless you have a measured reason not to):

```ts
'use server';

import { revalidatePath } from 'next/cache';

import { apiErrorMessage } from '@/lib/api-error-message';
import { api, isNextNavigationSignal } from '@/lib/api-client';

export type RoleMutationResult = { ok: true } | { ok: false; error: string };

export async function assignRoleAction(userId: string, roleId: string): Promise<RoleMutationResult> {
  try {
    await api(`/api/v1/users/${userId}/roles`, { method: 'POST', body: { roleId } });
    revalidatePath('/admin/users');
    return { ok: true };
  } catch (err) {
    if (isNextNavigationSignal(err)) throw err;
    return { ok: false, error: apiErrorMessage(err) };
  }
}
```

`revokeRoleAction` takes the identical shape over
`api(\`/api/v1/users/roles/${userRoleId}\`, { method: 'DELETE' })`.

**AC-1b — re-throw Next navigation signals, and say why.** `api()` calls `redirect()` on **401**
(`api-client.ts:103-106`): an expired access token sends the admin to `/{portal}/login?error=session_expired`.
`redirect()` works by throwing. A `catch` that does not re-throw it converts a login redirect into an inline error
strip reading `NEXT_REDIRECT;replace;/admin/login…`. `api-client.ts:126-140` already exports
`isNextNavigationSignal` with a docblock saying exactly this. **`roles/actions.ts` does not call it** — copying that
file verbatim would import a live defect along with the shape. Copy the shape; add the guard. The gap in
`roles/actions.ts` (three actions) is registered as a follow-up in §8, **not** fixed here (different route, and
widening is forbidden by GUARDRAILS §5).

### AC-2 — `UsersTable` renders the refusal, reachably

1. Component state gains `const [error, setError] = useState<{ userId: string; message: string } | null>(null)`.
2. `assignRole` sets `setError(null)` **before** the call (so a retry clears the previous refusal), and on
   `result.ok === false` sets `{ userId, message: result.error }`.
3. **`router.refresh()` runs only when `result.ok === true`.**
4. The `finally { setBusy(null) }` **stays** — the spinner must clear on every path, success, refusal and throw.
5. The refusal renders as an extra `<tr>` inserted **immediately after** the offending user's row:
   `<tr><td colSpan={4}>` wrapping a `div role="alert"`. This is the association required by the AC: the message sits
   in the table's own reading order, adjacent to the row it concerns, rather than in a page-level region a
   screen-reader user never reaches. Do **not** substitute a persistent empty `aria-live` container elsewhere on the
   page — *an `aria-live` region that never receives focus and never announces is the same silence in a different
   costume.*
6. The alert carries a stable `id` (e.g. `` `role-error-${u.id}` ``) and the row's trigger button carries
   `aria-describedby={error?.userId === u.id ? \`role-error-${u.id}\` : undefined}`, so a keyboard user who tabs back
   to the trigger hears the reason again.
7. **Focus.** The menu closes on click, which can leave focus on a removed node. On a refusal, return focus to that
   row's trigger button (a `ref` per row, or `document.getElementById` on the button's id — either is acceptable;
   pick one and keep it). Without this, `role="alert"` announces once and the user has no way back to the context.
8. Dismissible: a trailing icon button, `type="button"`, `aria-label="Masquer le message d'erreur"`, calling
   `setError(null)`. It must be a real `<button>` — not a clickable `<span>`.
9. The message text is the API's, prefixed by a short French frame so an operator sees what failed. Copy:
   **« Rôle non assigné — {message} »**. Do not invent a friendlier substitute for the API's sentence: the API's
   sentence names the exceeding permission codes, which is the only actionable part.
10. Responsive: the alert is inside a `colSpan={4}` cell, so it inherits the table's width; the text must wrap
    (`break-words`), never force a horizontal scroll.

### AC-3 — one total extractor, in `apps/web/src/lib/`

New file `apps/web/src/lib/api-error-message.ts` exporting exactly one function:

```ts
export function apiErrorMessage(err: unknown): string
```

Its **return type is `string` for every input**. It must be correct on all of:

| Input | Result |
|---|---|
| `ApiError` with body `{ message: 'Permission(s) refusée(s)' }` | that string |
| `ApiError` with body `{ message: { message: 'Plafond…', missing: [...] } }` | the **inner** string |
| `ApiError` with body `{ message: ['a', 'b'] }` (class-validator's array form) | `'a · b'` — same separator `apiResultFromError` already uses (`api-client.ts:158-160`) |
| `ApiError` with body `null`, `undefined`, `''`, a bare string, or a number | `` `HTTP ${err.status}` `` |
| `ApiError` with body `{ message: 42 }` or `{ message: {} }` | `` `HTTP ${err.status}` `` — never `String(object)`, never `'[object Object]'` |
| a plain `Error` | `err.message`, or a generic French fallback if it is empty |
| a thrown string / `null` / `undefined` / object | a generic French fallback, e.g. `'Une erreur inattendue est survenue.'` |

Implementation notes: narrow with `typeof` at every step; never assert a body shape with `as` and then read through
it. It must import `ApiError` from `@/lib/api-client` and use `instanceof`. It must be **pure** — no `console`, no
`headers()`, no `process.env`, nothing that ties it to a request scope, so any future caller (client or server) can
use it.

**Docblock requirement.** Name `PF-174`, state the React-child hazard in one sentence, cite
`apps/api/src/shared/auth/privilege-ceiling.ts:147-152` as the upstream source of the constraint, and note that
`apps/web/src/app/admin/roles/actions.ts` (3 sites) and `apiResultFromError` in `@/lib/api-client` (14 importing
files) are **candidates for delegation, deliberately not retrofitted in this slice**. Per **DNC-06**, write no
sentence the code does not do: if you do not implement the `string[]` case, do not claim it.

### AC-4 — do **not** pre-filter or disable the role menu (a refused product decision)

`PF-174`'s own text ends *"and stop offering roles the caller cannot grant."* **That half is decision-blocked and is
not implemented here.** Which roles a `school_admin` may grant is exactly the open question

- Add **no** new filter, no `disabled`, no "non autorisé" badge, no client-side permission check.

### 5.2 Accessibility (WCAG 2.2 AA)

- `role="alert"` on a node **inserted** into the DOM (not a pre-existing empty container that later gains text) —
  insertion is what makes assistive tech announce it.
- `aria-describedby` from the trigger button to the alert while it is shown (AC-2.6).
- Focus returned to the trigger on refusal (AC-2.7), so the announcement has a reachable context.
- Dismiss control is a `<button type="button">` with an `aria-label`; it is keyboard reachable and in the natural tab
  order right after the alert text.
- Contrast: `text-red-900` on `bg-red-50` is the same pair the invite form already ships; do not lighten it.
- Target size: the dismiss control must be ≥ 24×24 CSS px (WCAG 2.5.8) — an `h-4 w-4` icon needs padding around it.
- The alert must **not** auto-dismiss on a timer. `S-E06-1`'s land note records a timed redirect being removed from
  this same route folder as a **WCAG 2.2.1** failure; do not reintroduce the pattern.
