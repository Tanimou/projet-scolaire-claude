## 1. Why — the defects, read from the source

### 1.1 `PF-179` — three catch blocks, three different answers, zero navigation re-throws

`apps/web/src/app/admin/roles/actions.ts` is **71 lines** and exports four actions. Three of them carry a blanket
`catch` (`:24-31`, `:44-50`, `:58-64`) and **none re-throws the Next.js navigation signal**:

```ts
// createRoleAction — :24-31
} catch (err) {
  if (err instanceof ApiError) {
    const body = err.body as { message?: string | { message: string; missing?: string[] } };
    const msg = typeof body?.message === 'string' ? body.message : body?.message?.message ?? `HTTP ${err.status}`;
    return { ok: false, error: msg };
  }
  return { ok: false, error: (err as Error).message };
}
```

```ts
// updateRoleAction — :44-50 · deleteRoleAction — :58-64 (byte-identical to each other)
} catch (err) {
  if (err instanceof ApiError) {
    const body = err.body as { message?: string };
    return { ok: false, error: body?.message ?? `HTTP ${err.status}` };
  }
  return { ok: false, error: (err as Error).message };
}
```

`api()` calls `redirect()` on a **401** (`apps/web/src/lib/api-client.ts:111-114`), and `redirect()` works by
**throwing**. So an admin whose Keycloak session expired mid-edit has the redirect caught by these blocks, returned as
**data**, and rendered at `RoleBuilderForm.tsx:236` inside the red strip — while the browser stays exactly where it
was. The user is told nothing true and is never sent to login.

The second half of `PF-179` is the divergence itself (`S-E06-8`'s **F2**): `createRoleAction` understands NestJS'
nested `{ message: { message, missing } }` form; `updateRoleAction` and `deleteRoleAction` do not, and their
`body?.message ?? …` returns the **object** through a field the signature declares `string`. That is the exact hazard
`apps/api/src/shared/auth/privilege-ceiling.ts:147-152` documents *in the API source* as a written plea to a frontend
it does not own. Its two consumers fail differently, and the difference is worth knowing before you write the AC:
`RoleBuilderForm.tsx:236` renders `{error}` as a **React child**, so an object unmounts the whole role editor
(« Objects are not valid as a React child »); `DeleteRoleButton.tsx:19` interpolates it into `alert()`, so an object
prints `[object Object]`. One is a crash, one is a lie.

### 1.2 What the admin actually sees today — **measured, and it is not what prior documents quote**

`docs/daily-improvement-v3/NEXT-c.md:41` and the operator brief both say the strip renders
`NEXT_REDIRECT;replace;/admin/login…`. **Read against the pinned runtime, both halves of that string are wrong**, and
recording them unexamined would put a string in the PR body that never appears on screen (`DNC-06`).

Measured in `apps/web/node_modules/next/dist/client/components/redirect.js:42-55`, Next **15.5.18** (the pinned
version, `apps/web/node_modules/next/package.json`):

| | value | consequence |
|---|---|---|
| `error.message` | `'NEXT_REDIRECT'` — `new Error(REDIRECT_ERROR_CODE)`, `:44` | this is what the `(err as Error).message` branch returns, so **`NEXT_REDIRECT` is the string on screen today**, bare, with no destination |
| `error.digest` | `` `NEXT_REDIRECT;${type};${url};${statusCode};` `` — `:49` | never rendered by these actions (they read `.message`), but it is what `isNextNavigationSignal` tests |
| `type` inside a server action | **`push`**, not `replace` — `:53` reads `actionAsyncStorage.getStore().isAction` and picks `RedirectType.push` when true | the digest here is `NEXT_REDIRECT;push;/admin/login?error=session_expired;307;`. `replace` is the *render-time* default |

**Nothing about the defect changes** — a framework internal is rendered as a business refusal and the navigation never
happens. Only the quoted characters change. Use `NEXT_REDIRECT` (the rendered value) and
`NEXT_REDIRECT;push;…;307;` (the digest) if you quote anything at all. `isNextNavigationSignal`
(`api-client.ts:141-148`) tests `digest.startsWith('NEXT_REDIRECT')`, which matches both `type`s and both defaults —
**the guard is correct as written and needs no change.**

### 1.3 `PF-180` — three more actions that show a status code and throw the reason away

`apps/web/src/app/admin/settings/preferences-actions.ts` (146 lines) collapses every `ApiError` to `` `HTTP ${status}` ``
at `:52`, `:100-102` and `:141-143`, and **never reads `body.message`**. A permission refusal, a class-validator
rejection and a proxy 502 are therefore indistinguishable on screen: `PreferencesPanel.tsx:121/140/165/184` writes the
string straight into its error strip via `setError(res.error ?? 'Erreur')`. This is not `PF-174`'s silence — something
*is* shown; it just carries nothing the operator can act on.

### 1.4 `Promise.allSettled` is strictly worse here than a `catch`, and that is why the bulk actions need more than a swap

`setChannelForKindsAction` (`:76-104`) and `setCadenceForKindsAction` (`:118-145`) fan out N PATCHes through
`Promise.allSettled`. A `catch` at least *has* the thrown value in a position where re-throwing is one line; a settled
rejection has been **converted into data by the language**. So when `api()` calls `redirect()` on a 401 inside one of
those PATCHes, the navigation signal becomes `results[i].reason` and **can never propagate** — the 401 redirect is
unreachable **by construction**, not by omission. Neither bulk action can be fixed by changing its message
formatting alone; the rejected-reason scan in AC-3 is the load-bearing part.

The two failure blocks (`:97-103` and `:138-144`) are **byte-identical**. Factoring them is `F2`'s remaining half.

### 1.5 Why the shared converter cannot be used today without the type change in AC-1

`apiResultFromError` returns `ApiResult<never>`, i.e. `{ ok: true; data: never } | { ok: false; error: string }`. The
`{ ok: true; data: never }` member is assignable to `ApiResult<T>` for every `T` (`never` is assignable to anything),
which is why the 16 existing call sites compile. It is **not** assignable to `{ ok: true; id: string }` —
`createRoleAction`'s success member — nor does it spread cleanly into `BulkChannelResult`. The converter's declared
type currently advertises a success it can never return, and that phantom member is the only thing standing between
these six actions and the shared seam. **AC-1 removes the phantom; it does not add a capability.**

## 3. Acceptance criteria

### AC-1 — `apiResultFromError` returns the failure member, and only that

In `apps/web/src/lib/api-client.ts`, immediately after the `ApiResult` declaration (`:150`):

```ts
/**
 * Le membre **échec** d'`ApiResult`. `apiResultFromError` ne peut renvoyer que
 * celui-ci ; l'annoncer permet aux actions dont la branche succès n'est pas
 * `{ ok: true; data: T }` — `{ ok: true; id: string }`, `BulkChannelResult` —
 * d'utiliser le convertisseur partagé au lieu d'en réécrire une copie.
 */
export type ApiFailure = Extract<ApiResult, { ok: false }>;
```

and change the signature at `:177`:

```ts
export function apiResultFromError(err: unknown): ApiFailure {
```

**The body does not change.** In particular `if (isNextNavigationSignal(err)) throw err;` stays the **first**
statement — before the `instanceof ApiError` check and before the `console.error`. Weakening or reordering that line
fails `G-DNC` and reintroduces `PF-179` inside the fix for it.

**Why this is safe, measured not argued.** `ApiFailure` is a member of `ApiResult<T>` for every `T`, so narrowing a
return type cannot break an assignment that previously succeeded. And every existing call site is the same one
expression: `grep -rn "apiResultFromError(" apps/web/src --include=*.ts --include=*.tsx | grep -v "return apiResultFromError(err);"`
returns **exactly one line**, the declaration itself — **16 importing files, 20 call sites, zero of them destructure
the result, test `.ok === true` or read `.data`.**

### AC-2 — the three `admin/roles` actions delegate, and keep their public types exactly

`apps/web/src/app/admin/roles/actions.ts`:

1. Import line `:6` becomes `import { api, apiResultFromError } from '@/lib/api-client';`. **`ApiError` must be
   dropped** — it has no other use in the file, and a 27th `@typescript-eslint/no-unused-vars` warning would put

2. All three `catch` bodies become exactly:
   ```ts

   }
   ```
3. **The declared return types are unchanged, character for character**:
   `createRoleAction`: `Promise<{ ok: true; id: string } | { ok: false; error: string }>`;
   `updateRoleAction` and `deleteRoleAction`: `Promise<{ ok: true } | { ok: false; error: string }>`.
   Do **not** "harmonise" them to `ApiResult<T>` — `RoleBuilderForm.tsx:138-139` and `DeleteRoleButton.tsx:18-19`

### AC-3 — the three preference actions delegate; the two bulk actions also re-throw

`apps/web/src/app/admin/settings/preferences-actions.ts`:

1. Import line `:5` becomes
   `import { api, apiResultFromError, isNextNavigationSignal } from '@/lib/api-client';`. **`ApiError` must be
   dropped** — same lint ceiling reason as AC-2.1.
2. `updatePreferenceAction` (`:51-54`) — the whole `catch` body becomes `return apiResultFromError(err);`.
   Its declared return type `Promise<{ ok: boolean; error?: string }>` **stays as it is**; `{ ok: false; error: string }`
   is assignable to it. (Tightening it to a discriminated union would be an improvement and is **not** this slice —
   see F1.)
3. **One** module-local helper replaces the two byte-identical blocks at `:97-103` and `:138-144`:

   ```ts
   /**
    * Chemin d'échec partagé des deux actions groupées.
    *
    * **Pourquoi un balayage explicite des raisons rejetées (PF-179/PF-180).**
    * `Promise.allSettled` transforme un rejet en **donnée** : le signal de
    * navigation que `redirect()` jette sur un 401 (`api-client.ts:111-114`)
    * devient un `reason` et ne peut plus, par construction, atteindre le
    * runtime. On le retrouve donc à la main et on le re-jette. Le balayage
    * couvre **toutes** les raisons, pas seulement la première : les PATCH
    * partent en parallèle, l'ordre de `results` est celui de `kinds`, et un lot
    * mixte (un 403 métier sur un kind, un 401 sur un autre) est possible.
    */
   function bulkFailure(
     results: PromiseSettledResult<unknown>[],
     succeededKinds: NotificationKindCode[],
   ): BulkChannelResult {
     const reasons = results.flatMap((r) => (r.status === 'rejected' ? [r.reason as unknown] : []));
     const navigation = reasons.find(isNextNavigationSignal);
     if (navigation !== undefined) throw navigation;
     return { ...apiResultFromError(reasons[0]), succeededKinds };
   }
   ```

   and each bulk action's tail becomes:

   ```ts
   return bulkFailure(results, succeededKinds);
   ```

5. **Totality**: `bulkFailure` is only reached when at least one promise rejected, so `reasons[0]` exists. It is safe

   never be mistaken for a signal.
6. `BulkChannelResult` is **unchanged**, and both actions still return `succeededKinds` on **both** branches —

### 6.2 G-DNC — reproduce none of DNC-01…DNC-12

All twelve read at `docs/daily-improvement-v3/audit-findings-index.md:308-324`. Three are load-bearing:

- **DNC-10** (*hard-coded demo-account billing bypass* — the register's "backdoor by string comparison" seam).
  **The converter must gain no options bag and no bypass flag.** No `apiResultFromError(err, { rethrow: false })`, no
  `raw: true`, no `NODE_ENV`/`SKIP_*` branch, no second exported variant that skips the navigation check. A shared
  refusal path with an off switch is a backdoor with better manners. The one legitimate way to *not* re-throw is to
  not call the converter at all — and no action in this slice does that.
- **DNC-06** (*guides promise deeper behaviour than runtime delivers*). Every comment, docblock and PR sentence this
  slice writes must describe only what the code does. §1.2 exists because two inherited strings failed this test;
  do not reintroduce them. Do not claim `PF-180` is "tested".
- **DNC-08** (*an unclassifiable state reported as a pass*). No new path may return `{ ok: true }` on a failure or
  `{ ok: false, error: '' }`. Both are structurally impossible after this diff — `apiErrorMessage` never returns an
