## 1. The defect, stated as a sequence

`apps/api/src/modules/identity/register.controller.ts` `registerParent()` (`:65-126`) is **the one unauthenticated
account-creation path in the product**. It runs four writes as four independent statements. There is no
`$transaction` and no compensating action anywhere in the file — measured, not assumed:

```
grep -c auditLog     apps/api/src/modules/identity/register.controller.ts   → 0
grep -c '$transaction' apps/api/src/modules/identity/register.controller.ts → 0
```

| Step | Line | What it does | Reversible? |
|---|---|---|---|
| a | `:78-83` | `keycloak.findUserByEmail(email)` → if found, `ConflictException` | read only |
| b | `:94-102` | **`keycloak.createUser(...)` — an ENABLED realm identity holding `parent`, `emailVerified: true`, no required actions** | **no** |
| c | `:103` | **`keycloak.setUserPassword(kcUserId, body.password, false)` — a PERMANENT password** | **no** |
| d | `:106-110` | `prisma.tenant.upsert` of the `demo` tenant | yes, if it were in a transaction |
| e | `:112-123` | `prisma.userProfile.create` | yes, if it were in a transaction |
| — | — | **no `auditLog` row is written on any path** | — |

**Two independent defects live here, and the fix must close both.**

**(i) The orphan.** A failure at step **e** — a `P2002` on `authProviderId`/`email`, a pool timeout, a driver
hiccup — leaves an **enabled Keycloak identity with a permanent password, holding the `parent` realm role, and no
`UserProfile`**. That is exactly the orphan class `PF-163` named and `S-E04-9` removed from the sibling `invite`
path. It is worse here in one respect: step **c** has already set a password the registrant *chose and knows*, so
the identity is immediately loginable. On first login,
`apps/api/src/shared/auth/user-sync.service.ts:38-55` finds no profile and **self-provisions one** into the `demo`
tenant (`PF-165`), and `PermissionsGuard` derives permissions from the realm role. The retry path is also a dead
end: step **a** answers `409` forever (`:80-83`), advice that *completes* the failure rather than fixing it.

**(ii) The silence.** Account creation is a privileged mutation by `G-AUDIT`'s own definition, and this handler
writes **no audit row at all**. The audit trail `V3-E04` exists to complete has a hole exactly the shape of "who
created accounts on this platform, from where, when". `TOOL-03` is why no gate caught it: the audit-write sweep
counts *existing* audit writes, so a mutation with **zero** of them contributes nothing to the population and passes
every rule silently. **`TOOL-03` is a known, recorded finding and is NOT in scope here** — do not touch
`scripts/**` or `apps/api/src/shared/quality/**` (see §9).

The trigger is a DB fault, not attacker-controlled: **availability-triggered, not exploitable on demand.** That is
why this is `P2` as a finding, and why the diff is nonetheless tagged `P1` risk — it edits the unauthenticated
account-creation path.

transaction in its own method is what makes the call-site `catch`/`.catch()` legal. `.catch()` is used rather than
`try` at the call site for the same reason, one layer out.

## 3. Functional requirements

- **FR-1** — The two local writes (`tenant.upsert`, `userProfile.create`) and one new audit row execute inside a
  single `this.prisma.$transaction`, in a private method.
- **FR-2** — Both Keycloak calls stay outside that transaction, before it, in their current order.
- **FR-3** — The transaction writes exactly one audit row through `writeAudit`, with a newly declared action code
  `user.register`.
- **FR-4** — Provenance (`actorRole`, `portal`, `ipAddress`, `userAgent`) is derived **before** the transaction
  opens, through the canonical seams only.
- **FR-5** — A transaction failure deletes the Keycloak identity this request created; a failed deletion is loud and
  names the orphan.
- **FR-6** — Every caller-observable behaviour is otherwise byte-identical.

## 4. The provenance question — the brief's premise was measured and is **false**. Read this before writing AC-4.

The task brief for this slice asserts: *"This endpoint is public so the request genuinely IS the operator's
browser (unlike the web→api hairpin PF-31 is about)."* **That is not true of the deployed topology, and the
implementation must not encode it.**

Measured at `c8ee4f3`:

- The only caller is `apps/web/src/app/parent/register/actions.ts:21`, a **`'use server'` server action**. It runs
  in the **web container** and reaches the API with a bare `fetch` (`:25-31`), whose headers are exactly
  `Content-Type` and `Accept`. Its own docblock says why: *"does NOT use the auth-aware api() helper because
  there's no session yet"* (`:18-20`).
- Consequently it sends **none** of `x-pilotage-client-ip` / `x-pilotage-client-user-agent` /
  `x-pilotage-forward-token`. The forwarding seam that would add them —
  `clientProvenanceHeaders` (`apps/web/src/lib/client-provenance.ts:332-350`) — is wired into
  `apps/web/src/lib/api-client.ts:86` and `apps/web/src/app/api/proxy/[...path]/route.ts:51`, and **this action
  goes through neither**.
- So `extractAuditClientHints` takes **branch 2** (`client-hints.ts:306-317`): nobody claims to relay, and `req.ip`
  is the **web container's** address — one constant address shared by every registrant. That is `PF-31` verbatim.

**What this changes in the implementation: nothing about the seam, everything about the claims.**

- **Still add `@Req()` + `extractAuditClientHints(req)`.** It is the one legal extraction point, it never invents a
  value, and under the short-chain rule (`ADR-036` D4, `client-hints.ts:312-315`) it prefers `null` to a wrong
  address. It is also already correct for any future caller that *does* forward.
- **Do NOT write a comment or a test claiming the recorded ip is the parent's browser.** Write the opposite, in the
  file: today it is the relay's address or `null`, and making it real is a **one-line change in
  `apps/web`** (route the action through the same forwarding seam) that is **out of this slice's owned paths**
  (track b owns `apps/api/**` + the one vocabulary line). Record it as a follow-up in the ADR append (§8), do not
  take it here.
- The unit tests in §6 pass hints **directly**, so they pin the wiring (`hints → row`) without asserting anything
  about production topology.

**The role/portal half.** There is **no JWT on this path** — and `deriveAuditProvenance` is nonetheless mandatory.
`apps/api/src/shared/quality/audit-provenance-gate.spec.ts` `G-3` (`:160-190`) asserts that **exactly one file under
`apps/api/src` decides an actor role from realm roles**, stated over the *behaviour* (a bracketed literal naming all
four realm roles; a `portal:` ternary resolving to a portal name), not over an identifier — precisely so a new
anonymous copy cannot slip past. So:

```ts
// There is no JWT on this public path, and inventing `actorRole: 'parent'` here
// would be a second place that decides an actor role — the exact shape
// `audit-provenance-gate.spec.ts` G-3 forbids. Instead we hand the canonical
// mapper the ONE fact this handler actually knows, because it is the fact this
// very request is granting: the `parent` realm role, the same literal already
// passed to `keycloak.createUser` at :100. That is an OBSERVATION of what is
// being granted, not a GUESS about a caller — which is why it is honest.
const selfRegistrationClaims = {
  realm_access: { roles: ['parent'] },
} as unknown as KeycloakJwtPayload;
const provenance = deriveAuditProvenance(selfRegistrationClaims, extractAuditClientHints(req));
```

The single-element array `['parent']` does **not** trip `declaresRolePrecedenceOrdering` (which fires only when one
bracketed literal names all four roles, `audit-provenance-gate.spec.ts:157-163`), no `portal:` literal is written
at all, and `actorRole: 'school_admin'` never appears. All three `G-2`/`G-3` matchers stay green **and** the
derivation stays in its one home.

## 5. Acceptance criteria — verbatim, each with its own evidence

**AC-1** — The two LOCAL writes (`tenant.upsert`, `userProfile.create`) and the new audit row occur inside ONE
`this.prisma.$transaction`. Extract them into a private method (mirror `persistInvitedProfile`) — this is REQUIRED,
not stylistic: `scripts/audit-write-check.js` rule B walks every AST ancestor of a `writeAudit` call and turns red
if a `try` appears anywhere above it, function boundaries included, so the transaction MUST live in its own method
separate from the call site's catch.
*Evidence:* the new private method exists and contains all three writes; §6 case (a) asserts `$transaction` is
opened exactly once; §6 cases (b)(c) assert nothing is committed on failure.

**AC-2** — Both Keycloak calls (`createUser`, `setUserPassword`) stay OUTSIDE the transaction, before it. An HTTP
round-trip inside an interactive Prisma transaction is how a 5 s timeout becomes an incident. This ordering is
already correct in the file — preserve it.
*Evidence:* §6 case (a) counts Keycloak calls made *inside* the `$transaction` callback and asserts `0`, using the
counter pattern from `invite.controller.spec.ts:102-108,153-167`.

**AC-3** — The transaction writes exactly one audit row through the shared seam: `await writeAudit(tx, { ... })`
from `../../shared/audit/write-audit`, as ONE unconditional statement with an INLINE OBJECT LITERAL and the
transaction client first. Never wrap it in an `if`; if you need a guard, use an early return ABOVE it
(`users.service.ts` `revokeRole` `:209` and `:231-236` is the local precedent). `action` must be a code declared in
`AUDIT_ACTIONS` — none fits, so ADD exactly one:

```ts
{ code: 'user.register', label: 'Création d’un compte parent' },
```

to `packages/contracts/src/audit/vocabulary.ts`, **next to the existing `'user.invite'` entry at `:337`**.
`resourceType: 'user_profile'` already exists (`vocabulary.ts:194`) — reuse it.
*Evidence:* both directions of `audit-vocabulary-gate.spec.ts` stay green — FORWARD (`:844`) needs the label,
REVERSE (`:854`) needs a writer, and the writer is only visible to the extractor if the object literal is inline
(rule C, `audit-write-check.js:53-58`). The declared floors are `toBeGreaterThanOrEqual` (`:622-625`), so one added
code cannot break them, and the new private method takes **no `action` parameter**, so it is not a forwarder and
must **not** appear in the closed forwarder list at `audit-vocabulary-gate.spec.ts:744-775`.
*Style note:* the label uses the typographic apostrophe `’`, like every neighbouring entry, and names what the row
actually records — a **parent** account created by self-registration, distinct from `user.invite`'s
*"Invitation d’un utilisateur"*.

**AC-4** — Provenance is REAL, not a null placeholder, and is derived BEFORE the transaction opens. Add `@Req()` to
the handler and use `extractAuditClientHints(req)` from `../../shared/audit/client-hints` to get ip/userAgent. For
`actorRole`/`portal` you MUST go through the canonical mapper `deriveAuditProvenance` — do NOT hand-write
`actorRole: 'parent'`. Pass a minimal locally-declared payload carrying the realm role this handler actually grants
(`realm_access.roles = ['parent']`, matching the literal already at `:100`) plus the hints, and COMMENT why that is
honest rather than invented: the role is the one being granted by this very request, not a guess about a caller.
**Amended by §4:** the comment must also state that today's `ipAddress` is the relay's, not the registrant's,
because the only caller is a server action that does not forward the hint headers. Do not claim otherwise.
*Evidence:* `@Req() req: ClientHintsRequest` on the handler (the house signature —
`users.controller.ts:66`, `child-claims.controller.ts:85`), one `deriveAuditProvenance(...)` call above the
transaction, `actorRole: 'parent'` / `portal: 'parent'` observed on the committed row in §6 case (a).

**AC-5** — `actorId` is the newly created `UserProfile.id` and `resourceId` is that SAME id. Self-registration is
the one case where actor and subject coincide; say so in a comment. `resourceId` must be a bare uuid
(`AuditLog.resourceId` is `@db.Uuid`) — never a composite. `tenantId` is the demo tenant's id resolved by the
upsert inside the transaction.
*Evidence:* §6 case (a) asserts `actorId === resourceId === profile.id` and `tenantId === <upserted tenant id>`.

**AC-6** — When the transaction fails, the Keycloak identity created by THIS request is DELETED by a compensating
action, via `.catch()` at the call site (NOT a `try/catch` — see AC-1's reason), calling `this.keycloak.deleteUser`
(`keycloak-admin.service.ts:176`). When the compensating delete ITSELF fails, nothing is swallowed: log an error
naming the orphan id and throw with a French sentence containing that id, mirroring `orphanedKeycloakUserMessage`
in `invite.controller.ts:91-96`. The original failure travels as `cause` and is never masked.
*Copy note:* the reader here is the **registrant**, not an administrator — `ParentRegisterForm.tsx` renders
`res.error` from `actions.ts:44` raw, so this string IS user-interface copy. Write it for a parent (one French
sentence: the account could not be created, nothing was kept, quote this identifier to support), keep the id **in
the message string** (`actions.ts:32-37` keeps only `body.message`), and put it in a single module-level function
next to the handler, the way `invite.controller.ts` does.
*Evidence:* §6 cases (b)(c)(d).

**AC-7** — New spec file `apps/api/src/modules/identity/register.controller.spec.ts`, modelled on
`invite.controller.spec.ts`. Cases enumerated in §6.

**AC-8** — Behaviour a caller can observe is otherwise UNCHANGED: the two `400` validation branches (`:66-73`), the

*Evidence:* §6 case (e) asserts the exact 409 string and the exact response object; the DTO, the Swagger decorators
