## 1. What is broken, measured (2026-08-09, re-verified this run)

### 1.1 The `to` filter drops its own day

`apps/api/src/modules/analytics/analytics.service.ts:3316`

```ts
...(to ? { lte: new Date(to) } : {}),
```

`new Date('2026-08-08')` is `2026-08-08T00:00:00.000Z`. So `to=2026-08-08` returns **nothing written on
2026-08-08** — the filter excludes the day the user typed. `from` has the mirror defect at `:3315`
(`gte: new Date(from)` is 00:00 **UTC**, i.e. 02:00 in Paris in summer, so it over-includes the two hours
before the requested day started locally *and* under-includes the first two hours of it — the sign flips
with the season).

### 1.2 Three all-time counts standing beside a filtered table

`analytics.service.ts:3373-3401`. `data` and `total` are computed over `where` (all six filters). The KPIs
are not:

```ts
const todayStart = new Date();
todayStart.setHours(0, 0, 0, 0);          // ← the SERVER's zone. Same class of defect as 1.1.
const [today, criticalChanges, sensitiveExports] = await Promise.all([
  this.prisma.auditLog.count({ where: { tenantId, createdAt: { gte: todayStart } } }),
  this.prisma.auditLog.count({ where: { tenantId, action: { in: auditCriticalActionCodes() } } }),
  this.prisma.auditLog.count({ where: { tenantId, action: { in: auditExportActionCodes() } } }),
]);
```

`where: { tenantId, … }` **only**. No `from`, no `to`, no `actorId`, no `action`, no `resourceType`, no
`portal`. Filter the table to one actor on one day and the three cards keep reporting the whole tenant's
history. That is the G-TRUTH defect verbatim: a surface asserting something it did not measure.

The « ACTIONS AUJOURD'HUI » card is the sharpest instance — a card whose *title* is a time window sitting
above a table the user has just filtered to a different one.

### 1.3 The fourth card

`adminLogins` is already honest (`number | null`, renders « Non instrumenté », issues **no query** while
`AUDIT_LOGIN_ACTIONS` is empty — `analytics.service.ts:3388-3401`). That discipline is DNC-09 and it is
**correct**; you are not undoing it, you are removing the card it protects. `data-model.md` D-23 and
`contracts/openapi.yaml` `AuditKpis` already specify the removal + `distinctActors`; the code does not.
That disagreement is `PF-137`.

### 1.4 `Tenant` has no timezone

`apps/api/prisma/schema.prisma:249-263`. `Tenant` carries `id, name, slug, status, plan, settings Json,
createdAt, updatedAt` and **no `timezone`**. Only `School.timezone` exists (`:272`, default
`'Europe/Paris'`). A day-inclusive `to` computed in the *server's* zone would make two admins in two zones
read two different counts for the same filter — the very defect this slice closes. Hence the column, hence
**G-MIGRATION**.

`School.timezone` is deliberately **not** reused: the audit journal is tenant-scoped
(`audit_log.tenant_id`), a tenant can hold several schools, and there is no school on an audit row to pick
one from. Say this in the PR so no reviewer proposes it as a "simpler" alternative.

### 1.5 A fourth audit vocabulary survives — and is already wrong (`PF-134`)

`apps/web/src/app/admin/audit/AuditTable.tsx:57-86`. `pickActionTone` / `pickActionIcon` are inline
substring matchers on the raw action code, sitting next to the declaration that was supposed to replace
them. Measured: `coefficient.upsert` and `grade.unflag` are declared `critical: true` in
`packages/contracts/src/audit/vocabulary.ts`, are **counted by the « Modifications critiques » card**, and
contain none of `création|publish|approve|create|suppression|delete|reject|révision|update|mise à jour|export`
— so they fall through to `'neutral'`. The card says a critical change happened; the row for it is painted
unremarkable.

### 1.6 A null-portal row is reachable by no offered filter (`PF-123`, read half)

`analytics.service.ts:3435` builds the portal facet with `where: { tenantId, portal: { not: null } }`, while
the row filter at `:3311` matches `portal` **exactly**. `assessments.controller.ts:290` writes
`assessment.publish` with no `portal` key. So rows with `portal = NULL` exist, appear in the table, and
**no value the dropdown offers can select them** — there is no « Sans portail » option and there is no way
to ask for one.

### 1.7 An outage renders as an affirmative claim (`PF-139`)

`apps/web/src/app/admin/audit/page.tsx:64-71,135-139`. `safe()` swallows every `ApiError` to `null`; the
fallback then hard-codes `{ today: 0, criticalChanges: 0, sensitiveExports: 0, adminLogins: null }`. When
the analytics API is down the page renders **« 0 modifications critiques »** and an EmptyState reading
« Aucune entrée d'audit ». Both are affirmative statements about the audit log, made from a failed request.
`adminLogins: null` in that fallback is worse still: it reuses the **same sentinel** that means
« not instrumented ».

Second half, same finding: `KpiCard` renders `value` at `font-mono text-3xl font-bold` inside
`overflow-hidden` with `min-w-0` on the *label* group only
(`packages/ui/src/components/KpiCard.tsx:130-137`), so a long string value is **clipped, not ellipsised**.

## 2. What to build

### 2.1 The migration (G-MIGRATION — primary gate)

**Schema** — `apps/api/prisma/schema.prisma`, `model Tenant`, one line, additive:

```prisma
  timezone  String       @default("Europe/Paris")
```

Place it after `plan` and before `settings` so the column order matches the file's existing shape.

**Migration file** — `apps/api/prisma/migrations/<timestamp>_tenant_timezone/migration.sql`, generated with
`pnpm --filter @pilotage/api exec prisma migrate dev --create-only --name tenant_timezone`, then **read and
edited** to exactly:

```sql
-- Additive, expand phase. `Europe/Paris` is a NON-VOLATILE default, so
-- PostgreSQL 11+ stores it in the catalog and does NOT rewrite the table.
-- Contract phase: none — nothing is deprecated by this column.
ALTER TABLE "tenant" ADD COLUMN "timezone" TEXT NOT NULL DEFAULT 'Europe/Paris';
```

**Expand / contract plan.** Expand only. There is no contract phase: no column, constraint or index is
deprecated, and no code path reads a value this column replaces. Old application code ignores the column;
new application code reads it with a database-side default already populated for every existing row. The
two are therefore deployable in either order — state that in the PR.

**Rollback**, stated and executable, no data loss (the value is derivable, and today it is the default for
every row):

```sql
ALTER TABLE "tenant" DROP COLUMN "timezone";
```

**Evidence required:** `node scripts/schema-drift-check.js` green (it replays the migration ledger into a
disposable PostgreSQL and diffs *that database* against `schema.prisma` — `ADR-027`). Paste its output.
`prisma db push` must not appear anywhere in the diff or the run log.

### 2.2 One window resolver, shared (`packages/contracts`)

New file `packages/contracts/src/audit/window.ts`, re-exported from `packages/contracts/src/audit/index.ts`.
Pure functions, no Prisma, no Nest, no React — CJS-safe.

```ts
/** Thrown when a stored tenant timezone is not a zone this runtime knows. */
export class UnknownTimezoneError extends Error { readonly timezone: string; }

/** UTC instant at which the given calendar day STARTS in `timeZone`. */
export function zonedDayStartUtc(ymd: string, timeZone: string): Date;

export interface ResolvedAuditWindow {
  /** Inclusive lower bound, or null when `from` was absent. */
  gte: Date | null;
  /** EXCLUSIVE upper bound = start of the day AFTER `to`, or null when `to` was absent. */
  lt: Date | null;
  /** The zone the two bounds were computed in. Echoed to the client; never read from it. */
  timezone: string;
}

export function resolveAuditWindow(
  from: string | null,
  to: string | null,
  timeZone: string,
): ResolvedAuditWindow;
```

Rules the implementation must obey:

- **`lt`, never `lte`.** `lt = zonedDayStartUtc(to + 1 day, tz)`. An `lte` on the last microsecond of the
  day is a second boundary to get wrong; an exclusive next-day start has none.
- **DST-correct.** Compute the zone offset with `Intl.DateTimeFormat(..., { timeZone })` at the *candidate*
  instant, apply it, then **re-read the offset at the result and re-apply once if it changed**. A single
  pass is wrong on the two days a year the offset shifts across midnight. `Europe/Paris` never shifts at
  midnight, but the function is written for any tenant zone and the test must cover a zone that does
  (`America/Santiago` historically shifts at 00:00 — assert whatever the runtime's ICU actually says rather
  than a hardcoded expectation you cannot verify).
- **No dependency.** Do not add `date-fns-tz`, `luxon` or `dayjs`. `apps/api` has none of them, Node 22
  ships full ICU, and adding one to `packages/contracts` would put a runtime dependency in the package
  every app `require`s.
- **Malformed `from`/`to`** (not `YYYY-MM-DD`, or not a real calendar date) → treated as **absent**, exactly
  as today, and echoed back as `null` in `filters`. Do not 400: the query string is user-editable and the
  current behaviour is already lenient; changing it is out of scope.
- **Unknown timezone** → `throw new UnknownTimezoneError(tz)`. Do **not** silently fall back to
  `Europe/Paris`: a silent fallback is a count computed in a zone the response then mislabels, which is the
  G-TRUTH defect wearing a different hat. See §2.3 for how the service surfaces it.

### 2.3 `auditList` — one `where`, four KPIs, an echoed filter

`apps/api/src/modules/analytics/analytics.service.ts`.

```ts
const tenant = await this.prisma.tenant.findUniqueOrThrow({
  where: { id: tenantId },
  select: { timezone: true },
});
const window = resolveAuditWindow(from ?? null, to ?? null, tenant.timezone);

const where = {
  tenantId,
  ...(actorId ? { actorId } : {}),
  ...(action ? { action: { contains: action, mode: 'insensitive' as const } } : {}),
  ...(resourceType ? { resourceType } : {}),
  ...(portal ? (portal === AUDIT_PORTAL_NONE ? { portal: null } : { portal }) : {}),
  ...(window.gte || window.lt
    ? { createdAt: { ...(window.gte ? { gte: window.gte } : {}), ...(window.lt ? { lt: window.lt } : {}) } }
    : {}),
};
```

Then **every** KPI over **that same `where` object** — not a copy, not a reconstruction. The literal
`where` binding is passed to all five queries (`findMany`, `count`, and the four KPI reads). A reviewer must
be able to see that there is exactly one `where` in the function.

| KPI | Query | `scope` | `label` (server-supplied) |
|---|---|---|---|
| `eventsInRange` | **reuse `total`** — do not issue a fifth `count` | `filtered` | `Événements dans le filtre` |
| `criticalChanges` | `count({ where: { ...where, action: { in: auditCriticalActionCodes() } } })` | `filtered` | `Modifications critiques` |
| `sensitiveExports` | `count({ where: { ...where, action: { in: auditExportActionCodes() } } })` | `filtered` | `Exports sensibles` |
| `distinctActors` | `groupBy({ by: ['actorId'], where: { ...where, actorId: { not: null } } })` → `.length` | `filtered` | `Acteurs distincts` |

> **`eventsInRange` reuses `total` by construction.** AC-2 asks for `kpis.eventsInRange.value === total`.
> Computing it with a second `count` and then *asserting* the equality tests Prisma, not the code. Assign
> `eventsInRange = { value: total, … }` so the equality is **structural**, and let the test assert it anyway
> — the test's job is to catch a future author who splits them apart again.

> **`distinctActors` via `groupBy`, not `count({ distinct })`.** Prisma's `count` has no `distinct` on a
> scalar field in 5.22. `groupBy(['actorId'])` returns one row per distinct non-null actor; `.length` is the
> count. If the tenant ever exceeds a few thousand distinct actors this is worth revisiting — say so in a
> comment, do not pre-optimise.

**Response envelope** (the service's declared return type; **no new DTO class**, the controller keeps
returning the service result):

```ts
{
  data: AuditRow[];
  total: number;
  kpis: {
    eventsInRange:    { value: number; scope: 'filtered'; label: string };
    criticalChanges:  { value: number; scope: 'filtered'; label: string };
    sensitiveExports: { value: number; scope: 'filtered'; label: string };
    distinctActors:   { value: number; scope: 'filtered'; label: string };
  };
  filters: {
    timezone: string;   // resolved server-side, ECHOED, never accepted
    from: string | null;
    to: string | null;
    actorId: string | null;
    action: string | null;
    resourceType: string | null;
    portal: string | null;
  };
}
```

**Breaking change, stated:** `kpis.today` and `kpis.adminLogins` **disappear**. The single consumer is
`apps/web/src/app/admin/audit/page.tsx` and it lands in the same PR (the `S-E06-6` pattern). Grep for both
key names across `apps/` and `packages/` before you finish and confirm zero remaining readers.

**`UnknownTimezoneError` handling.** Let it propagate; map it in the controller (or a small `catch` in the
service) to a `500` whose message names the tenant id and the offending value. Do **not** degrade to a
default. There is no UI in this slice that writes `Tenant.timezone`, so the path is unreachable today — write
it honestly anyway, and cover it with a unit test. A tenant misconfigured by hand must produce a loud
failure, never a quietly different number.

**Delete** `todayStart` / `setHours(0,0,0,0)` and the `adminLogins` branch. Deleting the branch also removes
the last `portal: 'admin'` literal from `apps/api/src` — which is what `audit-provenance-gate.spec.ts:316`
already asserts. **`PF-138` is therefore closed by deletion, not by re-scoping the query**: check that gate
still passes and record in `PROGRESS.md` that the finding died with the card rather than being fixed.

## 3. Two decisions this story makes, so nobody re-litigates them in review

**D-E04-5-1 — the KPI envelope gains `label`; the contract's `Kpi` schema is amended.**
`contracts/openapi.yaml:331-336` declares `Kpi` as `required: [value, scope]`. This story ships
`{ value, scope, label }` and amends the schema to `required: [value, scope, label]` (the operator brief
calls it `KpiValue`; the file calls it `Kpi` — **keep the existing name**, do not rename a schema other
paths may reference). Rationale: the defect was a *title* that disagreed with the *number* under it; the
only structural cure is one object that carries both. This is **not** ADR-034 and does not claim it — the
canonical cross-product KPI envelope is reserved for V3-E03. Say so in the PR body verbatim.

**D-E04-5-2 — `sensitiveExports` stays defined by ACTION; the contract is corrected, not the code.**
`openapi.yaml:357-361` and `data-model.md` §3.6 define it structurally as `resourceType = 'export_job'`.
Their stated reason is that `action contains 'Export'` *« dépend d'une casse et d'une langue »*. **That
objection was already answered by `S-E04-4`**: the shipped predicate is not a substring match, it is exact
set membership over `AUDIT_EXPORT_ACTIONS ∪ LEGACY_AUDIT_EXPORT_ALIASES`, a declared registry
(`ADR-037`). Measured against the seed, the two definitions genuinely disagree:

| Row | `action` | `resourceType` | action-set | structural |
|---|---|---|---|---|
| `seed-demo.ts:1105-1110` | `export.grade_grid.request` | `export_job` | ✅ | ✅ |
| the 50 generic rows | `export.bulletin.request` | random from `student/user_profile/role/assessment/grade/academic_year` — **never `export_job`** | ✅ | ❌ |
| `seed-demo.ts:1174-1178` (legacy fixture) | `Export` | `Résultats` | ✅ | ❌ |

The structural criterion would silently drop every export the API's own writers record with a
non-`export_job` resource, and it would drop the legacy row the fixture exists to exercise. **Keep the
action-set criterion. Amend `openapi.yaml` and `data-model.md` §3.6 to match, and record the reversal and
its measurement in `PROGRESS.md`.** That is `PF-137` closed in the direction the evidence points.

**Consequence — implementation note 6 is vacuous, and that is recorded, not skipped.** Note 6 asks for an
`excludesLegacyRows` flag *where a KPI cannot match the legacy rows*. Under D-E04-5-2 all four can:
`eventsInRange` matches everything; `criticalChanges` and `sensitiveExports` include the frozen
`LEGACY_AUDIT_*_ALIASES`; `distinctActors` counts the legacy rows' `actorId`. **Do not add a field that can
only ever be `false`** — that is DNC-09 at the contract layer. Instead: (a) state the vacuity in
`PROGRESS.md` with this table, and (b) ship the positive-control test in §5 that proves each predicate
*does* reach its legacy alias. The residual risk that live data holds a French value outside the frozen 13
is **`PF-143`, already open**, and this story does not close it — reference it, do not absorb it.
