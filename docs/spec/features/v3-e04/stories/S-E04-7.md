### 2.1 `PF-162` first — the vocabulary becomes a type, not a convention

**File.** `apps/api/src/shared/audit/write-audit.ts` (lines 99 and 101).

Today `AuditWriteInput.action` and `.resourceType` are `string`. `apps/api` already depends on `@pilotage/contracts`
(`apps/api/package.json:50`), and the package exposes the subpath `@pilotage/contracts/audit`
(`packages/contracts/package.json:17-20`). Declare the two unions in `packages/contracts/src/audit/vocabulary.ts`
beside the arrays they are derived from, export them through the existing barrel
(`packages/contracts/src/audit/index.ts` re-exports `./vocabulary` — **add nothing to the barrel**), and use them:

```ts
// packages/contracts/src/audit/vocabulary.ts — derived, never hand-listed.
export type AuditResourceTypeCode = (typeof AUDIT_RESOURCE_TYPES)[number]['code'];
export type AuditActionCode = (typeof AUDIT_ACTIONS)[number]['code'];
```

**⚠ There is one real obstacle, measured — do not skip this paragraph.** Both arrays end in `] as const;`
(`vocabulary.ts:307`, `:316`) **but both also carry an explicit widening annotation**:

```ts
export const AUDIT_RESOURCE_TYPES: readonly AuditVocabularyEntry[] = [ … ] as const;   // :149
export const AUDIT_ACTIONS:        readonly AuditActionEntry[]     = [ … ] as const;   // :223
```

An explicit type annotation **wins over** `as const`, so `code` is `string` on the declared type and the two unions
above would silently resolve to `string` — a green typecheck, an invariant that cannot fire, and `PF-162` "closed"
while nothing changed. **That is the exact failure class this epic is named after.** Replace the annotation with
`satisfies`, which keeps the constraint check *and* the literal types:

```ts
export const AUDIT_RESOURCE_TYPES = [ … ] as const satisfies readonly AuditVocabularyEntry[];
export const AUDIT_ACTIONS        = [ … ] as const satisfies readonly AuditActionEntry[];
```

(TS is pinned at `^5.6.3`, so `satisfies` is available.) Then **prove the union is not `string`** — a
`@ts-expect-error` on an undeclared code is the proof, because it *fails to compile as an error* if the type widened.
Existing consumers of the two arrays (`labels.ts`, `analytics.service.ts:52/56/88`,
`audit-vocabulary-gate.spec.ts`) read them structurally and are unaffected; if any one of them breaks, **narrow that
consumer, do not re-widen the source**.

```ts
// apps/api/src/shared/audit/write-audit.ts
import type { AuditActionCode, AuditResourceTypeCode } from '@pilotage/contracts/audit';
…
  action: AuditActionCode;
  resourceType: AuditResourceTypeCode;
```

Assert the result with a negative type test in `write-audit.spec.ts`, in the `@ts-expect-error` shape `S-E04-6`
established at `:223`. **If this line does not turn the typecheck red when the `@ts-expect-error` is removed, the
union widened to `string` and the fix is to narrow the source — never to fall back to `string`:**

```ts
// @ts-expect-error — PF-162: an undeclared action code must NOT compile.
await writeAudit(tx, { …base, action: 'role.definitely_not_declared' });
```

**Why before the sweep:** the 27 conversions then typecheck against the real 57 actions / 25 resource types, and the
ratchet in 2.2 can trust that a code it reads off an AST is a code that exists. It also converts `ADR-035` D6 from
convention to invariant, matching D1 — the escalation panel's one deferred judgement call.

**Nothing in `apps/web` changes.** Zero label copies (`ADR-037` D1). If the sweep needs a code that is not in the 57
+ 25, it is **declared in `packages/contracts` with its French label** in the same diff, and only there.

### 2.2 The ratchet — `scripts/audit-write-check.js` (new, the durable half)

**If anything is cut from this slice, it is not this.** House pattern: read `scripts/observability-check.js` and
`scripts/link-integrity-check.js` and copy their shape — a header docblock that states what each rule is *for*, pure
exported helpers so the guard spec can drive them, a reviewed JSON baseline, a printed verdict line, exit code is the
gate. Parse with `require('typescript')` (`typescript@^5.6.3` is a root devDependency at `package.json:39`, and
`audit-vocabulary-gate.spec.ts:192` already uses `ts.createSourceFile` in this repo) — **not** with a regex. A regex
over `auditLog.create` cannot tell `tx.` from `this.prisma.`, and cannot see the enclosing function that keys the
baseline.

**Rule A — no `auditLog.create` outside the seam.** Every property-access call `<expr>.auditLog.create(...)` under the
walk root is a violation unless its site key is in the baseline. The seam file itself is excluded by path, once, and
the exclusion is a **single literal constant** printed in the verdict line so it cannot quietly widen.

**Rule B — no `writeAudit` call not given a transaction client.** Every `writeAudit(x, …)` call under the walk root
must pass, as its first argument, an identifier bound by a `$transaction` callback parameter in an enclosing scope
(the `await this.prisma.$transaction(async (tx) => { … })` shape — `schools.controller.ts:143` is the canonical
example). `writeAudit(this.prisma, …)` or `writeAudit(this.prismaService, …)` is red **textually**, which is the
belt to `ADR-035` D1's braces (the `AuditTransactionClient` brand). Neither replaces the other: D1 is compile-time and
needs a generated Prisma client that a fresh checkout does not have; this rule needs neither.

**Rule C — the inline-object-literal rule becomes checkable.** Every `writeAudit` call's **second** argument must be
an object literal, not an identifier. `write-audit.ts:123-129` and `ADR-035` D6.2 already state why:
`shared/quality/audit-vocabulary-gate.spec.ts` resolves `action`/`resourceType` from the AST of the call site, and a
pre-built variable is invisible to it — the code drops out of `EXTRACTED.seams` and the gate's
reverse-completeness direction then demands its real French label be **deleted**. Today that rule has a comment
behind it. After this slice it has a gate.

**Rule D — the baseline is a one-way ratchet.** The baseline may only **shrink**. Concretely, three failures:
(i) a site whose key is not in the baseline; (ii) a baseline row whose key matches **zero** sites (stale — remove it,
same rule as `link-integrity-baseline.json`'s `$doc`); (iii) two sites resolving to the same key (ambiguity).

**Rule E — every baseline row's finding id RESOLVES.** Each row carries `finding`, and the check reads
`docs/daily-improvement-v3/audit-findings-index.md` and requires the id to **exist as a row there** — ids appear as
`| **PF-31** |` in that file's tables. **Not a regex over the shape `PF-\d+`.** `S-E06-5` measured three live rows
citing ids that existed nowhere precisely because `link-integrity-check.js` validated the *shape*. A `finding` that
resolves to no row is a **failure naming the id and the file it was looked up in**.

**Site key — stable, and never a line number.** A line number drifts on the next unrelated edit, and a drifted key
either silently un-baselines a real site or silently covers a different one. The key is:

```
<repo-relative posix path>#<enclosing function or method name>[#<ordinal>]
```

The ordinal is present **only** when one function contains more than one site, and its absence when it is needed is
Rule D(iii). Example rows: `apps/api/src/modules/identity/invite.controller.ts#invite`,
`packages/imports-core/src/engine.ts#applyBatch`.

**`DNC-08` — a check that cannot run FAILS, and says which (this is `AC-4`).** Enumerated, each with its own exit and
its own message naming the path:

| Condition | Behaviour |
|---|---|
| a walk-root directory does not exist | exit **non-zero**, name the directory |
| a walk-root directory yields **zero** `.ts` files | exit **non-zero** — "nothing to check" is never a pass |
| a file under the root cannot be read | exit **non-zero**, name the file and the errno |
| a file cannot be parsed by `ts.createSourceFile` (syntactic diagnostics) | exit **non-zero**, name the file |
| `scripts/audit-write-baseline.json` missing or not valid JSON | exit **non-zero**, name the file |
| `docs/daily-improvement-v3/audit-findings-index.md` missing or unreadable | exit **non-zero** — Rule E cannot be evaluated, so the check cannot run |

No `catch` anywhere degrades any of these to a warning or a skip.

**`DNC-10` — there is no off switch.** No `--skip`, no `--force`, no `--allow`, no `SKIP_*` / `ALLOW_*` /
`AUDIT_*_DISABLE` env var, no `process.env` read that can change a verdict. `ADR-025` and `ADR-027` litigated this
shape already — follow them. The **only** flag the script accepts is `--update`, which rewrites the baseline for
review (the `link-integrity-check.js` affordance) and **refuses to add a row that has no `reason` and no resolving
`finding`**. `--update` is not a bypass: it cannot make a red run green, because a row it writes without those two
fields fails Rule E on the next run. Assert all of this **in the negative** in the guard spec (§4, W-3).

**Verdict line.** Last line of stdout, exactly one line, in the house format, and it **names the walk root**:
