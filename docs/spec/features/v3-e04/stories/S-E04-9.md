## 1. The defect, stated as a sequence

`apps/api/src/modules/identity/invite.controller.ts` `invite()` runs seven steps. `S-E04-7` wrapped steps **5–7**
(`userProfile.create` + optional `userRole.create` + `writeAudit`) in one `$transaction` at **:138**, correctly keeping
every Keycloak call outside it (an HTTP round-trip inside an interactive transaction is how a 5 s Prisma timeout
becomes an incident). That part is right and stays.

What it did not account for: steps **3–4** already happened and **neither is reversible**.

| Step | Line | What it does | Reversible? |
|---|---|---|---|
| 1 | `:87-92` | `keycloak.findUserByEmail(email)` → if found, `ConflictException` | read only |
| 2 | `:94-98` | build `requiredActions` (`UPDATE_PASSWORD`, plus `CONFIGURE_TOTP` for `school_admin`/`teacher`) | — |
| 3 | `:100-111` | **`keycloak.createUser(...)` — an ENABLED realm identity holding the requested realm role** | **no** |
| 4 | `:113-130` | `keycloak.sendExecuteActionsEmail(...)` — the activation email is sent | **no** |
| 5–7 | `:138-179` | `$transaction`: `userProfile.create` → optional `userRole.create` → `writeAudit` | yes (rollback) |

`ADR-035` **D2** makes an audit-insert failure **fatal** (`write-audit.ts:160-166` re-throws, never downgrades). So any
fault inside the transaction — a failed audit insert, a failed profile insert, a pool timeout — rolls step 5–7 back and
leaves an **enabled Keycloak identity holding `school_admin`/`teacher`/`parent` with NO `UserProfile`**.

Then step 1 turns that into a permanent dead end. Every retry hits:

```
Un utilisateur existe déjà avec l'email ${email}. Il peut se connecter directement.
```

— advice that **completes** the failure instead of fixing it. On first login,
`apps/api/src/shared/auth/user-sync.service.ts:38-56` finds no profile and **self-provisions one** under
`DEMO_TENANT_SLUG = 'demo'` (`:9`), `status: active`, and `PermissionsGuard` then derives permissions from
`REALM_ROLE_PERMISSIONS` (the realm role the invite granted) rather than from the profile. **The invitee lands in the
wrong tenant with admin powers** — the `ADR-002` invariant, breached.

The trigger is a DB fault, not attacker-controlled: **availability-triggered, not exploitable on demand.** That is why
this is P1 and not P0, and it is not a reason to defer it.

### The decision, already taken — do not re-litigate

**Resolution (a) COMPENSATE.** Resolution (b) — baselining `invite.controller.ts` back out under
`best-effort-post-commit` — is **rejected**: it only narrows the trigger from *"profile OR role OR audit write fails"*
to *"profile OR role fails"*, leaves the escalation path fully reachable through any profile-create failure, and trades
away the fail-closed audit guarantee `S-E04-7` just established at this site.

Concretely, therefore:

- **DO NOT** touch `scripts/audit-write-baseline.json`.
- **DO NOT** change the `27 = 10 + 17` arithmetic.
- **DO NOT** touch `apps/api/src/shared/quality/audit-write-gate.spec.ts` (`:577`, `:584`, `:612-621` assert that
  `identity/invite.controller.ts` is **absent** from the baseline — that assertion must stay green *as written*).
- `invite.controller.ts` **stays** in the audit sweep, using `writeAudit`, never `auditLog.create`.

If the gate goes red on any of those files, the implementation went the wrong way.

## 2. The one non-obvious constraint — read this before writing a `try`

`scripts/audit-write-check.js` enforces, over the walk root `apps/api/src + apps/worker/src +
packages/imports-core/src`: **no `writeAudit` call may sit inside a `try` block** (`ADR-035` D2; the failure message is
at `audit-write-check.js:571`).

The check is `insideTryBlock` (`audit-write-check.js:264-272`): it walks **every AST ancestor to the SourceFile**, and
**does not stop at function boundaries**. So this shape is **RED**:

```ts
// ❌ RULE B violation — writeAudit at :163 now has a TryStatement ancestor
try {
  profile = await this.prisma.$transaction(async (tx) => {
    /* … */ await writeAudit(tx, { /* … */ });   // ← lexically inside the try
  });
} catch (cause) {
  await this.keycloak.deleteUser(kcUserId);
  throw cause;
}
```

**Required shape:** extract the transaction into its own private method so the `writeAudit` call has no `try` ancestor,
and put the `try/catch` at the call site.

```ts
// ✅ writeAudit's ancestors are: arrow fn → $transaction call → return → persistInvitedProfile body
private async persistInvitedProfile(args: { … }) {
  return this.prisma.$transaction(async (tx) => {
    const created = await tx.userProfile.create({ … });
    if (args.customRoleSlug) { … }
    await writeAudit(tx, { … });     // unchanged shape (see AC-7)
    return created;
  });
}
```

`.catch(...)` on the promise instead of `try/catch` is also lexically clean, but the extracted method is the shape this
story specifies: it also keeps the compensation's **own** `try/catch` (needed by AC-2) far away from `writeAudit`.

Rule B's *first* half is unaffected: `tx` is still bound by a `$transaction` callback parameter.

## 3. Acceptance criteria (verbatim contract — each is checked)

### AC-1 — a rolled-back transaction must not leave an enabled orphan

When the `$transaction` aborts **for any reason**, the Keycloak identity created at step 3 **MUST NOT** survive as an
enabled account with no `UserProfile`. Compensate by deleting the freshly created `kcUserId`.

The compensation is **best-effort** and **MUST NOT mask the original error**: the caller still gets a failure, and the
**original cause remains the reported one** (re-throw the caught error unchanged after a successful compensation — do
not wrap it, do not replace its message).

**Compensate only what THIS request created.** *(Amended with AC-4: since the repair path is withdrawn, `createUser` at
step 3 is the **only** producer of `kcUserId`, so every identity reaching the rollback was created by this request and
the compensation is unconditional. The rule is unchanged; the branch that needed it is gone.)*

### AC-2 — a failed compensation is loud, never silent

If the compensation **itself** fails, the error surfaced to the admin **must name the orphaned `kcUserId`** so a human
can clean it up, and the failure **must be logged** (`Logger`, `error` level, carrying both `kcUserId` and the original
cause). Never swallow.

Precedence between AC-1 and AC-2 in that branch: AC-2 governs the message, AC-1 governs the information — the thrown
error names `kcUserId` **and** carries the original error (as `cause`, and its message inside the sentence) so the real
reason is not lost.

### AC-3 — `KeycloakAdminService` gains exactly one method

`apps/api/src/shared/keycloak/keycloak-admin.service.ts` today has **no** delete or disable. Read the whole file before
adding — it is 263 lines and every convention below is already in it:

- go through `private adminFetch(path, init)` (`:110-120`) — it acquires/caches the token and prefixes
  `${this.baseUrl}/admin/realms/${this.realm}`; **never call `fetch` directly**;
- return `Promise<void>` and throw `InternalServerErrorException` with the message shape
  `` `Keycloak <method>: HTTP ${res.status}` `` — exactly as `setUserPassword` (`:186-192`) and `setRequiredActions`
  (`:195-201`) do;
- place it beside the other user-lifecycle methods, with a one-line `/** … */` docblock in the file's voice.

```
DELETE /admin/realms/{realm}/users/{id}    →   adminFetch(`/users/${userId}`, { method: 'DELETE' })
```

**Treat `404` as success.** Keycloak answers `204` on delete; a `404` means the identity is already gone, which is the
state the caller wanted. A compensation that throws because its work was already done would turn a recovered request
into AC-2's loud failure for no reason.

**One method, not two.** `DELETE` is available in the Admin REST API, so the "or disable it" fallback in the finding is
not exercised; a second best-effort layer would need its own failure handling. Do not add `disableUser`.

### AC-4 — ⛔ WITHDRAWN AT IMPLEMENTATION — the repair path is not built

> **Ruled during Verify, recorded here so the spec does not stay a lie.** AC-4 below rests on the premise *"a Keycloak
> account with no local `UserProfile` is a known-broken state produced by exactly this bug."* **That premise is false in
> this repository**, and three reviewers raised it independently as a blocker:
>
> - `UserSyncService.ensureUser` (`user-sync.service.ts:23-56`) creates the `UserProfile` **lazily, at first login** —
>   so **every never-logged-in realm identity** has no profile, by design;
> - `infra/keycloak/realm-export.json` ships three of them (`admin@` / `teacher@` / `parent@pilotage.local`), absent
>   from `apps/api/prisma/seed-demo.ts`;
> - ADR-004 puts every tenant in **one realm**, so they are reachable from any tenant.
>
> Built as specified, the repair path let any `users.write` holder in any tenant overwrite an unrelated identity's
> password, add a realm role to it, and bind it **permanently** to their own tenant (`authProviderId` is globally
> unique). That is the ADR-002 breach the slice exists to close, through a new door.
>
> The sound version needs positive proof that this flow minted the identity — a Keycloak attribute stamped at
> `createUser` time, or a local invite-intent row. Neither fits this slice: Keycloak 26 disables unmanaged attributes by
> default and the realm export declares no `components` (the attribute would be dropped on write), and the intent row is
> a **schema change** while `G-MIGRATION` explicitly does not trigger here.
>
> **Shipped instead:** step 1 keeps its pre-slice behaviour — any existing Keycloak identity is refused, byte-identically.
> PF-163 is closed by AC-1/AC-2, which **delete** the orphan rather than adopt it. Recorded in `ADR-035` **D16/D17**;
> the repair path is re-pointed at a later slice that can carry a migration. The original text is kept below for the
> record.

A Keycloak account that exists for this email **but has no local `UserProfile`** is a known-broken state produced by
exactly this bug. The handler must be able to **finish the job** instead of refusing forever: **reuse the existing
`kcUserId` and proceed** (steps 2, then realm-role assignment + required actions + activation email against the
existing id, then the transaction).

A Keycloak account that **does** have a local `UserProfile` must still be refused with the **existing**
`ConflictException` and the **existing message, byte for byte**:

```
Un utilisateur existe déjà avec l'email ${email}. Il peut se connecter directement.
```

The distinction must be made by an **actual lookup**, never by a guess or a heuristic on the Keycloak payload.

### AC-5 — ⛔ WITHDRAWN WITH AC-4 — met structurally instead

> With no repair path there is **no second branch**: the handler issues **no local read** before the refusal, so the
> two narrow lookups below are not written, the untenanted `count({ where: { email } })` probe does not exist, and the
> "one bit" residual this AC accepted is **removed rather than documented**. Pinned by `invite.controller.spec.ts` case
> (vii): `userProfile.findUnique` and `userProfile.count` must both be **uncalled** on the refusal path. Original text
> kept for the record.

Facts from `apps/api/prisma/schema.prisma`, `model UserProfile`:

- `authProviderId String? @unique` — **globally** unique, and it is what links a profile to a Keycloak `sub`;
- `email String @db.Citext` with `@@unique([tenantId, email])` — email is unique **per tenant**, not globally;
- `tenantId String @map("tenant_id") @db.Uuid` — **this is the field that carries the scoping**, and it is set from
  `me.tenantId` where `const me = await this.users.ensureUser(jwt)` (`:79`). State that in a comment at the lookup.

The lookup is **two reads, both narrow**:

1. `userProfile.findUnique({ where: { authProviderId: <existing kc id> }, select: { id: true } })` — the link that
   `UserSyncService` itself follows first (`user-sync.service.ts:23-25`). Non-null ⇒ **refuse** (existing
   `ConflictException`, existing message), whatever tenant it is in.
2. `userProfile.count({ where: { email } })` — an **existence boolean and nothing more**. `> 0` ⇒ **refuse**, same
   exception, **same message**. A profile in another tenant is **not** a repairable state and the message must not
   differ, must not name the other tenant, and must not vary in status code.

Repair proceeds **only** when both reads say "nothing anywhere". The profile created on the repair path is written with
`tenantId: me.tenantId`, **identical to today's create at `:141`** — no new tenant resolution, no tenant derived from
the Keycloak payload.

**Accepted, documented residual (state it in the code comment and in the PR):** an admin holding `users.write` can now
distinguish *"KC account exists, no profile anywhere"* (200, repair) from *"KC account exists, profile somewhere"*
(409). That is **one bit**, it is the minimum AC-4 can be built on, and it discloses no tenant, no id and no field. The
two refusal branches must be **indistinguishable** to the caller — asserted by a test.

### AC-6 — the missing artefact lands with the fix (mandatory, not optional)

Create **`apps/api/src/modules/identity/invite.controller.spec.ts`**.

It **MUST** use a fake `$transaction` that **stages then commits**: the fake collects the callback's writes and applies
them to the committed set **only if the callback resolves**, so a callback throw is **observably not persisted**. A
fake that merely calls the callback and lets writes land regardless proves nothing.

The house pattern already exists — copy `makeDb()` from
`apps/api/src/modules/schools/schools.controller.spec.ts:45-117` (`staged` / `committed` arrays, `$transaction` clearing
`staged` on throw and appending to `committed` on resolve). Reuse it; do not invent a second idiom.

Required cases:

| # | Case | Must assert |
|---|---|---|
| i | happy path | profile **and** audit row are in `committed`; response `{ ok: true, userProfileId, kcUserId, emailSentTo }`; `keycloak.deleteUser` **not** called |
| ii | audit write throws | **nothing** persisted (no profile, no audit row) **and** `keycloak.deleteUser` called once with the created `kcUserId`; the rejection is the original `InternalServerErrorException` from `writeAudit` |
| iii | `userProfile.create` throws | same: nothing persisted, `deleteUser` called once with the created `kcUserId`, original error re-thrown unchanged |
| iv | compensation itself throws | the rejection **names the orphaned `kcUserId`**; `logger.error` was called; the original cause is still reachable |
| v | email exists in Keycloak | `ConflictException` with the exact existing message; `keycloak.createUser` **not** called; `$transaction` **not** called |
| vi | email exists **without** a profile (**amended with AC-4**) | the identity is **NOT adoptable**: same `ConflictException`, and `assignRealmRoles` / `setUserPassword` / `setRequiredActions` / `sendExecuteActionsEmail` / `$transaction` all **uncalled**. This is the security regression guard that keeps the withdrawn branch out. |
| vii | the refusal leaks nothing (**added with AC-5**) | `userProfile.findUnique` and `userProfile.count` **uncalled** — the refusal path issues no local read at all |

Plus the gate-specific cases in §4 (`G-TENANT`, `G-AUTHZ`).

**Evidence bar.** Each case must **FAIL against the pre-fix controller and PASS after**. "The test passes" is not
evidence on its own — the PR must state, per case, which pre-fix behaviour it fails on (e.g. *(ii) pre-fix: `deleteUser`
does not exist, so the assertion cannot even be written; against a stub it is never called*).

### AC-7 — the `writeAudit` call at `:163` is untouched

It stays **exactly** as it is: **one unconditional statement**, **inline object literal** as the second argument,
**inside** the transaction, **the transaction client as the first argument**. That shape is what
`scripts/audit-write-check.js` (rules B and C) and `shared/quality/audit-vocabulary-gate.spec.ts` parse from the AST.

- do **not** extract it into a helper;
- do **not** make it conditional;
- do **not** wrap it in `try`/`catch` (see §2);
- do **not** invent a new action code. `user.invite` is the declared code
  (`packages/contracts/src/audit/vocabulary.ts:337` — *« Invitation d'un utilisateur »*), and audit vocabulary is
  `S-E04-4`'s seam, not this story's.

*Amended with AC-4:* the draft added `repairedExistingKeycloakUser` to the `after:` payload to record the adoption
transition. With no adoption there is no transition, so the payload keeps **exactly** its four pre-existing keys
(`email` / `realmRole` / `customRoleSlug` / `requiredActions`) and this slice changes **no** audit surface at all.
Moving the statement into `persistInvitedProfile` (§2) is fine — it is the *shape* that is pinned, not the enclosing
function's name.
