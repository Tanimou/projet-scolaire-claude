## 2. PF-155 — a closure must not be able to file itself as a modification

### 2.1 The measurement

`apps/api/src/modules/schools/schools.controller.ts:74-82`, as it stands today:

```ts
class UpdateSchoolDto {
  @IsOptional() @IsString() @MaxLength(200) name?: string;
  @IsOptional() @IsString() timezone?: string;
  @IsOptional() @IsString() locale?: string;
  @IsOptional() @IsEnum(SchoolStatus) status?: SchoolStatus;   // ← the finding
  @IsOptional() @IsObject() @ValidateNested() @Type(() => SchoolAddressDto)
  address?: SchoolAddressDto | null;
}
```

`SchoolStatus` is `active | closed` (`schema.prisma:26-29`). So `PATCH /schools/:id {"status":"closed"}` validates,
reaches `update()`, spreads straight into `tx.school.update({ data: { ...rest } })` at `:193-201`, and closes the
school. Two things are wrong with that, and only one of them is obvious:

1. **It bypasses the refusal.** `DELETE /schools/:id` refuses to close a school that still holds students or
   academic years (`:234-238`, French copy: *« Impossible de supprimer une école contenant des élèves ou des années
   scolaires. Archivez-la plutôt. »*). `PATCH` has no such check. The same outcome, through a second door, with the
   guard on only one of them.
2. **It files the closure under the wrong action code.** `packages/contracts/src/audit/vocabulary.ts:300-301`:

   ```
   { code: 'school.update', label: 'Modification d’un établissement', critical: true },
   { code: 'school.close',  label: 'Fermeture d’un établissement',    critical: true },
   ```

   **Both are `critical: true`, so the « Modifications critiques » KPI count is unaffected** — this is *not* a
   G-TRUTH count defect. **The ATTRIBUTION is what is wrong.** An auditor who filters `/admin/audit` on
   « Fermeture d'un établissement » to answer *« quels établissements ont été fermés, par qui, et quand ? »* gets an
   **empty result** for every closure made this way. The trail contains the event, filed under a label that denies
   it.

### 2.2 What ships

**AC-1 — `status` leaves `UpdateSchoolDto`.** Delete the `@IsOptional() @IsEnum(SchoolStatus) status?: SchoolStatus;`
member. Replace it with a comment that says why, so the next reader does not "restore" it:

```ts

  // un établissement en contournant le refus de DELETE (élèves / années
  // scolaires, :234-238) ET en classant la fermeture sous `school.update`. Les
  // deux codes sont `critical`, donc le KPI ne bougeait pas : c'est
  // l'ATTRIBUTION qui était fausse, et un auditeur filtrant sur « Fermeture d'un
  // établissement » ne voyait pas ces fermetures. DELETE /schools/:id est la
  // SEULE porte (`school.close`). Ne pas dupliquer sa garde ici : dupliquer la
  // garde, c'est re-créer la deuxième porte.
```

## 3. PF-158 — no transition, no row

Three siblings do the opposite and write a `critical` row with byte-identical before/after:

|---|---|

### 3.3 What ships — `schools.controller.ts` `update()`

Field-level comparison, not merely "was the body empty". The double-click in AC-7 resubmits a *populated* form with
unchanged values, so an emptiness test would miss the case the AC is about.

```ts
/** Les six clés déclarées par `SchoolAddressSchema` (packages/contracts/src/dto/school.ts:13-26). */
const ADDRESS_KEYS = ['continent', 'country', 'city', 'quartier', 'line1', 'postalCode'] as const;

/** Égalité structurelle sur les clés connues — pas de JSON.stringify, dont l'ordre des clés n'est pas stable. */
function addressEquals(a: Record<string, unknown> | null, b: Record<string, unknown> | null): boolean {
  if (a === null || b === null) return a === b;
  return ADDRESS_KEYS.every((k) => (a[k] ?? null) === (b[k] ?? null));
}
```

then, inside `update()`, **after** the tenant guard at `:188` and **before** `$transaction` opens:

```ts

// ligne `school.update` (`critical: true`) gonflerait « Modifications critiques »
// à chaque double-clic ou rejeu client, et ferait diverger le KPI du registre

  (rest.name === undefined || rest.name === school.name) &&
  (rest.timezone === undefined || rest.timezone === school.timezone) &&

  (address === undefined

      // la colonne brute, pas `currentAddress` — une adresse stockée invalide se
      // parse en `null` et un effacement légitime serait pris pour un non-événement.
```

## 5. PF-157 — a lost race is not a second revocation

### 5.1 The measurement

`users.service.ts:136-171`. The `revokedAt !== null` idempotency guard at `:146` reads **before** `$transaction`
opens; the update inside is **unconditional**:

```ts
if (current.revokedAt !== null) return current;          // ← read, at T0
return this.prisma.$transaction(async (tx) => {
  const updated = await tx.userRole.update({            // ← write, at T1, unconditional
    where: { id: userRoleId },
    data: { revokedAt: new Date() },
  });
  await writeAudit(tx, { … action: 'role.revoke' … });   // ← critical row
```

Two concurrent `DELETE /users/roles/:id` calls both read `revokedAt: null` at T0, both pass, both update, and both
write a `critical` `role.revoke` for **one** revocation — with `revokedAt` holding the **retry's** clock. That is
precisely the defect the guard was added to close, restated at a smaller time scale. The guard's own docblock
(`:127-135`) claims it closes it; on this branch, it does not.

### 5.2 AC-11 / AC-12 — the fix, stated by the finding

Correctness must come from a **conditional update inside the transaction**. PostgreSQL serialises the two writes on
the same row; the loser re-evaluates `revoked_at IS NULL`, matches nothing, and gets `count: 0`.

```ts
async revokeRole(userRoleId: string, tenantId: string, provenance: AuditProvenance, actorId: string) {
  const ur = await this.prisma.userRole.findUnique({
    where: { id: userRoleId },
    include: { userProfile: true, role: true },
  });
  if (!ur) throw new NotFoundException('Assignment not found');
  if (ur.userProfile.tenantId !== tenantId) throw new ForbiddenException();

  const { userProfile: _userProfile, role, ...current } = ur;
  // AC-14 — chemin RAPIDE, et rien de plus. Il évite une transaction dans le cas
  // courant ; il ne décide RIEN. La correction est le `updateMany` conditionnel
  // ci-dessous. Voir PF-157.
  if (current.revokedAt !== null) return current;

  const revoked = await this.prisma.$transaction(async (tx) => {
    // PF-157 — `updateMany` et non `update` : la condition `revokedAt: null` est
    // réévaluée PAR LA BASE, au moment de l'écriture, sous le verrou de ligne.
    // Deux DELETE concurrents franchissent tous deux la garde ci-dessus ; ici,
    // un seul matche. `updateMany` renvoie un COMPTE, pas la ligne — d'où la
    // relecture.
    const { count } = await tx.userRole.updateMany({
      where: { id: userRoleId, revokedAt: null },
      data: { revokedAt: new Date() },
    });
    // Course perdue : la révocation a déjà eu lieu, il n'y a pas de transition
    // ici. On sort AVANT le seul `writeAudit` du bloc — on ne le met pas sous
    // condition (S-E04-7 / AC-8).
    if (count === 0) return null;

    const updated = await tx.userRole.findUniqueOrThrow({ where: { id: userRoleId } });
    await writeAudit(tx, {
      tenantId,
      actorId,
      action: 'role.revoke',
      resourceType: 'user_role',
      resourceId: userRoleId,
      provenance,
      before: {
        userProfileId: current.userProfileId,
        roleId: current.roleId,
        roleSlug: role.slug,
        roleName: role.name,
        grantedAt: current.grantedAt.toISOString(),
      },
      after: { revokedAt: updated.revokedAt?.toISOString() ?? null },
    });
    return updated;
  });

  // La forme de réponse ne bouge pas : un `UserRole` nu, jamais la jointure.
  return revoked ?? (await this.prisma.userRole.findUniqueOrThrow({ where: { id: userRoleId } }));
}
```

**AC-14 — the cheap pre-transaction guard stays**, explicitly labelled a fast path. Correctness comes from the
conditional update, not from it. Keeping both is not redundancy: the guard is what stops the common
already-revoked case from opening a transaction at all, which is what the existing
`users.service.spec.ts:300-315` test asserts and which must remain true.

**AC-13 — NO database backstop, and do not add one.** `@@unique([userProfileId, roleId, schoolId])`
(`schema.prisma:939`) **cannot** deduplicate here: `assignRole` writes `schoolId: null` (`:103`) and PostgreSQL
treats NULLs as distinct in a unique index. The right long-term fix is a **partial** unique index
`(user_profile_id, role_id) WHERE revoked_at IS NULL` — and it is a **SCHEMA CHANGE, DEFERRED**.

> **Do not touch `apps/api/prisma/schema.prisma`. Do not add any SQL or migration. G-MIGRATION MUST NOT TRIGGER on
> this diff.** Register the deferred index in the story report so the routine can queue it.
